# TD Game

Браузерная игра в жанре Tower Defense с PvP-режимом в реальном времени.

Замысел игры — что происходит на экране и по каким правилам — описан
в [docs/game-design.md](docs/game-design.md). Начинать знакомство с проектом
лучше оттуда: без понимания игры половина архитектурных решений выглядит
произвольной.

Работа через Claude и Codex: [настройка агентов](docs/agent-setup.md).

## Быстрый старт

Нужны Node.js 22+ и pnpm 10+.

```bash
pnpm install
```

```bash
COMPUTER_SECRET=локальный pnpm dev
```

Откроется клиент на `http://127.0.0.1:5173`, сервер поднимется на `http://127.0.0.1:3001`.

Секрет нужен затем, чтобы служба компьютерных дежурных могла объявить
серверу свои личности: она живёт отдельным процессом, и без общего
секрета сервер не поверит, что её комнаты — компьютерные. Без секрета
всё поднимется и заработает, но комнат компьютера в списке не будет
вовсе, и оба процесса скажут об этом в журнале. Так честнее, чем комнаты
компьютера без пометки: сесть играть с компьютером, думая, что играешь
с человеком, — хуже, чем не сесть вовсе.

Игра попросит представиться. Имя сохранится в куки этого браузера и будет
видно сопернику; удалить профиль и завести заново можно в любой момент
кнопкой «Сменить профиль».

Дальше открывается список комнат. Отсюда два пути:

- **Играть с компьютером** — вход в дежурную комнату, которую держит
  компьютерный соперник. Никакого особого режима за этим не стоит:
  компьютер такой же участник, как человек, со своим именем, своим
  местом в комнате и своим соединением, и матч с ним идёт через сервер
  ровно так же;
- **Создать комнату** — своя комната в общем списке. Откройте игру
  во втором окне (или на втором устройстве), войдите в комнату, и когда
  готовность подтвердят оба, у обоих начнётся матч на одной карте:
  создателю достанется первая сторона, вошедшему — вторая.

Список комнат живой: чужая комната появляется в нём сама, без обновления
страницы. Комнаты компьютера в нём помечены — имени мало, «Компьютер»
вполне может оказаться прозвищем человека.

Матч идёт на изометрической карте 48 × 48 клеток и целиком считается
сервером: он владеет тиком, принимает команды, назначает им тик
исполнения и объявляет исход. По сети при этом едет не мир, а команды —
кадр тика весит семь байт, когда команд нет, а это обычный случай.

Между нажатием и появлением действия в мире проходит задержка ввода:
несколько тиков, одинаковых для обоих участников и назначенных сервером
по худшему из каналов. Величина видна в панели матча. Отклик при этом
остаётся мгновенным — клиент показывает мир, в котором его собственные
ещё не подтверждённые команды уже применены.

Выход из идущего матча засчитывается поражением и спрашивает
подтверждения. Разрыв связи матч не останавливает: мир продолжает идти,
а вернувшийся догоняет его по истории команд.

В левом верхнем углу видна панель состояния: если индикатор зелёный,
а счётчик ответов растёт — вертикаль клиент → протокол → сервер собрана
правильно.

| Клавиши         | Действие                                              |
| --------------- | ----------------------------------------------------- |
| `W` `A` `S` `D` | движение генерала, направления привязаны к экрану     |
| `1` `2` `3`     | заказать штурмовика, снайпера, Теслу                  |
| `Q` `E` `R`     | выбрать стену, башню, снайперскую башню для постройки |
| `F`             | навести ядерный удар                                  |
| левая кнопка    | поставить выбранное в клетку под курсором             |
| правая кнопка   | назначить цель атаки для всех своих юнитов            |
| Пробел          | вернуть камеру к генералу                             |
| `Esc`           | отменить режим строительства или наведения            |
| стрелки, мышь   | прокрутка карты; клик по миникарте переносит взгляд   |

Кнопка «Новый матч» в панели «Карта» начинает новую партию с компьютером
на новой карте — она есть только против компьютера: с живым соперником
уйти на другую карту в одиночку невозможно, мир один и живёт на сервере.
Кнопка «Выйти в меню» есть всегда, но в идущем матче спрашивает
подтверждения: выход — это поражение.

## Структура репозитория

Монорепозиторий на pnpm workspaces, сборкой задач управляет Turborepo.

| Пакет               | Назначение                                                        |
| ------------------- | ----------------------------------------------------------------- |
| `apps/client`       | Vite + React 19 (меню и HUD) + PixiJS v8 (игровое поле)           |
| `apps/server`       | Node.js: Fastify для комнат и REST, WebSocket для реалтайма       |
| `apps/computer`     | Служба компьютерных дежурных: свой процесс, только точка входа    |
| `apps/arena`        | Инструмент разработки: безголовые матчи и разбор поведения        |
| `packages/sim`      | Детерминированное ядро симуляции, работает и в браузере, и в Node |
| `packages/protocol` | Бинарный сетевой протокол поверх `ArrayBuffer`                    |
| `packages/netplay`  | Ведение матча с обеих сторон: тик, кадры команд, предсказание     |
| `packages/bot`      | Компьютерный участник: комната, соединение, решения               |
| `packages/ai`       | Решения противника под управлением компьютера                     |
| `packages/shared`   | Общие типы, игровые константы, балансные конфиги                  |
| `packages/ui`       | React-компоненты и дизайн-токены                                  |

Зависимости направлены строго в одну сторону:

```
shared  ←  sim, protocol, ui
sim, shared  ←  ai
shared, sim, protocol  ←  netplay
netplay, ai  ←  bot
netplay, bot  ←  server
netplay  ←  client
```

Обратите внимание на две границы, которые держат честность игры.
`packages/netplay` не знает про транспорт: сообщения уходят через
переданную снаружи функцию, время приходит такой же, — поэтому весь
сетевой матч прогоняется в тесте без единого сокета. А `packages/bot`
не знает про `apps/server`: компьютер получает состояние мира только
из потока кадров, как и человек, и запрет на прямой доступ закреплён
линтом, а не договорённостью.

Библиотеки не знают о приложениях, а клиент и сервер не знают друг о друге.
Это не договорённость на словах — правила зашиты в ESLint и падают при нарушении.

## Боевая сборка: Docker

`pnpm dev` — это отладочные серверы с горячей перезагрузкой. Для боя
(и просто чтобы показать игру кому-то по сети) есть compose, собирающий
и поднимающий всё одной командой:

```bash
docker compose up --build -d
```

Игра встанет на `http://localhost:8080`. Остановить — `docker compose down`.

Поднимаются две службы:

| Служба   | Что внутри                                                                   |
| -------- | ---------------------------------------------------------------------------- |
| `server` | Node 22: HTTP для комнат и WebSocket для матчей, плюс компьютерные соперники |
| `web`    | nginx: раздаёт собранного клиента и проксирует `/api` и `/game` на сервер    |

Наружу торчит только `web`. Порт сервера сознательно не опубликован: иначе
у игры появился бы второй адрес, мимо прокси и мимо будущего TLS.

**Почему клиент за nginx.** Адреса сервера попадают в бандл на сборке —
`import.meta.env` это подстановка текста, а не чтение переменной в браузере.
Держать страницу и API на одном адресе выгодно тем, что вшивать становится
нечего: пути относительные, и один образ работает и на localhost, и на
боевом домене, и под https, где сокет сам станет `wss`. Если сервер
всё-таки вынесен на отдельный адрес, задайте `VITE_API_URL` и `VITE_WS_URL`
в `.env` — и пересоберите: без `--build` в контейнере останется старый бандл.

Настройки — в `.env` рядом с `docker-compose.yml`, образец в `.env.example`:
порт наружу, адреса сервера и запись матчей. Запись по умолчанию выключена,
и это не про место на диске: боевой сервер пишет партии живых людей, а
вопрос об их согласии ещё не решён (см. комментарий в
`apps/server/src/config.ts`).

## Три вещи, которые важно понять до первой правки

### 1. Симуляция обязана быть детерминированной

Клиент и сервер прогоняют **один и тот же код** симуляции независимо друг от друга
и сверяют результат контрольными суммами. Поэтому в `packages/sim` запрещены:

- `Math.random()` — вместо него seeded PRNG, чьё состояние лежит в состоянии мира;
- `Date.now()` и `performance.now()` — время измеряется номером тика;
- числа с плавающей точкой в состоянии мира — координаты хранятся в целых
  числах с фиксированной точкой (одна клетка = 1000 единиц);
- обращения к `window`, `document`, `process`.

Нарушения ловит ESLint, а golden-тест в
`packages/sim/src/determinism.golden.match.test.ts` проверяет, что тысяча тиков
даёт ровно ту же контрольную сумму, что и раньше.
Если вы намеренно поменяли игровые правила — обновите эталон тем же коммитом.

Этот тест проигрывает партию и потому лежит в матчевом наборе: `pnpm test`
его не запускает, `pnpm test:match` — запускает. Подробности про два набора —
в `CLAUDE.md`.

### 2. React не рисует игровое поле

Поле рисует PixiJS через WebGL, и его цикл живёт **вне** React-дерева.
React отвечает только за HUD и меню поверх canvas.

Общаются они через store (`apps/client/src/game/store.ts`), причём игровой цикл
пишет туда только те величины, которые реально видны в HUD. Позиции башен, врагов
и снарядов до React не доходят вообще — иначе 60 перерисовок в секунду съели бы
весь бюджет отзывчивости.

### 3. По сети ходят команды, а не состояние мира

Сервер авторитетен, но рассылает не мир целиком, а подтверждённые команды игроков
с номером тика. Клиент применяет своё действие немедленно, не дожидаясь сервера, —
отсюда мгновенный отклик. При расхождении контрольных сумм он откатывается
и переигрывает.

Сообщения кодируются в бинарный вид (`packages/protocol`), а не в JSON: пакеты
уходят десятки раз в секунду, и разбор строк на горячем пути создавал бы микрофризы.

Единственное исключение — комнаты ожидания: они разговаривают обычным JSON
поверх HTTP и Server-Sent Events. Правило этим не нарушено. Оно про **мир**,
а мир по-прежнему не передаётся, он вычисляется из seed и потока команд;
состав комнаты миром не является и в симуляцию не входит. Платить бинарным
кодеком, рассчитанным на тридцать пакетов в секунду, за событие, случающееся
дважды за партию, не за что — зато `PROTOCOL_VERSION` пришлось бы двигать
от правки формы кнопки.

## Разработка ведётся через OpenSpec

Любая заметная фича начинается не с кода, а с предложения:

```bash
openspec new change "имя-изменения"
```

Дальше по порядку создаются `proposal.md` (зачем), `specs/` (что именно должно
работать), `design.md` (как) и `tasks.md` (шаги). Только после этого пишется код.
Готовое изменение архивируется командой `openspec archive`, и его спецификации
переезжают в `openspec/specs/` — общую базу знаний о поведении системы.

Контекст проекта, который OpenSpec подставляет во все артефакты, лежит
в `openspec/config.yaml`.
