# Инструкции для Claude Code

## Что это за проект

Браузерный Tower Defense с PvP в реальном времени. Монорепозиторий,
TypeScript везде, ESM, pnpm workspaces + Turborepo.

Игровой замысел — в `docs/game-design.md`. Читайте его перед любой задачей,
затрагивающей геймплей: там же зафиксированы решения, которые из кода
не видны, например отказ от тумана войны и требование симметрии карты.

Главное нефункциональное требование — **отзывчивость интерфейса**.
Любое действие игрока даёт визуальный отклик в том же кадре.
Сетевая задержка маскируется предсказанием на клиенте, а не спиннерами.

## Порядок работы: ветка, рабочее дерево, атомарные коммиты

Над репозиторием одновременно работают несколько сессий. Правила ниже
нужны ровно затем, чтобы они не портили работу друг другу, — каждое
написано по следам уже случившейся потери.

### 1. Гейт: с чего начинается любая доработка

Гейт срабатывает на **доработку** — на всё, что меняет файлы репозитория.
Ответить на вопрос, прочитать код, объяснить устройство, посчитать
что-нибудь в скратчпаде можно и без него: там менять нечего.

Прежде чем тронуть хоть один файл, спросите пользователя прямо:

> **Заводить рабочее дерево под эту доработку?**

**«Да»** — заводите (правило 3) и работаете там. Гейт на этом закончен.

**«Нет»** — дальше по шагам, ни одного не пропуская.

1. **Где вы стоите:** `git rev-parse --abbrev-ref HEAD`.
   Ветка не `main`? Скажите об этом вслух — «текущая ветка не `main`,
   а `<имя>`» — и предложите переключиться на `main`. Молча дописывать
   в чужую ветку нельзя: её кто-то ведёт.
2. **Чисто ли дерево:** `git status --porcelain`.
   Вывод пуст — работайте в `main` прямо здесь, гейт закончен.
3. **Дерево грязное — правку не начинайте.** Покажите пользователю, что
   именно лежит несохранённым, и предложите три выхода:
   - всё-таки завести рабочее дерево;
   - завести просто новую ветку от `main`;
   - осознанно остаться в грязном `main`.

   Третий выход законен, но только как названное вслух решение
   пользователя, а не как то, что «само получилось».

Грязное — это и неотслеживаемые файлы тоже. Строки `??` чаще всего
оказываются чужой незавершённой работой, и `git add -A` поверх неё
её же и потеряет.

#### Откуда ответвляются ветки

**Всегда от `main`.** Ветка от ветки допустима **только** для подзадачи
внутри той задачи, которой занят этот чат. Всё остальное ответвляется
от `main` заново, а не от того, что случайно оказалось выложено.

**Перед заведением нового дерева `main` отправляют. Это обязательный
шаг, а не совет.** Из основного дерева:

```bash
git push origin main
```

Тогда `main` и `origin/main` совпадают, и вопрос «от чего ответвились»
не возникает вовсе.

Шаг обязателен потому, что `EnterWorktree` ответвляется от `origin/main`,
а не от локального `main`. Проверено 23.08.2026: дерево встало
на `87bc9b4` (тогдашний `origin/main`), тогда как локальный `main` был
на `c8008b4` — на коммит впереди и на три позади. Пропустив отправку,
вы заведёте дерево без последних коммитов и узнаете об этом в лучшем
случае из конфликта, а в худшем — никогда. Проверить после входа:

```bash
git log --oneline HEAD..main   # пусто — база верна
```

### 2. Коммитить в `main` вправе только основное дерево

Рабочих деревьев два вида, и права у них разные.

- **Основное дерево** — `C:\src\dezintegra\TD_Game`, то самое, где лежит
  `.git`. Оно всегда стоит на `main`, и работающий в нём коммитит
  в `main` напрямую.
- **Дополнительное дерево** — любое из `.claude/worktrees/`. Отсюда
  в `main` не уходит **ничего**: ни коммит, ни `git push origin HEAD:main`.
  Только своя ветка и pull request. Запрет безусловный: ни опечатка,
  ни «одна строчка» исключением не являются.

Как понять, где вы: `git worktree list` первой строкой печатает основное
дерево. Проще: если ваш путь содержит `.claude/worktrees/` — вы
в дополнительном, и запрет действует.

Оговорка про «ни `git push origin HEAD:main`» не придирка. Выложить
из воркри в `main` можно, не переключаясь на него: сам git такую отправку
не запрещает, а переключиться не даст — одна ветка не выкладывается
в два дерева сразу.

### 3. Ветку заводят новым рабочим деревом, а не переключением

**Основное дерево с `main` не сходит.** `git switch` в нём уводит за собой
**все** сессии, которые в этом дереве сидят, вместе с их незакоммиченными
правками. Поэтому ветка создаётся новым рабочим деревом (`git worktree`),
а не переключением, — и правило 2 держится само собой: в дополнительном
дереве `main` просто не может быть выложен.

Штатный способ — инструмент `EnterWorktree`: он заводит дерево
в `.claude/worktrees/<имя>` на ветке `worktree-<имя>`, ответвлённой
от `origin/main`. Смысл несёт имя изменения, приставка `worktree-`
служебная. Ручной эквивалент:

```bash
git worktree add .claude/worktrees/<имя> -b <ветка> origin/main
```

**Любая сборка, прогон тестов и запуск игры делаются только в своём
дереве.** Три вещи, без которых новое дерево не заработает:

- **`node_modules` не общие.** Начинать с `pnpm install --frozen-lockfile`,
  иначе не запустится ничего.
- **Порты берутся из среды**, чтобы не драться с соседним деревом:
  `CLIENT_PORT` у клиента, `PORT` у сервера, а `VITE_API_URL`
  и `VITE_WS_URL` сообщают клиенту адрес именно своего сервера.
  Без последних двух клиент постучится в зашитый 3001, то есть в чужое
  дерево, и вы проверите чужой код.

  ```bash
  CLIENT_PORT=5199 PORT=3055 VITE_API_URL=http://127.0.0.1:3055 \
    VITE_WS_URL=ws://127.0.0.1:3055/game pnpm dev
  ```

- **Кэш turbo у всех деревьев общий.** Он лежит в `.turbo` основного
  дерева, и turbo честно пишет об этом в шапке прогона: «using shared
  worktree cache». Пока входные данные задач объявлены верно, это просто
  ускорение. Но если проверка отвечает подозрительно быстро и «успешно»,
  перепроверьте с `--force`: возможно, вы читаете ответ соседнего дерева.
  Правите конфигурацию сборки — убедитесь, что файл назван в `inputs`
  или в `globalDependencies` в `turbo.json`.

### 4. Работа дробится на атомарные задачи

Каждый шаг `tasks.md` — **отдельный коммит, отправляемый сразу**
(`git push`). Не копите пачку коммитов до конца изменения.

**Неотправленный коммит — это хвост, а не отложенная работа.** Рабочие
деревья ответвляются от `origin/main`, проверки CI запускаются на отправку,
влитость ветки сверяется с origin. Всё, что лежит только локально, для
остальной машинерии не существует, и следующее дерево заведётся без этого.

Немедленная отправка снимает расхождение «впереди», но **не лечит
отставание**: `git push origin main` и `git fetch` перед заведением дерева
остаются обязательными. Проверить обе стороны разом:

```bash
git rev-list --left-right --count origin/main...main
```

Атомарная задача — та, которую можно проверить в одиночку:

- она собирается и проходит тесты **сама по себе**, без «следующего
  шага», который всё починит;
- в теле коммита есть что написать про «почему», и это не пересказ двух
  несвязанных правок;
- откат ровно этого коммита возвращает работоспособное состояние.

Стейджить только свои пути явным списком — `git add -- <файлы>`.
`git add -A` затаскивает в коммит чужую незавершённую работу.

### 5. Из дополнительного дерева работа попадает в `main` через pull request

PR открывается **один на всё изменение** целиком, а не на каждую задачу:
CI настроен на `pull_request` в `main`, и дробить его на десяток прогонов
незачем. Внутри PR коммиты остаются атомарными — их читают по одному.

PR открывают **черновиком сразу после первого коммита**, а не в конце
работы. Это не вежливость, а механика: CI настроен на событие
`pull_request`, и пока PR нет, пуши в ветку не запускают ничего вовсе.
С черновым PR каждый следующий пуш перезапускает проверки — то есть
каждая атомарная задача проверяется отдельно, как и задумано правилом 4.

```bash
gh pr create --draft --base main --title "<заголовок>" --body-file <файл>
```

**Перед вливанием черновой статус снимают** — `gh pr ready <номер>`. Пока
pull request черновик, `gh pr merge` отбивается ответом
`GraphQL: Pull Request is still a draft (mergePullRequest)`, каким бы готовым
изменение ни было. В конвейере это делает ревью первым подшагом вливания;
вливающий руками зовёт команду сам. Снимают статус, только решив влить:
на изменении, уезжающем в доработку, черновик остаётся — он и означает,
что работа не закончена.

**Слияние выполняет ревьюер конвейера, а не пользователь.** Прежнее правило
«слияние — решение пользователя» отменено осознанно: конвейер агентской
разработки доводит задачу до продакшена без человека, и ручное подтверждение
на каждом вливании превратило бы это в фикцию.

Взамен действуют три условия, и все три обязаны выполняться одновременно:

- проверки CI зелёные;
- ревью не выставило замечаний;
- конфликтов с `main` нет.

Отсутствие любого отменяет вливание и отправляет задачу в доработку. Ревью
на незавершённых или красных проверках не начинают вовсе: замечания к коду,
который не собирается, бесполезны.

Правило касается работы **через конвейер**. Изменение, которое ведёт человек
вручную, он же и вливает — там подтверждать нечего, кроме собственного
решения.

### 6. Проверки живут в CI, а не на машине

**Из дополнительного дерева `pnpm verify` не запускают.** Ни линт,
ни типы, ни тесты, ни сборку: всё это делает GitHub — одновременно
и бесплатно, репозиторий публичный. Рабочая машина слабая, и занимать
её на минуты ради ответа, который runner даёт сам, незачем.

Локально остаётся только узкое, по своим файлам:

```bash
npx eslint <свой файл>
npx prettier --check <свои файлы>
npx vitest run <свой файл теста>
```

**Задача не сделана, пока GitHub не сказал «зелено».** Не «у меня прошло»,
не «я не вижу, что могло сломаться» — зелёные проверки или ничего.

```bash
gh pr checks <номер> --watch          # ждать, пока проверки добегут
gh run view --job <id> --log-failed   # прочитать, на чём упало
```

Красный CI — это работа, а не повод отчитаться о сделанном. Прочитать
лог, починить, закоммитить отдельным атомарным коммитом, отправить,
дождаться снова.

Сколько ждать (замер 23.08.2026): формат и линт 24 с, типы 36 с,
сборка 35 с, сквозные проверки 2 мин 5 с, модульные тесты 5 мин 47 с.
Задачи идут одновременно, поэтому ждать приходится самую долгую.

### 7. Замеры производительности — не часть CI

На runner'ах GitHub видеокарты нет: Chromium рисует программно и выдаёт
около шестнадцати кадров на любой сцене, так что порог 55 недостижим
там в принципе. Поэтому замеры вынесены в `*.perf.spec.ts` и в обычный
прогон не входят.

- **Перед выкладкой замер обязателен.** `scripts/deploy.mjs` зовёт его
  сам; пропуск только по явному ключу `--no-perf`.
- **По ходу обычной задачи замер предлагают**, если правка могла задеть
  отрисовку: новые слои, спрайты, фильтры, частицы, работа в игровом
  цикле. Именно предлагают, а не делают молча: замер занимает минуту
  и требует тишины на машине.
- **Мерить на занятой машине бессмысленно.** `pnpm e2e:perf` проверит
  обстановку сам и откажется: он смотрит общий на все рабочие деревья
  замок и долю занятости процессора.

```bash
pnpm e2e:perf -- --check-only   # можно ли мерить прямо сейчас
pnpm e2e:perf                   # замерить
pnpm e2e:perf -- --history      # что было раньше
```

Замеров два вида, и путать их не надо.

- **Кадры в секунду** (`pnpm e2e:perf`) меряют отрисовку, поэтому требуют
  живой видеокарты и живой машины. Ни в CI, ни в контейнере смысла
  не имеют.
- **Стоимость тика** (`pnpm bench:tick`) меряет счёт: шаг мира и решения
  компьютерных сторон. Ни браузера, ни сервера — значит цифра сравнима
  и между машинами. Её же имеет смысл гонять в контейнере с выделенной
  долей процессора, см. `docker/bench.md`.

Оба пишут в общий журнал вместе с занятостью машины в ту минуту, и оба
показывают, что изменилось с прошлого раза. Одинокая цифра говорит мало:
порог ловит «стало совсем плохо», а между 61 и 56 кадрами разницы
в исходе теста нет — зато в жизни она есть.

Цифра, снятая под нагрузкой, говорит о нагрузке, а не о коде. 22.08.2026
при пяти потоках выходило 45–51 кадра при пороге 55, тогда как в одиночку
те же тесты проходили. 23.08.2026 соседняя сессия по той же причине
завысила стоимость решения ИИ вдесятеро — 28 мс вместо 2–4.

### 8. Проверки баланса — по расписанию, а не посреди задачи

Проверка баланса — это прогон арены на десятки матчей. Шестьдесят матчей
занимают машину минут на десять, чемпионат на несколько сотен — на часы.
Всё это время работать нельзя, а ответ почти никогда не нужен сию минуту.

**Агент не гоняет арену по своему усмотрению.** Правка задела правила
игры, цены, доход, силу юнита или темп — скажите об этом вслух
и спросите прямо:

> **Прогнать проверку баланса сейчас? Займёт около N минут, и машина
> всё это время будет занята.**

**«Да»** — гоняйте и разбирайте цифры в этой же задаче. По кнопке
на чужом железе (`.github/workflows/arena.yml`, вкладка Actions) либо
локально, если ответ нужен здесь и сразу.

**«Нет», «потом» или уклончивое молчание** — проверка не отменяется,
а **встаёт в очередь**: карточкой с меткой `run` на доске бэклога.
В карточке сказано, кого с кем мерить, сколько матчей, ради какой правки
и чего от неё ждали — последнее обязательно, разделом
`## Ожидаемый результат`. Устройство доски — в `manage/README.md`.

**Карточка заводится в момент вливания pull request**, а не едет вместе
с ним: бэклог живёт на доске Trello и в репозиторий не попадает вовсе.
Смысл прежнего правила — «очередь пополняется ровно тогда, когда изменение
попадает в `main`» — сохраняется, но держится теперь не на атомарности
коммита, а на порядке действий конвейера: вливший pull request помечает
это в задаче, и следующий цикл видит вливание без заказанного прогона
как незавершённое дело.

Полного равенства с прежним правилом здесь нет, и это надо знать. Вливание
и создание карточки — две операции, и обрыв между ними оставит влитую
правку без прогона до ближайшей сверки. Прежняя запись была неделимой,
потому что лежала в том же коммите.

Отдельного файла очереди нет — очередью служит сам бэклог. Два списка
ожидающей работы неизбежно расходятся, и однажды становится непонятно,
какому из них верить; а разойдясь, они ещё и дерутся за один файл
в параллельных pull request, что с прежним `balance/queue.json`
и происходило.

Накопившееся по ночам разбирает отдельная джоба
(`.github/workflows/balance.yml`): гоняет задачи-прогоны на runner'е,
сравнивает с прошлым разом и, если цифры разошлись, заводит Issue
с таблицами и с тем, куда смотреть. Что делать со сдвигом — решает
человек: он же и закрывает задачу, когда вопрос закрыт.

Третьего выхода нет. Либо проверка прогнана сейчас, либо она в очереди.
«Вроде и так видно, что не сломалось» — это не вывод, а именно та щель,
сквозь которую и накапливаются сдвиги, которых никто не заказывал.

## Порядок работы: OpenSpec

Заметные изменения ведутся через OpenSpec, а не сразу кодом:

1. `openspec new change "<имя>"` — завести изменение;
2. `proposal.md` — зачем и что меняется, обязателен раздел Non-goals;
3. `specs/<capability>/spec.md` — требования в формате Requirement + Scenario;
4. `design.md` — технические решения с обоснованием альтернатив;
5. `tasks.md` — шаги реализации, каждый проверяемый;
6. только после этого — код;
7. `openspec archive <имя>` — спецификации переезжают в `openspec/specs/`.

Контекст проекта для артефактов — в `openspec/config.yaml`.
Мелкие правки (опечатка, форматирование) допустимо делать без изменения.

**Изменение, не меняющее ни одного требования, ведётся без `specs/`**
и архивируется `openspec archive <имя> --skip-specs`. Дельта пишется,
когда правка вводит правило, которому обязано подчиняться будущее; дельты
нет, когда правка приводит единичный текст в согласие с тем, что уже
решено. Валидатор такое изменение отвергает всегда — ошибкой
`Change must have at least one delta`, и без `--strict` тоже; писать
требование ради её снятия не надо: оно уедет в `openspec/specs/` навсегда
как норма, которой никто не заказывал. Вместо дельты в предложении стоит
раздел `## Почему дельты нет`.

## Порядок работы: конвейер агентской разработки

Работа приходит не из разговора, а из **бэклога** — доски Trello
<https://trello.com/b/96MUi1Q2/td>. Оттуда её берёт конвейер: сам заводит
дерево и ветку, сам порождает процесс на каждый этап, сам вливает
и выкладывает.

Ведёт всё это **супервизор** — долгоживущий процесс Node
(`supervisor/bin/supervise.mjs`), а не сессия ИИ. Он порождает этапы
дочерними процессами `claude` и держит их дескрипторы: отсюда срок у этапа,
снятие зависшего вместе со всем поддеревом процессов и код возврата вместо
угадывания «жива ли сессия». Сам он к модели не обращается вовсе.

Доска — вся поверхность управления разом: очередь задач колонками
по состояниям, журнал каждой задачи её комментариями, вопросы владельцу
продукта там же. Устройство описано в `manage/README.md`, код конвейера —
в `supervisor/`.

Владелец продукта участвует двумя действиями: заводит карточку и отвечает
комментарием, если конвейер спросит. Ни редактор, ни `git push` для этого
не нужны — в этом и был смысл переезда бэклога из репозитория.

Конвейеру для доступа к доске нужны `TRELLO_KEY` и `TRELLO_TOKEN` в `.env`
рабочей станции; без них цикл останавливается, называя недостающее.
Недоступность Trello при этом паузы не взводит: обрыв связи лечится
ожиданием, а пауза снимается руками.

### Что это меняет для сессии

**Сессия конвейера выполняет ровно один переход состояния и завершается.**
Не «доделаю заодно и следующий этап»: каждый шаг проверяется в одиночку,
и падение сессии не уносит с собой несколько состояний сразу.

**Бэклог правит только супервизор.** Сессия-исполнитель не трогает доску
вовсе: ни карточку, ни её комментарии, ни метки, ни положение в колонке.
Всё, что она хочет записать, она возвращает отчётом — последним сообщением,
объектом JSON; супервизор читает его прямо из вывода процесса. Единственное
исключение — ответ владельца продукта: его человек пишет комментарием сам.

**Запрос подтверждения в автономном запуске оборачивается отказом, а не
ожиданием.** Это проверено делом, и следствие важнее удобства: незаписанное
разрешение больше не вешает работу — оно тихо меняет результат этапа.
Поэтому отказ попадает и в журнал цикла, и в журнал задачи.

**Отказ судят по следу этапа, а не по его наличию.** Само по себе отказанное
действие отчёта не отменяет: сессия часто обходит запрет другим путём
и работу доводит до конца. Отменяют отчёт два случая — попытка спросить
человека средствами приложения и отсутствие следа этапа при исходе `done`
(нет коммита в отправленной ветке, нет нового номера прогона — смотря
по этапу). Такая задача уходит в разбор сразу, а не по исчерпании
продолжений, и содержимое отброшенного отчёта уезжает в её журнал.

Прежнее правило — «отчёт при непустом перечне отказов не принимается
вовсе» — отменено осознанно. Мерка оказалась слишком грубой: вечер
31.08.2026 дал шесть отброшенных отчётов подряд, и ни один не потерян
из-за настоящей беды.

**Задачу конвейера руками не перехватывают.** Занятость видна прямо
на карточке: у занятой задачи проставлен исполнитель. Назначение и есть
захват — Trello отвергает повторное назначение того же участника,
и потому две станции одну задачу взять не могут. Снимете исполнителя
руками — задача станет свободной, и её возьмут заново. Нужно вмешаться —
взведите паузу
(`.pipeline/pause`), дождитесь окончания цикла и работайте.

### Чего конвейер не трогает

Ваши собственные рабочие деревья и ветки. Свои он узнаёт по строгому виду
имени — `worktree-<четыре цифры>-<имя>`, — и удалять деревья не умеет вовсе:
находку он называет вам, а убирает только после доказанного вливания.

Ручные сессии в квоту конвейера не входят. Он не знает, чем вы заняты,
и знать не должен.

### Что смотреть

```bash
node supervisor/bin/cycle.mjs        # что конвейер собирается делать
node supervisor/bin/board-setup.mjs  # всё ли на месте на доске
```

Оба сценария **ничего не делают** — печатают решение и завершаются.
У `cycle.mjs` исполнения нет вовсе: порождать этап и выходить нельзя,
процесс остался бы без хозяина, а это ровно та беда, ради которой затеян
супервизор. Работу ведёт `bin/supervise.mjs`, и он же держит замок
`.pipeline/supervisor.lock`.

Сама доска — <https://trello.com/b/96MUi1Q2/td>: перерисовывать её нечем
и незачем, она и есть состояние. Что делал сам супервизор — в
`.pipeline/cycle.log`, что делал конкретный этап — в
`.pipeline/logs/<id>-<этап>.log`: в списке сессий приложения этапы
не видны, зато в журнале есть код возврата, длительность, стоимость
и перечень отказанных действий.

## Архитектурные правила, которые нельзя нарушать

### Границы пакетов

```
shared  ←  sim, protocol, ui  ←  client, server
```

- `packages/shared` не зависит ни от чего внутреннего;
- `packages/sim` и `packages/protocol` зависят только от `@td/shared`;
- `apps/client` и `apps/server` не импортируют друг друга;
- библиотеки никогда не импортируют приложения.

Правила зашиты в `eslint.config.js`. Не ослабляйте их — чините код.

### Детерминизм ядра симуляции

В `packages/sim` **запрещены**:

- `Math.random()` — используйте seeded PRNG из `prng.ts`;
- `Date.now()`, `new Date()`, `performance.now()` — время это номер тика;
- `window`, `document`, `process` — ядро изоморфное;
- числа с плавающей точкой в состоянии мира — только целые
  с фиксированной точкой (одна клетка = `FIXED_POINT_SCALE` единиц).

Функция `step` обязана оставаться чистой: не мутировать входное состояние.

Меняете игровые правила — обновляйте эталон в
`determinism.golden.match.test.ts` тем же коммитом.

### Разделение React и PixiJS

- игровое поле рисует только PixiJS, React к `canvas` не прикасается;
- игровой цикл живёт вне React-дерева (`apps/client/src/game/`);
- обмен только через store, и только теми величинами, что видны в HUD;
- никакой игровой логики в компонентах.

### Сеть

- по сети ходят команды игроков, а не состояние мира;
- кодирование бинарное (`packages/protocol`), не JSON;
- декодер возвращает результат с ошибкой, а не бросает исключение:
  данные приходят из недоверенного источника;
- меняете раскладку байтов — увеличивайте `PROTOCOL_VERSION`.

### Стиль

- цвета, отступы, шрифты — только через CSS-переменные из
  `packages/ui/src/tokens.css`, литералов в компонентах быть не должно;
- гамма унаследована от дизайн-системы Dezintegra: графит + неон `#00FF29`;
- комментарии на русском, объясняют «почему», а не «что делает строка».

## Перед завершением задачи

```bash
pnpm verify
```

Формат, линт, типы, быстрые тесты и сборка одной командой. Всё должно
быть зелёным.

**Из дополнительного дерева этого не делают** (правило 6): там задача
считается сделанной по зелёному CI, а не по локальному прогону.

`format:check` стоит в `verify` первым, и попал он туда не сразу. Пока
его не было, проверка формата жила только в CI — а в CI никто не смотрел.
Сквозь эту щель молча разъехались шестьдесят семь файлов, и `main` падал
на них шесть прогонов подряд.

### Два набора тестов

Тесты делятся по признаку «нужна ли тесту партия целиком»:

- `pnpm test` — быстрый набор. Идёт от секунд (когда всё берётся
  из кеша Turborepo) до пары минут. Входит в `pnpm verify`;
- `pnpm test:match` — файлы `*.match.test.ts`, около четверти часа.
  Их тринадцать, и каждый проигрывает матч: противник под управлением
  компьютера, сходимость миров в сети, эталоны детерминизма, арена;
- `pnpm test:all` и `pnpm verify:all` — оба набора вместе.

**Матчевый набор сам не запускайте — спросите.** Четверть часа ожидания
это решение человека, а не ваше. Повод спросить возникает, когда правка
задевает `packages/sim`, `packages/ai` или игровой баланс: там регрессию
иначе не поймать. Из дополнительного дерева не запускайте и подавно —
за этим есть CI (правило 6).

В CI оба набора идут **разными задачами одновременно**: `быстрые тесты`
и `матчевые тесты`. Приклеить матчевый к быстрому значило бы отложить
ответ «сломано ли что-то очевидное» на те же четверть часа.

Заводите тест, которому нужен матч, — кладите его в `*.match.test.ts`.
Иначе он утяжелит набор, который обязан оставаться быстрым, и заметят
это не сразу.

## Коммиты

Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.

Один коммит — одна проверяемая задача (правило 4 выше). Тело коммита
объясняет «почему», а не пересказывает диф: по коммитам здесь
восстанавливают ход рассуждения, а не список изменённых строк.
