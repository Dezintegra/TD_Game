# Инструкции для Claude Code

## Что это за проект

Браузерный Tower Defense с PvP в реальном времени. Монорепозиторий,
TypeScript везде, ESM, pnpm workspaces + Turborepo.

Игровой замысел — в `docs/game-design.md`. Читайте его перед любой задачей,
затрагивающей геймплей: там же зафиксированы решения, которые из кода
не видны, например отказ от тумана войны и требование симметрии карты.

Главное нефункциональное требование — **отзывчивость интерфейса**.
Любое действие игрока даёт визуальный отклик в том же кадре.
Сетевая задержка маскируется предсказанием на клиенте, а не спиннерами.

## Порядок работы: ветка, рабочее дерево, атомарные коммиты

Над репозиторием одновременно работают несколько сессий. Правила ниже
нужны ровно затем, чтобы они не портили работу друг другу, — каждое
написано по следам уже случившейся потери.

### 1. Каждая доработка живёт в своей ветке

**В `main` не коммитят никогда**: ни правку опечатки, ни «одну строчку».
`main` меняется только слиянием pull request.

Ветку ответвляют **от `origin/main`**, а не от локального `main`:
локальный бывает и отстающим, и разошедшимся — проверьте
`git fetch origin && git rev-list --left-right --count origin/main...main`,
прежде чем считать его основой.

### 2. Ветку заводят новым рабочим деревом, а не переключением

`git switch` в общем дереве уводит за собой **все** сессии, которые
в нём сидят, вместе с их незакоммиченными правками. Поэтому ветка
создаётся новым рабочим деревом (`git worktree`), а не переключением.

Штатный способ — инструмент `EnterWorktree`: он заводит дерево
в `.claude/worktrees/<имя>` на ветке `worktree-<имя>`, ответвлённой
от `origin/main`. Смысл несёт имя изменения, приставка `worktree-`
служебная. Ручной эквивалент:

```bash
git worktree add .claude/worktrees/<имя> -b <ветка> origin/main
```

**Любая сборка, прогон тестов и запуск игры делаются только в своём
дереве.** Три вещи, без которых новое дерево не заработает:

- **`node_modules` не общие.** Начинать с `pnpm install --frozen-lockfile`,
  иначе не запустится ничего.
- **Порты берутся из среды**, чтобы не драться с соседним деревом:
  `CLIENT_PORT` у клиента, `PORT` у сервера, а `VITE_API_URL`
  и `VITE_WS_URL` сообщают клиенту адрес именно своего сервера.
  Без последних двух клиент постучится в зашитый 3001, то есть в чужое
  дерево, и вы проверите чужой код.

  ```bash
  CLIENT_PORT=5199 PORT=3055 VITE_API_URL=http://127.0.0.1:3055 \
    VITE_WS_URL=ws://127.0.0.1:3055/game pnpm dev
  ```

- **Кэш turbo у всех деревьев общий.** Он лежит в `.turbo` основного
  дерева, и turbo честно пишет об этом в шапке прогона: «using shared
  worktree cache». Пока входные данные задач объявлены верно, это просто
  ускорение. Но если проверка отвечает подозрительно быстро и «успешно»,
  перепроверьте с `--force`: возможно, вы читаете ответ соседнего дерева.
  Правите конфигурацию сборки — убедитесь, что файл назван в `inputs`
  или в `globalDependencies` в `turbo.json`.

### 3. Работа дробится на атомарные задачи

Каждый шаг `tasks.md` — **отдельный коммит, отправляемый сразу**
(`git push`). Не копите пачку коммитов до конца изменения.

Атомарная задача — та, которую можно проверить в одиночку:

- она собирается и проходит тесты **сама по себе**, без «следующего
  шага», который всё починит;
- в теле коммита есть что написать про «почему», и это не пересказ двух
  несвязанных правок;
- откат ровно этого коммита возвращает работоспособное состояние.

Стейджить только свои пути явным списком — `git add -- <файлы>`.
`git add -A` затаскивает в коммит чужую незавершённую работу.

### 4. В `main` работа попадает через pull request

PR открывается **один на всё изменение** целиком, а не на каждую задачу:
CI настроен на `pull_request` в `main`, и дробить его на десяток прогонов
незачем. Внутри PR коммиты остаются атомарными — их читают по одному.

`gh` на машине не установлен, поэтому PR открывают по ссылке, которую
печатает сам `git push` при первой отправке ветки. Ссылку отдают
пользователю: слияние — его решение, не агента.

## Порядок работы: OpenSpec

Заметные изменения ведутся через OpenSpec, а не сразу кодом:

1. `openspec new change "<имя>"` — завести изменение;
2. `proposal.md` — зачем и что меняется, обязателен раздел Non-goals;
3. `specs/<capability>/spec.md` — требования в формате Requirement + Scenario;
4. `design.md` — технические решения с обоснованием альтернатив;
5. `tasks.md` — шаги реализации, каждый проверяемый;
6. только после этого — код;
7. `openspec archive <имя>` — спецификации переезжают в `openspec/specs/`.

Контекст проекта для артефактов — в `openspec/config.yaml`.
Мелкие правки (опечатка, форматирование) допустимо делать без изменения.

## Архитектурные правила, которые нельзя нарушать

### Границы пакетов

```
shared  ←  sim, protocol, ui  ←  client, server
```

- `packages/shared` не зависит ни от чего внутреннего;
- `packages/sim` и `packages/protocol` зависят только от `@td/shared`;
- `apps/client` и `apps/server` не импортируют друг друга;
- библиотеки никогда не импортируют приложения.

Правила зашиты в `eslint.config.js`. Не ослабляйте их — чините код.

### Детерминизм ядра симуляции

В `packages/sim` **запрещены**:

- `Math.random()` — используйте seeded PRNG из `prng.ts`;
- `Date.now()`, `new Date()`, `performance.now()` — время это номер тика;
- `window`, `document`, `process` — ядро изоморфное;
- числа с плавающей точкой в состоянии мира — только целые
  с фиксированной точкой (одна клетка = `FIXED_POINT_SCALE` единиц).

Функция `step` обязана оставаться чистой: не мутировать входное состояние.

Меняете игровые правила — обновляйте эталон в `determinism.golden.test.ts`
тем же коммитом.

### Разделение React и PixiJS

- игровое поле рисует только PixiJS, React к `canvas` не прикасается;
- игровой цикл живёт вне React-дерева (`apps/client/src/game/`);
- обмен только через store, и только теми величинами, что видны в HUD;
- никакой игровой логики в компонентах.

### Сеть

- по сети ходят команды игроков, а не состояние мира;
- кодирование бинарное (`packages/protocol`), не JSON;
- декодер возвращает результат с ошибкой, а не бросает исключение:
  данные приходят из недоверенного источника;
- меняете раскладку байтов — увеличивайте `PROTOCOL_VERSION`.

### Стиль

- цвета, отступы, шрифты — только через CSS-переменные из
  `packages/ui/src/tokens.css`, литералов в компонентах быть не должно;
- гамма унаследована от дизайн-системы Dezintegra: графит + неон `#00FF29`;
- комментарии на русском, объясняют «почему», а не «что делает строка».

## Перед завершением задачи

```bash
pnpm verify
```

Это линт, типы, тесты и сборка одной командой. Всё должно быть зелёным.

**`verify` — не то же самое, что CI.** CI гоняет ещё и `pnpm format:check`,
а `verify` его не включает. Проверяйте формат по своим файлам явным
списком:

```bash
npx prettier --check <ваши файлы>
```

Именно по своим: `prettier --check .` по всему репозиторию сейчас красный
(191 файл на 23.08.2026), и это разбирается отдельной задачей — чужие
предупреждения в отчёте не ваша поломка.

## Коммиты

Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.

Один коммит — одна проверяемая задача (правило 3 выше). Тело коммита
объясняет «почему», а не пересказывает диф: по коммитам здесь
восстанавливают ход рассуждения, а не список изменённых строк.
