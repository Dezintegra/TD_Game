# Бэклог конвейера

Очередь работ, из которой конвейер агентской разработки берёт задачи сам.
Владелец продукта кладёт сюда запись — и больше ни во что не вмешивается,
пока конвейер не задаст вопрос.

## Устройство

```
backlog/
  schema.json        схема задачи, проверяется тестом
  tasks/<id>.json    по одному файлу на задачу
  journal/<id>.md    дозаписываемая история задачи
  examples/          образцы задач каждого типа, в работу не берутся
  questions.md       вопросы владельцу продукта и ответы на них
```

**Один файл на задачу.** Единый список стал бы вечной точкой конфликтов
между машинами — это уже произошло с `balance/queue.json`. Разные файлы git
разводит без вмешательства.

**Примеры лежат отдельно от задач.** В `backlog/tasks/` попадает только
настоящая работа: всё, что лежит там, конвейер рано или поздно возьмёт
в работу. Образцы для чтения и для тестов живут в `backlog/examples/`.

## Кто пишет

Бэклог правит **только оркестратор** и только из основного рабочего дерева,
отдельным коммитом на каждую смысловую правку, с немедленной отправкой.

Сессии-исполнители бэклог не трогают: всё, что они хотят записать — вопрос,
заявку на новую задачу, итог этапа, — они кладут в отчёт, а оркестратор
переносит.

Единственное исключение — **ответ владельца продукта**: его человек пишет,
коммитит и отправляет сам, а конвейер только читает.

## Типы задач и маршруты

| Тип       | Что это                       | Маршрут                                                                                    |
| --------- | ----------------------------- | ------------------------------------------------------------------------------------------ |
| `feature` | доработка кода                | `new → design → audit → implement → [benchmark] → pr → review → deploy → cleanup → closed` |
| `run`     | прогон с замерами             | `new → benchmark → closed`                                                                 |
| `note`    | замечание, вопрос или задумка | `new → triage → closed`                                                                    |

Аудит с замечаниями возвращает задачу в `design`, ревью с замечаниями —
в `revise`, а `revise` ведёт обратно в `pr`: правка требует нового прогона
проверок, и ревью на непроверенном коде не начинают. Состояния `failed`
и `awaiting-po` достижимы из любого рабочего состояния; куда возвращаться,
хранит поле `returnTo`.

Мелких правок в обход проработки не бывает: любая доработка кода идёт через
изменение OpenSpec. Так задумано — полнота картины важнее скорости.

## Как завести задачу

Скопировать подходящий образец из `backlog/examples/` в `backlog/tasks/`,
дать новый идентификатор вида `<число>-<короткое-имя>` и заполнить поля.
Идентификатор служит именем ветки, рабочего дерева и журнала, поэтому после
закрытия задачи не переиспользуется.

Обязательные для заполнения руками поля: `id`, `type`, `title`,
`description`, `priority`. Остальное конвейер проставит сам: `status`
начинается с `new`, `owner` пуст, `history` пуста, счётчики в нуле.

Задача типа `run` дополнительно требует раздел `run` с видом прогона
и с ожидаемым результатом. Без ожидания прогон нечем истолковать: цифра
сама по себе не говорит ни о чём.

## Приоритет

Меньшее число берётся в работу раньше. При равенстве раньше берётся задача
с более ранней отметкой заведения. Разумная шкала: `10` — горит, `50` —
обычная работа, `90` — когда-нибудь.

Прогоны имеют преимущество независимо от числа: пока есть готовый к запуску
прогон, новые задачи в проработку и имплементацию не берутся.

## Журналы

`journal/<id>.md` дозаписывается при каждой смене состояния: дата, пара
состояний, что сделано, какие решения приняты и почему. Журнал не
переписывается целиком и не форматируется prettier — он пишется автоматически.

Журнал задачи хранит состояние **задачи**. Работа самого конвейера — отказы
отправки, хвосты, конфликты — пишется в местный журнал цикла вне гита.
