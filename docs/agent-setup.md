# Claude и Codex

## Обычная работа

Откройте репозиторий или отдельное рабочее дерево в Claude Code либо Codex.
Общие правила находятся в `CLAUDE.md`; `AGENTS.md` направляет Codex к ним
и поясняет различия инструментов. История разговоров между приложениями
не переносится: передавайте имя изменения OpenSpec, ветку и номер PR.

В Codex доступны проектные навыки:

- `$openspec-propose` — подготовить изменение;
- `$openspec-explore` — исследовать вопрос;
- `$openspec-apply-change` — реализовать задачи;
- `$openspec-update-change` — обновить план;
- `$openspec-sync-specs` — синхронизировать требования;
- `$openspec-archive-change` — архивировать изменение.

Claude сохраняет свои `/opsx:*` и навыки из `.claude/skills`. Оба работают
с одним каталогом `openspec/`. Навыки Codex лежат в `.agents/skills` и не
требуют глобальных prompts. Если навык не появился, откройте новую сессию.
При обновлении OpenSpec проверяйте diff: проектные дополнения не должны
потеряться при повторной генерации.

## Рабочее дерево и игра в PowerShell

После согласования дерева с пользователем и сверки основной ветки:

```powershell
git worktree add .claude/worktrees/my-change -b codex/my-change origin/main
Set-Location .claude/worktrees/my-change
pnpm install --frozen-lockfile
$env:CLIENT_PORT = '5199'
$env:PORT = '3055'
$env:VITE_API_URL = 'http://127.0.0.1:3055'
$env:VITE_WS_URL = 'ws://127.0.0.1:3055/game'
$env:COMPUTER_SECRET = 'local-development'
pnpm dev
```

Пример портов выбирайте свободным для этого дерева. Клиент открывается
на `http://127.0.0.1:5199`. Не копируйте производственные секреты в дерево.
Настройки `.claude/launch.json` принадлежат Claude; запуск выше работает
из терминала обоих приложений.

## Автономный супервизор

Запускайте из основного дерева после вливания изменения:

```powershell
pnpm supervisor --provider=claude
pnpm supervisor --provider=codex
```

Это альтернативные команды, не два одновременных процесса. `--provider`
передаётся в форме `--provider=codex`. Не вставляйте отдельный `--`: пускатель
намеренно отвергает неизвестные доводы, чтобы не запустить конвейер случайно.
Прямая форма: `node supervisor/bin/launch.mjs --provider=codex`.

Поле `provider` можно сохранить в `supervisor/pipeline.config.json`;
ключ запуска имеет приоритет. Без поля и ключа остаётся Claude.
`--shadow`, `--detached`, `--quiet`, `--stop` сохраняют прежнее значение.
У обоих исполнителей один замок `.pipeline/supervisor.lock`, одна доска
и один реестр. Для смены исполнителя завершите текущий процесс через Ctrl+C
и дождитесь его выхода. Новый запуск не останавливает уже работающий.

Память каждой сессии помечена провайдером. Старые записи считаются Claude.
После смены провайдера прерванная задача получает новую сессию с прежним
назначением и журналом; чужой идентификатор не передаётся в resume.

## Настройка Codex

Нужен доступный Codex CLI и его собственная авторизация (`codex login`).
Проверка приложения: `node supervisor/bin/codex-runner.mjs codex --version`.
На Windows обёртка поддерживает npm-установку и `codex.exe`; нестандартный
путь задаётся в `codexCommand` до исполняемого файла либо `bin/codex.js`.
Секреты доски по-прежнему читает супервизор из своей среды.

- `stageModels.codex` и `stageModels.claude` — карты моделей по этапам.
  Приоритет: ключ этапа → `default` → прежнее `codexModel` / `stageModel`.
  Правило действует и для продолжения сессии; чужая карта не используется.
  Без модели во всех трёх местах ключ `--model` не передаётся.
- `codexModel` — запасная модель Codex, `stageModel` — запасная модель Claude.
- `codexWindowsSandbox` — Windows sandbox: `elevated` по умолчанию.
  `unelevated` оставлен для совместимости, но CLI 0.153.4 отказывается
  применять его к разделённым writable roots, а 0.146.0 давал Node spawn EPERM;
  автоматического переключения и отключения sandbox нет.
- `codexMaxTaskTokens` — бюджет тяжести задачи Codex, по умолчанию **25 000 000** токенов; положительное целое число, `null` отключает проверку.
- `maxTaskCostUsd` — денежный предел Claude, по умолчанию 25; на Codex не влияет.

Распределение TD_Game (полная инструкция — в `CLAUDE.md`):

| Этапы                                               | Codex | Claude    |
| --------------------------------------------------- | ----- | --------- |
| `triage`, `interpret`, `postmortem`                 | Astra | Fable 5.1 |
| `implement`, `revise`, `benchmark`, `deploy`        | Terra | Opus 4.8  |
| `decompose`, `design`, `audit`, `review`, остальные | Sol   | Opus 5    |

Создание MR/PR входит в реализацию и доработку. Ревью работает на Sol/Opus 5,
включая штатное завершение слиянием. Состояния `pr` и `cleanup` модель не запускают.
Проверка готовности среды Codex использует модель `deploy`, простая проба
сервера Codex — `default`. Неподдерживаемая модель не заменяется другой автоматически.
Проба сервера Claude в TD_Game использует `apiProbeModel: claude-opus-5`;
старые замеры цены пробы Haiku к этой настройке не относятся.
Новые настройки применяются при последующем запуске; активная сессия не меняется.

Считается сумма входных и выходных токенов всех сессий задачи. Кэшированные
входные уже входят в input_tokens и второй раз не прибавляются. Это объём
обработки контекста, включая повторное чтение, а не размер уникального кода.
По 30 последним логам Claude на 05.09.2026 прежнему порогу $25 соответствовало
примерно 24,8 млн токенов; 25 млн — округлённая начальная эвристика. Это не
пересчёт тарифов Codex и не квота подписки ChatGPT.

На границе этапов достижение бюджета отправляет задачу в decompose для
повторного анализа и дробления. Сам анализ и сквозные состояния восстановления
освобождены от проверки. Лимиты времени и продолжений сохраняются: CLI
сообщает usage в конце хода, поэтому немедленного прерывания по токенам нет.

Счётчик хранится в `.pipeline/codex-usage.json` основного дерева отдельно
от отчётов. Он учитывает сообщённый расход даже при неудачном выходе процесса
или неверном отчёте, сохраняется при перезапуске, смене этапа и провайдера.
Для resume берётся максимум накопительного расхода сессии, поэтому повторная
обработка события не удваивает сумму. Новые сессии прибавляются. Удаление
истории сессии не сбрасывает счётчик. При переносе супервизора на другую машину
перенесите и этот файл: счётчик локальный, в карточку доски он не записывается.

Без usage расход неизвестен; при включённом бюджете такой ответ не принимается
как успешный. Токены прерванного до выдачи usage хода оценить нельзя. Повреждённый
файл счётчика останавливает запуск, чтобы не обнулить бюджет незаметно.

На Windows адаптер явно включает sandbox и именованный профиль td-pipeline,
наследующий :workspace. Для коммитов профиль разрешает запись в общую .git
проекта и Git-каталог назначенного рабочего дерева. Обычный workspace-write
защищает эти каталоги от записи даже при дополнительных writable_roots.
Доверие Git safe.directory передаётся через окружение только для основного
и назначенного дерева, без глобального изменения Git и wildcard.
На остальных системах сохраняется workspace-write. Сеть включена,
approval_policy=never. Правила администратора продолжают действовать.

Личный config.toml не подмешивается (--ignore-user-config), поэтому Windows
sandbox задаётся адаптером явно; авторизация CLI сохраняется. Список разрешений
Claude не управляет командами Codex. Подробности штатных профилей:
[Permissions](https://learn.chatgpt.com/docs/permissions) и
[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox).

Перед первым рабочим оборотом супервизор проверяет реальное выполнение
читающей Git-команды через Codex. Одного ответа модели недостаточно: нужны
успешное событие команды, ожидаемый вывод и успешное завершение процесса.
Проба идёт из пустого временного каталога через git -C к проекту,
чтобы не готовить всё основное дерево как writable-root. Она ограничена двумя минутами; при отказе конвейер завершится до выдачи
задач. Диагностика — .pipeline/codex-readiness.log. На ручной паузе и в теневом
режиме проба не выполняется. Проба также проверяет SSH к TD_DEPLOY_HOST
(по умолчанию dezintegra) из той же среды Codex: BatchMode=yes,
ConnectTimeout=15, StrictHostKeyChecking=yes и только вывод фиксированного
маркера на сервере. Это проверка соединения, а не Docker, сборки или выкладки.
При недоступном псевдониме, ключе или неизвестном ключе сервера старт
останавливается до назначения карточек. Текст ответа модели без успешного
события SSH-команды не считается готовностью.

Если уже идущий этап получает declined, отказ попадает в журнал и создаётся
.pipeline/pause. Новые этапы не выдаются, текущие могут закончить отчёт.
Перезапуск паузу не снимает: сначала разберите причину, затем снимите её вручную.
Не отключайте sandbox для исправления отказа. Проверяйте точный путь и сообщение.

## Проверки адаптера

05.09.2026 на Windows проверены:

- CLI через обёртку: `codex-cli 0.146.0` (npm) и `0.153.4` (exe);
- настоящий ответ модели без инструментов: thread.started, agent_message,
  turn.completed с usage; разбор соответствует этим событиям;
- реальное продолжение сессии через resume с сохранением thread_id;
- usage после resume накопительный: из него вычитается сохранённый итог
  предыдущего захода, чтобы не учесть его дважды;
- узкие тесты запуска, завершения, токенового бюджета и разделения сессий.

После исправления 05.09.2026 проверен реальный связанный Git worktree:
Codex создал evidence.txt, выполнил git add и git commit (801b2c4),
завершил с кодом 0; независимая проверка показала новый коммит и чистое дерево.
Это отдельный тестовый репозиторий, без push и выкладки.
Первоначальный blocked by policy вызывало отсутствие Windows sandbox
при игнорировании пользовательского config.toml. Следующие проверки выявили
несовпадение владельца Git и защиту gitdir; оба случая учтены профилем запуска.
Предупреждение Git о недоступном личном global ignore не мешало коммиту
(код 0). Реальные выкладки затем выявили недоступность SSH-псевдонима
в sandbox; поэтому проверка SSH добавлена в стартовую пробу. Отдельный
Windows-пользователь sandbox не наследует доступ к личной .ssh владельца.
Исправлять это следует явной настройкой доступа с владельцем: адаптер
не копирует ключи, не расширяет ACL и не отключает sandbox автоматически.

Стартовая проба через исправленный адаптер на основном TD_Game прошла
05.09.2026: успешная команда, корректный вывод, код CLI 0.

GitHub-авторизация sandbox передаётся как GH_TOKEN в окружении процесса:
супервизор берёт существующий GH_TOKEN/GITHUB_TOKEN или ответ gh auth token.
Значение не записывается в конфиг, аргументы или журналы. Другие переменные
с названиями секретов (включая Trello) из окружения Codex исключаются.
Git HTTPS для github.com получает Authorization через GIT_CONFIG_COUNT,
GIT_CONFIG_KEY_n и GIT_CONFIG_VALUE_n в окружении каждого процесса Codex.
Заголовок ограничен https://github.com/, credential helper отключён для этого
хоста. Прежний helper через sh.exe работал в elevated, но падал на signal pipe
в unelevated; теперь авторизация Git не требует запуска MSYS-оболочки.
Точные safe.directory основного и назначенного дерева задаются там же.
Окружения этапов независимы; личный Git config и PATH не меняются.
Не выводите git config --list или окружение: они могут содержать заголовок.
Переменные Git trace/curl verbose не наследуются этой средой.

Перед выдачей задач проба проверяет также gh api user и git push --dry-run
в refs/heads/codex/readiness через настроенный remote. Ветка не создаётся
и не изменяется. Успешный доступ к API при ошибке dry-run не разрешает старт:
так выявляются ошибки Git-авторизации до захвата карточек.

Стартовая проба также запускает дочерний Node и, на Windows, `cmd` через Node.
Это необходимо для установочных скриптов pnpm и сборки: доступные Git и SSH
не исключают `spawn EPERM`. При неуспехе конвейер не выдаёт задачи и сообщает
причину в `.pipeline/codex-readiness.log`. Изоляция песочницы автоматически
не меняется. После устранения причины стартовая проба должна пройти целиком.

## Снимки выкладки

Перед deploy супервизор создаёт отдельное detached-дерево под
`.pipeline/deploy-checkouts` на закреплённой ревизии главной ветки.
Claude и Codex получают один контракт: `worktree`, `branch: null`,
`deploymentRevision`. Историческая ветка задачи не сливается с main.
Путь и хеш сохраняются в `.pipeline/stages.json` до запуска; продолжение
использует тот же снимок. Старый deploy без сохранённого снимка требует разбора.
Изменённый снимок не очищается автоматически. Снимки остаются на диске
для диагностики и продолжений; автоматической уборки в этой версии нет.

## Отдельный SSH-доступ конвейера

`TD_DEPLOY_SSH_CONFIG` — необязательный абсолютный путь к конфигурации OpenSSH.
Задайте его в локальном `.env` проекта или окружении супервизора. Пример:

```dotenv
TD_DEPLOY_SSH_CONFIG=C:/src/dezintegra/TD_Game/.pipeline/ssh/config
```

Без переменной Claude и Codex используют стандартную конфигурацию OpenSSH.
При заданном пути все удалённые проверки и SSH/SCP выкладки получают `-F`
отдельным аргументом, включая пути с пробелами. Ошибка файла останавливает
операцию; скрытого перехода на другую конфигурацию нет.

Для Windows elevated создайте отдельную пару ключей из той же изолированной
среды, в игнорируемом `.pipeline/ssh`. Добавьте публичный ключ пользователю
выкладки на сервере, сохранив существующие строки `authorized_keys`; опция
`restrict` отключает PTY и forwarding, не мешая обычным командам и SCP.
Приватный ключ не выводите и не копируйте из личного каталога. В отдельном
config задайте Host, HostName, User, IdentityFile, IdentitiesOnly yes и
UserKnownHostsFile. Ключ сервера возьмите из уже проверенного known_hosts,
а не принимайте неизвестный отпечаток автоматически.

Удалённая проверка с той же конфигурацией:

```powershell
node scripts/deploy-remote.mjs "true"
```

Помощник включает BatchMode=yes, ConnectTimeout=15, StrictHostKeyChecking=yes
и возвращает статус SSH. Startup Codex вызывает его с фиксированным маркером,
затем проверяет запуск дочерних процессов Node. После смены CLI или sandbox
проверьте также `pnpm install --frozen-lockfile` в отдельном диагностическом
дереве: успешный SSH сам по себе не подтверждает работу сборки.

### Общие файлы замеров Codex

Супервизор заранее создаёт отсутствующие .perf-lock и .perf-log.jsonl в основном дереве и выдаёт Codex запись именно в эти файлы. История и активный замок не обнуляются. После замера пустой файл замка сохраняется вместе с Windows ACL. PERF_LOG по-прежнему задаёт другой журнал относительно назначенного дерева; его родитель должен существовать. Во время обновления не запускайте одновременно замеры из старой версии, удаляющей файл замка: такой запуск может потребовать повторной подготовки файлов супервизором.

### Браузер для обязательного замера

После первой установки зависимостей и после обновления Playwright выполните из рабочего дерева под владельцем станции:

```powershell
pnpm exec playwright install chromium
```

Команда устанавливает соответствующие lockfile Chromium и Headless Shell в кеш Playwright. Без них обе сцены остановятся до открытия страницы. Сам `pnpm e2e:perf` перед проверкой загрузки собирает внутренние библиотеки, сервер и службу компьютеров; эти службы запускаются из dist без watch. Для нового снимка выкладки не требуется заранее собирать клиент или запускать полный verify.

На Windows обёртка замера сама запускает server, computer и Vite непосредственными дочерними процессами Node, проверяет их готовность и останавливает свои дескрипторы после прогона. Это сохраняет очистку в sandbox, где системный taskkill может быть недоступен. Отдельный запуск Playwright без обёртки этим управлением не пользуется; штатная команда замера — pnpm e2e:perf.
