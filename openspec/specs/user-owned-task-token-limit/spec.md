# user-owned-task-token-limit Specification

## Purpose
Дать владельцу возможность явно изменить полный бюджет Codex одной карточки,
не позволяя агенту повышать лимит, сбрасывать расход или распространять разрешение
на другие задачи.
## Requirements
### Requirement: Только владелец явно задаёт индивидуальный лимит

Система MUST получать индивидуальный лимит Codex только из точного комментария владельца Trello, созданного без API-приложения и без признака агента. Поддерживаются `Лимит токенов: <положительное безопасное целое>` и `Лимит токенов: общий`. Отчёт, заявка, машинный блок, свободный текст и комментарий API MUST NOT менять лимит.

#### Scenario: Явная команда пользователя

- **WHEN** владелец пишет в интерфейсе карточки `Лимит токенов: 35000000`
- **THEN** полный бюджет этой карточки становится 35000000, расход не обнуляется, бюджеты других карточек не меняются

#### Scenario: Агент подделывает команду

- **WHEN** API-комментарий того же пользователя, отчёт или машинный блок содержат команду или значение лимита
- **THEN** индивидуальный лимит не меняется, даже если комментарий не имеет машинной пометки

#### Scenario: Возврат общего бюджета

- **WHEN** последняя команда владельца — `Лимит токенов: общий`
- **THEN** задача наследует общий конфиг без изменения самого конфига

### Requirement: Лимит сохраняет силу после роста журнала

Система MUST выбирать последнюю команду по истории конкретной карточки, включая комментарии за пределами первой страницы. Ошибка чтения истории MUST NOT разрешать запуск с подставленным общим пределом. Отсутствующее свидетельство человеческого происхождения MUST NOT считаться разрешением.

#### Scenario: Старый лимит после перезапуска

- **WHEN** после команды опубликовано более тысячи комментариев и супервизор перезапущен
- **THEN** лимит восстанавливается из полной истории; дочерние карточки его не наследуют

#### Scenario: Ошибка чтения следующей страницы

- **WHEN** Trello не отдаёт часть истории
- **THEN** цикл не запускает задачи на основании неполного снимка

### Requirement: Гейт и журнал используют эффективный бюджет

Система MUST использовать пользовательский предел вместо общего для обычных запусков Codex и указывать его в журнале этапа. Неверное значение MUST удерживать обычные запуски без изменения попыток. Новый предел MUST NOT отменять зависимости, неизвестный расход или замечания ревью. Команда в awaiting-po MUST учитываться штатным обработчиком ответа.

#### Scenario: Возобновление после исчерпания

- **WHEN** расход 26093350, общий лимит 25000000 и пользователь задаёт 35000000 в ожидающей карточке
- **THEN** ответ возвращает карточку на сохранённый этап, последующие обычные этапы допускаются при выполнении остальных условий, журнал показывает 35000000

#### Scenario: Неверная сумма

- **WHEN** последняя человеческая команда содержит ноль, отрицательное, дробное или небезопасное целое
- **THEN** обычный запуск удерживается с понятной причиной до новой корректной команды
