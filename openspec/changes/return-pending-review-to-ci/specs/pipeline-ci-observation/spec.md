## ADDED Requirements

### Requirement: Временный недопуск review передаётся в ожидание CI

Review SHALL возвращать `waiting-ci` при пригодном свежем результате `pending` общего подтверждения CI, если нет самостоятельных замечаний или подтверждённого конфликта. Супервизор SHALL переводить задачу в существующее состояние `pr`. Исполнитель MUST NOT ждать через watch, вливать PR, снимать черновик либо создавать коммит ради передачи ожидания. Дальнейшие опросы SHALL использовать общий алгоритм CI; свежий success для актуального SHA SHALL оставаться обязательным перед рассмотрением diff и непосредственно перед вливанием с защитой `--match-head-commit`. Смена SHA SHALL отменять прежний допуск.

#### Scenario: Pending при входе

- **WHEN** GitHub ещё определяет слияние, данные временно недоступны либо проверки идут и общий инструмент выдаёт пригодный pending
- **THEN** review завершает работу с waiting-ci, задача переходит в pr, diff не рассматривается и исправляющий revise не запускается

#### Scenario: Pending непосредственно перед вливанием

- **WHEN** первоначальный success разрешил проверку diff, замечаний нет, а повторное подтверждение даёт pending
- **THEN** задача возвращается в pr без ready и merge, предыдущий success не используется

#### Scenario: Повтор ожидания и новый успех

- **WHEN** после waiting-ci два опроса подряд дают pending, затем опрос даёт success
- **THEN** задача остаётся в pr на первых двух опросах без сессии и лишнего комментария, затем допускается новый review со свежей проверкой

#### Scenario: Смена вершины

- **WHEN** между первоначальным допуском и вливанием изменился локальный или удалённый SHA
- **THEN** прежний допуск отменяется, новая вершина не вливается; при отсутствии самостоятельных замечаний задача передаётся в pr для проверки актуального SHA и нового review

#### Scenario: Реальные причины доработки

- **WHEN** есть содержательные замечания, подтверждённый failure либо конфликт, включая конфликт merge-tree
- **THEN** waiting-ci не скрывает их, review возвращает rejected с причиной, а опрос pr сохраняет прежние маршруты failure/conflict в revise

### Requirement: Результат CLI различает ожидание и поломку вызова

Настоящий процесс `review-ci` SHALL выдавать один JSON и коды success=0, failure=1, pending=2, conflict=3; неверные аргументы SHALL завершаться кодом 64 без обращения к GitHub. Потребитель SHALL проверять JSON и идентичность вызова, а не выводить failure только из ненулевого кода оболочки. Отказ запуска, повреждённый вывод и необъяснённое противоречие JSON с кодом процесса MUST NOT давать success или молча считаться обычным pending. Диагностика SHALL различать код процесса CLI и код транспортной оболочки.

#### Scenario: Реальный процесс с временно неизвестным слиянием

- **WHEN** тест запускает настоящий bin/review-ci.mjs с контролируемым ответом gh UNKNOWN
- **THEN** получены ровно один JSON state=pending и код дочернего процесса 2; тест вызова одной функции не заменяет эту проверку

#### Scenario: Отрицательные результаты и неправильный вызов

- **WHEN** настоящий CLI получает success, failure, conflict или неверные аргументы
- **THEN** наблюдаются соответственно 0, 1, 3 и 64; последний случай не вызывает gh

#### Scenario: Оболочка сообщает единицу

- **WHEN** в журнале инструмента указан exit_code=1 при state=pending
- **THEN** проверка сопоставляет прямой код дочернего процесса и результат той же команды через оболочку, сохраняет версии и выводы; подтверждённая нормализация оболочкой явно объясняется, необъяснённое расхождение остаётся ошибкой вызова без вливания
