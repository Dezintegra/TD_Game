## Decisions

### 1. Отделить повод проверки от доказательства

Повод — завершённый живой запуск с failed-отчётом, неуспешным ответом или отсутствием пригодного отчёта перед продолжением/исчерпанием. Для обычного done диагностика не требуется. API-overload остаётся существующим отдельным путём; лимит токенов и ошибка учёта не получают обхода через новый механизм. Отказы политики и чужой stage в отчёте сохраняются и проходят прежние проверки доверия, даже если диагностика независимо обнаружила сбой.

Нормализатор provider возвращает факты исполнения (идентификатор события, порядковый номер, завершённость, exit code или структурированную ошибку порождения), не заключение «машина сломана». Разбор текста stderr и список слов EPERM/SSH запрещены. Текст нужен лишь журналу. Проба выполняется один раз на запуск и не вызывается рекурсивно для собственной неудачи.

Использовать отдельный диагностический адаптер над существующими командами readiness с результатом `{ verdict, context, checks }`. Каждый check содержит supervisor-owned id, argv, время, фактический контекст, статус `passed | failed | missing` и ссылку на ограниченный вывод. Прямой контроль выполняется через ту же оболочку/профиль ограничений, что у назначенного provider: вне sandbox зелёный процесс не доказывает здоровье sandbox. Если адаптер не может воспроизвести профиль или подтвердить исполнение, это `inconclusive`, не поломка машины. Codex использует существующие сборщики invocation/executionArgs/environment; Claude — действующий контекст stage-command/settings. Адаптеры тестируются раздельно. Никаких дополнительных разрешений для пробы.

Контрольные операции фиксированы кодом установленного супервизора, не берутся из команды/текста агента и не используют изменённые task scripts: shell marker, существующий node child-process probe без node_modules, чтение Git в назначенном дереве, GitHub authentication, dry-run push собственной ветки; только deploy дополнительно проверяет настроенный SSH host. Профиль обязательных проверок задаётся этапом: shell/Node для всех, Git/GitHub/push для этапов работы с веткой, SSH для deploy. Дефект теста или сборочного скрипта не влияет на контроль дочерних процессов. Git rejection из-за состояния ветки (например non-fast-forward) не является доказательством сбоя транспорта: такая проверка даёт inconclusive, транспорт подтверждается отдельной фиксированной проверкой доступа; классификация не использует прозу Git. Dry-run с новой диагностической ref, как в readiness, не обновляет remote и позволяет избежать этого смешения.

Наблюдавшийся сбой фиксированного обязательного контроля подтверждает недоступность возможности в данном контексте; это не заявление о поломке всей ОС. Отсутствие события, один общий таймаут диагностической сессии, ошибка модели или неверный marker дают inconclusive. Полностью успешные проверки — healthy. Failed-отчёт при healthy/inconclusive идёт прежним путём; жалоба не обеспечивает бесконечного бесплатного повтора. Для контроля, не породившегося, нужен структурированный результат runner об ошибке запуска конкретного контрольного процесса; молчание runner этого не заменяет.

Лимит одной группы диагностик — 120 секунд, процессы снимаются существующим killTree. Проверки последовательны, первая доказанная неисправность завершает группу; на восстановлении обязаны пройти все обязательные проверки. Нет установок пакетов, сборки, сервера игры и записи на production; SSH — только marker, push — только dry-run. Диагностические файлы, если нужны, создаёт супервизор в принадлежащем пробе подкаталоге назначенного workspace. Стоимость диагностической сессии фиксируется отдельно как служебная, фактический расход этапа не стирается.

Альтернатива «звать старый readiness и любой false считать поломкой» отвергнута: не различает непроверенность и сбой, проверяет другой cwd. Альтернатива «только агент указывает component» отвергнута: он может дать повод, но не выбрать результат.

### 2. Одна запись результата до любых эффектов

Расширить конверт 0233 версионированным полем disposition: `diagnosing`, `ordinary`, `infrastructure-held`, `retry-ready`, `retry-claimed`, `settled`. `report` остаётся неизменённым, для отсутствующего отчёта — null вместе с raw-result reference; эта запись не выдаётся `applyReport` за валидный отчёт. Сохранить назначенные provider, cwd, branch, stage, launchId, startedAt, batch, deployment revision, snapshot попыток и доказательство списания продолжения именно этому launchId. Не брать batch и право на refund из ответа агента.

Сначала зафиксировать конверт `diagnosing` в store, затем освободить live и провести проверку до ordinary transfer. Pending блокирует competing mutations и fail-stage уже на этом промежутке. После перезапуска diagnosing продолжается ограниченной новой пробой; терминальных эффектов до её решения нет. Хранилище читается после владения замками и раньше recovery, как требует 0233. Ошибка записи оставляет результат в памяти и закрывает планирование; гарантия не распространяется на убийство процесса до первой успешной записи.

Общий контракт с 0243 для списания: один supervisor-owned launchId назначается до spawn обоим provider и используется в assignment, live descriptor, результате и записи попытки. В store 0233 сохраняется операция списания с состоянием `not-required | pending | confirmed`; снимок attempts в prompt не является подтверждением. Initial и replacement имеют not-required. Для обычного continuation pending фиксируется до spawn, а confirmed — только после независимого подтверждения записи получателем по ключу launchId. Доказанный отказ до рождения завершает операцию без списания; неизвестный результат записи остаётся pending. Finish вправе сохранить результат и провести диагностику раньше завершения saveTask, но settlement/refund и следующий запуск ждут разрешения pending. Запись списания и компенсация сериализуются для этой задачи: после подтверждённого списания берётся свежая карточка, затем исполняется refund по квитанции 0233. Поздний callback saveTask не пишет старый снимок поверх компенсации. Перезапуск сверяет квитанцию исходной операции, не выводит факт списания из общего числа continuations и не переиздаёт неопределённую запись вслепую.

При confirmed сохранить evidence и infrastructure-held, затем взвести существующий `.pipeline/pause`, не затирая чужую причину паузы. При обрыве между этими действиями восстановленный hold вновь взводит паузу. Находившиеся в работе дети заканчивают штатно и сохраняют свои отчёты. Пауза запрещает запись на доску, но не приём результата на диск. Свободный процессный слот не изображается занятым; удержание выдачи обеспечивает пауза.

Git evidence — HEAD, branch, upstream/remote ref, список локальных коммитов сверх удалённой ветки и dirty-path summary при доступности. Неудавшееся чтение — `unknown` с причиной и последним доверенным снимком, а не пустой хвост. Нельзя reset, cleanup, пересоздание дерева, force-push или автоматический push произвольной ветки. Сохраняются и неотслеживаемые файлы; существующий push-tail не обходит hold. В журнале будут оба исхода и отдельный диагностический вердикт.

### 3. Восстановление — идемпотентное разрешение одного повтора

Пауза снимается человеком существующим способом. Снятие само по себе не доказывает восстановление: до новых запусков held-контексты повторно проверяются. Failed/inconclusive снова взводит паузу и сохраняет hold; таймер не запускает пробу на каждом обороте. Изменившийся профиль/путь требует сверки с сохранённым назначением, а не выдаётся за тот же контекст.

После healthy план 0233 записывает в журнал исходный отчёт и независимое доказательство, сохраняет статус этапа, реальный расход, возвращает только фактически начисленное этому launchId продолжение и фиксирует право на один замещающий запуск. Initial launch refund не получает; старые continuation/cycleFailure/spawnFailure/API counters не обнуляются. Компенсация не должна запускать обычный `applyReport(failed)`, разбор или заявки/исключения из failed-отчёта: полный отчёт остаётся диагностическим материалом. Один ключ операции на refund исключает повтор при потере ответа Trello. После всех квитанций очередь завершает именно план инфраструктурного удержания, а не план обычного failed.

Право на повтор хранится в том же конверте до handoff; оно пропускается перед проверкой maxContinuations только для одного связанного запуска. Замещающий запуск не увеличивает continuations. Владелец, зависимости, лимит токенов, слоты и эксклюзивность по-прежнему проверяются: инфраструктурное исключение не даёт безлимитной работы. Перед spawn сохраняется new launchId/claim; после неопределённого spawn сначала сверяются live descriptor и данные процесса, без второго spawn. Если отсутствие процесса доказано, claim возвращается в retry-ready; неизвестность удерживает. После успешного handoff запись settled остаётся доступной для диагностики через существующий архив/журнал результатов, активный конверт подтверждается штатно.

Отчёт уже сдан — прежняя сессия забывается и замещающий запуск получает свежую сессию того же этапа, как в forget-reported-stage-sessions; без отчёта разрешён прежний resume. В обоих случаях prompt включает исходный отчёт, диагностику, оставшуюся работу и Git evidence. Исполнитель сначала сверяет дерево/коммиты/PR и выполненные внешние действия, затем продолжает. Это не автоматическое повторение последней команды.

Общий шлюз выдачи проверяется до claim в execute и синхронно непосредственно перед порождением в spawnStage, без await между последней проверкой и spawn. Он объединяет существующие ограничения и, если 0243 уже влита, её mayLaunch; healthy инструментов не открывает API-запрет или ручную паузу. Результат `availability-held` означает доказанное отсутствие spawn, обрабатывается как skipped: сохранённый retry-claimed возвращается в retry-ready без потребления entitlement, списания continuation, spawnFailure или cycleFailure. Обрыв до записи возврата восстанавливается сверкой claim/live descriptor; неизвестность по-прежнему удерживает. Подготовленное дерево и назначение остаются. Entitlement потребляется только после подтверждённого рождения и устойчивого handoff; ни API-восстановление, ни повторный skipped не создают второе право. Для deploy действуют те же правила, но только после допуска из Decisions 4.

Структурный api-error маршрутизируется раньше инструментальной классификации: note-api-error остаётся единственным владельцем его возврата, infrastructure settlement для такого launch не создаётся. Обработчик API использует тот же подтверждённый факт списания; сигнал контроллеру доступности не компенсирует попытку. Обычный failed может дать наблюдение серии 0243, но только независимый инструментальный контроль 0244 разрешает инфраструктурный refund. Альтернативы «снять entitlement при claim» и «вернуть continuation по снимку finish» отвергнуты: первая теряет повтор при отложенном spawn, вторая допускает компенсацию до списания и её затирание поздним saveTask.

Граница эффектов из Decisions 3 распространяется и на `dependencyUpdates`: полный payload остаётся в неизменном отчёте, но diagnosing/confirmed hold и infrastructure settlement не вызывают планирование адресатов, их захват, запись зависимостей или подтверждение таких записей. После healthy эти поручения не превращаются в отложенную очередь доставки: в журнале/архиве явно фиксируется «сохранено, не исполнено: infrastructure disposition». Settlement подтверждает только собственные эффекты и сохранность полного отчёта, а не мнимую доставку поручений. Новый отчёт replacement может заново обосновать поручение, старый автоматически не исполняется. Альтернатива «исполнить адресные поручения перед классификацией» отвергнута: она меняет чужие карточки по отчёту, оставленному лишь диагностическим материалом.

Обычный допустимый failed при healthy/inconclusive сохраняет весь контракт 0242: валидацию, свежие чтения, захваты и инвалидирование старых действий, независимое подтверждение каждого адресата перед переходом источника и снятием pending. Сбой подтверждения сохраняет ordinary report для повторной доставки. Уже начатый ordinary plan при миграции/перезапуске не переклассифицируется в infrastructure и не теряет частично выполненные поручения; транспортный сбой доставки сам по себе не является новым сбоем инструментов исполнителя.

### 4. Deploy удерживается целым назначенным пакетом

В конверте ведущая, полный batch и deployment snapshot/revision неизменны. Ни excluded, ни deployed из failed-отчёта не разносятся в terminal columns во время hold. Все участники защищены от обычного transfer, push-tail, cleanup и нового формирования batch. Восстановление готовит тот же пакет; новые карточки ждут следующего.

Это явное исключение из пересборки пакета при продолжении в требовании «Выкладка идёт пакетом» изменения batch-deploy: infrastructure hold/retry использует сохранённое назначение, включая resume без отчёта. Обычное продолжение без infrastructure hold/retry entitlement по-прежнему пересчитывает пакет на момент выдачи сессии. Пересборка инфраструктурного пакета отвергнута: она может сменить ведущую, добавить новые карточки или исключить исходных участников и тем самым оторвать повтор от сохранённых эффектов и ревизии.

Если предыдущая команда могла уже выложить код, до выдачи deploy retry супервизор контрольным чтением сверяет удалённую ревизию и имеющиеся deployment evidence. Известный опубликованный revision передаётся продолжателю как уже выполненный эффект: он завершает оставшиеся проверки и отчёт без повторной публикации. Недоступная/неоднозначная ревизия удерживает пакет с диагностикой до разрешения неопределённости. Проба не изменяет production. Успешный отчёт с частичной доставкой — исключительно путь квитанций 0233, повторной сессии нет.

Безопасность сохраняется в каждом промежуточном коммите: шаг 3.2 разрешает replacement только для этапов кроме deploy. Deploy остаётся удержанным даже при healthy-диагностике и готовом retry entitlement; claim/spawn для него запрещены. Шаг 3.3 впервые разрешает deploy retry тем же коммитом, который добавляет обязательную проверку удалённой ревизии и эффектов. Перенос проверки в более поздний коммит отвергнут: до него повтор мог бы заново выполнить уже состоявшуюся публикацию. Узкий тест шага 3.2 фиксирует отсутствие deploy spawn при непроверенной ревизии.

### 5. Согласование норм без скрытого приоритета

Все перечисленные согласующие правки входят в коммиты интеграции, а сейчас фиксируются только планом своего изменения:

- `append-addressed-card-dependencies` (0242), «Stage reports can address dependency additions» и «Dependency writes require independent confirmation»: явно ограничить принятие поручений и обязательность их доставки/подтверждения ordinary disposition; сохранить все сценарии обычного accepted/failed и отказа доверия. Добавить парные сценарии: confirmed failed сохраняет полный `dependencyUpdates` без адресных операций при hold, settlement и restart; ordinary failed доставляет его штатно с независимым чтением, а ошибка подтверждения запрещает снятие отчёта. Infrastructure settlement получает собственное подтверждение сохранённого диагностического payload, не ложные квитанции адресатов. Уже в 2.2 gate disposition ставится перед любыми эффектами `transferReport`, включая обработчик 0242; в 3.1 то же исключение явно распространяется на settlement/acknowledgement. Порядок общих правок: сначала влить 0233 и 0242, освежить базу, затем подключать gate 2.2 и settlement 3.1 поверх их фактического API; соседние реализации не копировать. Относительный порядок вливания 0233 и 0242 не задаётся, но перед 2.2 обе интеграции должны присутствовать и обычная подтверждаемая доставка 0242 должна работать через store 0233. Сохранить также влитую обработку split-зависимостей и guards свежего старта; инфраструктурное исключение их не обходит.

- `supervise-the-pipeline`, требования «Ответ сессии берётся из кода возврата и вывода», «Срок этапа и снятие поддерева процессов» и «Прерванный этап возобновляется, а не начинается заново»: обычное применение failed и предел продолжений действуют при отсутствии подтверждённого инфраструктурного hold; исходы остаются раздельными, hold не переписывает отчёт. У существующих сценариев failed/исчерпания уточнить отсутствие hold, сохранить все THEN; добавить confirmed-контроль и обычную ошибку теста. Норму resume оговорить уже сданным отчётом, сохранив согласование forget-reported-stage-sessions.
- `count-only-real-launches`, «Продолжение засчитывается за родившийся процесс»: добавить адресную однократную компенсацию подтверждённого инфраструктурного launch и единственный замещающий запуск без начисления; остальные причины и сценарии оставить.
- `count-only-real-launches`, «Сессия не просится, пока места нет»: явно ограничить правило остановки по исчерпанию продолжений отсутствием infrastructure hold и действующего retry entitlement. Сценарий «Пределы исчерпаны при занятой машине» получает это условие в WHEN, сохраняя THEN об остановке обычной задачи независимо от мест. Добавить сценарий: при исчерпанных продолжениях и подтверждённом hold задача не получает fail-stage; после восстановления действующее entitlement разрешает ровно один replacement с обычной проверкой мест/эксклюзивности. Занятые места откладывают replacement, не уничтожая право; после его потребления исключение прекращается. Другие пределы, приоритеты и существующие сценарии сохраняются. Оговорку hold внести уже в 2.2 вместе с его подключением, оговорку entitlement и сценарий replacement — в 3.2; скрытый приоритет новой дельты над безусловной старой нормой недопустим.
- `batch-deploy`, «Отчёт пакетной выкладки разносится по задачам пакета»: обычное разнесение применяется к ordinary disposition; infrastructure-held сохраняет пакет без failed/cleanup, до проверки удалённых эффектов. Сценарии успешного пакета и квитанции 0233 сохраняются.
- `batch-deploy`, «Выкладка идёт пакетом»: в шаге 3.3, одновременно с первым разрешением deploy replacement, ограничить абзац «Продолжение прерванной пакетной выкладки SHALL пересчитывать перечень пакета на момент выдачи сессии» обычным продолжением без infrastructure hold/retry entitlement. Для подтверждённого инфраструктурного повтора, в том числе resume без отчёта, явно предписать исходные ведущую, полный состав и deployment revision из конверта, без нового отбора участников. Оговорить общие правила выбора новой ведущей и исключения удержанных/исчерпавших пределы задач: они не пересобирают сохранённый инфраструктурный пакет; неизвестность назначения удерживает его. Сохранить существующие сценарии обычного отбора и добавить парные сценарии: инфраструктурный повтор после восстановления получает исходный пакет, даже если появилась новая более приоритетная карточка, а обычное продолжение пересчитывает состав по прежнему правилу. Квитанции 0233 не заменяют эту оговорку: она действует и при отсутствии отчёта.
- `persist-unapplied-stage-reports`, «Accepted stage reports survive supervisor restart»: расширить сохранение диагностическим конвертом с null report, не объявляя его допущенным отчётом. «Pending reports are restored before recovery and scheduling» и «Report acknowledgement follows complete delivery»: удержание заканчивается обычной доставкой либо подтверждённым infrastructure plan и безопасным handoff; до этого повтор запрещён, после него разрешён ровно один связанный launch. Сохранить все существующие сценарии и добавить сбои при refund/handoff.

Имена ADDED своей дельты уникальны относительно основы и 0233; подменять отсутствующую основу MODIFIED нельзя. Порядок архиваций указан в proposal.

Общие участки с `stop-launches-on-session-outages` (0243) — finish, launchId/provider, continueStage/saveTask/noteApiError, scan и spawnStage. Перед 2.1–2.2 и 3.2 освежить main и сверить фактически влитые реализации этих участков с Decisions 2–3. Если 0243 уже влита, расширить её единственный факт списания и финальный mayLaunch gate, не добавляя параллельных обработчиков. Её синхронное наблюдение завершения выполняется после нормализации ответа до ранних выходов finish; диагностика 0244 его не задерживает и не повторяет. Если 0243 ещё не влита, 0244 сама вводит необходимую идентичность запуска, барьер подтверждения списания и обработку отложенного spawn на существующем шлюзе, без контроллера быстрой серии и зависимости от его модулей. Контракт mayLaunch/availability-held проверяется внедряемым запретом. При последующем совмещении 0243 подключается к этому шлюзу и факту списания; второй refund и второй launchId запрещены. Таким образом порядок поставки свободный, а точки интеграции и проверки заданы сейчас, не отложены на аудит. Если соседние нормы уже присутствуют в свежей базе, теми же коммитами уточнить их ordinary failed как путь без confirmed tool hold и сохранить единственного API-обработчика; если отсутствуют, не создавать копии чужой дельты. Совместные регрессии обязательны при обоих порядках интеграции.

## Risks / Trade-offs

- Проверка после события может уже застать восстановившуюся среду → healthy не оправдывает прошлую ошибку; это сознательная строгая граница подтверждения.
- Диагностическая сессия может не выполнить контроль → inconclusive, никакого вывода по отсутствию событий. Доказать все виды поломок не обещаем.
- Зависимость 0233 не влита → runtime-интеграция ждёт PR 172, независимого store нет.
- Перезапуск между spawn и записью результата → claim и сверка процесса; неопределённость удерживает, а не удваивает эффект.
- Пауза после сбоя одной задачи задерживает станцию → соответствует существующей машинной паузе; живые этапы не снимаются.

## Migration Plan

После PR 172 обновить существующую версию конверта совместимой миграцией: старые pending получают ordinary, уже начатые планы не переклассифицируются. Новые diagnosing создаются только для новых завершений. Подключать runtime после готовности store и восстановления; менять main из рабочего дерева не требуется. Обновление супервизора штатное после остановки цикла; откат разрешён при пустой активной очереди, иначе сохранить файлы и остановить несовместимую версию.

Игра не затронута: реконнект/рассинхрон матча, golden-эталоны, PROTOCOL_VERSION неизменны. Запреты Math.random/Date.now/float в sim соблюдены отсутствием правок sim. Арена не требуется.
