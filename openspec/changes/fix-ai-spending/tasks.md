# Задачи

Порядок продиктован одним: **сначала базовая линия, потом правки.**
Сравнивать будет не с чем, если снять её после.

Правки едут в новый профиль, базовый остаётся нетронутым. Так их можно
стравить напрямую и откатить сменой имени, не откатывая код.

      ≈29 000, юнитов 5–9, ничьих около половины).

      тем же, а не похожим.
      *Проверка:* запросы выполняются на существующей базе и дают числа
      из предложения.

## 2. Окупаемость удара

- [ ] 2.1 Считать ценность цели по оставшейся стоимости, а не по головам:
      `стоимость × здоровье / полное здоровье`, для чужих со знаком плюс,
      для своих со знаком минус.
      *Проверка:* юнит-тест — скопление из десяти добитых юнитов
      оценивается заметно дешевле десяти целых.
- [ ] 2.2 Вывести порог из цены удара и стоимости юнита. Убрать
      `worthUnits` из профиля, добавить коэффициент окупаемости
      со значением по умолчанию «не в убыток».
      *Проверка:* тест — при нынешнем балансе порог равен цене удара,
      делённой на стоимость юнита; при удвоении цены удара в балансе
      порог удваивается сам.
- [ ] 2.3 Тест на отказ от невыгодного удара: шесть целых юнитов
      в радиусе — удара нет; полсотни — есть.
      *Проверка:* оба случая проходят.

## 3. Запас по обстановке

- [ ] 3.1 Разделить в `tryNuke` поиск цели и решение бить: поиск
      возвращает лучшее скопление и его ценность, решение сравнивает
      с порогом. Обход карты при этом остаётся один — второй ради
      запаса недопустим.
      *Проверка:* число обходов карты за решение не выросло; замер
      стоимости матча в арене не ухудшился.
- [ ] 3.2 Заменить `reserve` фазы с признака «держать цену удара»
      на «удар в этой фазе интересен». Держать запас только когда поиск
      нашёл оправданную цель.
      *Проверка:* тест — при пустой карте энергия доступна тратам целиком;
      при скоплении, оправдывающем удар, — удерживается.
- [ ] 3.3 Обновить `profile.ts`: поле `reserve` фазы меняет смысл,
      комментарий объясняет, почему запас стал свойством обстановки.
      В комментарии назвать тупик, из которого выбираемся: энергия
      заперта → нечем производить → армии малы → скопления не набираются
      → удар не оправдан → запас не тратится.
      *Проверка:* `pnpm --filter @td/ai typecheck` зелёный.

## 4. Накопление не глушит дешёвое

- [ ] 4.1 Провести через исход попытки цену желаемого: `wait` должен
      сообщать, на что и сколько копится.
      *Проверка:* поле доезжает до наблюдателя и до таблицы `attempt`.
- [ ] 4.2 Прерывать перебор трат только для покупок не дешевле желаемого.
      *Проверка:* тест — противник, копящий на дорогое улучшение,
      всё равно заказывает юнита; на сопоставимую по цене покупку
      не отвлекается.
- [ ] 4.3 Сверить, что предел терпения срабатывает реже.
      *Проверка:* распределение `wait_streak` в базе сместилось к нулю;
      число решений со `streak = 8` заметно упало.

## 5. Покупка с большей прибавкой обходит очередь

- [x] 5.1 Считать прибавку от юнита: его урон за ожидаемое время жизни,
      переведённый в энергию курсом, который уже есть в `posture.ts`.
      *Проверка:* юнит-тест — величина растёт с прокачкой атаки
      и не зависит от размера войска.
- [x] 5.2 Считать прибавку от боевого улучшения: процент прибавки,
      применённый к тому, чем игрок владеет. В комментарии объяснить
      главное: прокачка умножает то, что уже есть, и при пяти юнитах
      умножать нечего.
      *Проверка:* тест — при войске в пять юнитов прибавка мала,
      при войске в полсотни велика; отношение примерно десятикратное.
- [x] 5.3 Разрешить покупке с большей прибавкой обойти очередь фазы.
      Экономику из сравнения исключить явно: её прибавка выражается
      в будущем доходе, а не в уроне.
      *Проверка:* тест на оба случая из спецификации — при малом войске
      покупается машина, при большом прокачка; улучшение экономики
      сравнению не подвергается.
- [x] 5.4 Сверить, что сопровождение генерала стало частным случаем
      этого правила, а не осталось вторым механизмом рядом.
      *Проверка:* поведение при уходе генерала вперёд без прикрытия
      не изменилось; отдельная ветка `escorting` либо исчезла, либо
      сведена к настройке порога.
