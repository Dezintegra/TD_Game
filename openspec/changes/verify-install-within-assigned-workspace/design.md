## Context

Источники: переданный журнал 0232; `validation.md` и `.matchlog/0226-install-check.mjs` дерева 0226; `.pipeline/logs/0226-sohranit-chistotu-snimka-vykladki-posle--implement.log` (в том числе EPERM и предупреждение filesystem violation); `supervisor/lib/provider.mjs`, `codex-readiness.mjs`, `codex-node-probe.mjs` свежей базы `272a54e`.

Провайдер строит Windows профиль `td-pipeline` на `:workspace`, отдельно разрешая общую `.git`, gitdir назначенного дерева и служебные perf-пути. Это не обещание разрешения любой повторной подготовки другого workspace. Readiness подготавливает sandbox основного cwd и проверяет запуск процессов; ни новая Git-копия, ни создание pnpm-store ею не проверяются.

Наблюдаемая локализация сбоя из операторского журнала: перенос `-C` самой песочницы во вложенную копию дал `setup refresh had errors: SetNamedSecurityInfoW failed: 5` для копии, `.agents` и `.git` (05.09.2026, 20:07:22 UTC); сохранение исходного `-C` и смена cwd только дочернего pnpm дали код 0, 346 пакетов за 47.3 с и непустой кеш. Копия находится внутри workspace; доступ дочернего процесса работает при исходной границе. Значит поддерживаемый способ устраняет наблюдаемый отказ повторной подготовки доступа, не требуя новой ACL. Это не доказательство конкретной внутренней ошибки алгоритма ACL Codex: её детализация вне этой задачи.

Старая восстановленная копия не доказывает свежую подготовку целиком. В прочитанном validation 0226 повторная свежая проба пока неуспешна; результаты этого design не подменяют её и не закрывают пункт 3.1 чужой задачи.

## Goals / Non-Goals

Цель — общая воспроизводимая проверка от новой копии до установки и положительных/отрицательных файловых условий внутри уже назначенной песочницы. Границы и Non-goals перечислены в proposal. Ядро, протокол, рассинхрон и реконнект не затрагиваются; golden-эталоны и PROTOCOL_VERSION не меняются. Запреты Math.random, Date.now и плавающей точки в состоянии мира сохраняются: новых изменений в sim нет.

## Decisions

### 1. Явный диагностический вход без повторного запуска sandbox

Добавить библиотеку `supervisor/lib/install-snapshot-check.mjs` и тонкий CLI `supervisor/bin/check-install-snapshot.mjs`. Без аргументов CLI печатает помощь; единственный рабочий режим `--run` использует текущий cwd, HEAD и закреплённую версию pnpm. Не принимать произвольные пути вывода или команды. CLI запускается инструментом из назначенного дерева; внутри уже действующей песочницы повторный `codex sandbox` не нужен и не выполняется.

Отклонены: перенос cwd инструмента в копию (воспроизводит отказ setup refresh); изменение ACL и writable roots (не нужно по успешной диагностике и выходит за задачу); установка в основном дереве (не проверяет новую копию); добавление установки в обычный readiness (каждый старт потребовал бы сети и сотен пакетов, а 0127 и 0231 имеют другой предмет).

В `stage-settings.json` добавить только точные PowerShell-разрешения формы без доводов и `node supervisor/bin/check-install-snapshot.mjs --run`, с тестом отсутствия расширения на другие bin-команды. Пока основное дерево не содержит нового разрешения, живая проба в реализации вызывается через разрешённый `node .matchlog/0232-install-check.mjs`: короткий локальный файл импортирует ту же библиотеку, не копирует её алгоритм и не меняет cwd. Это штатный разрешённый способ исполнения, а не изменение sandbox. Обе команды документируются; команды оболочки не склеиваются.

### 2. Свежая копия фиксированной ревизии

Определить realpath назначенного cwd; проверить его Git-корень и чистоту. HEAD должен совпадать с upstream после выполненного исполнителем fetch/push; записать SHA. Не fetch-ить и не пушить автоматически. В `.matchlog/` проверить реальные пути существующих родителей до записи (включая junction); создать уникальный собственный каталог через mkdtemp и повторно проверить вложенность. Снимок, архив и диагностика лежат только в нём. Не использовать системный tmp и не удалять старые копии.

Выгрузить `git archive` указанного SHA, распаковать в дочерний `snapshot/`, создать самостоятельный Git-репозиторий, добавить явный список отслеживаемых файлов из `ls-tree` и сделать локальный базовый коммит. Реестр worktree не меняется. Пользовательские hooks отключить только в копии указанием пустого собственного hooksPath; имя автора настроить локально. Исключить унаследованные GIT_DIR/GIT_WORK_TREE/GIT_INDEX_FILE для дочерних Git-команд; не выводить окружение. При необходимости Git safe.directory задавать только точным путём собственной копии на вызов, без глобальной записи и wildcard.

Локальный core.excludesFile указывает на заведомо отсутствующий файл внутри собственного каталога; проверяется, что его нет. `.git/info/exclude` не получает дополнительных правил. Чтобы fsmonitor не скрыл сбой с `error: daemon terminated`, отключить его только в копии и проверять stderr Git на ошибки наряду с кодом возврата. Базовый полный porcelain пуст; node_modules и store отсутствуют. `.gitignore` берётся из SHA без дописывания правил.

### 3. Прямой дочерний pnpm

Запускать установку через Node и найденный установленный pnpm CLI, как в успешной диагностике. Разрешить установленный pnpm из окружения/расположения запуска по существующим проектным подходам, проверить его версию против packageManager; не зашивать `C:/Program Files/...`, не скачивать иной CLI через npx. Ненайденный или несовместимый pnpm — явная ошибка prerequisites.

Дочерний процесс получает массив аргументов `install`, `--frozen-lockfile`, `--store-dir`, `.pnpm-store`, cwd snapshot, windowsHide и конечный таймаут (10 минут). shell не нужен. Store не создавать заранее и не подкладывать маркеры. Ошибку spawn, сигнал, таймаут и ненулевой exit различать в диагностике; незавершённый процесс не считается успехом. Предпочесть асинхронное ожидание с ограничением времени и завершением собственного процесса; не оставлять фоновые установки после отказа. Исходный cwd процесса не меняется через process.chdir.

### 4. Один контроль чистоты и два независимых отрицательных случая

После exit 0 рекурсивно подтвердить реальные файлы пакетов в `.pnpm-store`, затем полный `status --porcelain --untracked-files=all` и `check-ignore -v` для store и одного его файла. Источником должно быть правило `.pnpm-store/` из проектной `.gitignore`, а не личный ignore или общий `.matchlog` внешнего репозитория.

В той же копии изменить один известный отслеживаемый исходник, проверить отказ того же предиката чистоты и точное имя. Восстановить только записанные проверкой байты этого файла, убедиться в чистоте. Затем создать уникальный посторонний файл вне игнорируемых каталогов и независимо подтвердить отказ с `??`. Удалить только этот созданный контрольный файл и снова подтвердить чистоту. Ни reset, ни clean, ни фильтрация статуса не применяются. При ошибке оставить копию для диагностики.

Диагностика вне snapshot, в собственном каталоге пробы: этап, SHA, cwd родителя/ребёнка, реальные пути, версии, коды и безопасные выдержки stdout/stderr, файл кеша и источник ignore, статусы каждого контроля. Не печатать секреты и полное окружение. Итог успеха появляется только после всех условий. Запуск вне Windows остаётся полезной файловой пробой, но не маркируется доказательством Windows sandbox; сведения о версии и профиле Codex фиксируются из запускающей сессии, поскольку библиотека сама по себе не может доказать внешнюю изоляцию.

### 5. Быстрые тесты и обязательная живая проба

Тесты используют реальные временные Git-репозитории внутри собственного `.matchlog`, подменяя только установщик. Проверять смену cwd лишь у дочернего процесса, уникальность, отсутствие внешних записей, выход через realpath, несовпадение ревизии/версии, ошибку установки, пустой store, ошибку Git даже с пустым stdout, неверный источник ignore и оба отрицательных контроля. Контроль удаления `.pnpm-store/` из fixture обязан обнаружить кеш. Заглушка подтверждает алгоритм, не доступ Windows.

Отдельная живая проба выполняется при реализации в назначенной Windows sandbox над уже отправленным кодом. В validation.md записывается точная команда через штатный CLI либо разрешённый импорт из `.matchlog`, версия Codex и профиль из контекста запуска, SHA и все результаты. При сетевой или средовой ошибке пункт остаётся открытым; автоматическое отключение защиты или перенос кеша не допускаются. После смены sandbox/способа запуска документация предписывает повторить эту же пробу. Полный test:pipeline, сборка и арена здесь не нужны.

## Risks / Trade-offs

- Живой прогон зависит от сети и установленного pnpm → отдельный явный режим, таймаут и сохранённая стадия отказа; быстрые тесты без сети.
- Непустая старая копия способна дать ложный успех → уникальная копия каждый раз, отсутствие store до установки, SHA и путь в результате.
- Смена cwd в будущем вернёт ошибку подготовки → тест параметров процесса и документированный повтор живой пробы; профиль провайдера не переписывается.
- Защита .git/.agents может зависеть от версии Codex → проверять создание нового репозитория в живой пробе, не объявлять прошлое восстановление окончательной гарантией.
- Диагностические копии занимают место → сохранять только собственные пробы, показывать их путь; широкая автоматическая уборка не входит в команду.

## Migration Plan

Доставить библиотеку и автономные тесты, затем CLI с точными разрешениями и инструкцией. Выполнить живую проверку и отправить validation.md. Изменение не требует миграции среды или архивации соседних дельт. Откат убирает команду и её разрешения, не меняя sandbox, readiness и подготовленные чужие деревья.

## Open Questions

Продуктовых вопросов нет. Новая полная проба остаётся проверкой реализации, не обещанным результатом проработки. Если исходная граница sandbox перестанет позволять свежую подготовку, сохранить точный отказ и завершить реализацию без заявления об успехе; ACL автоматически не исправлять.
