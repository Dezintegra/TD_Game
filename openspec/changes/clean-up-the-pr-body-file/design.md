## Context

Свежая база на начало проработки: `62ea9fe`, `git -C . merge origin/main` ответил `Already up to date.`. В `supervisor/skills/implement.md:143–157` нет размещения и уборки тела PR; `.gitignore:20` исключает `.matchlog/`. Постановка задачи передаёт результат 0197: точечный `git clean` сработал после отказа Remove-Item. Проработка не повторяет операции удаления и не приписывает себе новую пробу.

`PowerShell(git -C:*)` и `PowerShell(gh pr:*)` уже стоят в `supervisor/config/stage-settings.json`. Проверка разрешений не гарантирует выполнение в любой будущей среде: отказ нужно назвать в отчёте по действующим правилам, а не расширять команду.

## Goals / Non-Goals

Цель — законченный порядок обращения с файлом в существующем шаге открытия PR, сохраняющий чужие файлы. Не-цели перечислены в proposal; в частности, новый автоматический очиститель или тестовый парсер инструкции не нужен.

## Decisions

### Один путь рядом с открытием PR

Указать тело PR как отдельный файл внутри назначенного дерева, например `.matchlog/<taskId>-pr-body.md`, и тот же путь передать в `gh pr create --draft --base main --title "<заголовок>" --body-file <файл>`. Не перезаписывать уже существующий файл неизвестного происхождения. Если задача 0139 уже уточнит размещение, взять её путь; не добавлять второе конкурирующее место. Отчёт этапа остаётся отдельным понятием, его инструкции здесь не переписываются.

Альтернатива — выбрать обязательный новый неигнорируемый путь — отвергнута: создала бы мусор по умолчанию и дублировала 0139. Оставить только `.matchlog/` без ветки уборки тоже недостаточно: продолжение старой сессии может иметь уже созданный неигнорируемый файл.

### Удаление после подтверждённого успеха

Сначала получить успешный результат `gh pr create`, сохранить номер для `links.pr`. При ошибке или неопределённом результате файл по этому порядку не удалять: он может понадобиться для восстановления открытия PR. Созданный PR не открывать повторно ради уборки.

Для файла, оставленного вне ignore, инструкция предписывает перед удалением:

1. Подтвердить по собственной записи создания/журналу текущей задачи, что это именно её временное тело PR и после создания в нём нет чужих правок. Совпадения имени с taskId недостаточно.
2. Проверить разрешённый абсолютный путь файла относительно абсолютного корня назначенного дерева: обычный отдельный файл внутри этого дерева, без выхода через `..`, ссылки или junction. Не принимать каталог, корень дерева, путь другого дерева или шаблон. В команду подставить один проверенный относительный путь в кавычках, без wildcard и pathspec magic.
3. Проверить Git-категорию и исходный статус отдельными вызовами: `git -C <дерево> ls-files -- <точный относительный путь>`, `git -C <дерево> check-ignore -v -- <точный относительный путь>`, `git -C <дерево> status --porcelain --untracked-files=all`. У отслеживаемого файла есть вывод ls-files, у игнорируемого — check-ignore; код 1 check-ignore без диагностической ошибки означает отсутствие совпадения. Нельзя считать произвольную ошибку проверки разрешением удалить. Для целевого неигнорируемого файла ожидается строка `??` в статусе.
4. Только при выполнении всех условий вызвать `git -C <дерево> clean -f -- <точный относительный путь>`, затем отдельно `git -C <дерево> status --porcelain --untracked-files=all`. Собственная строка исчезла, прочие строки и чужие файлы сохранились. Если проверка не удалась или файл остался, не объявлять уборку успешной и назвать проблему в отчёте.

Не добавлять `-d`, `-x`, `-X`, второй `-f`, точку вместо файла, маски или очистку всего дерева. Альтернатива с Remove-Item отвергнута по исходному отказу 0197; повторять её или менять разрешения не предписывается. При неподтверждённой принадлежности остановить только эту операцию удаления и описать оставшийся файл, не «исправлять» статус удалением неизвестного.

### Игнорируемый файл не требует этой уборки

Для тела в игнорируемом `.matchlog/` явно объяснить два факта: обычный `git status` его не показывает и `clean -f -- <файл>` без расширяющих ключей его не удаляет. Можно оставить его там; это не незакоммиченный мусор обычного статуса. Даже если в статусе есть другие `??`, они не становятся целями уборки тела PR.

Альтернатива — добавить `-x` ради удаления тела — отвергнута: выходит за подтверждённую форму и создаёт лишний риск для игнорируемых материалов других задач.

### Требование и проверка

Дельта нужна: инструкция вводит обязательные условия будущего удаления, которых нет в требовании раннего PR. Новое ADDED-требование в `dev-pipeline-worker` не копирует целиком существующее требование и его сценарии. Архивация после `agent-backlog-pipeline` сохраняет единый Purpose способности.

Для документационной правки достаточно ручной сверки всех сценариев дельты с текстом и существующих проверок конвейера на имплементации. Новый тест, повторяющий слова инструкции, не добавляется. Живую повторную пробу удаления не требуем: форма уже подтверждена постановкой; этот этап проектирует текст, а не доказывает разрешения заново.

## Risks / Trade-offs

- Проверка статуса сама по себе не доказывает владение → отдельно требуются запись создания и отсутствие чужих правок.
- Пересечение с 0139 → перед правкой освежить базу, сохранить один выбранный там путь рядом с командой; область уборки зависит от ignore, не от имени каталога.
- Ссылка на номер шага может сломаться → дополнять существующий шаг, не перенумеровывать последующие.
- Игнорируемый файл остаётся на диске → это сознательно допустимо; общая уборка `.matchlog/` вне задачи.

## Migration Plan

Один документационный коммит в `implement.md` плюс отметка tasks; новые сессии получают обновлённый скилл после штатного вливания. Откат возвращает прежний текст. Форматы данных, протокол, sim и состояние мира не меняются; реконнект, рассинхрон, PROTOCOL_VERSION и эталоны детерминизма не затрагиваются. Запреты Math.random, Date.now и плавающей точки в ядре сохраняются без изменений.
