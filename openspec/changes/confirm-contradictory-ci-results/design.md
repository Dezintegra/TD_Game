## Decisions

### 1. Узкий fallback с прежним контрактом переходника

Добавить `supervisor/lib/ci-confirmation.mjs`: чтение подтверждений через переданный `run`, нормализация и проверка данных. `readExternal` расширяет исходный запрос PR полями `number,url,state,headRefOid`; сначала сохраняет существующие guards mergeable. Fallback вызывается только при CheckRun с точной тройкой IN_PROGRESS/SUCCESS/валидный completedAt. Без неё остаётся прежний маршрут и одно чтение PR. Чистое `summariseChecks` само сеть не вызывает и без доказательств продолжает считать такую проверку pending.

Не переставлять conclusion перед status: успешный conclusion сам по себе не доказывает окончание текущей попытки. Не вводить специальный случай по PR 219 или названию «затронутые области». Выделение модуля ограничивает рост общего io.mjs, а подставляемый запускатель позволяет проверять весь штатный путь без сети.

### 2. Подтверждение по идентичности, а не по имени

Из URL PR получить ожидаемые host/owner/repo; принять только точные GitHub Actions detailsUrl того же репозитория с числовыми run/job ID. Не обращаться к произвольным URL из ответа: собирать относительные REST endpoints из проверенных компонентов. REST run должен подтвердить repository, id, head_sha, event pull_request, запись нужного PR и его head в pull_requests, workflow_id, run_attempt. Отсутствие такой связи означает pending, не догадку по ветке или имени.

Читать `repos/{owner}/{repo}/actions/runs/{run_id}` и `repos/{owner}/{repo}/actions/runs/{run_id}/attempts/{attempt}/jobs?per_page=100&page={page}`. Номер attempt берётся из актуального run, не из URL старого задания. Сверять ID, run_id, run_attempt, head_sha, name и конечные поля задания; точные времена должны быть корректны и согласованы с CheckRun. Для обычных заданий допускаются completed/success и completed/skipped. Исключение in_progress/success/время завершения допускается только под подтверждённым completed/success workflow этой попытки. Это необходимо, поскольку REST воспроизводит исходный дефект; требовать от REST такого job completed означало бы сохранить зависание.

REST-поля и endpoints сверены с [Workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run) и [Workflow jobs API](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt). Источник актуальной попытки — run_attempt; endpoint попытки фиксирует состав её заданий. Версии и реальные поля дополнительно проверяются сохранённым ответом проекта, не предположением о поведении gh.

### 3. Полнота и актуальность всего набора

На ветке fallback подтвердить все Actions runs, представленные в rollup, и все их задания, а не только проблемное. Для каждого run прочитать все страницы jobs, сверить total_count и уникальные ID; пустота, дубли, потеря страницы, несовпадение количества или принадлежности дают pending. Требовать однозначное соответствие всех rollup CheckRun заданиям; отсутствующий в rollup job также требует pending до согласованного снимка. Неподдержанный тип проверки не пропускать. Это консервативное ограничение только fallback, не изменение обычной обработки CI.

Дополнительно прочитать список runs для текущего head_sha и event pull_request с полной пагинацией; отфильтровать по проверенной связи с PR и workflow_id, найти актуальные запуски. Более новый run того же workflow делает старое доказательство непригодным даже при прежнем rollup. Не искать «последний успешный»: так был бы скрыт новый красный или работающий прогон. Если обнаружен новый workflow run этого PR, ещё не представленный в rollup, полнота не доказана — pending. Для данного PR один workflow и 7 заданий полностью сопоставляются.

Наличие failure/cancelled/timed_out или другого недопустимого conclusion запрещает success. Достоверный актуальный неуспех остаётся failure; неизвестная принадлежность/полнота/актуальность — pending. Обычный набор SUCCESS/SKIPPED и условные пропуски сохраняются, хотя бы один SUCCESS обязателен.

### 4. Ограниченная повторная сверка вместо постоянного кеша

После сбора прочитать PR заново с теми же полями и повторить актуальные метаданные runs и список запусков. Сравнить head, состояние PR, mergeable и семантический набор проверок (ID/URL, имя, тип, status/conclusion, времена; порядок массива значения не имеет), а также run ID, attempt, head, status/conclusion и набор связанных запусков. Изменение любого существенного поля отменяет результат; конфликт всегда возвращает conflict, UNKNOWN — pending. Не повторять сбор внутри того же опроса: следующий цикл попробует снова.

Повторное чтение jobs не нужно при неизменной завершённой попытке и прежнем составе checks; старт новой попытки обнаруживается повторным run_attempt. GitHub не предоставляет атомарный снимок PR и Actions: гонку после последнего чтения полностью исключить нельзя. Повторная сверка ограничивает окно, а штатная проверка перед вливанием сохраняется.

Общий бюджет fallback — максимум 30 обращений gh, включая повторную сверку; страницы максимум по 100 элементов, каждый вызов через существующий ограниченный по времени запускатель. Достижение лимита или предела выдачи API с недоказанной полнотой даёт pending с причиной. Дедупликация run ID допускается только внутри одного опроса. Постоянный кеш успешного результата не вводится. Это ограничивает нагрузку и исключает перенос успеха на новый head/attempt. У штатного случая PR 219 запас достаточен: один run, одна страница jobs и списка runs.

### 5. Регрессия и живая приёмка разделены

Автоматический тест читает независимую fixture с исходным противоречием, проводит её через `createIo(...).readExternal(task, 'ci')` с подставным `run` и требует success. Изменение только одной защитной предпосылки должно закрывать success. Удаление вызова подтверждения из readExternal должно ломать положительную регрессию; прежнее чистое сведение того же rollup должно возвращать pending. Контроль команд доказывает чтение попытки и повторную сверку, но не заменяет проверку результата.

Приёмка на implement — один живой вызов исправленного readExternal для PR 219 из своего дерева, без запуска супервизора, записи на доску или ручного перезапуска CI. Временный скрипт `.matchlog/confirm-ci-219.mjs` импортирует createIo и resolveConfig, запускает только readExternal с `{ links: { pr: 219 } }`, перехватывает read-only запросы для сохранения свидетельств. В `evidence/pr-219-verification.json` записать время UTC, SHA реализации до коммита свидетельства, исходные ответы, запросы/коды, head/attempt и итог. Нужен success при актуальном успешном CI. Если внешнее состояние изменилось или чтение недоступно, записать фактический результат, пункт не закрывать и вернуть причину по контракту этапа; не подменять живую приёмку fixture или перезапуском.

## Risks / Trade-offs

- Неполная/несогласованная выдача GitHub → безопасное pending с причиной; цена — возможное дополнительное ожидание, а не ложное review.
- Новый запуск на том же SHA → проверка актуальных runs и повторная сверка, а не доверие только номеру попытки старого run.
- Слишком большой ответ → бюджет обращений и контроль total_count; усечённый набор не считается полным.
- Несколько workflows, одноимённые задания и матрицы → идентичность по run/job ID и проверка каждого элемента; имена лишь дополнительная сверка.
- Форки или непривязанный к PR run → консервативное pending на fallback, расширение способов доказательства связи за рамками задачи.

Игровые пакеты, протокол и состояние мира не меняются: реконнект/рассинхрон, golden-эталоны и PROTOCOL_VERSION не затронуты. Math.random, Date.now и дробные значения в ядро не добавляются; время UTC используется лишь в свидетельстве внешней проверки.

## Migration Plan

Один атомарный коммит подключает подтверждение вместе со всеми защитами и регрессией; следующий фиксирует живую приёмку. После вливания обычный запуск супервизора получает новое поведение. Миграции карточек/реестра нет. Откат модуля и подключения возвращает безопасное pending и исходное зависание, не оставляя разрешающего состояния на диске. Автоматический маршрут служебного diff остаётся за супервизором.
