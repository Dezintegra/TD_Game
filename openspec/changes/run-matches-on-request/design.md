## Context

Замер полного прогона от 24.08.2026, машина под нагрузкой (в системе
крутилось 42 процесса node от соседних сессий, так что абсолютные
секунды завышены; соотношения от нагрузки не зависят — все тесты
мерились в одинаковых условиях).

| | время | тестов | прогонов файлов |
| --- | --- | --- | --- |
| матчевые | 1684 с | 133 | 14 |
| остальные | 332 с | 1330 | 73 |

По пакетам `packages/ai` — 1388 с из 2016 с, то есть 69% времени
в одном пакете. Для сравнения: `apps/client` с его 610 тестами —
94 секунды, `packages/shared` с 85 тестами — меньше секунды.

Причина у всех тринадцати одна и та же: они проигрывают партию.
`TICKS_PER_SECOND` равен 30, осадный тест гоняет два матча по 420
игровых секунд — это по 12 600 вызовов `step` на матч, и в каждом
двое противников под управлением компьютера принимают решения.
Всего за прогон проигрывается около 57 минут игрового времени.

Вторая, независимая причина: корневая `test` — это `vitest run`
напрямую, мимо Turborepo. Задача `test` в `turbo.json` описана
и даже кеширована (`turbo run test --dry` показывает готовые записи
с экономией 69 секунд на `@td/sim#test`), но корневая команда её
не вызывает. Из-за этого правка в клиенте пересчитывает тесты ядра
и противника.

## Goals / Non-Goals

**Goals:**

- Обычная правка не должна запускать матчевые тесты вовсе.
- Матчевый набор должен запускаться одной короткой командой и целиком.
- Правка в одном пакете не должна пересчитывать тесты соседних.
- Ни одна существующая проверка не должна пропасть или ослабнуть.
- Граница между наборами должна быть видна в дереве файлов,
  без чтения кода.

**Non-Goals:**

- Не ускоряем сами матчевые тесты и не сокращаем их окна.
- Не трогаем e2e: Playwright уже отделён и командой, и задачей в CI.
- Не заводим per-package `lint`: корневой проход стоит шесть секунд,
  дробить его незачем.
- Не вводим новых зависимостей — ни `cross-env`, ни чего-либо ещё.

## Decisions

### Признак — имя файла, а не тег внутри теста

Взято: файлы матчевого набора получают имя `*.match.test.ts`.

Почему не тег в `describe` с фильтром по `-t`: тег не виден в дереве
проекта. Открыв `packages/ai`, по именам сразу понятно, какие шесть
файлов стоят минут; с тегом это надо искать чтением. Вдобавок фильтр
по имени теста всё равно загружает и разбирает файл, а исключение
по имени файла — нет.

Почему не `*.slow.test.ts`: имя должно говорить, **что это за тест**,
а не жаловаться на его симптом. Медленные они не сами по себе,
а потому что проигрывают партию, — и когда через год кто-то заведёт
новый тест, «нужен ли ему матч» ответить куда проще, чем «медленный ли
он». Слово `match` вдобавок уже принято в предметной области проекта.

Дробить файл между наборами запрещено намеренно: граница по файлу
проверяется взглядом и не разъезжается при правках.

### Два набора — две задачи Turborepo, а не один корневой прогон

Взято: у каждого затронутого пакета появляются обе команды, `test`
и `test:match`, и обе становятся задачами Turborepo.

Рассматривался и отклонён вариант проще: матчевый набор запускать
единым корневым прогоном по отдельному файлу workspace, без задач
и без кеша. Он дешевле в файлах — один новый файл вместо шести, — но
теряет главное. Матчевый набор дороже всего, и именно на нём кеш
окупается сильнее всего: правка, не задевшая `packages/ai` и
`packages/sim`, отдаст все 1684 секунды из кеша. Это превращает
`pnpm verify:all` перед вливанием из «сходить за кофе» в «подождать
полминуты» — то есть делает полную проверку тем, что не жалко
запускать. Ради этого шесть восьмистрочных конфигураций не жалко.

### Отдельный файл конфигурации на пакет, без переменных среды

Взято: рядом с `vitest.config.ts` появляется `vitest.match.config.ts`,
а команда пакета — `vitest run --config vitest.match.config.ts`.

Отклонено — переключение набора через переменную среды
(`TD_MATCH=1 vitest run`): на Windows команды `package.json` не умеют
задавать переменные переносимо, для этого нужен `cross-env`, то есть
новая зависимость ради одного флага.

Отклонено — переключение флагами командной строки
(`vitest run --exclude ...`): CLI-флаг `--exclude` **заменяет** список
по умолчанию, а не дополняет его, так что вместе с матчевыми файлами
пришлось бы вручную перечислять `node_modules` и `dist`. Забытая
строка в этом перечне превращается в обход половины репозитория,
и заметить это по зелёному прогону нельзя.

Отклонено — позиционный фильтр (`vitest run match.test`): он сужает
уже отобранный набор, а `exclude` из конфигурации отрабатывает раньше,
поэтому матчевые файлы всё равно остались бы отброшены.

Отдельный файл лишён всех трёх бед, читается за десять секунд
и, в отличие от флагов, попадает во входные файлы задачи Turborepo —
то есть его правка честно сбрасывает кеш.

### Два окружения ядра переезжают в сам пакет

Взято: `packages/sim` прогоняет node и jsdom своими командами —
`"test": "vitest run && vitest run --environment jsdom"` и так же
для `test:match`. Флаг `--environment` перекрывает значение из
конфигурации, отдельный файл ради этого не нужен.

Сегодня оба прогона описаны в корневом `vitest.workspace.ts`,
и в комментарии к нему сказано почему: вложенные workspace Vitest
не поддерживает, а ключ `test.projects` появился только в третьей
версии. Под Turborepo эта помеха исчезает — каждый пакет
запускается сам по себе, и никакой вложенности не возникает.

Побочная выгода: изоморфность теперь проверяется и при запуске
пакета в отдельности (`pnpm --filter @td/sim test`), а не только
из корня. Раньше локальный прогон пакета молча проверял одно
окружение из двух.

### Корневой `vitest.workspace.ts` остаётся, но меняет роль

Он больше не точка входа для `pnpm test` — той теперь заведует
Turborepo. Он остаётся для запусков вручную, когда нужен весь
репозиторий одним процессом (например, разовый прогон с фильтром
по имени теста). Двойное описание `sim` из него уходит: оно
переехало в команды пакета.

### Переименование — отдельным коммитом и через `git mv`

`packages/ai/src/profile.test.ts` на 24.08.2026 правится соседней
сессией в рамках `upgrade-nuke-damage-and-radius`. Переименование —
самая недружелюбная к слиянию операция, а переименование вместе
с правкой содержимого распознаётся хуже всего. Поэтому все тринадцать
переносов идут одним коммитом, в котором нет ничего, кроме
переименований.

### Чего не делаем: `vitest --changed`

Флаг выглядит точным решением задачи «гонять только затронутое»,
но здесь он тихо соврёт. В `tsconfig.base.json` нет `paths`,
в конфигурациях Vitest нет `resolve.alias` — пакеты видят друг друга
через собранный `dist`. В графе модулей тесты `@td/ai` связаны
с `packages/sim/dist/index.js`, а не с исходниками ядра, и правка
`packages/sim/src/step.ts` не пометит их затронутыми. Прогон
пройдёт зелёным, ничего не проверив.

Turborepo этот случай отрабатывает верно: он считает граф по сборке,
и `test.dependsOn: ["^build"]` втягивает хеш зависимостей в ключ
кеша.

## Risks / Trade-offs

**Матчевый набор станет запускаться реже — и это цель, а не побочный
эффект.** Риск в том, что регрессия в поведении противника доживёт
до вливания вместо того, чтобы упасть через минуту после правки.
Смягчается тремя способами: CI гоняет полный набор на каждый push
и pull request; `verify:all` перед вливанием остаётся обязательным
по требованию `quality-gates`; а правило в `CLAUDE.md` называет три
зоны (`packages/sim`, `packages/ai`, баланс), при касании которых
матчевый набор гоняется не дожидаясь вливания.

**Переименование конфликтует с чужой незавершённой работой.**
Смягчается отдельным коммитом из одних переименований (см. выше),
но полностью не снимается: если соседняя сессия добавит в
`profile.test.ts` новые тесты, при слиянии их придётся переносить
руками. Об этом сказано в `proposal.md` в разделе Impact.

**Шесть новых файлов конфигурации — это шесть мест, где можно
разойтись.** Например, забыть в `vitest.match.config.ts` окружение
или назвать проект так же, как быстрый. Смягчается тем, что все
шесть однотипны и коротки, и тем, что задача с ошибкой в `include`
немедленно печатает «No test files found» — молчаливого прохода тут
не бывает.

**Осадный тест остаётся тем, чем был, — пятнадцатиминутным.**
Соблазн срезать ему окно с 420 секунд до 240 велик: это почти
четверть всего прогона. Но окно подобрано под длину партии, и тест
служит канарейкой темпа игры — он падает при каждой правке скорости
и стоимости. Укоротив окно, мы сломаем ровно то, ради чего он
заведён, и узнаем об этом не сразу. Он переезжает, но не меняется.

**Абсолютные цифры замера завышены** (машина была занята), поэтому
обещать «прогон уложится в 332 секунды» нельзя. Обещать можно
соотношение: из быстрого набора уходит около 84% времени. Линию
«после» стоит переснять на свободной машине — это отдельная задача
в `tasks.md`, и её результат надо записать, а не отметить галочкой.
