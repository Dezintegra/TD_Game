## Context

Свежая база этапа: `ab22998`; fetch и merge origin/main завершились `Already up to date.`. `.gitignore:2` содержит `.pnpm-store/`. Коммиты `9fa4652124c358c7b670ce2d27aef84d0ee4e93c` и `08257f439f55cc198f6ec0886ae5058a2c61897d` имеют одинаковый diff `.gitignore` (blob `81da5f3` → `8b4e2e8`); второй — #158 и предок origin/main.

`prepareDeploySnapshot` в `supervisor/lib/deploy-snapshot.mjs` создаёт detached-снимок и проверяет обычный porcelain-статус при создании и повторном использовании. Установка выполняется позднее исполнителем. В `supervisor/skills/deploy.md`, шаг 6, проверка статуса предшествует установке; второй проверки нет. Сторож в `supervisor/config/transitions.test.mjs` проверяет присутствие отдельных строк, но не их порядок. `deploy-snapshot.test.mjs` покрывает изменённый отслеживаемый файл, однако фикстура содержит только исключение `.pipeline/`, без проектного ignore.

## Goals / Non-Goals

Цель — замерять только снимок, подтвердивший чистоту после установки, и доказать, что локальный кеш не мешает этому даже без личных исключений Git. Границы перечислены в proposal: не меняем механизм подготовки/назначения, не ремонтируем снимки и не доставляем #158 повторно.

## Decisions

### 1. Использовать уже доставленный проектный ignore

`.pnpm-store/` остаётся в `.gitignore`; код проверки продолжает читать обычный `git status --porcelain`. Не фильтруем строки по имени кеша и не добавляем `--untracked-files=no`: это скрывает часть фактов о снимке. Глобальный ignore и `.git/info/exclude` не подходят как источник гарантии, поскольку зависят от машины и могут быть недоступны. В этой сессии Git действительно сообщил `unable to access .../.config/git/ignore: Permission denied`, сохранив код 0; это предупреждение не равно ошибке команды.

### 2. Добавить вторую проверку в текущий шаг подготовки

В шаге 6 сохранить первоначальные команды и доводы про измерение дерева и файлы сборки. Вынести установку в собственный блок PowerShell, следом отдельным блоком — повторный porcelain-статус. Проза рядом явно требует успешного кода установки и проверки, пустого stdout, остановки с `failed` до замера при нарушении и запрета исправлять снимок. Следующие шаги не перенумеровываются.

Альтернатива «перенести единственную проверку после установки» потеряла бы раннюю защиту до изменения окружения. Перенос установки в `prepareDeploySnapshot` увеличил бы обязанности супервизора и время подготовки процесса без необходимости. Проверка только после замера тратит дорогой ресурс на заведомо непригодное дерево.

### 3. Сторожить последовательность в действующем тестовом файле

Расширить охрану deploy в `supervisor/config/transitions.test.mjs`, сохранив проверки detached-ревизии, доводов и запрета merge. Проверять рабочую часть шага подготовки по границам заголовков шагов, выделяя команды из блоков PowerShell; упоминания в Non-goals, запретах, комментариях и поздней прозе не засчитывать как исполнение. Внутри шага требуется порядок: исходный статус → установка → повторный статус; весь шаг расположен раньше шага замера. Проверять также явные условия остановки при неуспешной установке, непустом статусе и ошибке статуса.

Для проверки самого сторожа использовать строковые копии текста: удалить только вторую проверку, переставить её до установки, перенести после начала замера, удалить условие остановки. Эти отрицательные примеры не меняют файл правил на диске. Диагностика называет файл и конкретное нарушение. Простое `includes` на установку и статус отвергнуто: обе строки уже есть сегодня и такой тест не ловит дефект.

### 4. Проверять границу чистоты реальным Git

Дополнить `supervisor/lib/deploy-snapshot.test.mjs`. Фикстура коммитит содержимое действующего корневого `.gitignore`, прочитанное через путь от модуля, а не копию строки `.pnpm-store/`: удаление проектного исключения должно краснить тест. Все Git-процессы фикстуры и вызываемый `prepareDeploySnapshot` используют локальный `core.excludesFile`, указывающий на отсутствующий файл в собственном каталоге фикстуры. Это воспроизводимо отключает личные исключения на Windows и Linux без правки глобальной конфигурации или ACL. Проверить, что `.git/info/exclude` фикстуры не добавляет исключение кеша.

После создания снимка записать непустой вложенный файл `.pnpm-store/v-test/files/cache-entry`, проверить пустой статус и повторный приём того же пути/ревизии. На независимых фикстурах вместе с кешем изменить отслеживаемый `source` и создать `unexpected-source.txt`: статус обязан назвать соответствующий путь, повторная подготовка — бросить ошибку, содержимое обоих файлов — сохраниться. Проверка происхождения исключения через `git check-ignore -v` должна указывать проектный `.gitignore`. Отсутствующий личный файл моделирует отсутствие доступных личных правил; реальная ошибка ACL не навязывается всем платформам.

Быстрые тесты моделируют файловые последствия установки и не утверждают, что запускали pnpm. Дополнительно при реализации провести один настоящий `pnpm install --frozen-lockfile --store-dir .pnpm-store` в свежем собственном проверочном снимке отслеживаемых файлов текущего коммита. Такой снимок — изолированный тестовый Git-репозиторий внутри `.matchlog/0226-install-check/`, созданный вспомогательным скриптом из отслеживаемого содержимого; он не является деревом супервизора. В нём применить тот же локальный `core.excludesFile`, проверить наличие кеша, происхождение ignore и пустой статус до/после установки. Команды выполняются с рабочим каталогом снимка через параметр инструмента, без цепочек смены каталога. Ни сборка, ни perf, ни выкладка для этой пробы не нужны.

## Risks / Trade-offs

- Сторож текста чувствителен к перестройке инструкции → ограничить мерку исполняемыми блоками шага и семантическими условиями остановки; негативные примеры фиксируют реальные потери защиты.
- Синтетический кеш не доказывает успешность настоящей установки → отдельная проба pnpm с записью версии, ревизии, кода возврата и статуса; сетевой сбой не считать успешной пробой.
- Старый сохранённый снимок до #158 не содержит исключения → он по-прежнему отклоняется при грязном статусе. Менять его ревизию, подсовывать ignore или чистить кеш исполнителю нельзя; это прежнее правило разбора.
- Проверка действует на момент её выполнения → дальнейшие существующие проверки выкладки сохраняются; глобальная защита от любых последующих внешних записей не входит в задачу.

## Migration Plan

Реализация меняет инструкцию и тесты одним PR в назначенной ветке. #158 уже на основной ветке, cherry-pick не нужен; чужие ветки и снимки не трогаются. Архивация — после `prepare-deploy-snapshot`, с добавлением уникальных требований, без перезаписи требований предшественника. При откате PR исчезнет дополнительная проверка, но уже влитое проектное исключение остаётся.

Игровой код, состояние мира, рассинхрон и реконнект не затронуты. Запреты `Math.random`, `Date.now` и дробного состояния симуляции сохраняются; эталоны детерминизма и `PROTOCOL_VERSION` менять не требуется. Заявка на арену не нужна.
