## Why

Владелец поручил удерживать весь повторный implement задачи `0243-ostanavlivat-novye-zapuski-pri-nesostoya` до завершения `0242-dat-otchetu-etapa-adresnoe-poruchenie-na` и подтверждённого вливания PR 177. Сейчас tasks.md и design.md `stop-launches-on-session-outages` называют PR 177 предусловием лишь шага 3.1; независимость модели 1.1 допускает ошибочное прочтение как разрешение начать сессию раньше. По постановке это уже расходовало сессии.

## What Changes

- Согласовать два плановых файла существующего изменения 0243: общее предусловие действует до первого действия повторного implement, а независимость модели 1.1 описывает только устройство коммита.
- После поставки канала 0242 передать супервизору точное `dependencyUpdates` для 0243: добавить 0242 в `dependsOn` и результат `merged-pr` с PR 177, сохранив остальные данные.
- Подтвердить запись независимым чтением обработчика 0242 и проверить существующий допуск 0073 на изолированных снимках. Различать передачу поручения, сохранение карточки и фактическую допустимость запуска.
- В предусловии 0243 назвать обновление её назначенного дерева из `origin/main` и доказательство наличия результата PR 177 до реализации.

## Non-goals

Повторная реализация шлюза зависимостей, канала 0242, API-паузы и иной функциональности 0243; прямые записи доски; возврат failed-карточки в работу; запуск настоящей сессии для проверки; изменение приоритетов, лимитов и прочих зависимостей. Соседнее `bind-tool-outage-prerequisites` для 0244 не изменяется. Арена и изменения игровых пакетов не входят в работу.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

Нет: это применение существующих правил к конкретной карточке и согласование порядка уже заказанной работы. Нового постоянного требования нет.

## Impact

Реализация изменит `tasks.md` и `design.md` существующего `stop-launches-on-session-outages`, добавит воспроизводимые свидетельства проверки в каталог этого изменения 0247 и передаст адресное дополнение метаданных. Если артефакты 0243 ещё отсутствуют в main, переносится их существующий полный каталог из её опубликованной ревизии, без кода и без создания второго имени изменения; подробности в design. Производственный код супервизора не меняется.

Отзывчивость интерфейса и игровой сетевой трафик не меняются: ни клиент, ни сервер, ни протокол не затронуты. Служебный трафик — штатное чтение/дополнение/подтверждение карточки механизмом 0242 и проверки GitHub механизмом 0073, без новых циклов опроса.

Зависимость поставки: поручение выдаётся только после доставки `append-addressed-card-dependencies` (0242, PR 177) в используемый супервизор. Изменение архивируется ПОСЛЕ `append-addressed-card-dependencies`; архивация без дельт — с `--skip-specs`, отдельным уполномоченным этапом. `require-merged-pr-for-dependencies` уже реализовано в main, хотя его дельта ещё открыта. С `bind-tool-outage-prerequisites` общие механизмы, но разные карточки и плановые файлы; зависимость между этими двумя операциями не вводится.

## Почему дельты нет

- `card-dependencies / Explicit prerequisite metadata`: добавляются значения одной карточки; общий формат не меняется. Открытая дельта `require-merged-pr-for-dependencies` уже определяет `dependencyResults`.
- `card-dependencies / Gate task launches on completion` и открытая модификация 0073: по-прежнему нужны closed, совпадающий links.pr и MERGED в настроенную главную ветку; удержание сохраняет состояние и счётчики. Номера 0242 и 177 — данные применения этого правила.
- `card-dependencies / Completion includes all decomposition descendants` и `Result evidence is read without worker sessions` из 0073: потомки и актуальные доказательства остаются обязательными; изолированная проверка не меняет их смысл.
- Три требования открытой дельты 0242 — `Stage reports can address dependency additions`, `Dependency additions preserve current card data`, `Dependency writes require independent confirmation` — уже задают адресное объединение, сохранность и независимое подтверждение. Здесь используется их точный контракт, включая failed без возврата в работу.
- Все четыре требования дельты `stop-launches-on-session-outages` в `pipeline-supervision-resilience` (учёт завершений, быстрая серия, сохранение попыток и раздельные паузы) остаются дословно прежними. Перенос предусловия с шага 3.1 на повторную сессию исправляет план исполнения по уже принятому решению владельца, не поведение этих механизмов.

После правки ни основная спецификация, ни открытая дельта не читаются иначе. Каталог specs здесь не создаётся.
