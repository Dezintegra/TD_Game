# Проектное решение

## Что здесь решается

Пять вопросов, и все технические — выводимые из кода сторожа, из текста
правил разрешений и из соседнего сторожа в том же файле. Продуктового
решения задача не требует.

1. Как признак формы правила доезжает от разбора до сверки.
2. Чем меряется точная форма.
3. Той же ли меркой сверяются запреты.
4. На чём проверяется, что сторож теперь краснеет.
5. Почему правится и нормативный текст соседнего изменения, а не только
   его пояснение.

## Откуда известно, что форм действительно две

Не из внешней памяти, а из этого же файла. Сторож «перечень сценариев
открыт точной формой, а не с любым доводом»
(`supervisor/config/transitions.test.mjs:346`) требует в настройке
`Bash(pnpm run)` без хвоста и **запрещает** `Bash(pnpm run:*)` — целиком
на том основании, что без хвоста правило не открывает `pnpm run verify`,
`pnpm run deploy` и прочее, закрытое правилами 6 и 8 проекта. Если бы
среда мерила приставкой обе формы, этот сторож был бы бессмыслен,
а конвейеру давно открыли бы выкладку.

Отсюда и вывод: разница форм в среде есть, а `prefixOf` её стирает.
Дальше в этом документе она принимается как данность, и проверять её
отдельным опытом изменение не берётся — опыт над правилами разрешений
означал бы правку настройки живого конвейера ради наблюдения.

## Решение 1: форма едет вместе с телом одним значением

Разбор правила отдаёт не строку, а пару — тело и признак формы:

```js
const patternOf = (rule, shell) => {
  const wrapped = new RegExp(`^${shell}\\((.*)\\)$`).exec(rule);
  if (!wrapped) return null;
  const body = wrapped[1];
  return body.endsWith(':*')
    ? { body: body.slice(0, -2), exact: false }
    : { body, exact: true };
};
```

`null` для чужой оболочки остаётся как был: правило `Bash(...)` о правах
в PowerShell не говорит ничего.

**Отвергнутый вариант: оставить `prefixOf` строкой, а форму выяснять
в `coversCommand` по сырому правилу.** Тогда `coversCommand` пришлось бы
передавать и правило, и оболочку — то есть разбирать обёртку дважды,
двумя местами, которым положено расходиться. Признак — часть результата
разбора, там ему и место.

**Отвергнутый вариант: две функции, `prefixOf` и `exactOf`, а вызывающий
выбирает.** Выбирать он может только по той же примете — хвосту `:*`, —
значит разбор всё равно раздваивается, и вдобавок вызывающий обязан
помнить, какая функция к какой форме. Пара «тело плюс признак»
не оставляет места для такой ошибки.

## Решение 2: точная форма меряется совпадением целиком

`coversCommand` собирает регулярное выражение по телу правила
и закрывает его по-разному:

- приставка — `^<тело>(\s|$)`, как сегодня. Граница по пробелу
  обязательна и остаётся: без неё `gh pr` покрыло бы выдуманное
  `gh press`;
- точная форма — `^<тело>$`.

Экранирование спецсимволов и толкование звёздочки внутри тела (`*` →
`.*`, она стоит вместо довода) не меняются ни для одной из форм.

**Отвергнутый вариант: точную форму мерить как «приставка, у которой
команда не имеет продолжения».** Это то же самое, записанное длиннее
и через отрицание; но главное — такая формулировка соблазняет добавить
«кроме случая, когда доводы безобидны», а безобидность доводов сторожу
не видна. Совпадение целиком не оставляет щели для оговорок.

**Отвергнутый вариант: считать точную форму никогда не покрывающей
команду из `MERGE_PATH`.** Соблазнительно тем, что у всех трёх команд
списка есть доводы, и код вышел бы короче. Отвергнут: это верно
для сегодняшнего `MERGE_PATH` и перестанет быть верным, едва в списке
появится команда без доводов. Мерка обязана зависеть от формы правила,
а не от нынешнего состава списка.

## Решение 3: запреты меряются той же меркой

Тот же `patternOf` и тот же `coversCommand` применяются к `deny`. Запрет
приставочной формы гасит команду с любыми доводами; запрет точной формы
гасит только дословно равную команду.

**Почему не «любое совпадение запрета считать непокрытием» (мерка
строже для `deny`, чем для `allow`).** Соблазн понятен: ошибиться
в сторону тревоги кажется безопасным. Но сторож, объявляющий непокрытой
команду, которую среда пропускает, лечится единственным доступным
способом — расширением правил разрешений либо снятием запрета, то есть
ослаблением настройки ради успокоения теста. Ложная тревога здесь
дороже молчания: она толкает править не сторожа, а то, что он сторожит.

Сторож зеркалит среду. Обе формы, обе стороны, одна мерка.

## Решение 4: проба на порчу — на выдуманной настройке, а не на живой

Третья проба встаёт рядом с двумя уже стоящими (строки 404–425) и,
как они, подаёт `uncoveredMergeCommands` рукописный объект прав:

```js
const exactly = {
  allow: ['Bash(gh pr view)', 'Bash(gh pr ready)', 'Bash(gh pr merge)',
          'PowerShell(gh pr view)', 'PowerShell(gh pr ready)', 'PowerShell(gh pr merge)'],
  deny: [],
};
```

Ожидание — **шесть** строк: три команды на две оболочки, ни одной
покрытой. Проверяется длина списка, а не вхождение одной строки: список
из пяти означал бы, что одна форма прочтена иначе, и такую разницу надо
видеть.

**Отвергнутый вариант: проверять правку временной подменой
`stage-settings.json`.** Настройка живая: этим файлом среда выдаёт права
идущим этапам. Тест, который её переписывает, ставит на кон работу
соседних сессий ради наблюдения, которое рукописный объект даёт
даром.

**Отвергнутый вариант: обойтись сегодняшними двумя пробами.** Ни одна
из них не задевает точную форму: `narrowed` сужает правило до
`gh pr merge:*`, `shadowed` гасит запретом `gh pr ready:*` — обе
приставочные. Правка без третьей пробы была бы непроверяемой, а сторож
на сторожа — ровно то, чего задача просит.

## Решение 5: правится и требование соседнего изменения, а не только пояснение

Задача называет `design.md` изменения `undraft-before-merge` (Решение 4,
строки 96–113). Но то же ложное утверждение стоит и в нормативном тексте
его дельты — `specs/dev-pipeline-supervisor/spec.md`: «Совпадение
по приставке — единственный порядок сверки, применяемый средой,
и проверять надо именно его».

Оставить его нельзя. Изменение не заархивировано, требование ещё
не закон, но заархивируется оно раньше нашего (см. «Зависимости»
в предложении) — и тогда в `openspec/specs/dev-pipeline-supervisor`
встанут рядом два требования, спорящие о том, как среда мерит правила.
Разбирать этот спор будет тот, кто не писал ни одного из них.

Правится один абзац: ложная безусловность снимается, ссылка на форму
правила ставится. Смысл требования — «три команды вливания покрыты
поимённо, и ни один запрет их не перекрывает» — и все три его сценария
остаются нетронутыми: они верны при любой мерке.

**Отвергнутый вариант: заменить требование `undraft-before-merge` своим,
объявив его `MODIFIED`.** Невозможно по форме: `MODIFIED` пишут поверх
требования, которое дословно есть в `openspec/specs/`, а этой
способности там ещё нет вовсе — её заводит незаархивированное
`supervise-the-pipeline`. Дельта поверх отсутствующей основы проходит
`openspec validate` и падает при архивации.

## Границы применимости

Изменение не задевает `packages/sim`: ни правил игры, ни эталонов
детерминизма, ни профилей арены. Прогон арены не нужен, эталоны
не пересматриваются, `PROTOCOL_VERSION` не растёт — раскладка байтов
протокола не меняется ни на бит.

Поведение при рассинхроне и переподключении не затронуто: геймплея
изменение не касается вовсе, и раздел этот пустует по существу,
а не по недосмотру.

Запреты ядра соблюдаются даром: ни `Math.random`, ни `Date.now`,
ни числа с плавающей точкой здесь не появляются. Правится один тестовый
файл на Node, исполняемый вне игрового ядра, и два документа OpenSpec.

## Чем проверяется на месте

Набор конвейера живёт в своём корне, и обычный `vitest` его не видит:

```
npx vitest run --root supervisor config/transitions.test.mjs
```

Это узкая проверка по своему файлу — то, что правило 6 проекта из
дополнительного дерева разрешает. Полный набор (`pnpm test:pipeline`
внутри `pnpm test`) гоняет CI.
