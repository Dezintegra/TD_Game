## Context

`execute.mjs:transferReport` обрабатывает `requests` и `amendments` перед `saveTask` источника и удалением отчёта. `parseReport` сохраняет неизвестные поля JSON; специальной схемы отчёта там нет. `dependencies.mjs` уже содержит `dependencyFormatProblem`, `dependencyCycleProblem` и неизменяемую этой задачей семантику допуска.

`backlog-trello.mjs:readTask` читает Map снимка, а `saveTask` пересобирает описание и меняет колонку. Поэтому пара этих методов не годится ни для свежего дополнения, ни для доказательства записи. Map также скрывает дубликаты ID. `metaOf` выбирает известные поля, что опасно для неизвестных ключей свежего служебного блока.

## Goals / Non-Goals

Цель — один проверяемый канал поручений существующим карточкам, сохраняющий данные и не подтверждающий неудачную запись. Границы перечислены в proposal: в частности, ни живой записи 0238, ни изменения планировочной семантики, ни реализации восстановления отчётов PR 172.

## Decisions

### Контракт и чистое планирование

Поле `dependencyUpdates` отсутствует либо является массивом; `null` — ошибка. Пустой массив — без действий. Элемент имеет ровно четыре поля: `taskId`, `dependsOn`, `dependencyResults`, `reason`. Пример формы (условные ID):

```json
{
  "dependencyUpdates": [{
    "taskId": "0003-consumer",
    "dependsOn": ["0002-producer"],
    "dependencyResults": [{"taskId": "0002-producer", "kind": "merged-pr", "pr": 42}],
    "reason": "Поручено постановкой задачи закрепить результат предшественника"
  }]
}
```

`dependsOn` непустой; `dependencyResults` может быть пустым для зависимости только по закрытию. При добавлении результата к существующему ребру ID повторно указывается в дополнении. Повторы внутри одного дополнения и несколько элементов на одного адресата отклоняются; повтор между дополнением и карточкой нормален. Предшественник проверяется на полный ID существующим валидатором; его завершённость здесь не требуется — смысл операции именно в ожидании будущего результата. Отсутствующего предшественника по-прежнему блокирует обычный допуск, а не новая трактовка.

Новый чистый модуль `dependency-updates.mjs` проверяет оболочку, адресата и объединяет поля без мутации. Вызывает `dependencyFormatProblem` и для дополнения (с `id` адресата), и для результата, `dependencyCycleProblem` — для актуального графа с подставленными кандидатами всех элементов. Форма ID адресата проверяется тем же контрактом полного ID без второго независимого определения регулярного выражения. Идентичные результаты сравниваются по значениям трёх полей, не по порядку JSON-ключей. Другой PR — ошибка, не «последний победил».

Валидация всех элементов предшествует первой записи. Она использует коллекцию карточек, включая негодные и архивные совпадения, до построения Map. Получатель — единственная годная неархивная карточка, кроме источника и `closed`. `failed` разрешён: запрет из `amendments` здесь неприменим, предусловие готовит возможный возврат, но не выполняет его. Пустое `reason` запрещено; содержание служит основанием в диагностике и журнале источника, не машинным доказательством продуктового согласия.

Альтернатива — расширить `amendments` — отвергнута: у комментариев другой контракт ошибок и получателей. Универсальный patch отвергнут, поскольку позволил бы менять состояние и стирать условия.

### Специализированная операция хранилища

Ввести IO-операцию `appendTaskDependencies(update, context)` с ответом `{ok, outcome, why, task}`. Исполнение вызывает её после проверки отчёта и до любых существующих побочных действий отчёта. Отсутствующий метод при непустом поле — явная ошибка, без тихого пропуска. Trello IO реализует канал непосредственно; если включён старый файловый адаптер без поддержки, тот возвращает явный unsupported, а не ложное подтверждение.

Порядок для изменяемого адресата:

1. Прочитать актуальную коллекцию карточек настроенной доски для однозначного разрешения ID (не только Map снимка). Проверить карточку штатным разбором и `checkCard`, сверить физический card ID и принадлежность доске.
2. Если актуальные данные уже содержат дополнение, повторное чтение подтверждает no-op: записи и захвата не требуется.
3. Иначе получить временный эксклюзивный захват тем же механизмом назначения участника, которым конвейер сериализует обычные старты. Использовать именно новое назначение, без ветки `acquire`, допускающей старого владельца с той же машиной. Уже назначенная карточка означает занятость даже в `failed`; чужой захват не снимать.
4. После захвата снова прочитать карточку и актуальный граф, повторить проверки и объединение. Это сохраняет зависимости, добавленные между снимком и захватом. Все писатели нового канала пользуются этим же захватом.
5. Одним PUT передать только `desc`. Собирать его из свежего человеческого текста и исходного служебного объекта с заменой только двух полей. Не вызывать общий `saveTask`, не отправлять `idList`, `name`, метки, позицию или `owner`.
6. Независимым GET прочитать сохранённую карточку, снова разобрать/валидировать и проверить ID, требуемые пары, включение всех прежних зависимостей и результатов, равенство остальных данных. Сравнение служебного объекта структурное; человеческий текст сохраняется без смыслового переписывания.
7. В `finally` освободить только захват, полученный этим вызовом; ошибка освобождения тоже не успех. Подтверждённые данные перенести в локальный снимок. Результат содержит адресата и диагностируемую причину.

Обычные процессы не прерываются. Работающая или оставшаяся назначенной карточка возвращает retryable busy: освобождение её прежнего назначения не входит в этот канал. Так техническая сериализация не превращается в захват чужой задачи.

Альтернатива «свежий GET, PUT, GET без захвата» отвергнута: два супервизора могут перезаписать дополнения друг друга. Сравнение перед PUT без захвата также не является compare-and-swap. Ручная запись в обход назначения не сериализуется; обнаруженное расхождение при подтверждении — ошибка, автоматического отката старым описанием нет.

### Порядок применения отчёта и снимок цикла

Проверить `report.taskId` против action/source, `stage` против action и карточки, исход и доверие. При `verdict.problems` либо провале доверия адресных записей нет. Законный `question` или `failed` может содержать поручение: решение о переходе само по себе не является ошибкой формы. При любой ошибке нового канала вернуть `result: failed` с полным `why`, не только словом `outcome`; не писать переход источника, не снимать отчёт и отметку начала этапа. Сначала новый канал, затем текущие requests/amendments и остальные действия: его ошибка не порождает попутных карточек.

По нескольким адресатам допускается частичное выполнение, а не распределённая транзакция. Отчёт остаётся целым; повтор строит объединение заново и не делает повторный PUT уже достигнутого состояния. Успех источника перечисляет подтверждённых адресатов и основания в его штатной записи журнала. Отдельные комментарии адресату не нужны для успеха и не размножаются при повторе.

После изменения адресата недостаточно исправить Map: список действий цикла мог быть рассчитан ранее. IO отмечает адресата как изменённого; исполнитель откладывает остальные предвычисленные действия для него до следующего свежего сканирования. Это касается и старта, и последующей записи метаданных. Данные допуска не меняются: `pendingDependencies` получает новый снимок обычным путём. Глобальную проблему устаревших записей всех остальных операций здесь не исправлять.

### Проверки и архитектура

Чистые тесты проверяют форму, адресацию, объединение, циклы и конфликт результатов. Тесты адаптера подменяют Trello и моделируют новые поля после снимка, отказ каждого сетевого шага, подтверждение с потерянным полем, занятость и повтор. Тесты execute проверяют порядок IO, сохранение источника/отчёта при ошибке, частичный успех и отложенное действие устаревшего цикла. Существующие тесты допуска остаются контролем неизменности семантики.

Геймплей, sim и протокол не затрагиваются: реконнект и рассинхрон матча прежние, эталоны детерминизма и `PROTOCOL_VERSION` не меняются. Запреты `Math.random`, `Date.now` и дробных чисел в состоянии мира остаются в силе; канал не пишет состояние мира. Новых зависимостей npm нет.

## Risks / Trade-offs

- Дополнительные запросы к Trello → только по непустому полю, последовательные адресаты, без фонового опроса и бесконечного повтора внутри одного цикла.
- Обрыв после захвата может оставить назначение → не присваивать его повторным вызовом; явно диагностировать busy, использовать штатное восстановление захватов оператором. Не обещать автоматическое снятие чужого назначения.
- Ручная конкурентная запись в обход захвата → readback ловит видимые расхождения, но линейризуемость произвольных ручных PUT не обещается; такой гарантии текущий адаптер не предоставляет.
- Ошибка формы сохраняет отчёт для диагностики и повторной доставки → не объявлять успешный переход и не терять исходный payload; не переписывать ошибочный отчёт автоматически.
- PR 172 меняет доставку → при реализации сверить актуальную границу приёмки и сохранить правило «адресаты до перехода источника», без зависимости от его ещё невлитого кода.

## Migration Plan

Доставить обработчик и документацию одним PR на все активные станции до использования поля: старый исполнитель переноса неизвестное поле игнорирует. Затем 0241 может поручить конкретную запись отдельно. Сохранённые данные уже поддерживаются нынешним валидатором; миграция карточек не нужна. При откате прекратить выдачу новых поручений и сохранить неприменённые отчёты до восстановления обработчика; подтверждённые зависимости не удалять.
