## Context

На базе `ab22998` после `git -C <дерево> fetch origin` и `git -C <дерево> merge origin/main`:

- `transferReport` забывает исходный этап только в ветке подрывающего отказа, а при `rejected` — целевой этап, если задача не остановлена. Обычный успешный исход оставляет исходную сессию.
- `assignmentFor` строит `continuation` исключительно из `io.lastSession`; комментарий ошибочно выводит прерывание из наличия любого сохранённого идентификатора.
- `supervisor.forgetSession` уже удаляет всю запись пары taskId/stage и сохраняет результат через `saveStages`. Вместе с sessionId исчезает startedAt; API и схема достаточны для решения.
- `evidenceFor` читает startedAt до приёмки. `transferReport` снимает отчёт с очереди после удавшейся записи задачи; ошибки создания заявок и дополнений тоже оставляют отчёт для повтора.

## Goals / Non-Goals

Цель — отделить оконченный отчётом заход от прерванного процесса, включая полный круг audit → design → audit и review → revise → pr → review.

Не меняем счётчики, маршруты, формат отчёта, живость процесса, хранение потерянного вывода, выбор исполнителя и правила промпта. Миграция исторически оставленных сессий по журналу доски и транзакционное восстановление после аварии между отдельными записями не входят в задачу.

## Decisions

### Забывать исходный этап в точке завершения переноса

В обычной ветке `transferReport` вызвать существующий `io.forgetSession?.(action.taskId, action.stage)` после успешного `saveTask`, перед `removeReport`. Исход брать из назначения `action.stage`, поскольку `verdict.status` уже называет следующий этап. Не ограничивать забывание `rejected` или `done`: любой обработанный отчёт завершает заход, включая вопросы, остановку, достигнутый предел возвратов и будущие разрешённые исходы.

В ветке `trust.verdict === 'undermining'` перенести нынешнее раннее забывание исходной сессии в успешное завершение `halt`, перед удалением отчёта. Так обе ветки сохраняют startedAt при ошибке записи, и повтор приёмки не превращает проверяемый след в «сверять нечем». Сведения о доверии всегда вычисляются до забывания. Если перенос не дошёл до успешной записи, новое забывание не выполняется.

Существующее забывание целевого этапа при `rejected && !halted` и прошлого postmortem оставить: оно защищает также от старых записей, созданных до обновления. Не вводить широкую очистку всех этапов задачи. Повторное забывание одной пары допустимо: нынешний метод возвращает false, если запись уже отсутствует.

Альтернативы: забывать только аудит при rejected оставило бы успешный аудит и ревью; забывать при выходе процесса стёрло бы startedAt до приёмки и разрушило продолжения по сроку; заставлять промпт игнорировать память оставило бы ложный continuation. Новый признак completed в схеме избыточен: существующего удаления записи достаточно для штатного цикла.

### Сохранять назначение и постоянное хранение

Логику `assignmentFor`, `stage-prompt.mjs` и формат состояния не менять. Уточнить комментарии `assignmentFor` и `forgetSession`: сохранённый идентификатор относится к ещё не завершённому переносом отчёта заходу. После забывания прежний API сам даёт `continuation: false`, `sessionId: null`; новая дата начала задаётся штатным запуском. Проверить это и через повторное создание супервизора из сохранённых данных.

Альтернатива — анализировать историю карточки при каждом назначении. Она требует новых запросов и не нужна для новых завершений. Старые записи не мигрируем: массовое удаление могло бы лишить памяти действительно прерванные этапы.

### Проверять цепочку поведения, а не только вызов метода

В `execute.test.mjs` обновить противоречащий тест успешного этапа и ожидания возврата. Для полного круга использовать изменяемое хранилище пар taskId/stage: нынешний fakeIo возвращает постоянный `over.lastSession`, а forgetSession только пишет строку в steps; такая заглушка не докажет свежесть назначения. Дать выбранным проверкам совместные lastSession/forgetSession со состоянием либо расширить fakeIo с сохранением прежних сценариев.

Проверить оба круга возврата, done/question/failed, остановку приёмкой и пределом возвратов, независимость чужих пар, чтение startedAt до забывания. Ошибки saveTask и предшествующих записей должны оставлять исходную запись для повтора; успешный повтор её удаляет. Контроль без отчёта по сроку сохраняет sessionId и startedAt. В `supervisor.test.mjs` существующие тесты saveStages/forgetSession использовать как основу для проверки перезапуска: забытая пара отсутствует, незавершённая соседняя сохранилась. Процессы и доску в этих проверках не запускать.

## Risks / Trade-offs

- Удаление startedAt слишком рано меняет результат повторной приёмки → забывание после успешной записи, отдельные проверки обеих веток transferReport.
- Правка только списка вызовов может пропустить исходный дефект → полный круг с реальным изменением тестового хранилища и проверкой назначения с новым журналом.
- Доска и локальный saveStages не являются транзакцией → авария между успешной записью доски и удалением сессии остаётся существующим ограничением. Гарантия перезапуска здесь относится к завершившемуся переносу; новую систему восстановления не заявляем.
- Изменение 0225 правит соседние счётчики → перед реализацией освежить базу и сохранить его независимую логику, если она уже влита.
- Открытые спецификации ещё не архивированы → ADDED с уникальным именем; порядок архивации из proposal. Сценарий `outlive-the-supervisor` «Этап завершился» описывает выход процесса, а наша очистка происходит при более позднем переносе.

Геймплей не затронут: рассинхрон и реконнект игры, эталоны детерминизма, `PROTOCOL_VERSION` остаются прежними. В sim ничего не добавляется, запреты Math.random, Date.now и дробных чисел в состоянии мира соблюдаются без исключений. Арена и замер кадров не нужны.

## Migration Plan

Один атомарный коммит реализации с регрессиями и отметкой tasks; черновой PR открывается после его отправки. Проверки CI ведёт супервизор. Правка начинает действовать после штатной загрузки обновлённого кода супервизора; текущая сессия его не снимает. Формат хранилища совместим, миграции нет. Откат коммита возвращает прежнее поведение, но не восстанавливает удалённые идентификаторы; такие этапы безопасно начнутся заново.
