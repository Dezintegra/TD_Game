## Context

База освежена `git -C . fetch origin` и `git -C . merge origin/main`: Already up to date. В `run-stage.mjs` структурный `api-error` проверяется раньше общей неудачи, стоимость остаётся `null`, когда поле отсутствует. В `supervisor.mjs:finish` API-ответ кладётся в `apiFailures`, а `execute.mjs:noteApiError` возвращает продолжение и снимает запись после успешного `saveTask`. `scan` исключает такую задачу из выдачи. В `bin/supervise.mjs:loop` `judgeApi` смотрит длину этой очереди после `turn`: обработанная очередь теряет сигнал, а закрытие процесса между оборотами не вызывает пробу.

Существующие `shouldProbe`, `judgeProbe`, `pause.api` и `pause` дают расписание и раздельность остановок. `probeApi` выбирает исполнителя по настройке. У Codex нет достоверного значения долларовой стоимости: расход токенов не превращается в доказанный ноль долларов.

## Goals / Non-Goals

Весь повторный implement 0243, включая модель 1.1 и возобновление прежней сессии, удерживается до closed у `0242-dat-otchetu-etapa-adresnoe-poruchenie-na`, links.pr=177 и доказанного MERGED PR 177 в настроенную main. Независимость коммитов описывает их проверяемость после допуска и не разрешает преждевременный запуск. Удерживает существующий шлюз зависимостей; реальную failed-карточку эта проверка в работу не возвращает.

Цели: остановить следующую выдачу при подтверждённой недоступности независимо от границы оборота; закрыть выдачу уже на время пробы; оставить настоящим неудачам их обычную обработку; исключить повторный возврат и потерю сигнала при снятии записи из очереди.

Вне объёма: протокол инструментальных отказов 0244, универсальная долговечная доставка 0233, новые исходы отчётов и схемы карточек, смена способа оплаты продолжений, остановка живых процессов. Игра, реконнект и рассинхрон матча не затрагиваются. `packages/sim` и `packages/protocol` не меняются: эталоны и `PROTOCOL_VERSION` не обновляются, запреты `Math.random`, `Date.now` и float в состоянии мира остаются без изменений. Время в супервизоре — существующий внедряемый источник часов, не время симуляции.

## Decisions

### 1. Общий контроллер выдачи получает завершение один раз

Добавить в тестируемую обвязку `api-health` состояние `open / checking / paused`, счёт новых структурных отказов и длину быстрой серии. `finish` передаёт нормализованное наблюдение: идентификатор запуска, provider, исход, код, длительность от `child.startedMs`, исходную стоимость и число ходов. Идентификатор берётся из существующего `launchId`, который нужно обеспечить для обоих исполнителей; повторная доставка того же завершения не меняет состояние.

Контроллер обновляется синхронно до возврата из `finish`, затем запрашивает одну подтверждающую пробу через внедрённый callback. Обработку следует подключить до очередей и ранних выходов для разных исходов, но после разбора ответа: завершения `done`, `timeout` и `failed` тоже нужны для сброса серии. Ошибка записи лога или расхода не должна разрешать выдачу при уже установленной недоступности.

Длина `apiFailures` больше не источник здоровья. Новый `api-error` прибавляет отдельный счёт после последней пробы; при `pauseAfterApiErrors` (по умолчанию 1) выдача синхронно закрывается. Счёт не теряется на границе оборота и при `forgetApiFailure`. Успешная проба потребляет накопленные сигналы; старые записи, ожидающие возврата, повторной пробы не вызывают. Эта более ранняя проверка сохраняет достаточность порога из `pause-on-api-overload`.

Отвергнуто: только перенести `judgeApi` в начало оборота. Между оборотами и внутри заранее вычисленного списка действий останется окно. Только запрет в `scan` также отвергнут: снимок может устареть после любого `await`.

### 2. Независимая консервативная серия

Настройки: `pauseAfterFastFreeFailures: 3` (целое не меньше 2) и `fastFreeFailureMaxSeconds: 30` (конечное положительное число). Отсутствующие настройки получают эти умолчания; некорректные значения отвергаются при чтении настроек с явной диагностикой. Порог API остаётся отдельным.

В серию входит только завершившийся процесс с исходом `failed` или `api-error`, ненулевым целочисленным кодом, без `run.error` и без `killedBy`, конечной длительностью от 0 до 30 секунд включительно, конечной числовой стоимостью строго 0 и целым числом ходов 0 или 1. Не использовать округлённую цену из консоли и `cost ?? 0`. В `readAnswer` исходная отсутствующая цена остаётся неизвестной. Параметры относятся к текущему заходу, не сумме предыдущих resume.

Серия общая для завершений текущего исполнителя на этой станции, в порядке наблюдения `finish`, не по карточкам и не по оборотам. Любое другое завершение обнуляет её: успех, платная/медленная неудача, отсутствующая или нечисловая цена/длительность/число ходов, таймаут, shutdown. Простой без завершений не меняет серию. Саму пробу в серию не включать. Достижение любого из двух порогов запускает одну и ту же пробу, одновременное достижение обоих не удваивает запрос.

Тридцать секунд покрывают наблюдавшиеся 9–12 секунд с запасом на запуск; три независимых завершения не объявляют одиночную короткую задачу общим сбоем. Отвергнуто угадывание по тексту авторизации и по одному быстрому выходу. Подтверждающая проба ограничивает цену ошибочного срабатывания эвристики.

### 3. Запрет проверяется в месте порождения

Контроллер отдаёт текущий `mayLaunch`. Его проверяют перед началом действий выдачи в `execute` (до захвата новой карточки) и ещё раз синхронно в `supervisor.spawnStage`, непосредственно перед вызовом порождения без `await` между проверкой и порождением. Это покрывает продолжения, новые этапы и ведущую задачу пакетной выкладки, даже если закрытие произошло во время подготовки дерева или сетевой записи.

Возвращать различимый результат `reason: 'availability-held'`, обрабатываемый всеми вызывающими путями как `skipped`, с доказанным отсутствием spawn, без `countSpawnFailure`, `countContinuation`, отказа оборота и запуска разбора. Сохранять только уже подтверждённое валидное назначение/подготовленное дерево; неподтверждённый новый захват освобождается по контракту 0242 из Decisions 6. Финальная проверка гарантирует запрет порождения. Уже родившиеся процессы остаются живыми до собственного завершения/срока.

Отвергнуто использование `busy` без отдельной причины: потеряется объяснение остановки. Отвергнуто массовое снятие процессов: часть сессий может работать и иметь неотправленный коммит.

### 4. Одна проба и существующие две паузы

Вынести координацию из вложенного `judgeApi` в тестируемый контроллер с внедрёнными пробой, часами и операциями файла паузы. Бинарный вход только связывает события завершения и обслуживание расписания. Проба остаётся выбранным исполнителем, дешёвой моделью без контекста проекта и собственного системного промпта; новых обращений к модели в чистой логике нет.

`checking` закрывает выдачу до запуска пробы, в том числе если реализация пробы впоследствии станет асинхронной. Одновременно допускается только одна проба. Ненулевой код, исключение запуска, таймаут или неразбираемый ответ пробы не являются успехом. Успех проверяется структурно и требует нормального завершения процесса. Это также закрывает текущую возможность Claude-пробы принять конверт без `is_error` за успех при ненулевом коде.

Неудача подтверждает остановку: записать существующий `pause.api` с причиной, временем и попыткой, оставив запрет в памяти закрытым даже при ошибке записи. Успех снимает только `pause.api`, очищает потреблённые сигналы и быструю серию. Если снятие файла не удалось, выдача остаётся закрытой. Существующие backoff и повтор последней задержки сохраняются. Позднее завершение ранее запущенной сессии само по себе паузу не снимает. Под взведённой паузой новые завершения не обходят срок очередной пробы.

Восстановление обслуживается и до следующего чтения доски/выдачи, поэтому сохранённый `pause.api` закрывает первый запуск после перезапуска. В режиме dry-run не делать проб и записей. Ручная пауза остаётся независимой. При успешной пробе с открытой паузой человека выдача по-прежнему запрещена. Под `pause.api` доска не читается, как требует существующая дельта; очереди возвратов ждут снятия паузы.

На перезапуске неподтверждённые счётчики в памяти начинают с нуля; сохранённая пауза продолжает действовать. Долговечное хранение каждого завершения не добавляется: это пересекло бы отдельную работу по восстановлению отчётов. Гарантия обработки очереди здесь относится к живущему супервизору и существующим механизмам её доставки.

### 5. Сигнал доступности не является повторным списанием или возвратом

Для структурного `api-error` оставить `note-api-error` единственным владельцем возврата: callback здоровья только закрывает выдачу/запускает пробу, не правит задачу. Очередь снимается только после успешного сохранения, повторное действие без записи ничего не делает. Подтверждающая или успешная проба не снимает очередь и не возвращает продолжение второй раз. Неотправленный возврат исключает эту задачу из продолжений и проверки их исчерпания; это проверяется и при устаревшем списке действий.

Уточнить данные записи API-отказа идентификатором запуска и признаком фактического списания продолжения на него: первый запуск не должен возвращать чужое более раннее продолжение. Применение возврата должно следовать за успешной записью списания в `continueStage`, даже если процесс завершился прежде окончания `saveTask`. Повтор без успешной записи сохраняет очередь; успешная запись и синхронное снятие записи остаются единым обработчиком, без нового обработчика возврата в контроллере здоровья. Пакетная выкладка не получает возврат на каждую карточку: только там, где было соответствующее списание.

Обычный `failed`, даже входящий в подтверждённую быструю серию, сохраняет исход и обычные счётчики при отсутствии независимого confirmed tool hold 0244. Подтверждение API-пробой говорит о доступности сейчас, а не доказывает, что каждая предыдущая ошибка была вызвана этим сбоем. Поэтому возврат по эвристике отвергнут: он скрыл бы настоящие дефекты. Только отдельный инструментальный контроль 0244 может разрешить infrastructure settlement для такого failed. Неизвестная цена не мешает возврату структурного `api-error`, но не допускается в быструю серию. Журнал должен называть фактические код/время/ходы/известность цены; утверждение «ходов не было» при одном ходе убирается из затронутого сообщения.

### 6. Совместимый контракт общих обработчиков с 0244 и 0242

Повторная проработка сверена с актуальной main `48d6c25`, опубликованным design 0244 в `cc27621` и удалённым diff PR 177. Отсутствие соседних каталогов в main не означает отсутствия пересечения. Ниже уточнены общие данные Decisions 1 и 5 и последовательность шлюза Decisions 3.

**Владелец данных запуска.** Единственный supervisor-owned launchId назначается до spawn обоим provider и передаётся в assignment, live descriptor, результат и операцию списания. Контроллер здоровья собственного id не создаёт. Общий факт списания принадлежит жизненному циклу supervisor/execute: `not-required | pending | confirmed`. Initial и replacement имеют not-required; обычное continuation получает pending до spawn, но счёт растёт только после рождения. Доказанный отказ до spawn закрывает pending без списания. Confirmed ставится после подтверждения сохранения операции для этого launchId, не по prompt или общему числу continuations. Неизвестный результат записи остаётся pending и блокирует refund/следующий запуск. Запись списания и возврат сериализуются по задаче: после confirmed берётся свежая карточка; поздний callback не пишет старый счёт поверх компенсации.

Если 0244/0233 уже влиты, использовать их единственную запись запуска, квитанцию операции и восстановление store. Если нет, 0243 вводит этот контракт в существующей памяти запуска/очереди; долговечность и квитанции при перезапуске добавляет 0244 через 0233. При совмещении память расширяется общим store, а не остаётся параллельным источником истины. API-компенсацией владеет только note-api-error; инфраструктурной — только settlement 0244. Один launch не получает обе компенсации. API-ошибка replacement с not-required не возвращает исходную попытку повторно и не воссоздаёт потреблённое инфраструктурное право.

**Порядок finish.** После нормализации синхронно передать наблюдение API-контроллеру до асинхронных сохранений, диагностики и ранних выходов. Затем структурный api-error маршрутизировать в API-очередь раньше инструментальной классификации: infrastructure settlement для него не создаётся. Обычный failed может дать сигнал быстрой серии и независимо перейти в diagnosing/infrastructure-held 0244. Оба факта сохраняются; инструментальная диагностика не задерживает и не повторяет сигнал API. Позднее healthy инструментов не открывает API-запрет, успешная API-проба не снимает infrastructure hold или ручную паузу.

**Последовательность старта поверх 0242.** Общее предусловие действует до всего повторного implement, а перед шагом 3.1 повторно проверяется: PR 177 должен быть влит и подтянут, 0242 закрыта; чужие файлы не копировать. В execute сохранить invalidated-set перед выбором обработчика, затем mayLaunch перед acquire. После acquire обязательны readStartTask и повторный claimTask по свежей карточке. Если чтение не подтвердило владельца, статус или зависимости, сначала исполнить прежний путь 0242: invalidate, release только held.newClaim, явная ошибка при неподтверждённом освобождении. API-пауза не маскирует эту ошибку и не отменяет освобождение неподтверждённого захвата; все остальные действия карточки в том же execute пропускаются. После успешного чтения снова проверить mayLaunch: закрытие до сохранения назначения также инвалидирует действие и освобождает только новый неподтверждённый захват. Ранее принадлежавший станции захват не освобождать. После сохранения валидного назначения/подготовки дерева поздний availability-held оставляет их для нового сканирования. Между финальным mayLaunch в spawnStage и порождением нет await. Восстановление не обходит guards свежести.

**Отложенный replacement 0244.** Общий шлюз проверяется до durable claim и перед spawn. Если API-пауза возникла после сохранения retry-claimed, availability-held доказывает отсутствие spawn: владелец retry store возвращает claim в retry-ready без потребления entitlement, продолжения, spawnFailure или cycleFailure. Подготовленное назначение остаётся. Ошибка записи обратного перехода сохраняет claim и блокировку; после перезапуска 0244 сверяет descriptor/процесс: доказанное отсутствие разрешает retry-ready, неизвестность удерживает, подтверждённое рождение исключает второй spawn. Право потребляется лишь после подтверждённого рождения и устойчивого handoff. API-контроллер не удаляет claim и не создаёт entitlement. После восстановления повтор снова проходит guards владельца, зависимостей, токенов, слотов и эксклюзивности; deploy сохраняет batch/revision и проверку опубликованных эффектов 0244. Повторное закрытие API или занятый слот не уничтожают право.

**Порядок поставки.** 0243 и 0244 могут вливаться в любом порядке: первая вводит общий контракт в своём объёме, вторая расширяет те же точки. Перед 2.1 и 3.1 освежить main и сверить фактически влитые обработчики; использовать существующий launchId, факт списания и шлюз. Если 0244 отсутствует, проверить контракт replacement через внедряемый адаптер, не создавать её store/диагностику. Если присутствует, те же сценарии выполняются с её реальным retry store и recovery. Эти проверки входят в коммит подключения шлюза, а не откладываются до будущего аудита. Отвергнуты второй refund, второй launchId и потребление права при claim: они дают двойной возврат или теряют повтор при отложенном spawn. Простое слияние без сохранения guards 0242 отвергнуто: оно разрешает запуск по устаревшей карточке.

## Risks / Trade-offs

- Независимость модели ошибочно прочитана как ранний допуск → удерживать всю повторную сессию до closed 0242 и MERGED PR 177, включая 1.1; перед 3.1 повторять проверку свежести.

- Ложная быстрая серия → только проба, без переклассификации ошибок или бесплатных повторов.
- Codex не сообщает долларовую цену → эвристика не срабатывает по отсутствующим данным; структурный путь и проба продолжают работать.
- Проба дешёвой модели может пройти при проблеме отдельной модели → сохраняется принятый в `pause-on-api-overload` охват пробы; проверка каждой модели отдельно вне этой задачи.
- Возврат ждёт конца API-паузы → до его применения не допускаются повтор и проверка лимита этой задачи; пауза не расходует новые попытки.
- Сбой записи/перезапуск в окне доставки → не расширять обещания до долговечной exactly-once доставки; будущая работа 0233 должна сохранить тот же единственный обработчик возврата.
- Одновременные изменения общих файлов → соблюдать контракт Decisions 6, интегрировать шлюз после PR 177 и проверять совместимость с 0244 в обоих порядках поставки; независимый store не создавать.

## Migration Plan

До первого действия реализации подтвердить закрытие 0242 и выполнить отдельно `gh pr view 177 --json number,state,mergedAt,baseRefName,mergeCommit`, `git -C <дерево> fetch origin`, `git -C <дерево> merge origin/main` и `git -C <дерево> merge-base --is-ancestor <mergeCommit-PR-177> HEAD`. Ожидаются number=177, MERGED, корректный mergedAt, база main и код 0 проверки предка. SHA берётся из mergeCommit ответа PR, не из головы ветки, чтобы учитывать squash. Проверить наличие обработчика dependencyUpdates и post-claim readStartTask в назначенном дереве. При отсутствии доказательств/результата реализация удерживается с отчётом; конфликт слияния обрабатывается по правилам этапа. Перед 2.1 и 3.1 дальнейшее освежение и сверка совместимости сохраняются. Любой порядок поставки 0243/0244 из Decisions 6 разрешён лишь после этого общего допуска 0243.

Реализация поставляется независимыми проверяемыми коммитами из tasks.md, с черновым PR после первого. Новые поля настройки имеют умолчания, формат `pause.api` совместим с прежним. Обновление супервизора штатное, без ручной правки доски. Откат кода не удаляет существующую паузу: прежняя версия сможет снять её обычной пробой.
