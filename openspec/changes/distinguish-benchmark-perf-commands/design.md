## Context

На свежем main первый тест `scripts/perf-instructions.test.mjs` использует глобальный matchAll по `pnpm e2e:perf`, отбрасывает history и ожидает две строки. В `supervisor/skills/benchmark.md:228` подготовка записана после «Спроси машину:» в inline-коде, а в строках 242–244 замер расположен в powershell-блоке. Пояснение PR 219 в разделе запретов содержит третье упоминание без портов. Исходный Git-объект `1898e4fe4d2243d8c9685fd394005292ebe1ab39:supervisor/skills/benchmark.md` прочитан; `gh pr view 219` подтвердил эту же голову и OPEN.

## Goals / Non-Goals

Цель — проверять исполняемые предписания, сохранив строгую проверку двух вызовов и исходный регрессионный текст. Границы — proposal.md. Исполнение Markdown, общий парсер PowerShell, унификация всех сторожей, изменения deploy и политики разрешений не входят в работу.

## Decisions

### 1. Отделить структурную выборку от проверки аргументов

В том же тестовом файле выделить проверку benchmark, принимающую Markdown строкой; ею пользоваться для живого файла, снимка и всех мутаций. Найти единственный верхнеуровневый пункт с `kind: perf`, ограниченный следующим верхнеуровневым пунктом. Отсутствующая или неоднозначная секция — ошибка. Не привязываться к номерам 5 и 6.

Внутри секции учитывать полные строки вызовов `pnpm e2e:perf` в powershell-ограждениях и существующую форму прямого предписания: inline-команду непосредственно после «Спроси машину:» в нумерованном подпункте вне ограждений. Сохранить порядок и позиции исходного текста. Учитывать все такие предписания, включая повторённые подпункты и несколько строк/блоков; не брать только первый результат. Для ограждений учитывать отступы списков, LF/CRLF и парность открытия/закрытия. Комментарии и строки пояснений внутри блоков не считать вызовами. Блоки `text`, JSON и без языка — неисполняемый материал для этого сторожа; их содержимое не проверять как inline-предписания.

Обычная проза и inline-код без формы прямого предписания не выбираются даже внутри perf-секции и даже если содержат полную правильную команду с портами. Пояснение вне секции тоже не выбирается. Исторический пример считывается без предварительной правки разметки. Ошибочные порты, режимы, аргументы и дубли MUST оставаться в выборке до валидации: нельзя отбирать по наличию правильных флагов или устранять повторы множеством.

Альтернативы: поиск по всему Markdown воспроизводит дефект; только fenced-блоки теряют подготовку; перенос подготовки в блок требует правки исходного текста и не решает приёмку неизменённого снимка; фильтр «есть два порта» маскирует потерю ключа; общий AST-парсер с зависимостью избыточен для двух документированных форм. Узкий структурный контракт намеренно делает изменение формы предписания видимой ошибкой сторожа.

### 2. Проверять каждый вызов, а затем пару

Ровно два выбранных вызова: подготовка, затем замер. Полные аргументы передать существующему `parsePerfOptions`. Для каждого проверить собственные явные `clientPort` и `serverPort`, отсутствие неизвестного хвоста, history и force; checkOnly равен true только у первого. Сравнить пары портов; числа 5199/3055 не зашивать как единственно правильные. Согласованная замена на 5209/3065 должна проходить. Существующий запрет подстановки окружения и проверку powershell-формы замера сохранить, заменив хрупкое сравнение фиксированного отступа структурным условием. Составные команды не принимать.

### 3. Регрессия хранит первоисточник

На implement сохранить полный Git blob указанного SHA в `scripts/fixtures/benchmark-pr-219-1898e4f.txt` без вырезания разделов и редактирования пояснения. Расширение txt защищает исторический Markdown от автоформатирования. Рядом source.json содержит repository, pr=219, commit, path и blobOid, сверенные с Git; чтение через git show само по себе не должно добавить BOM или превратить LF в CRLF. Проверять идентичность содержимого Git blob; идентификатор можно получить `git -C <дерево> rev-parse 1898e4fe4d2243d8c9685fd394005292ebe1ab39:supervisor/skills/benchmark.md`. Снимок самодостаточен для CI без сети и без доступа к историческому объекту.

Контроль старого алгоритма на снимке фиксирует 3 результата после исключения history, новый сторож принимает 2. Старый алгоритм остаётся только в узком тесте воспроизведения, не служит реализацией новой выборки. Положительные контроли добавляют отдельно прозу, inline-код, text/JSON/безъязыкий блок с полными командами, включая вставки внутри perf-секции; также проверяют оба перевода строк и согласованную смену портов.

Отрицательные контроли удаляют и дублируют каждый вызов; удаляют каждый порт в каждом вызове; меняют каждый порт только в одном вызове; убирают check-only у подготовки и добавляют его замеру. Дополнительно проверить обе команды без портов, оба режима одинаковыми и дубли в одном блоке. Поясняющие полные команды остаются рядом в отрицательных контролях: ими нельзя восполнить пропавший запуск. Мутация обязана подтвердить, что меняет ожидаемую строку/позицию, иначе тест может оказаться пустым. Всё выполняется над строками в памяти, без запуска замеров и сетевых проб.

## Risks / Trade-offs

- Привязка legacy inline к «Спроси машину:» → явно описанная поддерживаемая форма и тест на исчезновение/дублирование; перефразирование требует согласованного обновления сторожа.
- Слишком широкий разбор ограждений → контроли с неисполняемым блоком, содержащим целое предписание и текст powershell-ограждения, и проверка парности.
- Совместный файл с deploy → дифф и узкий тест должны сохранить все проверки deploy без ослабления.
- Старый зелёный CI не доказывает применение → проверка актуальной головы и её совпадения с ответом review-ci при передаче задачи 0052.

Симуляция, реконнект, rollback и формат протокола не затрагиваются. Эталоны детерминизма и PROTOCOL_VERSION не меняются; запреты Math.random, Date.now и дробного состояния мира остаются в силе, код в ядро не добавляется.

## Migration Plan

Один атомарный коммит реализации содержит новый сторож, снимок, происхождение и все контроли; сразу после отправки implement открывает собственный draft PR. CI наблюдает супервизор, review вливает исправление в main штатным маршрутом. Откат — отмена коммита исправления через обычный PR, исторический дефект при этом вернётся.

Доставка в main и приёмка PR 219 — последующие действия конвейера, не пункты реализации до собственного вливания. В отчёте implement и описании PR передать сессии review это условие и связь с 0052. После вливания 0309 зависимость 0052 снимается штатно; назначенная сессия 0052 освежает свою ветку из origin/main, сохраняет пояснение и отправляет её. Сессия 0309 не пишет в чужое дерево. Супервизор наблюдает CI PR 219, затем назначенная сессия проверяет `gh pr view 219 --json headRefOid` и `node supervisor/bin/review-ci.mjs --pr 219 --head <актуальный-sha>`. Нужны код 0, state success, expectedHead = observedHead = актуальная голова и свидетельство наличия исправления в ней. Если голова сменилась, старый ответ недействителен. Результат записывается в отчёт/журнал связанной задачи; успех design или локального теста не объявляется этим подтверждением. Новая задача и обратная зависимость не нужны.
