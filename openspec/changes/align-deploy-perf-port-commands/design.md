## Context

Актуальный файл — `supervisor/skills/deploy.md`, а не снятый путь plugins/pipeline из постановки. Шаг 8 содержит четыре `$env:` и два вызова perf без портовых ключей. `scripts/perf-options.mjs` уже предоставляет `parsePerfOptions` и `resolvePerfPorts`: ключи перекрывают окружение, адреса клиента и компьютера вычисляются из выбранного серверного порта, порт метрик по умолчанию равен серверному плюс один.

`scripts/perf-instructions.test.mjs` сейчас проверяет только benchmark.md. Его регулярное выражение ищет также текст вне исполняемых блоков; перенос такой выборки на deploy.md посчитает поясняющие упоминания команды дополнительными запусками.

## Goals / Non-Goals

**Goals:** проверять те порты, с которыми затем запускается замер; обе команды самодостаточны при отдельных вызовах оболочки; регрессионная проверка обнаруживает потерю любого ключа и расхождение пары.

**Non-Goals:** новый механизм запуска, переназначение портов метрик, автоматический подбор портов, изменение правил занятости, игровой код и расширение разрешений. Полный перечень границ — в proposal.md.

## Decisions

### Два самостоятельных вызова с одной парой

В шаге 8 убрать четыре присваивания, а команды записать отдельными исполняемыми блоками powershell:

```powershell
pnpm e2e:perf -- --client-port 5199 --port 3055 --check-only
```

```powershell
pnpm e2e:perf -- --client-port 5199 --port 3055
```

Историю оставить самостоятельной командой `pnpm e2e:perf -- --history`. Пояснить согласованную замену двух чисел в обеих командах. Четыре переменные больше не устанавливаются исполнителем: обёртка формирует окружение служб сама. Пояснение проверки должно учитывать и порт метрик: проверяются клиентский, серверный и метрик; при отсутствии COMPUTER_METRICS_PORT в унаследованном окружении пример означает 5199, 3055 и 3056. Не предписывать отдельного присваивания для метрик.

Сохранить остальной порядок шага, порог CPU 35 %, замок, ожидания, чтение журнала и различение просадки FPS и несостоявшегося замера. `--check-only` не резервирует порты до следующей команды; обычный запуск повторяет проверку доступности по существующему контракту.

Альтернативы: четыре отдельных `$env:` не передают состояние следующему вызову; склейка присваиваний с pnpm нарушает правила команд; новая обёртка дублирует доставленные ключи. Исправление только одного вызова оставляет разные порты у проверки и запуска. Поэтому оба вызова и их проверка меняются одним коммитом.

### Проверять исполняемые команды, а не снимок документа

Расширить существующий `scripts/perf-instructions.test.mjs`, сохранив покрытие benchmark.md. Для deploy.md извлекать команды perf только из ограждённых исполняемых блоков powershell; не считать упоминания в прозе, inline-вставках, запретах и JSON-примере отчёта. В блоках замера каждая команда должна быть одной физической строкой, начинаться с pnpm и не содержать подготовки окружения или склейки команд.

Ожидаются три исполняемых вызова: check-only, замер и history. Разобрать аргументы через уже существующий `parsePerfOptions`; у первых двух проверить наличие обоих портовых ключей, значения примера 5199/3055, равенство пар, режимы checkOnly=true/false, history=false, force=false и пустой passthrough. У истории — history=true, остальные режимы false, пустые ports и passthrough. Отдельно исключить присваивания всех четырёх переменных в исполняемых блоках шага 8: одна проверка `PORT=` не ловит `$env:PORT = ...`.

Проверку выборки сделать проверяемой на строках в памяти в том же файле теста: реальная инструкция принимается; удаление каждого из двух ключей из любого вызова, замена порта только у одного вызова, возвращение присваивания и склейка с командой отвергаются. Дополнительное упоминание pnpm в прозе не меняет выборку. Контроль не должен проходить лишь из-за нулевого числа извлечённых команд. Новых файлов помощников и дублирования парсера не требуется.

Для проверки применимости портов достаточно разбора команд и существующих тестов 0077, проверяющих передачу конфигурации службам. Браузер, SSH, открытие портов и настоящий замер в тесте не нужны. Альтернатива — снимок всего Markdown — ловит несвязанные редакторские изменения и плохо объясняет расхождение; запуск реального perf слишком дорог и проверяет машину вместо текста инструкции.

### Граница спецификации

ADDED в существующей performance-metrics закрепляет обязанность deploy.md. MODIFIED требования из accept-perf-port-flags недопустим: его ещё нет в основной спецификации, а его нормативные потребители — другой скилл и сценарий. Архивация после accept-perf-port-flags сохраняет порядок описания интерфейса и потребителя.

## Risks / Trade-offs

- [Соседние изменения deploy.md] → править только команды и связанное пояснение шага 8, освежить базу перед реализацией.
- [Ложный зелёный тест при неверном извлечении] → точное число исполняемых вызовов, проверка режимов и отрицательные контроли в памяти.
- [Порты заняты между проверкой и запуском] → сохранить повторную проверку самого perf; готовность не обещает резервирование.
- [Порт метрик переопределён окружением] → явно сохранить существующее правило COMPUTER_METRICS_PORT; новая инструкция задаёт только два поддерживаемых ключа.

## Migration Plan

Один коммит реализации исправляет скилл, его тест и отмечает собственную задачу. После отправки открывается черновой PR. Изменений данных и развёртывания игры нет; маршрут после вливания определяет супервизор по полному diff. Откат атомарного коммита возвращает прежнюю инструкцию вместе с прежним покрытием. Архивация — отдельно, после accept-perf-port-flags.

## Архитектурные ограничения

Симуляция, сетевой протокол и игровой цикл не затрагиваются. Рассинхрон и реконнект остаются прежними; обновления эталонов детерминизма и PROTOCOL_VERSION не требуются. Запреты Math.random, Date.now и дробных значений в состоянии мира сохраняются: правка не добавляет кода ядра.
