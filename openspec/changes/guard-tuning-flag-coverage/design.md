## Context

На базе `e98868e4` интерфейс `RuleTuning` и обязательный объект `NEUTRAL: RuleTuning` находятся в `packages/shared/src/rules.ts`; `ruleTuning()` возвращает копию полного нейтрального набора в новом модуле. Поля: income, speed, towerHealth, baseHealth, unitRadius, map. `TUNING_FLAGS` в `apps/arena/src/main.ts` задаёт направление CLI → поле. `FLAG_OF` в `scripts/experiment/tempo-factorial.mjs` задаёт фактор → CLI с `--`.

`main.ts` безусловно вызывает `main()`, импортирует исполнение матча и SQLite через ingest. `tempo-factorial.mjs` после 0099 уже защищён проверкой прямого запуска; SQLite загружается внутри main. Его существующий тест проверяет точный список трёх экспортов.

В scripts есть отдельный Vitest-корень с маской `**/*.test.mjs`. CI запускает этот набор до сборки внутренних пакетов. Поэтому тест не должен требовать `dist` арены или `@td/shared`, разрешаемого в собранный пакет.

## Goals / Non-Goals

Цель — быстрый автоматический сигнал при потере покрытия любого поля в любой из двух таблиц, включая будущие множители. Таблицы остаются самостоятельными, но получают общий проверяемый контракт полноты. Границы и исключения перечислены в proposal; геймплей и матрица эксперимента не меняются.

## Decisions

### 1. Отдельный модуль данных арены

Перенести существующую таблицу с её комментарием и аннотацией `Readonly<Record<string, keyof RuleTuning>>` в `apps/arena/src/tuning-flags.ts`, экспортировать `TUNING_FLAGS`. Единственный импорт модуля — `import type` для `RuleTuning`; исполняемых зависимостей нет. `main.ts` импортирует таблицу через `./tuning-flags.js` и продолжает использовать её в `tuningOf` и `tuningArgs`; собственного второго литерала не остаётся. Тип `RuleTuning` в main всё ещё нужен сигнатурам функций.

Это даёт безопасный экспорт без изменения способа прямого запуска арены или дочерних run-one. Альтернатива — экспортировать прямо из main и защищать его запуск: потребовала бы проверок границы исполнения и зависимостей SQLite ради одной таблицы. Вынос всего CLI или перенос таблицы в shared расширил бы область и занёс знание об аргументах приложения в изоморфную библиотеку. Тест не импортирует main; публичная точка данных — новый модуль.

В `tempo-factorial.mjs` добавить только экспорт к существующему `FLAG_OF`, сохранив порядок, записи и защиту запуска. Обновить точное ожидание экспортов в `tempo-factorial.test.mjs`: FACTORS, FLAG_OF, cells, shardOf. Старые вычислительные и CLI-проверки остаются.

### 2. Независимый источник ожидаемых полей

Новый `scripts/experiment/tuning-flags.test.mjs` импортирует исходные `../../packages/shared/src/rules.ts` и `../../apps/arena/src/tuning-flags.ts` относительно своего файла, а также `./tempo-factorial.mjs`. Vitest преобразует TS; runtime-импорта собранных пакетов здесь нет. Никаких новых alias, конфигураций или зависимостей.

Состав полей берётся из `Object.keys(ruleTuning())` после сброса в нейтральное состояние; после тестов состояние восстанавливается. Проверяется непустота ожидаемого состава. `NEUTRAL: RuleTuning` уже требует все обязательные поля интерфейса: добавление поля без нейтрального значения остановит проверка типов; с нейтральным значением, но без записи в таблице, остановит новый тест. Типовые ошибки не замещаются приведением `as RuleTuning`, `Partial` или отключением проверки типов. Тест читает актуальный исходник, поэтому старый dist не скроет новое поле.

Альтернатива — вручную выписать поля или сравнить только две таблицы: обе могут одновременно забыть новое поле и дать зелёный результат. Regex по интерфейсу зависел бы от форматирования; TypeScript AST добавлял бы лишний разбор там, где уже есть полный типизированный runtime-объект. Оговорка: если будущая задача сделает поля необязательными или добавит наследование с иной моделью нейтральных значений, ей придётся сохранить полноту этого источника либо пересмотреть способ извлечения; это не повод менять текущую модель правил сейчас.

### 3. Сравнение через общие CLI-ключи

Локальный помощник в файле теста принимает ожидаемые поля и обе таблицы, возвращает диагностические различия. Он используется и для рабочих объектов, и для отрицательных контролей:

1. Сравнивает множества ожидаемых полей и значений `TUNING_FLAGS` в обе стороны.
2. Преобразует ключи `TUNING_FLAGS` добавлением ровно `--` и сравнивает полученное множество со значениями `FLAG_OF` в обе стороны.
3. Выводит отсортированные отсутствующие/лишние имена с названием таблицы; основной тест требует пустой список нарушений.

Проверка не сравнивает количество записей вместо содержимого и не сравнивает имена факторов с полями. В частности, `baseHp` поддерживается, хотя его нет в `FACTORS`. `FACTORS` — выбранная матрица эксперимента, а не реестр всех допустимых множителей. Политику дополнительных псевдонимов полей этот сторож не вводит: сравниваются множества покрытия.

Дополнительно для каждого ключа действующего `FLAG_OF` проверить точную развёртку `cells({ [factor]: [1, 2] })` в две именованные ячейки. Так экспорт рабочей таблицы проверяется вместе с её потреблением без запуска эксперимента. Сохранить явные существующие цепочки towerHealth/towerHp, baseHealth/baseHp, unitRadius/radius как проверки совместимости имён, не превращая их в полный ожидаемый реестр.

### 4. Чувствительность и безопасность

Отрицательные контроли используют копии входов и тот же помощник: удалить запись из TUNING_FLAGS; отдельно удалить запись из FLAG_OF; добавить синтетическое новое поле к ожидаемому составу, оставив обе таблицы прежними; заменить значение FLAG_OF на неизвестный ключ, сохранив число записей; подставить неизвестное поле в TUNING_FLAGS. Для каждой порчи проверить конкретные имена и сторону расхождения. Не мутировать экспортированные рабочие объекты.

До динамического импорта установить подмены внешних эффектов факторного инструмента: child_process, используемые операции записи/удаления/создания fs и SQLite, перехват stdout/stderr. Сбрасывать кеш модулей и восстанавливать argv/spy; проверить чужие аргументы и отсутствие argv[1]. Сохранить независимость положительной проверки реальных таблиц от подмен: сами RuleTuning, TUNING_FLAGS и FLAG_OF не мокать. Подмены должны остановить настоящий запуск даже при возврате регрессии импорта. Использовать существующий подход `tempo-factorial.test.mjs`; не запускать арену для доказательства отсутствия запуска.

### 5. Границы архитектуры и совместимость

Перекрёстный тест находится в scripts, не в packages/shared: библиотека не импортирует приложение. В sim нет правок, `Math.random`, `Date.now` и float-состояние мира не добавляются. Эталоны детерминизма не обновляются, поскольку правила не меняются. Байтовая раскладка протокола не меняется, увеличивать `PROTOCOL_VERSION` не требуется. Рассинхрон, реконнект и клиентское предсказание сохраняют прежнее поведение: правка вне исполнения сетевого матча.

## Risks / Trade-offs

- Проба через dist проверит старые поля → импортировать конкретные TS-исходники назначенного дерева и чистый модуль данных.
- Тест зелёный на согласованно неполных таблицах → независимый ruleTuning, типизированный NEUTRAL и контроль нового поля.
- Перенос таблицы потеряет запись, добавленную 0012 → при обновлении базы переносить актуальный полный объект, не восстанавливать шесть записей из этого документа. Не добавлять killBounty до появления игровой реализации.
- Экспорт расширяет API tempo-factorial → согласовать точное ожидание экспортов, сохранить все существующие CLI-тесты и неприкосновенность FACTORS.
- Проверка полноты сама по себе не доказывает семантику каждого нового множителя → игровые проверки и тесты передачи конкретных значений остаются ответственностью добавляющей его задачи.

## Migration Plan

Один атомарный коммит реализации до двух часов: экспортируемые данные, подключение к CLI, сторож и согласование существующего теста. После отправки открывается черновой PR. Миграций данных нет. Откат этого коммита возвращает исходное расположение таблицы и прежний набор экспортов вместе с удалением сторожа.
