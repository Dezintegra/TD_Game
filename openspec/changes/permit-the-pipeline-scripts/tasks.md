# Задачи

Каждый шаг — отдельный коммит, собирающийся и проверяемый сам по себе.
Прогон сторожей везде один и тот же:

```
npx vitest run --root supervisor config/transitions.test.mjs
```

Ключ `--root supervisor` обязателен: без него тесты конвейера не находятся
вовсе, и прогон зеленеет, ничего не прогнав.

## 1. Открыть перечень сценариев и набор тестов конвейера

- [x] В `supervisor/config/stage-settings.json`, в перечень `allow`, добавить
      четыре правила: `Bash(pnpm run)`, `PowerShell(pnpm run)`,
      `Bash(pnpm test:pipeline:*)`, `PowerShell(pnpm test:pipeline:*)`.
      Первые два — **точной формой, без хвоста `:*`**.
- [x] Дописать в `$pnpmNote` того же файла, почему открыт голый `pnpm run`,
      а не `pnpm run:*`, и назвать закрытые им сценарии поимённо.
- [x] Открыть черновой pull request сразу после этого коммита: до его
      появления пуши в ветку не запускают проверок CI вовсе.

**Проверка:** `node --check` к JSON неприменим, поэтому — прогон сторожей
выше (файл читается тестом `правила разрешений не пишутся в форме, которая
молча не работает`, и испорченный JSON уронит его на разборе).
Дополнительно: `npx prettier --check supervisor/config/stage-settings.json`.

## 2. Открыть безопасный осмотр инструмента

- [ ] Добавить в `allow` четыре правила точной формой:
      `Bash(node supervisor/bin/launch.mjs --help)`,
      `PowerShell(node supervisor/bin/launch.mjs --help)`,
      `Bash(node supervisor/bin/board-setup.mjs)`,
      `PowerShell(node supervisor/bin/board-setup.mjs)`.
- [ ] Завести в файле `$binNote` — почему открыты два сценария поимённо,
      а не `node supervisor/bin/*`, и что именно открыла бы широкая форма.

**Проверка:** прогон сторожей. Плюс живая проба самой команды:
`node supervisor/bin/launch.mjs --help` обязана напечатать перечень ключей
и завершиться с кодом 0 (её разрешает не новый файл, а уже стоящее правило
на `node` в этом дереве — если откажут, отметить это в отчёте и не считать
шаг проваленным).

## 3. Закрыть подъём и снятие супервизора поимённо

- [ ] Добавить в `deny` (обе оболочки):
      `node supervisor/bin/supervise.mjs:*`,
      `node supervisor/bin/launch.mjs --stop:*`,
      `node supervisor/bin/launch.mjs * --stop:*`,
      `node supervisor/bin/launch.mjs --shadow:*`,
      `node supervisor/bin/launch.mjs --dry-run:*`,
      `node supervisor/bin/board-setup.mjs --execute:*`,
      `node supervisor/bin/backlog-migrate.mjs:*`.
- [ ] Дописать в `$denyNote`, почему `--stop` опаснее подъёма: пускатель
      снимает поддерево, а этап — потомок супервизора, то есть снимает себя.
- [ ] Убедиться глазами и словами в теле коммита, что **ни один** новый
      запрет не является приставкой ни одного разрешения (грабли `$cleanupNote`:
      запрет, перекрывший своё же разрешение, отнял у этапа отчёт).

**Проверка:** прогон сторожей.

## 4. Завести сторожа на обе границы

- [ ] В `supervisor/config/transitions.test.mjs` добавить тест: в перечнях
      `allow` и `deny` нет правила, совпадающего с `pnpm run` плюс хвост `:*`
      (то есть широкой формы), при этом точная форма `pnpm run` присутствует
      в обеих оболочках.
- [ ] Тем же тестом или соседним: для каждой из форм `supervise.mjs`,
      `launch.mjs --stop`, `launch.mjs --shadow` в `deny` есть правило
      и в `Bash`, и в `PowerShell`.
- [ ] Комментарием в тесте объяснить, зачем он: расширение правила до широкой
      формы стоит одного символа и замечено будет не раньше, чем этап
      что-нибудь выложит.

**Проверка:** прогон сторожей — новый тест зелёный. И проба на порчу:
временно вписать в `allow` строку `Bash(pnpm run:*)`, убедиться, что тест
краснеет и называет виновное правило, вернуть файл как было. Проверка,
пережившая выключение своей особенности, декоративна.

## 5. Назвать открытые команды в правилах этапов

- [ ] В `supervisor/skills/implement.md` и `supervisor/skills/revise.md`,
      рядом с уже стоящим `npx vitest run <свой файл теста>`, добавить строку:
      правка в `supervisor/` проверяется `pnpm test:pipeline`, потому что
      её сторожа лежат в чужих файлах и узким прогоном по своему файлу
      не ловятся.
- [ ] Больше в скиллах не трогать ничего: перечень отказов, порядок отчёта
      и правила коммита к этой задаче отношения не имеют.

**Проверка:** `npx prettier --check supervisor/skills/implement.md supervisor/skills/revise.md`
плюс прогон сторожей — `transitions.test.mjs` читает тексты скиллов
и упадёт, если правка испортит проверяемую им форму.

## 6. Убедиться делом, что отказов больше нет

- [ ] После вливания дождаться первого этапа, звавшего `pnpm test:pipeline`
      или `pnpm run`, и посмотреть его лог в `.pipeline/logs/<id>-<этап>.log`:
      в перечне отказанных действий этих команд быть не должно.

**Проверка:** наблюдаемый результат — пустой перечень отказов по этим
командам в логе этапа. Шаг исполняется **после** вливания, потому что
правила вступают в силу для следующего запуска этапа, а не для текущего;
если к концу изменения такого этапа ещё не случилось, шаг переносится
заметкой в бэклог заявкой в `requests`, а не отмечается сделанным.
