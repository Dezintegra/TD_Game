## Context

База освежена `git -C . fetch origin` и `git -C . merge origin/main`: Already up to date, HEAD `c3d7700`. В `supervisor/lib/io.mjs:540–554` уже реализован вызов `confirmContradictoryCi`; алгоритм в `ci-confirmation.mjs` проверяет идентичность, jobs актуальной попытки, страницы, список runs и повторную сверку. `review.md:70–89` использует отдельную мерку gh pr checks. Поле конфликта и локальная проверка merge-tree остаются независимыми предохранителями.

`createIo` при создании только формирует функции; вызов `readExternal` для CI не требует доски или файлов runtime. `createCommandRunner` уже исполняет gh через execFileSync с windowsHide и поддержкой timeout. `STAGE_COMMANDS.review` пока содержит только три команды gh; `uncoveredForStage` проверяет Bash и PowerShell. Новая команда не покрыта действующим allow по имени и требует адресного разрешения. Тесты `io.test.mjs` и fixture `testing/ci-pr-219.json` уже дают воспроизводимый пример; список runs и повторные ответы в тестах моделируются, это не живой снимок.

## Goals / Non-Goals

Цель — единый проверяемый результат CI у супервизора и review с привязкой к рассматриваемому коммиту. Границы и пересечения названы в proposal. Алгоритм 0297 и его исходы не переписываются.

## Decisions

### 1. Тонкий вход к существующему переходнику

Добавить `supervisor/bin/review-ci.mjs` и тестируемый модуль `supervisor/lib/review-ci.mjs`. Форма вызова из назначенного дерева: `node supervisor/bin/review-ci.mjs --pr <pr> --head <sha>`. PR — положительное безопасное целое, SHA — полный 40-значный hex. Неизвестные, повторные и отсутствующие доводы отклоняются до чтения GitHub. CLI использует `createCommandRunner(process.cwd())`, модуль — `createIo` с `resolveConfig({}).config` и переданным run; вызывается только `readExternal({links:{pr}}, 'ci')`.

Обёртка run наблюдает ответы gh pr view и проверяет открытость, номер, URL и ожидаемый head при каждом чтении. Несовпадение закрывает success, но выявленный CONFLICTING остаётся conflict. Номер и URL должны согласоваться с запрошенным PR в текущем репозитории gh; дальнейшие связи run/job проверяет существующее подтверждение. Обёртка не нормализует статусы и не вычисляет успех workflow. Ошибки и некорректные ответы не выбрасывают процесс без диагностируемого результата. Существующий `readExternal` остаётся единственным источником состояния CI, а дополнительный guard связывает его с кодом, который проверяет review.

Отвергнуты копия алгоритма в CLI (два расходящихся решения), прямой вызов одного confirmContradictoryCi (обошёл бы обычный маршрут и исходный guard конфликта), доверие переходу супервизора в review (его наблюдение уже устарело), скрипт node -e или разовая самоделка в .matchlog (нет стабильного разрешённого контракта).

### 2. Результат и границы чтения

Stdout — один JSON: `state`, `pr`, `url`, `expectedHead`, `observedHead`, `why`/`failed`, `mode` (ordinary или confirmed), `runs` (проверенные run ID, attempt, head для успешного confirmed). При отсутствии наблюдаемых данных — null/пустой массив, без выдуманных значений. Сведения берутся из ответов текущего вызова; неполные данные при неуспехе не называются подтверждёнными. `mode: confirmed` выставляется только при фактическом использовании общего fallback с success. Коды: 0 success, 1 failure, 2 pending, 3 conflict, 64 ошибочные аргументы. Неожиданная внутренняя ошибка даёт ненулевой код и явную причину, никогда success.

Команда не принимает путь к старому отчёту, fixture, произвольному endpoint или программе. В боевом пути только чтения gh pr view и gh api, уже используемые readExternal. Подставляемый run предназначен для модульных тестов, не является CLI-опцией. Каждое чтение ограничено 15 секундами, включая первое pr view, где общий переходник пока не задаёт timeout. Бюджет fallback 30 обращений сохраняется; вместе с первым чтением не более 31 запроса на вызов. Никаких циклов ожидания, постоянного кеша, записи отчёта или запуска супервизора.

### 3. Порядок review и свежесть решения

В шаге 3 review получить SHA через `git -C <дерево> rev-parse HEAD` и передать его команде. Успех разрешает шаг 4 (проверку конфликта), затем чтение diff. Старую фразу «переходи к шагу 5» заменить: она пропускала обязательный guard. FAILURE сопровождается доступной диагностикой упавшей проверки; pending/conflict возвращают rejected с причиной. Отказ выполнения команды или непригодный вывод — failed по действующему контракту, без допуска. gh pr checks может служить вспомогательным чтением, но не второй меркой, отменяющей подтверждение.

Непосредственно перед действиями шага 8 снова выполнить команду для того же SHA и убедиться, что локальный HEAD не изменился. Изменился локальный HEAD — rejected и новое ревью, а не подстановка нового SHA в старый вердикт. Новый success не отменяет замечания или конфликт merge-tree. Только затем прежние gh pr ready и gh pr merge. Команде слияния передать `--match-head-commit <sha>` для защиты от смены вершины между чтением и вливанием, сохранив установленный способ слияния. Это не отключает серверные проверки GitHub. Указания «один раз» и ссылку на шаг 3 в оговорке старых tasks согласовать с двумя ограниченными проверками, не разрешая watch.

Повторная проверка после чтения diff нужна потому, что ревью занимает время и на том же SHA может начаться новая попытка. Полной атомарности между API Actions и merge нет: повторная сверка алгоритма и новый вызов сужают окно, match-head защищает именно SHA, но не фиксирует попытку workflow. Расширять контракт GitHub или вводить собственный кеш разрешений задача не пытается.

### 4. Разрешения и проверяемость

Добавить адресные `PowerShell(node supervisor/bin/review-ci.mjs:*)` и `Bash(node supervisor/bin/review-ci.mjs:*)`, поскольку существующая мерка SHELLS пока требует обе оболочки. Не менять SHELLS в этой задаче. Добавить фактическую форму вызова с тестовым PR и SHA в STAGE_COMMANDS.review, а также форму merge с match-head. Существующее gh pr:* покрывает вторую. Согласовать комментарии о выборке review, которые сейчас предполагают только gh. Проверить удаление allow отдельно для каждой оболочки, deny, точное правило без аргументов и отсутствие строки из инструкции. Существующие запреты supervise/launch сохраняются.

В `review-ci.test.mjs` прогнать исходную fixture через настоящий модуль review с подставляемым транспортом, не подменяя readExternal на success. Доказать отличие: summarisePullRequest исходного снимка даёт pending, вход review даёт success. Повторить с согласованно изменёнными PR/run/job ID: номер 219 не является условием. Проверить отрицательные случаи дельты, включая отказ каждого чтения, SHA, попытку, новый run, неполные страницы, дубли, чужие связи, конфликт и UNKNOWN на обоих чтениях. При мутации результата между двумя вызовами прежний success не сохраняется. Отдельно проверить JSON/exit code CLI, неверные аргументы без сетевых вызовов и отсутствие мутирующих команд. Доступность и текст инструкции проверяются отдельным `review-ci-contract.test.mjs` с положительным примером и мутациями.

Живое состояние PR 219 может измениться: детерминированная регрессия исходного противоречия обязательна и не заменяется случайным текущим success. Проверка CLI использует подставляемый транспорт в тестах, включая контракт запуска процесса и сериализации; это автоматическая регрессия, не свидетельство живого состояния GitHub. Изменять чужой PR или перезапускать CI ради прежнего противоречия нельзя. Первый штатный review после доставки выполняет реальный вызов по своему текущему назначению; отдельный обязательный прогон чужой карточки в tasks не включается.

## Risks / Trade-offs

- GitHub не даёт согласованного снимка → сохраняются консервативный pending, полнота и повторная сверка 0297; возможна задержка, ложный успех не разрешается.
- Новая оболочка вокруг io может исказить исход → интеграционная fixture и контроли проходят именно через вход review, старые io-тесты остаются регрессией общего поведения.
- Статическое покрытие не доказывает всю среду → дополнить его проверкой входа CLI и транспорта, не объявлять это живой приёмкой GitHub; реальный review явно диагностирует любой отказ запуска.
- Старое дерево задачи может не содержать новой команды → review завершается с явной причиной недоступности; не копирует случайный скрипт и не ослабляет допуск. Обновление дерева делает штатный revise, которому разрешено слияние свежей базы.

Игровые пакеты не затронуты: рассинхрон, реконнект, golden-эталоны и PROTOCOL_VERSION не меняются. Math.random, Date.now и дробные числа в состояние мира не добавляются.

## Migration Plan

Сначала единым атомарным коммитом добавить работающий вход с регрессией, разрешениями и инструкцией, затем закрепить расширенные контроли отдельным проверяемым коммитом. После первого коммита implement открывает draft PR. Настройку этап получает из основного дерева после штатного вливания; проверки реализации используют уже разрешённый npx vitest. Миграции карточек и реестра нет. Откат первого коммита возвращает прежний консервативный отказ review, без сохранённого разрешения на диске.

## Open Questions

Продуктовых вопросов нет. На implement проверяются сценарии и транспорт; актуальное внешнее состояние заново проверяет каждый штатный review. На design подтверждены код и постановка, живой успех не заявляется. Наличие `--match-head-commit` проверено локальным `gh pr merge --help`.
