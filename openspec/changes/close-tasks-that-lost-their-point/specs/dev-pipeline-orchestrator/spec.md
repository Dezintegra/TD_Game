## ADDED Requirements

### Requirement: Уборка задачи без pull request решается содержимым ветки

Требование **уточняет «Уборка после успешного завершения»** (изменение
`agent-backlog-pipeline`, способность `dev-pipeline-orchestrator`) и второй
мерки влитости не заводит. Там сказано: «Влитость SHALL подтверждаться
состоянием pull request по свежим данным», а сценарий «Ветка не влита» велит
переводить задачу в `failed`. Написано это в предположении, что pull request
у задачи есть, — верном для всякой задачи, дошедшей до уборки концом маршрута.

У задачи, закрываемой по снятому предмету, pull request не заводился вовсе:
она уходит в уборку прямо из проработки, и спрашивать нечего. Здесь названо,
чем мерить именно этот случай.

Уборка за задачей, у которой pull request не заводился, SHALL решаться
по содержимому её ветки, а не по одному лишь отсутствию ссылки. Если ветка
не содержит ни одного собственного коммита сверх главной — не считая слияний
главной ветки в неё, — уборка SHALL быть разрешена: терять нечего.

Если собственный коммит в ветке есть, уборка SHALL останавливать задачу,
как и прежде: в дереве лежит несделанная работа, и удалять её молча нельзя.

Там, где pull request заведён, подтверждение влитости SHALL действовать
во всей полноте: содержимое ветки его MUST NOT заменять и MUST NOT ослаблять.
Мерки две, и границу между ними задаёт наличие pull request, а не удобство
случая.

#### Scenario: Закрытая по снятому предмету задача убирается

- **WHEN** задача пришла в `cleanup` без pull request, а её ветка не содержит
  ни одного коммита сверх главной
- **THEN** дерево, локальная и удалённая ветки удаляются, запись реестра
  снимается, задача переходит в `closed`

#### Scenario: В ветке без pull request лежит работа

- **WHEN** задача пришла в `cleanup` без pull request, а в её ветке есть
  собственный коммит
- **THEN** уборка не выполняется, задача останавливается с причиной, и ветка
  остаётся нетронутой

#### Scenario: Слияние главной ветки работой не считается

- **WHEN** ветка задачи содержит только коммит слияния главной ветки, сделанный
  сессией при подтягивании свежей базы
- **THEN** уборка считает, что своей работы в ветке нет, и удаляет дерево
  и ветки

#### Scenario: У задачи есть pull request

- **WHEN** задача пришла в `cleanup` с заведённым pull request, а её ветка
  пуста относительно главной
- **THEN** уборка решается подтверждением влитости pull request, как и прежде,
  а пустота ветки разрешением не считается
