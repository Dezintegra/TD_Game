## Context

База после `git -C . fetch origin` и `git -C . merge origin/main` — `734733f`, слияние ответило `Already up to date.`. Дефект находится в `report-plan.mjs:105–113` и `denials.mjs:195`: каждый уровень независимо пропускает проверку при пустом списке. `denials.test.mjs` прямо описывает прежний пропуск. `prepareReportPlan` сохраняет операции переноса и на повторе возвращает готовый план, не читая мир заново.

## Goals / Non-Goals

Цель — одинаковая приёмка `done` с одинаковыми уликами независимо от попутных отказов. Границы перечислены в proposal: таблица TRACE, алгоритмы улик, схема отчёта, правила игры и восстановление планов не меняются.

## Decisions

### Строгость уже задана

CLAUDE.md в разделе конвейера называет отсутствие следа при `done` причиной отмены отчёта и немедленного разбора. Выбираем применение этой нормы и при пустом перечне. Мягкая отметка при доказанном отсутствии следа отвергнута: она оставляет известный бесполезный переход в аудит. Это техническое согласование с нормой, а не новый выбор за владельца.

### Один судья и два устранённых пропуска

Сохранить интерфейс `judgeDenials`, чтобы не разносить переименование по проекту. Вызывать его в `transferReport` для всех отчётов, нормализовав отсутствующий `denials` в `[]`; убрать безусловный ранний `passing` по пустому массиву внутри судьи. Для исходов не `done` передавать пустые улики и не звать сборщик: их ветка после проверки обращения к человеку остаётся `passing`. Для `done` собирать существующий набор через `evidenceFor`, до применения ссылок из отчёта к задаче. Сохранить все существующие CHECKS и их трёхзначный результат.

Изменить только пояснения в `report-plan.mjs`, `denials.mjs` и комментарии `io.mjs`, обещающие сбор лишь при отказах. Не делать второй судья для случая без отказов: две таблицы неизбежно разойдутся. Не чинить лишь один пропуск: второй всё равно даст `passing`.

### Диагностика должна соответствовать фактам

При `missing` использовать существующий `halt` с содержимым отчёта и пустым массивом отказов. Добавлять фрагмент «Отказано: …» только при непустом списке. При `none` и пустом списке писать нейтральное «проверить след этапа нечем: …»; при непустом сохранить понятную диагностику отказов. Использовать существующий `denialsNote` для записи причины: менять схему журнала ради названия поля не требуется. Для `TRACE: none` и неизвестного этапа сохранять `unverifiable`, не выдавая это за подтверждение работы. Последующий `applyReport` по-прежнему проверяет допустимость перехода.

### Сохранённый план не судить повторно

Оставить ранний возврат `saved` в `prepareReportPlan` и существующие предохранители повторно доставленного отчёта. При первоначальной проверке применяется новый контракт; уже сохранённые планы воспроизводятся по прежнему решению. Иначе повтор после записи задачи мог бы получить новые улики и противоположный переход. Не менять порядок забывания сессии и снятия отчёта после успешного `halt`.

### Проверки результата

В `denials.test.mjs` прогнать существующие типы следов с пустым списком и с одним обычным отказом, проверяя равенство вердикта и конкретную причину. Не ограничиваться тестом свежего коммита: он зелёный и при старом дефекте. Обязательный отрицательный случай — старый коммит при отправленной ветке без хвоста; отрицательные и положительные контроли для PR, ветки и run приведены в дельте. Проверить неопределённые улики, неизвестный этап и `none`, исходы не `done` и приоритет AskUserQuestion.

В `report-plan.test.mjs` использовать реальные `prepareReportPlan` и `judgeDenials` с подставными I/O, без мокирования судьи. Для одного `design` и одинаковых известных улик сравнить остановку при `denials: []`, отсутствии поля и попутном отказе. Проверить `postmortem`, содержимое записи, отсутствие ложного «Отказано», cleanup и положительный переход при свежем коммите. Проверить вызов сборщика для `done`, отсутствие вызова при иных исходах, запись нейтральной диагностики при недостаточных уликах и неизменность saved-plan при изменившихся уликах. Проверку неудачной записи `halt` провести через экспортированный `transferReport` в том же файле: отчёт и сессия не удаляются до успеха.

Текущие фикстуры без улик могут законно получить дополнительную отметку `unverifiable`. Исправлять их только по смыслу сценария; не подставлять всему набору свежие улики, скрывающие отрицательные случаи. `execute.test.mjs` уже предоставляет `stageEvidence`, его затронутые ожидания согласовать при необходимости.

## Risks / Trade-offs

- Дополнительные локальные Git-вызовы на каждый `done` → использовать готовый сборщик без новых сетевых обращений; не оптимизировать его и не менять источники в этой задаче.
- Более частое выявление старых коммитов и старых номеров прогонов → ожидаемое исправление. Локальный perf остаётся отдельной задачей 0293, её не блокирует этот узкий переход к общей мерке.
- `lastCommitAt` не отличает merge-коммит от собственной работы → известная граница существующего прибора, его усиление не входит в устранение условий пропуска. Собственная работа исполнителя по-прежнему обязательна правилами этапа.
- В основных specs ещё нет dev-pipeline-supervisor → ADDED с отдельным именем требования; архивируется ПОСЛЕ `supervise-the-pipeline` и `judge-denials-by-deeds`. Противоречие прежних требований об отказах остаётся предметом 0292, не размножаем их здесь.

## Migration Plan

Один атомарный коммит реализации с обеими правками и регрессиями, сразу отправка и черновой PR. Миграции данных и зависимостей нет. Обновление начинает действовать при штатном запуске супервизора с новой ревизией; работающий процесс этап не перезапускает. Откат коммита возвращает прежнюю приёмку; уже доставленные решения задним числом не пересчитываются.

Ядро `packages/sim` и протокол не затрагиваются: эталоны детерминизма и `PROTOCOL_VERSION` не меняются. Запреты `Math.random`, `Date.now` и дробных чисел в состоянии мира сохраняются; новых обращений в ядро нет. Рассинхрон, реконнект и прогон арены к этой служебной правке неприменимы.
