# Шаги реализации

Каждый шаг — отдельный коммит, собирающийся и проверяемый сам по себе.
Порядок не случаен: правки идут перед сторожем, который их стережёт, иначе
коммит со сторожем оказался бы красным сам по себе.

Узкие проверки гоняются по своим файлам: `npx vitest run --root plugins/pipeline`
и `npx prettier --check <свои файлы>`. Полный набор — дело CI.

## 1. Разрешить установку зависимостей

- [ ] В `plugins/pipeline/config/stage-settings.json` добавить
      `Bash(pnpm install:*)` и `PowerShell(pnpm install:*)`.
- [ ] Рядом завести `$pnpmNote`: почему именно `pnpm install`, а не `pnpm:*`
      — полный набор проверок, матчевый набор и арена запрещены скиллам
      словами, и правило `pnpm:*` сняло бы этот запрет молча. Назвать дату
      и место отказа (01.09.2026, задача 0043, `cycle.log:12736–12738`):
      заметка без следа через месяц читается как вкусовщина.

**Проверка:** `npx vitest run --root plugins/pipeline` зелёный (файл
разбирается как JSON, стоящие сторожа формы правил не покраснели).

**После этого шага открывается черновой pull request** — до него отправки
в ветку не запускают ни одной проверки CI.

## 3. Сказать про приставку общо, а не одним примером

- [ ] В каждом скилле, где стоит абзац «Звать средства полным путём»,

      и приставку меняют — ключ перед именем средства (`npx --yes …`),

- [ ] Примеры оставить иллюстрациями после утверждения, а не вместо него.
      Назвать случай 0043: разрешённое `npx prettier` было позвано как
      `npx --yes prettier@3 --check` и отказано (`cycle.log:12739`).

**Проверка:** в каждом файле `plugins/pipeline/skills/*.md`, содержащем
абзац о приставке, встречаются все пять названных форм; `npx prettier
--check` по правленым файлам зелёный.

## 5. Покрыть команды выкладки

Скилл выкладки первая сверка обошла: она искала строки, начинающиеся
с имени средства, а здесь так начинается меньше половины. Ниже — все
девять непокрытых, поимённо и с решением по каждой.

- [ ] Четыре присваивания перед замером (`deploy.md:172–175`) — правила
      точной формой: `PowerShell($env:CLIENT_PORT='5199')`,
      `PowerShell($env:PORT='3055')`,
      `PowerShell($env:VITE_API_URL='http://127.0.0.1:3055')`,
      `PowerShell($env:VITE_WS_URL='ws://127.0.0.1:3055/game')`.
      Строки правил переписать из скилла посимвольно, вместе с кавычками:
      сверка идёт по тексту.
- [ ] Рядом завести заметку `$deployEnvNote`: эти четыре вызова своей
      работы не делают — средство PowerShell хранит между вызовами рабочий
      каталог, но не переменные, поэтому до `pnpm e2e:perf` присваивания
      не доживают. Правило кладётся потому, что команда показана скиллом,
      а сам дефект скилла ведётся задачей 0079 бэклога. Без этой заметки
      разрешённую бесполезную команду через месяц прочтут как «так и надо».
- [ ] `[Console]::OutputEncoding = [Text.Encoding]::UTF8`
      (`deploy.md:197`) — правило точной формой: это не команда средства,
      а выражение PowerShell, и приставки в обычном смысле у него нет.
- [ ] `Push-Location <дерево>` (`deploy.md:198`) — `PowerShell(Push-Location:*)`
      и `PowerShell(Push-Location*)`. Здесь состояние живёт: рабочий каталог
      между вызовами сохраняется, поэтому вызов свою работу делает.
- [ ] `node scripts/deploy.mjs` (`deploy.md:199`) — **две** формы в обеих
      оболочках: `node scripts/deploy.mjs:*` и `node scripts/deploy.mjs*`.
      Приставка здесь путь со слешем и точкой, то есть ровно та форма,
      на которой форма `:*` уже подводила (`$formNote`, `node .matchlog/`).
- [ ] Две формы `ssh` (`deploy.md:91`, `:95`, `:106`, `:157`) — с приставкой,
      включающей ключи и имя хоста:
      `ssh -o BatchMode=yes -o ConnectTimeout=15 dezintegra:*` и
      `ssh -o BatchMode=yes dezintegra:*`, в обеих оболочках. Широкое
      `ssh:*` не заводить: оно открыло бы выполнение чего угодно на любой
      достижимой ключом машине, а узкое пришпиливает хост и `BatchMode`
      (без него ssh может уйти в запрос пароля и подвесить сессию).
- [ ] Записать в `$deployNote`, почему разрешение на `ssh` новых
      возможностей не даёт: `node scripts/deploy.mjs` ходит на ту же машину
      тем же ключом, и разрешение на выкладку уже есть.

**Проверка:** `npx vitest run --root plugins/pipeline` зелёный; каждая
строка блоков `powershell` и `bash` файла `deploy.md` либо покрыта
правилом, либо названа в списке заведомо непокрытых.

## 7. Сторож: команда скилла против правила разрешений

- [ ] Дописать в `plugins/pipeline/config/transitions.test.mjs` проверку
      по устройству из `design.md`: взять **все** строки блоков `bash`,
      `sh` и `powershell` всех `skills/*.md`, отбросить пустые и
      комментарии (`#` в начале и хвост после `#`), склеить строки,
      кончающиеся на `\`, с продолжением, и потребовать для каждой либо
      покрывающее правило `allow` той же оболочки, либо запись в списке
      заведомо непокрытых.
- [ ] Оболочку брать из пометки блока, а не угадывать: правило `Bash(…)`
      покрывает строки только из `bash`/`sh`, `PowerShell(…)` — только
      из `powershell`.
- [ ] Списка распознаваемых средств не заводить. Записать в комментарии,
      почему: сверка со списком (`git`, `gh`, `pnpm`, `npx`, `node`,
      `openspec`) уже пропустила весь этап выкладки — `Push-Location`
      не имя средства, `[Console]::OutputEncoding = …` не команда вовсе,
      а присваивание переменной окружения в PowerShell (`$env:ИМЯ='…'`)
      не совпадает с формой Bash (`ИМЯ=значение`) ни единым знаком.
- [ ] В комментарии теста записать **оба** слепых пятна. Первое: он сверяет
      текст с текстом и не знает настоящего разбора разрешений, поэтому
      правило, верное по виду и негодное по разбору (как `node .matchlog/:*`),
      для него неотличимо от годного. Второе: покрытие считается только
      по `allow`, запреты в сверку не входят — команда под запретом будет
      объявлена покрытой; сегодня такое место одно (`revise.md:155`,
      задача 0078), и учить сторожа запретам значило бы подделать разбор
      звёздочки в середине приставки.
- [ ] Убедиться, что сообщение о падении называет и команду, и файл
      скилла: сторож, сообщающий «не покрыто», заставит следующего искать
      руками.

**Проверка:** `npx vitest run --root plugins/pipeline` зелёный на нынешнем
дереве; проба порчей — временно убрать строку `pnpm install:*` из
разрешений, увидеть падение с именем команды, вернуть строку.

## Чего в списке нет и почему

- **Проверки «в `cycle.log` нет отказов»** здесь нет, хотя задача просит
  именно её. Настройки отдаются этапу из основного дерева, поэтому изнутри
  своего pull request правило не проверить ничем: подтвердить его может
  только первый живой этап после вливания. Наблюдение уходит заявкой.
- **Прогона арены** не нужно: правила игры, цены, доход, сила юнита и темп
  не затронуты — правка целиком в `plugins/pipeline` и `openspec`.
- **Обновления эталонов детерминизма** не нужно: `packages/sim` не тронут.
- **Правки запрета `git -C * push --force:*`** здесь нет. Бьёт ли он
  по законному `--force-with-lease`, проверяется пробой, а проба — живой
  этап после вливания; сузить запрет наугад значило бы ослабить защиту
  общей истории ради догадки. Ведётся задачей 0078; здесь место названо
  в `revise.md` и в `design.md`, чтобы отказ на нём не был неожиданностью.
- **Правки порядка работы этапа выкладки** здесь нет: четыре присваивания
  `$env:` отдельными вызовами бесполезны, но чинится это перестройкой
  шага скилла, а не правилом разрешений. Ведётся задачей 0079.
