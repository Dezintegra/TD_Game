## Decisions

### 1. Один нормализатор и прежний формат хранения

Переиспользовать evidenceText для успешной проверки, сохранив действующую семантику объявления: проверка trim только определяет непустоту, но не меняет текст. Массив проверяется целиком до join LF; исходные переносы и повторные строки не теряются. Состояние хранит строку, поэтому миграция существующих инцидентов и схемы доски не нужна. Отвергнуты String(value), filter(Boolean), обрезка и сохранение массива в metadata: первые скрывают неверные данные, последнее нарушает действующий контракт хранения.

### 2. Различение причин до побочных эффектов

Результат verifyIncident расширить машинным различием invalid-report / probe-failed при сохранении человекочитаемой problem. Проверять объект, incidentId, boolean passed и evidence; индекс неправильного элемента указывать с нуля. Несовпадающий ID — ошибка incidentVerification.incidentId. Отсутствующая отметка начала — отдельная диагностика pipelineIncident.probeStartedAt; никакого синтетического now вместо неё. Источник отметки остаётся прежним: карточка либо io.incidentProbeAt после рестарта.

При `outcome !== done` сохраняется путь неуспешной пробы с явным именем outcome; корректный `passed:false` также требует пересмотра диагноза. Для done негодные/отсутствующие поля и отсутствие начала возвращают invalid-report до halt, addSpent, saveTask, forgetSession и removeReport. Для done с корректным payload passed false — probe-failed. Успешный payload не отменяет суд над следом и остальные проверки отчёта. Уже verified и неприменимый этап сохраняют прежнюю семантику verifyIncident; идемпотентность обеспечивает доставка, а не повторная запись verifiedAt.

ReportValidationError через существующий durable-маршрут оставляет отчёт отклонённым с причиной; повтор по таймеру не создаёт новую сессию. Явный retry после починки приёмника допускается для неизменённого корректного отчёта. Исправление самих фактов нельзя выдумывать. Отвергнуто продолжать любой done после ошибки evidence: это закрывает инцидент без доказательств.

### 3. Адресная повторная приёмка исторической остановки

#### Удержание до подготовки отчёта

Уточнение после аудита: `incidentPolicy` добавляет источник в probes при завершённых fixedBy и пустом probeStartedAt, а раздел 3б `scan.mjs` выдаёт return-task в исходный этап. Замок только на время вызова адаптера не закрывает промежуток до него. Поэтому адресное удержание является частью ремонта и действует раньше проверки fixedBy, независимо от наличия восстановленного отчёта в очереди.

Ввести версионируемый список адресных восстановлений `supervisor/config/incident-report-recoveries.mjs`. Единственная начальная запись содержит полный ID источника 0199, исходный stage design, launchId `34ba94e3-40a8-409b-a8ad-c1193e043888`, исторический incidentId `466e17d3d44d84cddf5c828b` и полный ID ремонта 0368. Это поручение удерживать конкретный результат, а не доказательство успешности и не исключение из приёмки. Данные берутся из постановки и исторического лога; неизвестный ID нового инцидента в список не выдумывается. Другие задачи автоматически в список не добавляются.

Общий предикат удержания в `pipeline-incidents.mjs` использует этот список и подтверждение исправляющей доставки. Пока подтверждение отсутствует или недоступно, источник удержан, включая случай неполного инцидента, смены ID, отсутствия исторического лога или очереди. Отсутствие записи runtime не означает снятие удержания: список поставляется вместе с кодом и действует после рестарта без предварительной записи чужой карточки. Не подставлять probeStartedAt для запрета запуска — это было бы ложным свидетельством начала пробы.

`incidentPolicy` не включает удержанный источник в probes и не разрешает ему рабочую сессию. `scan.mjs` применяет тот же предикат до return-task, иных автоматических возвратов/сверок и выбора start-stage/continue-stage/retry-tool-stage, включая пакет с источником. `execute.mjs` повторяет проверку перед возвратом и перед захватом/запуском по свежим данным: старый список действий тоже не обходит удержание. Источник нельзя отдать автоматическому postmortem, уборке или иной мутации вместо адресного переноса. Сохраняются чтение, диагностика и доставка именно исправляющего отчёта; чужой захват не снимается. Независимые задачи и исправления продолжают обслуживаться по прежним правилам областей инцидентов.

`io.mjs` передаёт сканеру и исполнителю подтверждение из существующих квитанций получателя и reportStore; нового файла состояния ожидания нет. Удержание снимается только после независимого подтверждения всех эффектов исправляющего плана по детерминированному ключу: перехода в audit, записи результата проверки связанного инцидента и полного журнала. Одного verifiedAt, статуса audit, исчезновения конверта или completed у 0368 недостаточно. После удаления доставленного конверта подтверждением остаются квитанции получателя. При ошибке чтения источник остаётся удержанным; повтор доставки проверяет получателя и завершает недостающие эффекты. Запись списка сохраняется после успеха, чтобы потеря локального runtime не разрешала повторный design. Неизвестная последующая работа требует диагностики, а не автоматического снятия удержания.

#### Подготовка и доставка

Подключение к работающему циклу обязательно: `supervisor/bin/supervise.mjs` собирает state для scan, поэтому передаёт туда результат чтения подтверждения тем же помощником `io.mjs`, который использует execute. Аналогично подключить чтение в диагностическом `supervisor/bin/cycle.mjs`, не добавляя ему исполнения. Предикат не должен зависеть от того, передал ли вызывающий необязательное поле: отсутствие данных удерживает адресный источник. Проверки io и восстановления должны покрывать реальную сборку входа для scan, а не только вручную подставленное success. Согласование `schedulingStore.recovered` в supervise не должно объявлять завершённым адресное восстановление по одному verifiedAt до подтверждения журнала.

Нужен узкий адаптер `supervisor/lib/incident-report-recovery.mjs` для владельца супервизора. Он готовит исправляющий план через существующий prepareReportPlan, а не второй автомат доставки. Вход — исходный неизменный отчёт/конверт, launchId, startedAt, machine, снимок назначения и инцидента пробы, текущая карточка, доказанная квитанция/журнал ошибочного halt и подтверждение уже учтённого расхода. Восстановление из лога допускается только по полному конечному JSON и сверенной идентичности запуска; произвольная строка из журнала не является отчётом.

Перед подготовкой: текущий источник остановлен (failed с сохранённым returnTo исходного этапа), свободен, без более нового рабочего запуска/применённого результата и без конкурирующего отчёта; промежуточный postmortem, диагностировавший ошибку приёмника, допустим и сохраняется. ID исторического и текущего инцидента должен совпадать, либо должна быть явно доказана их связь в истории; при недоказанной смене ID перенос удержать. Проверка исходного payload должна пройти исправленный verifyIncident. Проверить оба коммита на удалённой ветке, её отсутствие хвоста, существующий change и собственный след после ИСХОДНОГО startedAt. Новый коммит в 0199 для этой проверки не нужен.

Лог postmortem 0199 от `2026-09-14T12-16-13.460Z`, запуск `4c54e3d7-a82e-47b1-907a-1cecc354c1a6`, действительно объявляет новый диагноз приёмки. Поэтому восстановление обязано различать старую пробу инструментов и проверку нового дефекта приёмника. Старый incidentVerification проверяется только со своим историческим ID и началом; его ID не переписывается. Для нового связанного инцидента отдельно сохраняется свидетельство фактического исполнения исправленной приёмки этого отчёта, с его текущим ID, временем начала этой проверки владельцем и ссылкой на исходный launchId. Это проверка доставки без новой сессии design. Нельзя закрывать новый инцидент одним старым passed:true. Связь нового диагноза именно с ошибочным отказом этого запуска, выполнение его fixedBy и check.expectation проверяются до подготовки; финальное подтверждение хранится вместе с успешным переходом и журналом. Отрицательный тест обязан отклонять попытку использовать старый ID для несвязанного нового инцидента.

Адаптер предоставляет обычной приёмке проверенный исторический контекст этапа только для вычисления результата; expected для записи остаётся АКТУАЛЬНОЙ остановленной карточкой. Он сохраняет текущие бюджет, spent, recovery.returns, ресурсы и историю, исключает повторное списание подтверждённой цены старого запуска. Не подставлять глобально status=design и не изменять startedAt, чтобы обойти проверку давности. Итоговый исправляющий переход failed → audit сохраняется одной операцией saveTask с verifiedAt и нормализованным свидетельством; журнал прямо называет пересмотр ошибочного halt. Если обычный план не даёт ожидаемого успешного перехода, восстановления нет.

Ключ исправляющей доставки детерминирован по исходному launchId/reportId и виду ремонта. Старые квитанции halt не стирать и не использовать как квитанции нового перехода. Сначала сохранить конверт и неизменный план в существующую очередь, затем исполнять report-delivery со стандартной проверкой expected и квитанциями. Повтор/рестарт использует тот же ключ и план; при потерянном ответе проверить получателя до следующей записи. После успеха повтор только подтверждает сохранение. Частично исполненные старые планы автоматически не перепланировать.

Вызывать адаптер вправе только обслуживание под существующим исключительным владением супервизора; worker не правит чужую карточку и .pipeline. Инструкция в supervisor/README.md должна показать подключение адаптера к штатным io/reportStore владельца, подготовку без записи и явную передачу плана на доставку. Сканер автоматически удерживает адресный источник, но не восстанавливает историю и не применяет исторический отчёт сам. Новый CLI запуска супервизора и broad allow не нужны. Наличие адаптера, защиты сканирования/исполнения и проверенного протокола — доставляемый результат implement; живое применение выполняет владелец данных по поручению карточки 0368.

Отвергнуты обычный возврат failed → design (оплатит повторную проработку), прямое verifiedAt (обходит проверку) и один store.retry (не восстанавливает удалённый отчёт и уже применённое состояние). Отклонены удержание только в памяти или только во время вызова адаптера (теряются при рестарте либо оставляют гонку), ручное редактирование 0199 исполнителем (чужая карточка) и общий запрет всех проб (мешает независимому восстановлению 0366). Адресный список выбран для уже известной исторической остановки: он позволяет удержать её даже до восстановления полного конверта, не выводя успех из номера задачи.

## Risks / Trade-offs

- Исторический отчёт мог быть удалён из очереди → использовать исходный лог и доказательства halt; при нехватке конкретных данных удержать восстановление, не создавать новый результат.
- Более новый диагноз мог изменить ID → сверить историю; не перепривязывать evidence молча.
- Перенос может оборваться → существующие durable-план, expected и квитанции, тесты сбоя после карточки и журнала.
- Рабочий супервизор может оставаться на старой ревизии → живое применение только после подтверждения загруженного ремонта. Merge сам не закрывает инцидент.

## Migration Plan

Первый коммит согласует приёмник, назначение и ошибки с unit/integration проверками; второй добавляет адресное удержание, восстановление, проверки настоящего сканера/исполнителя и памятку. Существующие строковые записи читаются без миграции.

Порядок живого обновления обязателен: до того, как завершение 0368 станет доступно старому циклу как выполненный fixedBy, владелец ставит существующую устойчивую паузу и дожидается окончания текущего цикла на всех станциях, способных захватить 0199. Это предварительное действие владельца, передаваемое в отчёте implement до review, а не действие worker над .pipeline. Под паузой обновляется исполняемая ревизия супервизора с адресным списком и обоими предикатами; владелец подтверждает загруженную ревизию каждого допускаемого процесса. Старый процесс нельзя возобновлять после выполнения ремонта. Первый разрешённый scan уже обязан удерживать 0199, даже если ремонт завершён, probeStartedAt нового инцидента пуст и отчёта ещё нет в очереди. Пока это не подтверждено, пауза сохраняется; merge не служит разрешением её снять. Пауза переживает обрыв обновления и рестарт. После загрузки защиты независимые циклы можно продолжить до ручной подготовки отчёта — адресное удержание уже действует.

Откат кода не требует преобразования verificationEvidence, но возврат к версии без защиты допустим только под сохраняемой паузой до завершения адресного восстановления либо повторной установки совместимой защиты. Нельзя удалять очередь, список или квитанции ради возобновления старого цикла.

После ремонта владелец супервизора использует исходный запуск 0199 и протокол выше. Проверяемый результат: audit, прежний change, оба SHA в ветке, все три свидетельства в сохранённом инциденте и журнале, подтверждённая доставка, отсутствие нового design и повторного списания. Этот результат фиксируется отдельно от зелени тестов; до него живое восстановление не объявляется состоявшимся.

## Validation

На implement: `pnpm install --frozen-lockfile --prefer-offline`, затем `pnpm test:pipeline lib/pipeline-incidents.test.mjs lib/execute.test.mjs lib/stage-prompt.test.mjs lib/report-delivery.test.mjs lib/incident-report-recovery.test.mjs lib/scan.test.mjs lib/io.test.mjs`. Файлы указываются относительно supervisor; не запускать полный verify/матчевый набор.

Регрессия аудита проходит через настоящий scan и execute, без подмены incidentPolicy: источник 0199 в failed, новый связанный инцидент без probeStartedAt, 0368 сначала незавершена, затем completed. До вызова адаптера ни один цикл не выдаёт return-task или новый design; независимый незатронутый этап доступен. Повторить на заново загруженных данных при пустой очереди, недоступном логе, неизвестном списании и ошибке чтения квитанций; удержание сохраняется без расхода попыток. Передать execute устаревшие return-task/start-stage/continue-stage и пакет с 0199 — ни записи возврата, ни spawn. Затем доставить исходный отчёт: audit ровно один раз; обрыв после saveTask до журнала сохраняет удержание, повтор заканчивает журнал. После подтверждения и удаления конверта следующий scan допускает audit, но не design; повтор адаптера ничего не списывает. Отдельно проверить, что одна запись verifiedAt либо completed у ремонта при отсутствии квитанций защиту не снимает.

Матрица: строка; массив из трёх строк с повторами и переносами; null/undefined/пустая/пробельная строка; пустой массив; пустой или нестроковый элемент в начале/середине/конце; неверный ID; passed false и неboolean; отсутствие начала в обоих источниках; отметка после рестарта; outcome failed/question/blocked; нет собственного свежего отправленного следа. Через обработчик проверить отсутствие побочных эффектов invalid-report, сохранение rejection и полный путь done → audit. Через durable-доставку проверить рестарт и потерю подтверждения; чтение metadata инцидента должно сохранить строку целиком. Отдельная фикстура исходного 0199 проверяет ошибочный halt → исправляющий перенос → audit без нового spawn и расхода, плюс отрицательные контроли новой работы, чужого захвата, неизвестного списания и другого инцидента.

## Open Questions

Продуктовых вопросов нет. Точные квитанции halt, исходный снимок инцидента и учёт старого расхода требуют свежего чтения владельцем при живом восстановлении; текущий design их не подменяет. При недостатке данных протокол возвращает конкретную недостающую улику и сохраняет задачу, отчёт и инцидент.
