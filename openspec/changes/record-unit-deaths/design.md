# Проектное решение

## Главный выбор: гибель обнаруживается наблюдением, а не сообщается ядром

Гибель ищет **арена**, сравнивая состав юнитов до и после шага мира.
В `runMatch` уже есть оба состояния разом — `world` и `next`, — поэтому
разность даёт список погибших без единой правки `packages/sim`.

Почему разность точна, а не приблизительна:

- юнит покидает `WorldState.units` ровно одним путём. `fromWorking`
  отсеивает тех, у кого `alive === false`, а флаг снимается только
  гибелью (`combat.ts`, взрыв ядерного удара). Другого выхода из мира
  у юнита нет: он не уходит с карты и не переходит к другой стороне;
- идентификаторы не переиспользуются. `nextEntityId` только растёт,
  поэтому «был на прошлом тике и нет на этом» не может означать
  «появился новый под тем же номером»;
- шаг мира чист: `world` после вызова `step` не тронут, и сравнивать
  есть с чем.

### Отвергнутые варианты

**Событие о гибели внутри `packages/sim`** — например, массив `deaths`
в состоянии мира по образцу `rejections`. Дало бы причину гибели
и убийцу, которых снаружи не видно. Отвергнуто: ради вопроса о потерях
по типам пришлось бы тронуть ядро, чьё состояние ходит по сети и входит
в контрольную сумму, обновить эталоны детерминизма и объяснить каждому
читателю, почему поле в сумму не входит. Цена несопоставима с ответом,
а ответ разность даёт целиком. Если однажды понадобится **причина**
гибели — идти придётся именно этим путём, и тогда он и будет оправдан.

**Считать по взрывам (`WorldState.blasts`).** Взрыв уже лежит в состоянии
и несёт сторону и место. Отвергнуто по двум причинам сразу: типа юнита
во взрыве нет вовсе (там `BlastKind` — вид взрыва, а не вид машины),
и живёт взрыв несколько тиков, так что «новые за этот тик» пришлось бы
опять-таки вычислять разностью — только по данным, где нужного поля нет.

**Счётчик потерь в снимке состояния** (`sample.deaths_since_last`).
Дёшево и бесполезно: снимок снимается раз в игровую секунду, а типа
в счётчике нет. Разложить потери по типам — ровно то, ради чего задача
заведена, — счётчик не позволяет. Схема арены хранит факты, а не выводы;
счётчик — уже вывод.

**Записывать гибели в тонкую запись сервера.** Нарушило бы требование
«Запись матча содержит входы, а не состояние»: гибель — следствие входов,
она выводится воспроизведением. Воспроизведение идёт через тот же
`runMatch`, поэтому логи живых матчей получают гибели даром.

## Устройство разности

Отдельная чистая функция в `apps/arena/src/deaths.ts`:

```ts
export const deathsBetween = (
  before: readonly UnitState[],
  after: readonly UnitState[],
  tick: number,
): DeathRecord[];
```

Внутри — множество идентификаторов из `after` и обход `before`: чего
в множестве нет, то погибло. Стоимость O(число юнитов) на тик.

Двухуказательная прогулка по двум спискам, упорядоченным по возрастанию
идентификатора, обошлась бы без множества и без выделения памяти. Она
не выбрана намеренно: порядок в `units` сегодня действительно
возрастающий (новые дописываются в конец, фильтр порядок сохраняет),
но нигде не закреплён и не проверяется, а молчаливая опора на незакреплённый
инвариант ломается тихо — потерянными гибелями, которых никто не ждёт.
Выигрыш при этом не измерен и заведомо мал: рядом каждый тик работает
шаг мира, который те же сотни юнитов двигает, наводит и обсчитывает.

Функция чистая и потому проверяется списками, собранными руками, —
без матча, без мира и за миллисекунды.

## Что стоит в записи и почему

| Поле       | Откуда                                                |
| ---------- | ----------------------------------------------------- |
| `tick`     | `next.tick` — тик, на котором юнита не стало           |
| `player`   | владелец юнита                                        |
| `unitType` | тип юнита                                             |
| `unitId`   | идентификатор                                         |
| `cell`     | `cellAt(position)` из состояния **до** шага            |

Тик берётся послешаговый — тот же, что у записей команд, — и это делает
записи одного тика сопоставимыми между собой.

Клетка берётся из состояния до шага, и это единственное место,
где запись приблизительна: за тот же тик юнит успел бы сдвинуться
не более чем на один шаг движения, то есть на десятые доли клетки.
Взять положение после шага нельзя — погибшего в `next.units` уже нет.
Оговорка записана и в комментарии к типу записи: «последнее известное
положение», а не «место гибели с точностью до тика».

Идентификатор нужен не для соединений, а для проверок: он позволяет
убедиться, что гибель не задвоена, и отличить две гибели одного типа
на одном тике друг от друга.

## Порядок записей внутри тика

Гибели пишутся сразу после записей команд того же тика и до снимка
состояния. Порядок «решение — команды — гибели — снимок» сохраняет
уже сложившееся правило: запись о случившемся идёт после записи
о намерении.

## База

Новая таблица рядом с прочими зависящими от матча:

```sql
create table if not exists death (
  match_id  text not null,
  tick      integer not null,
  player    integer not null,
  unit_type integer not null,
  unit_id   integer not null,
  cell      integer not null
);
create index if not exists death_by_match on death (match_id, player, tick);
```

Имя `death` добавляется в `CHILD_TABLES` — иначе повторная сборка того же
лога задвоит строки. Это ровно та ошибка, которую легко не заметить:
сборка не падает, а числа растут вдвое, и виноватым выглядит противник.

Миграции не нужны: база пересобирается из логов целиком, так решено
в `schema.ts` и подтверждено требованием «Схема меняется без
переигрывания».

## Прежние логи

Матч, сыгранный до этой правки, гибелей не содержит и не приобретёт.
Ноль в такой выборке означает «не записывалось», а не «никто не погиб»,
и это ловушка ровно того рода, что портит сравнение «до и после».

Различать эти два случая надо по версии кода матча — `match.git_sha`
в заголовке; отбирать матчи для сравнения потерь следует по ней.
Оговорка пойдёт в раздел «Запросы» README арены рядом с примером
запроса, а не останется в этом файле: читают её там.

Заводить признак «этот лог умеет писать гибели» ради того же различия
не стали: версия кода уже записана в каждом матче и отвечает на более
общий вопрос, а второй источник той же истины разъехался бы с первым.

## Чего эта правка не задевает

**Рассинхрон и переподключение.** Правило проекта требует назвать
поведение при рассинхроне для всего, что задевает геймплей. Здесь
называть нечего, и это вывод, а не пропуск: `packages/sim` не меняется,
состав состояния мира прежний, контрольная сумма считается по тем же
величинам, сетевого обмена в арене нет вовсе. Клиент и сервер этого кода
не исполняют — `apps/arena` в них не импортируется.

**Эталоны детерминизма.** Не обновляются: правила игры не тронуты,
`determinism.golden.match.test.ts` и `profile.golden` считают то же самое.
Если после правки хоть один из них покраснел — значит наблюдение
всё-таки вмешалось в матч, и чинить надо наблюдение, а не эталон.

**`PROTOCOL_VERSION`.** Не растёт: раскладка байтов не менялась.

**Запреты ядра.** Новый код живёт в `apps/arena` и в ядро не попадает:
ни `Math.random`, ни `Date.now`, ни чисел с плавающей точкой в состоянии
мира не добавляется. Единственное новое число — номер клетки, целое.
