## Context

Проработка выполнена на `origin/main` 48d6c25 после fetch/merge. В основе есть `card-dependencies`, реализация `pendingDependencies` в `supervisor/lib/dependencies.mjs` и удержание до квот/пределов в `scan.mjs`. Живые процессы и готовые отчёты из удержания исключены. Проверки этих границ находятся в `dependency-state.test.mjs`.

`append-addressed-card-dependencies` прочитано из удалённой ветки 0242 (PR 177): в актуальной главной ветке канала пока нет. `confirm-stage-tool-outages/tasks.md` из ветки 0244 требует PR 172 для report store и оба PR перед интеграцией runtime gate. Состояние 0244 по назначению — `awaiting-po`; это не доказательство текущих полей зависимостей. Доска на design не читалась и не менялась, вливания PR не проверялись.

## Goals / Non-Goals

Цель — передать точное дополнение одной существующей карточке, получить независимое подтверждение и проверить применение неизменного допуска. Границы — proposal: без кода механизмов, прямой записи карточек, возврата в работу и вмешательства в живые процессы.

## Decisions

### 1. Одно поручение на оба условия

После поставки 0242 использовать в последнем обычном отчёте implement следующий фрагмент. Это пример payload, а не отчёт design и не отдельный файл отчёта:

```json
{
  "dependencyUpdates": [
    {
      "taskId": "0244-podtverzhdat-poteryu-rabotosposobnosti-i",
      "dependsOn": [
        "0233-sohranyat-neprimenennyy-otchet-etapa-pri",
        "0242-dat-otchetu-etapa-adresnoe-poruchenie-na"
      ],
      "dependencyResults": [
        { "taskId": "0233-sohranyat-neprimenennyy-otchet-etapa-pri", "kind": "merged-pr", "pr": 172 },
        { "taskId": "0242-dat-otchetu-etapa-adresnoe-poruchenie-na", "kind": "merged-pr", "pr": 177 }
      ],
      "reason": "0246 / bind-tool-outage-prerequisites / implement / payload-v1; основание 0245 и tasks.md confirm-stage-tool-outages; 0233-sohranyat-neprimenennyy-otchet-etapa-pri / merged-pr / 172; 0242-dat-otchetu-etapa-adresnoe-poruchenie-na / merged-pr / 177"
    }
  ]
}
```

Оба ребра отправляются одним элементом: частичное поручение оставляет второе условие незащищённым. Супервизор объединяет со свежими данными и сохраняет оба поля одним PUT. Не заменять массивы этим фрагментом вручную. Идентичные значения — no-op с независимым чтением; другой PR для того же предшественника — диагностируемый конфликт, не перезапись.

### 2. Поставка канала и момент подтверждения

До выдачи поручения проверить PR 177 на `MERGED`, непустой корректный `mergedAt` и `baseRefName`, совпадающий с `mainBranch` конфигурации супервизора. Освежить своё дерево, проверить поставленный контракт и свидетельство использования обработчика активными супервизорами. Только наличие кода в рабочем дереве не доказывает обновление живого процесса. Если поставку подтвердить нельзя, вернуть предусмотренный этапом вопрос о поставке 0242; не отправлять неизвестное старому обработчику поле и не реализовывать его здесь.

PR 172 и закрытие 0233 не задерживают запись условий: ждать их до дополнения означало бы оставить преждевременный запуск без защиты. Возврат 0244 из awaiting-po не нужен и не выполняется.

Последний отчёт передаётся после окончания сессии, поэтому implement пишет «поручение подготовлено и передано; запись ещё не подтверждена». Подтверждение делает сам обработчик 0242 независимым GET до перехода источника; его запись в журнале источника и успешный переход проверяет следующая сессия review. Не добавлять в tasks неисполнимое ожидание собственного отчёта. Review не вправе считать один payload или ответ PUT подтверждением. Приёмка использует следующую воспроизводимую цепочку:

1. Implement сохраняет точный объект `dependencyUpdates`, включая `reason`, в `verification.md` отправленного коммита и дословно включает его в последний отчёт. `reason` связывает адресата, обе пары, источник 0246 и редакцию поручения. При изменении payload меняется его редакция в reason; повтор доставки неизменного поручения сохраняет её. Это сохранённый фрагмент поручения, не отдельный файл отчёта.
2. Review сопоставляет сохранённый объект с записью журнала источника `Зависимости <taskId> подтверждены: <reason>` и переходом по соответствующему отчёту implement. Сохраняет в verification.md текст записи, её дату/доступный идентификатор и ссылку на коммит с payload. Совпасть должны полный адресат и reason, а через него — обе пары и редакция. Общая фраза о завершении этапа или собственное заявление implement эту запись не заменяют.
3. Review связывает эту запись с проверенным контрактом ревизии, которую использовал обработавший отчёт супервизор: SHA, свидетельство работающей ревизии, пути/строки реализации и результаты узких проверок из implement. В прочитанной ветке 0242 `execute.mjs` добавляет указанную запись только после `appendTaskDependencies(...).ok`; `backlog-trello.mjs` возвращает успех после независимого чтения, проверки сохранности и успешного освобождения собственного захвата, если он приобретался. Для no-op независимое свежее чтение подтверждает уже имеющиеся пары, а новый захват и PUT не требуются. На поставленной ревизии эти связи необходимо проверить заново.

Журнал не обязан содержать снимки до/после, протокол GET, отдельный результат сравнения или освобождения: эти гарантии устанавливает проверенный контракт, а конкретное успешное применение — связанная запись супервизора. Тесты контракта сами по себе применения не доказывают. Нет любого звена либо ревизию обработчика установить нельзя — запись остаётся неподтверждённой для приёмки; восстановление доставки остаётся у супервизора, а не у ручного повторного PUT. При недостающем журнале использовать предусмотренное правилами чтение локального лога, а не редактирование доски.

### 3. Проверка сохранности и допуска

В `verification.md` этого изменения исполнитель фиксирует ревизию проверки, команды/результаты и отдельно два вывода: «запись условий» и «допуск запуска». Для первого вывода review предъявляет все три звена Decisions 2 и явно отделяет наблюдаемую запись супервизора от гарантий, выведенных из проверенного контракта. Счётчики, состояние, ранее сохранённые зависимости и результаты, неизвестные поля, человеческий текст и выполненная работа сохраняются по контракту 0242. Его проверка охватывает сравнение независимого чтения с ожидаемым объединением и свежими исходными данными, отказ при потере поля и при ошибке освобождения захвата. Работающая/занятая карточка остаётся занята; собственный временный захват снимает только обработчик. Не добывать подтверждение прямой записью или остановкой процесса.

Для поведенческой проверки использовать импорт настоящих `pendingDependencies` и `scan` в изолированной пробе с подставными снимками и доказательствами, без Trello, spawn и изменения production-карточек. Проба не копирует алгоритм допуска. Снимок потребителя содержит точные два ребра из payload; сохранить дополнительные зависимость и результат как контроль объединения. Сценарии запуска/продолжения моделируются на копии в `new` и `implement`, отдельно от настоящего awaiting-po.

| Условия на копии | Ожидаемый результат |
| --- | --- |
| Для каждого из двух предшественников по очереди: не closed при влитом PR; closed при OPEN/CLOSED PR; нет доказательства; неверный номер или база; некорректная дата | Удержание start и continuation, отсутствие fail-stage из-за пределов и изменений attempts; второй предшественник полностью удовлетворён |
| Оба ребра удовлетворены, потомок splitInto открыт | Удержание до закрытия потомка |
| Оба ребра удовлетворены, прочее предусловие открыто | Удержание по прочему условию |
| Оба ребра удовлетворены, нет иных ограничений | Штатное действие старта/продолжения на следующем свежем снимке |
| Оба ребра удовлетворены, awaiting-po либо пауза/квота/предел попыток | Нет обхода соответствующего штатного ограничения; awaiting-po сохраняется |
| Живой процесс; либо уже готовый отчёт | Нет прерывания процесса/потери отчёта из-за новых зависимостей |

Существующие тесты 0242 дают контроль сохранности, независимого GET, повторной доставки и устаревшего запуска другой станции. Здесь не создаётся второй обработчик или постоянный набор тестов с захардкоженными номерами карточек. Временную воспроизводимую пробу можно хранить в `.matchlog/0246-prerequisites.mjs` и запускать `node .matchlog/0246-prerequisites.mjs`; её исходный текст и вывод включить в verification.md для воспроизводимости. Ни один тест не выдаёт живой запуск.

Фактический допуск оценивается только по свежему штатному снимку после записи: закрытие обоих предшественников и их частей, доказательства GitHub для настроенного репозитория/ветки и все остальные ограничения. Положительная модель не доказывает фактическую готовность. Если 0244 всё ещё awaiting-po, итог прямо говорит «условия записаны, запуск не разрешён состоянием awaiting-po». Ждать закрытия предшественников или реального запуска ради завершения этой операции не требуется.

### 4. Альтернативы и архитектура

Прямая запись через Trello или общий saveTask отвергнута: нарушает владельца записи и может затереть прочие поля. `requests` создаёт новую задачу и не адресует существующую; `amendments` не является каналом метаданных. Повторная реализация 0242 создаёт двух владельцев протокола. Проверка только PR пропускает незакрытую карточку; проверка только закрытия пропускает невлитый результат. Принудительный старт ради проверки нарушает awaiting-po и расходует сессию.

Игровые пакеты не затронуты. Рассинхрон и реконнект игры, эталоны детерминизма и `PROTOCOL_VERSION` прежние. Запреты `Math.random`, `Date.now` и дробного состояния мира остаются в силе; операция состояния мира не создаёт. Арена не нужна.

## Risks / Trade-offs

- Канал ещё не поставлен → подтвердить поставку до выдачи поля; design не утверждает, что она состоялась.
- Карточка занята, конфликт результата, ошибка PUT/GET → передача отчёта не подтверждается; сохранить диагностику и использовать штатную доставку 0242, не снимать чужой захват.
- Письмо сохранено, ответ потерян → повторное независимое чтение и no-op существующего обработчика, без ослабления условий.
- Данные изменились после проверки → допуск остаётся обязанностью свежего сканирования; историческая проверка не даёт постоянного разрешения.

## Migration Plan

После поставки 0242 проверить механизм и подготовить поручение в implement. Супервизор применяет его при обработке последнего отчёта; review подтверждает применение по независимому чтению обработчика и отдельно фиксирует доступный факт допуска. Это последовательные этапы разных сессий. При откате документации не удалять уже подтверждённые зависимости: откат Git не откатывает карточку. Изменение условий потребует отдельного назначения.
