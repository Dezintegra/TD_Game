## Context

В `packages/shared/src/rules.ts` applyRuleTuning принимает только положительные конечные множители и запирается созданием первого мира. resetRuleTuning снимает блокировку для тестов. `balance.ts` округляет производные величины и ограничивает их снизу единицей. Поэтому ноль недопустим, а «очень маленькое» не означает неподвижность. `packages/sim/src/step.test.ts` не сбрасывает tuning в hooks; это подходящий первоначальный набор. Навигационный тест «юнит доходит до слабой преграды» из navigation.test.ts перебирает клетки без времени и скорости, поэтому связывать его с speed было бы неверно.

## Goals / Non-Goals

Цель — воспроизводимый малый список чувствительных проверок и честная диагностика пропусков. Non-goals перечислены в proposal: игровые правила, полный матчевый набор и автоматическая починка тестов сюда не входят.

## Decisions

### Каталог и начальные пары

`scripts/mutation/catalog.mjs` экспортирует две коллекции: mutations и pairs. Связь содержит mutationId, testFile, fullName (массив предков describe и имя it), rationale и проверяемую производную величину. Никакого произвольного shell-текста. Пустые/дублированные id и пары, неизвестные ключи RuleTuning, нейтральная либо не меняющая производную величину порча — error. Пара с потерянным тестом остаётся ошибкой, а не исчезает при обнаружении файлов.

Первоначально три пары из `packages/sim/src/step.test.ts`; полные describe-имена исполнитель снимает из файла при реализации и фиксирует в каталоге дословно:

| id | Порча | Имя it | Причина ожидаемой красноты |
| --- | --- | --- | --- |
| fragile-base-under-fire | baseHealth: 0.000001 | останавливается в четырёх клетках от края основания и бьёт по базе | База с одной единицей здоровья не переживает первый выстрел; проверка требует живую базу после остановки и дальнейшего обстрела. |
| fragile-building-progress | towerHealth: 0.001 | снайперская башня на середине возведения заметно слабее готовой | Максимум становится единицей, промежуточное здоровье не может оказаться между 0.3 и 0.7 максимума; проверяется различимость незавершённой постройки. |
| income-overwhelms-payment | income: 100000 | ставит стену рядом с генералом и списывает энергию | Доход тика перекрывает платёж за стену; утверждение об уменьшении запаса обязано заметить нарушение соотношения дохода и расхода. |

Это проверка чувствительности к названной крайности, а не доказательство дефекта правил или полноты теста. Значения взяты из чтения текущего кода, живой прогон на design запрещён. На implement обязательна проверка baseline/detected всех трёх; при неожиданном survived его нельзя скрывать удалением пары или ослаблением утверждения. Нужно проверить обоснование, допускается уточнить множитель в рамках того же свойства с записью причины. Изменение смысла проверки требует возврата проработки. Примеры speed 0.25, towerHealth 2 и baseHealth 0.1 из карточки не обязательны: большинство относительных утверждений закономерно переживает их.

Пара со speed для этого теста отвергнута после чтения строки 1780: бюджет подхода вычисляется от текущей скорости, поэтому замедление законно переживается. Для baseHealth проверяется другой явный контракт того же теста: здоровье базы после выстрелов остаётся положительным. Это не проверка длительности полного матча.

### Исполнение без утечек и ложной красноты

Оркестратор `scripts/mutation/run.mjs` создаёт для каждой пары два независимых запуска установленного Vitest, с cwd пакета sim и отдельной конфигурацией `scripts/mutation/vitest.config.ts`. Она включает только выбранный файл, окружение node, один worker, изоляцию и setup-файл. Обычные конфиги пакетов не изменяются; полный workspace и Turbo не запускаются. Исходники shared и sim разрешаются согласованными alias в эту же копию проекта, чтобы setup и тест видели один экземпляр rules и balance. Сборки на каждую мутацию нет.

Setup `scripts/mutation/setup.ts` читает дескриптор запуска из среды исключительно в тестовой оснастке, импортирует shared, применяет настройку до загрузки тестового файла, записывает tuning и производные значения. Проверяет их перед и после выбранного теста; сброс либо неприменение — error. После теста reset вызывается в finally. Даже при аварии процесс уничтожается, а следующий создаётся заново: безопасность не зависит от выполнения finally. Значения мира по-прежнему целые; Math.random и Date.now в sim не добавляются. Протокол, PROTOCOL_VERSION, рассинхрон и реконнект не меняются, поскольку порча не достигает игры. Golden-эталоны не обновляются: штатные игровые правила не меняются. Прогон арены не нужен по той же причине.

Выбор по экранированному полному имени дополнен сверкой структурированного результата: ровно один ожидаемый тест реально исполнен, его путь и предки совпадают. Пропущенные из-за фильтра соседние тесты допустимы; skip выбранного — нет. Собственный reporter `scripts/mutation/reporter.ts` фиксирует вход и выход тела теста, ошибки hooks и runner, тип ошибки утверждения. Вспомогательная instrumentation в setup отделяет тело теста от hooks. Одного exit code или строки AssertionError недостаточно: ошибка assertion в beforeEach не detected. Неклассифицированный сбой — error. Все результаты привязаны к уникальному каталогу запуска, фазе и паре; старый файл не может быть принят за новый.

На каждый дочерний процесс максимум 10 минут, принудительное завершение с очисткой дочерних workers; предел workflow 90 минут. Сначала baseline, при его ошибке мутант не исполняется. Следующие пары продолжаются после ошибки для полной сводки. Для каждой пары отдельный итог; общий exit 0 только при непустом наборе и всех detected, exit 1 для survived, exit 2 для errors (при смешанном итоге ошибки имеют приоритет). Валидные mutations без pairs получают uncovered без запуска. Пустой каталог пар — конфигурационная ошибка, даже если все мутации uncovered.

### Ночной workflow и публикация

`.github/workflows/mutation.yml`: schedule `30 2 * * *` и workflow_dispatch, ubuntu, Node 22, pnpm по packageManager, frozen install. Права contents: read, issues: write; concurrency отдельно от balance, cancel-in-progress: false. Никакой записи в main и доступа к Trello. Результаты в `.matchlog/mutation/<run-id>/`: JSON, Markdown, stdout/stderr и отчёты дочерних процессов. Summary и upload-artifact с retention 30 дней выполняются даже при красном исполнителе; отсутствие результата явно называется, не маскируется пустой зеленью.

Публикация — модуль `scripts/mutation/issue.mjs`, использующий GitHub API с токеном только на шаге публикации. Находит открытый Issue по устойчивому маркеру этой способности и обновляет его либо создаёт один новый. Issue включает все survived: mutationId, tuning, file, fullName, SHA, baseline/mutant status и ссылку на Actions. Ошибки располагаются отдельно. Автозакрытия нет. Ручной запуск не на main сохраняет артефакты без публикации Issue, чтобы проверка ветки не создавала ложные производственные уведомления; этот режим явно помечен диагностическим. Стандартный ночной запуск main обязан публиковать Issue при survived. Ошибка API делает шаг красным, отчёт остаётся артефактом.

### Отвергнутые варианты

- Один процесс с reset между мутациями: глобальные ссылки и аварийные hooks могут протечь.
- Любой ненулевой код считать успехом: потерянный тест, import error и timeout дают декоративную зелень.
- Запускать все матчи или добавлять прогон в PR: стоимость растёт с числом мутаций и задерживает каждую правку.
- Исправлять существующий балансный workflow: его очередь и журнал не нужны этой способности.
- Golden checksum как начальная пара: ловит любое изменение состояния, но не объясняет конкретное поведение.

## Risks / Trade-offs

Vitest 2.1.x и hooks могут иметь тонкости reporter API → исполнитель проверяется короткими фикстурами, включая assertion в hook, timeout, skip, неверный selector и оборванный JSON; неоднозначность всегда error. Реальную чувствительность трёх пар подтверждает implement, а не чтение исходников. Начальный список не характеризует весь набор sim/ai. Изменение test title потребует обновить связь; это намеренная видимая ошибка. Неисправный GitHub API не должен уничтожать локальный отчёт.

## Migration Plan

Сначала чистая модель классификации и её тесты, затем изолированный исполнитель с тремя парами и интеграционными фикстурами, затем workflow и публикация. Все коммиты самостоятельно проверяемы. Откат workflow отключает расписание, удаление оснастки не меняет игру. Приёмка расписания после вливания — первый штатный ночной запуск, его ожидание не является задачей implement.

## Open Questions

Продуктовых развилок нет. Точный адаптер событий установленного Vitest и результаты трёх пар подлежат технической проверке при реализации; тесты на design не запускались.
