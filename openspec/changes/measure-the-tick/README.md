# measure-the-tick

В боевом коде проекта нет ни одного замера времени. Поиск по
`performance.now|hrtime|console.time|PerformanceObserver` в `apps/server`,
`packages/netplay`, `packages/bot` и `packages/ai` даёт ноль совпадений.

Из-за этого разбор жалобы «игра подлагивает» пришлось вести снаружи —
и он дважды дал разные ответы на один вопрос, разойдясь вдесятеро.
Первый заход обвинил компьютерного соперника (≈28 мс на решение),
перемер оправдал его (1,8–3,6 мс). Разница целиком объясняется
загрузкой машины, на которой мерили. Это изменение существует затем,
чтобы третьего раза не было.

Ставится: задержка цикла событий, длительность такта и шага мира,
догон и списанные долги на сервере; длительность и частота раздумий
компьютера как игровая величина; распределение длительности кадра
и разброс прихода кадров на клиенте; отметки реального времени
в записи матча. Отдача — точка `/metrics`, ноль новых контейнеров.

**Главное правило устройства:** гистограмма копится внутри процесса,
наружу уходят перцентили. Среднее — ровно тот прибор, который эту
беду уже один раз спрятал.

**Порядок.** Независимо от `predict-only-for-the-watching`. Делать
стоит **до** `give-the-computer-its-own-process`: вынос компьютера
в отдельный процесс надо чем-то проверять, а проверить его нечем.

**Заводит новую капабилити `performance-metrics`.** После архивации
у неё будет заглушка `TBD - created by archiving change` вместо
Purpose — дописать по содержанию требований, это известная недоработка
CLI. Кроме неё дельты трогают `match-telemetry` (ADDED, отметки
времени) и `match-hud` (MODIFIED поверх «Диагностические величины
доступны проверкам»). Обе существуют в `openspec/specs/`.

**Чего изменение не делает.** Не заводит хранилища метрик и графиков
(ни Prometheus, ни VictoriaMetrics, ни Grafana), не использует Yandex
Monitoring, ничего не оптимизирует, не пересматривает пороги «не ниже
55 кадров» в `isometric-view`, `object-elevation` и `unit-appearance`.

**Про квантование раздумий компьютера.** Вопрос разобран в `design.md`
и отложен: величина не просит (p50 = 1,8–3,6 мс при бюджете 33,33),
а нарезка по времени сломала бы воспроизводимость и оба эталонных
теста. Там же записано, какой формы должна быть нарезка, если приборы
однажды покажут, что она нужна: по расписанию тиков, а не по секундомеру.
