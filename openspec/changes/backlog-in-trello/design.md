# Технические решения

## Устройство карточки

Задача раскладывается по карточке так, чтобы человеческое было видно,
а машинное не мешалось.

| Что                    | Где живёт                          | Кто правит |
| ---------------------- | ---------------------------------- | ---------- |
| Заголовок              | название карточки, после префикса   | человек    |
| Идентификатор          | машинный блок; префикс в названии   | конвейер   |
| Описание               | описание карточки над блоком        | человек    |
| Состояние              | колонка доски                       | конвейер   |
| Приоритет              | положение карточки в колонке        | человек    |
| Тип задачи             | метка `feature` / `run` / `note`    | человек    |
| Вид прогона            | метка `arena` / `perf` / `bench-tick` | человек  |
| Ожидаемый результат    | раздел описания                     | человек    |
| Владелец, ссылки, счётчики, `returnTo`, отметки времени | машинный блок | конвейер |
| Журнал этапов          | комментарии карточки                | конвейер   |
| Вопрос владельцу       | комментарий карточки                | конвейер   |
| Ответ владельца        | комментарий карточки                | человек    |

Машинный блок — HTML-комментарий в конце описания:

```
Человеческое описание задачи.

<!-- pipeline
{"id":"0031-imya","owner":null,"returnTo":null,"links":{...},"attempts":{...}}
-->
```

Markdown его не показывает, значит владелец продукта служебных отметок
не видит. Проверено делом: Trello возвращает описание байт в байт вместе
с кавычками и угловыми скобками внутри блока, так что JSON переживает
дорогу без экранирования.

### Почему не настраиваемые поля

Первым замыслом вид прогона и приоритет жили в настраиваемых полях
(Custom Fields). Проба это отвергла: `POST /1/customFields` отвечает
`403 Custom Fields Power-Up disabled for board`. Поле требует включённого
на доске дополнения, а дополнение — действия человека в интерфейсе, о
котором конвейер узнает только отказом посреди работы.

Взамен вид прогона стал меткой. Метки создаются через API без всяких
дополнений, механизм чтения меток всё равно нужен для типа задачи, и
зависимость от состояния доски исчезает вовсе. Потеря невелика: видов
прогона ровно три, и выпадающий список им не нужен.

## Почему колонка равна состоянию

Рассматривались два способа.

**Крупные колонки плюс поле состояния.** Восемь колонок вместо
четырнадцати: «проработка» вбирает `design` и `audit`, «проверки» —
`benchmark`, `pr` и `review`. Точное состояние хранится отдельно.
Доска читается взглядом, помещается на телефон.

**Колонка на состояние.** Четырнадцать колонок, горизонтальная прокрутка,
зато состояние хранится ровно в одном месте.

Выбран второй, и вот чем решилось. При крупных колонках каждая смена
состояния — две записи: колонка и поле. Две записи не бывают атомарными,
а значит однажды разойдутся: обрыв между ними оставит карточку в колонке
«проверки» с полем `design`. Дальше начинается худшее: конвейер верит
полю, человек верит колонке, и доска врёт ровно тогда, когда на неё
смотрят — при разборе затыка.

Довод «четырнадцать колонок неудобны на телефоне» остаётся в силе,
и он настоящий. Но неудобная правда лучше удобной лжи, а прокрутка
лечится фильтром Trello по метке.

Проба показала приятное следствие: смена колонки и правка описания
делаются **одним** запросом `PUT /1/cards/{id}`. То есть переход
состояния вместе с обновлением машинных полей атомарен, и разойтись
внутри карточки нечему.

## Захват задачи

Это главное место, где переезд отбирает у конвейера опору.

Сейчас захват — отправка коммита с полем `owner` в `main`. Она надёжна
потому, что `git push` есть «сравни-и-запиши»: сервер отвергает отправку,
не ускоряющую ветку. Проигравшая машина узнаёт об этом отказом.

Trello такой операции не даёт вовсе. `PUT` перезаписывает значение молча,
а условной записи по версии в API нет. Две машины записали бы себя
по очереди, обе получили бы `200 OK`, и обе считали бы, что победили.

Рассмотрены три замены.

**Поле владельца с перечитыванием.** Записать себя, подождать, перечитать:
если там чужое имя — уступить. Отвергнуто. Это не блокировка, а гадание
о задержке сети: обе машины могут перечитать до записи другой и обе увидеть
себя. Ненадёжность здесь стоит двух рабочих деревьев и двух pull request
по одной задаче.

**Файл-замок в репозитории.** Оставить в git крошечный `manage/claims/<id>`.
Отвергнуто по смыслу изменения: бэклог уезжает из репозитория целиком,
а половинчатый переезд оставил бы владельца продукта с двумя местами,
куда надо смотреть.

**Аннотированный тег `claim-<id>`.** Был принят, реализован — и отвергнут
до того, как его успели подключить к циклу. Механизм рабочий: проба
показала, что вторая машина получает `! [rejected] (already exists)`,
потому что в аннотированный тег входят имя создателя и время, и объекты
у станций получаются разные. Заодно проба закрыла два соблазна: и ветка,
и простой тег отвечают второй машине `Everything up-to-date` с кодом ноль,
поскольку обе станции стоят на одном коммите.

Отвергнут он не за ненадёжность, а за неуместность. Бэклог уехал
на доску, а замок от него остался бы в репозитории; захват при этом
человеку не виден вовсе, и вдобавок появляется хозяйство, которое надо
чистить.

**Назначение исполнителя карточке.** Принято. Захват — это

```
POST /1/cards/{id}/idMembers   value=<участник доски>
```

Проба на живой доске:

| Операция                                   | Ответ Trello                             |
| ------------------------------------------ | ---------------------------------------- |
| первое назначение                          | `200`                                    |
| повторное назначение того же участника      | **`400 member is already on the card`**  |
| `PUT` карточки с полем `idMembers`          | `200`, перезаписывает молча              |
| назначение постороннего идентификатора      | `400 member not found`                   |

Вторая строка и есть «сравни-и-запиши». Третья объясняет, почему первым
заходом механизм был отвергнут: проверялась правка карточки, а она таким
свойством не обладает.

Выигрыш против тега двойной. Захват **виден на доске** — ради этого она
и заводилась; и в репозитории не остаётся ничего, что надо было бы
чистить.

**Цена — различение станций.** Участник доски один на все машины, потому
что токен один: назначить «станцию-1» и «станцию-2» нельзя. Имя станции
пишется в служебный блок следующим действием, и обрыв между назначением
и записью оставит карточку занятой неизвестно кем. Разбирает это сверка:
хозяином считается станция, у которой есть рабочее дерево задачи.
Различать станции по-настоящему можно было бы, заведя каждой свой аккаунт
Trello и пригласив в доску, — три ручных шага на станцию плюс отдельный
токен каждой.

**Захват спрашивается у хранилища.** Файловому бэклогу отдельный захват
не нужен вовсе: его роль исполняет отправка записи владельца в главную
ветку, которая либо проходит, либо отбивается. Поэтому исполнение зовёт
`io.acquire`, а что это значит — знает хранилище.

## Приоритет положением карточки

Числовое поле `priority` исчезает. Порядок задаётся положением карточки
в колонке, и это единственный способ его изменить.

Соблазн оставить число был: сортировка по нему привычна, а «горит»
и «когда-нибудь» проще выразить десяткой и девяноста. Но число
и положение — два представления одного порядка, и они разойдутся при
первом же перетаскивании карточки. Тогда владелец продукта поднимет
карточку вверх, ничего не произойдёт, и он потеряет доверие к доске
целиком.

Trello хранит положение дробным числом `pos` (проверено: меньшее значение
выше), так что сортировка достаётся конвейеру даром.

Правило «прогоны приоритетнее проработки и имплементации» остаётся
в коде: оно про тип задачи, а не про её место в очереди.

## Чем заменяется схема

`manage/schema.json` отвергал кривую задачу до того, как она попадала
в работу. Над карточкой схемы нет — её правит человек мышью.

Взамен проверка при чтении и метка «не разобрано». Требуется немного:
ровно одна метка типа, а для `run` — метка вида прогона и непустой раздел
ожидаемого результата. Всё остальное конвейер проставляет сам.

Причина пишется комментарием и называет недостающее. Метка снимается
сама, как только карточка исправлена, а комментарий остаётся: он часть
истории.

Проверка не останавливает очередь. Негодная карточка пропускается,
прочие работают — как и сейчас с негодным файлом задачи.

## Как конвейер отличает свои записи

Ответ владельца продукта — это комментарий без пометки конвейера,
появившийся после вопроса.

Тонкость, которую легко проглядеть: конвейер пишет комментарии **тем же
пользователем Trello**, что и человек, — токен-то один. Значит по автору
их не различить, и без пометки конвейер принял бы собственный вопрос
за ответ на него же и вернул бы задачу в работу, ничего не спросив.

Пометка — устойчивый префикс в начале текста комментария. Проба
подтвердила, что текст возвращается без изменений, включая эмодзи.

Отдельный пользователь Trello для конвейера решил бы это чище, но требует
второго аккаунта, приглашения на доску и второго токена — три ручных шага
ради того, что решается одним префиксом.

## Где живёт код

`plugins/pipeline/lib/io.mjs` — единственное место, где конвейер трогает
настоящий мир, и в его шапке прямо сказано, что решений там не
принимается. Это и есть точка подмены.

Хранилище бэклога выносится за интерфейс: методы чтения задач, записи
задачи, дозаписи журнала и чтения ответа получают вторую реализацию
поверх Trello. Счётная часть — `scan.mjs`, таблица переходов, раскладка
слотов — не меняется ни строкой и о Trello не знает.

Проверяемость сохраняется тем же приёмом, что и сейчас: сетевой слой
принимается доводом. Разбор карточки в задачу и сборка задачи в карточку
— чистые функции, они и покрываются тестами. Ходить в сеть в тестах
не придётся.

## Цена цикла

Измерено пробой на настоящей доске:

| Что                                     | Время  |
| --------------------------------------- | ------ |
| Чтение всех карточек с полями и метками  | 242 мс |
| Чтение комментариев всей доски           | 230 мс |
| Вся картина мира: четыре запроса разом   | 357 мс |
| То же пакетным чтением `/1/batch`        | 438 мс |
| Перенос карточки с правкой описания      | 395 мс |
| Создание карточки                        | 512 мс |

Полное чтение картины мира — **четыре** запроса: колонки, метки, карточки
и комментарии. Все четыре берутся пачкой на всю доску, а не по карточке,
и уходят разом, а не по очереди: по очереди они стоили бы секунды, разом
отвечают за 357 мс. Холостой цикл поэтому укладывается в требование
«холостой прогон обязан стоить секунды».

Пакетное чтение Trello (`/1/batch`) пробовалось и отвергнуто. Адреса
перечисляются в нём через запятую, а запятые есть и внутри параметров —
`fields=name,closed`; четыре запроса развалились на десять кусков,
половина из которых пустые. Выигрыша при этом никакого: пакет ответил
за 438 мс, то есть медленнее четвёрки разом.

Ограничения Trello — триста запросов на ключ и сто на токен за десять
секунд (по документации, делом не проверялось). Цикл раз в пять минут
тратит два-три запроса и в предел не упирается даже близко.

## Пределы длины

Описание и комментарий — ровно 16384 знака каждый; больше Trello
отвергает с `400 invalid value`. Проверено делом.

Описанию этого достаточно с большим запасом: машинный блок занимает
около четырёхсот знаков.

Журнальной записи — почти всегда достаточно, но не всегда: разбор
падения с куском лога переваливает легко. Поэтому запись, не влезающая
в предел, разбивается на несколько пронумерованных комментариев.
Усечение запрещено: обрезанный лог падения бесполезен ровно в том
случае, ради которого его и писали.

## Перенос существующих задач

Двадцать девять задач и двенадцать журналов переезжают одноразовым
скриптом: карточка на задачу, комментарий на каждую запись журнала,
колонка по состоянию, метки по типу.

Закрытые задачи переносятся в архив Trello, а не на доску: их
шестнадцать, и колонка `closed` из них была бы нечитаемой. Архив
при этом не забвение — номера архивных карточек считаются занятыми,
иначе идентификатор однажды достанется дважды.

Переезд делается **двумя** коммитами, а не одним. Сперва конвейер учится
работать от Trello и работает, пока файлы ещё лежат на месте; лишь потом,
убедившись делом, отдельным коммитом удаляются `manage/tasks/`,
`manage/journal/`, `manage/questions.md`, `manage/schema.json`
и `manage/board.html`. Обратный порядок оставил бы нас без бэклога
в случае, если что-то не заработает.

## Что делать с правилом 8

`CLAUDE.md` требует, чтобы заявка на проверку баланса ехала **тем же
pull request**, что и правка, которая её вызвала. Смысл требования —
атомарность: очередь пополняется ровно тогда, когда изменение попадает
в `main`, а не раньше и не позже.

Карточка Trello в pull request не едет физически. Атомарность
восстанавливается переносом момента: карточка прогона заводится
не при открытии pull request, а при его вливании — тем же действием
конвейера, что и вливание.

Полного равенства не выходит. Вливание и создание карточки — две
операции, и обрыв между ними оставит влитую правку без заказанного
прогона. Лечится сверкой: конвейер, вливший pull request, помечает это
в карточке задачи, и следующий цикл видит вливание без заказанного
прогона как незавершённое дело.

Формулировку правила придётся переписать. Молча сломанное правило хуже
переписанного: по нему всё ещё будут работать люди.

## Влияние на игру

Никакого. Изменение не трогает ни `packages/sim`, ни `apps/client`,
ни `apps/server`. Поведение при рассинхроне и переподключении, которого
требует правило проработки, здесь описывать нечего: изменение не касается
матча вовсе.
