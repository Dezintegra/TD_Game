# Задачи

Каждый пункт — отдельный коммит, отправляемый сразу. Каждый собирается
и проверяется сам по себе: следующего шага, который что-нибудь починит,
нет ни у одного.

Прогон арены изменению не нужен: правил игры, цен, дохода, силы юнита
и темпа оно не задевает вовсе — правятся два документа и один тест
на Node вне игрового ядра.

## 1. Сторож на покрытие команд вливания правилами разрешений

Завести в `supervisor/config/transitions.test.mjs` проверку: команды
`gh pr view`, `gh pr ready` и `gh pr merge` покрыты правилами
`stage-settings.json` в обеих оболочках — совпадают с приставкой хотя бы
одного правила `allow` и не совпадают с приставкой ни одного `deny`.

Мерка сверки — приставка команды, как в среде: у правила снимается обёртка
`Bash(...)` / `PowerShell(...)` и хвост `:*`, остаток сверяется с началом
команды.

Ставится первым, потому что ничего не ломает и ничего не требует: он
проверяет уже существующую настройку и должен зеленеть на ней сразу.

**Проверка:** `pnpm test:pipeline` зелёный. Проба на порчу: временно
заменить в `stage-settings.json` обе строки `gh pr:*` на `gh pr merge:*` —
сторож обязан покраснеть и назвать `gh pr ready` непокрытой; вернуть
строки на место, прогнать снова, убедиться, что зелено.

**После этого коммита** — открыть черновой pull request (`gh pr create
--draft --base main`), иначе проверки CI на последующие пуши в ветку
не запустятся вовсе.

## 2. Снятие чернового статуса в правилах этапа ревью

Правка `supervisor/skills/review.md`, три места:

- **шаг 2**: `gh pr view <pr> --json state,mergedAt` → добавить `isDraft`
  в перечень полей и сказать, зачем он читается здесь, а не позже: чтобы
  не ходить к сети дважды;
- **шаг 8**: перед `gh pr merge` встаёт подшаг «снять черновой статус» —
  `gh pr ready <pr>`, вызываемый только при истинном `isDraft`. Назвать
  и ответ, ради которого всё затеяно (`GraphQL: Pull Request is still
  a draft (mergePullRequest)`), и дату, когда он получен (03.09.2026,
  задача 0130): без этого следующий редактор скилла примет подшаг
  за перестраховку и уберёт;
- **шаг 9 либо тот же 8**: неудача `gh pr ready` — исход `failed`
  с текстом ответа, а не молчаливый переход к `gh pr merge`.

**Проверка:** `npx prettier --check supervisor/skills/review.md` зелёный;
`pnpm test:pipeline` зелёный (в `transitions.test.mjs` есть сторожа
на содержимое скиллов, и правка не должна их уронить). Глазами: подшаг
стоит внутри ветки «вливай», а не отдельным шагом до вердикта.

## 3. Запрет снимать черновик с изменения, уезжающего в доработку

В разделе «Чего делать нельзя» файла `supervisor/skills/review.md` завести
строку: черновой статус снимают, только решив вливать. Pull request,
возвращаемый в доработку, остаётся черновиком — черновик и есть внешний
признак незавершённости, видимый помимо конвейера.

Отдельным пунктом от задачи 2 потому, что это отдельная мысль и отдельный
сценарий спецификации: та задача учит снимать, эта — не снимать зря.
Откат ровно этого коммита оставляет работоспособный скилл.

**Проверка:** `npx prettier --check supervisor/skills/review.md` зелёный;
`pnpm test:pipeline` зелёный. Глазами: запрет не противоречит подшагу
из задачи 2, а очерчивает его границу.

## 4. Фраза о черновике в правиле 5 CLAUDE.md

В правило 5 (`Из дополнительного дерева работа попадает в main через pull
request`) добавить, что перед вливанием с pull request снимают черновой
статус, иначе слияние отбивается ответом о черновике. Правило 5 — то самое
место, где черновик заводится; человек, вливающий изменение руками,
упирается в ту же стену.

Идёт последним: памятка описывает уже сложившийся порядок, а не
предвосхищает его.

**Проверка:** `npx prettier --check CLAUDE.md` зелёный. Глазами: фраза
стоит рядом с `gh pr create --draft` и с тремя условиями вливания,
а не в конце правила отдельным абзацем.
