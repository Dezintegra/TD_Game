# Ревью снимает с pull request черновой статус перед вливанием

## Зачем

Правило 5 `CLAUDE.md` предписывает открывать pull request **черновиком**
сразу после первого коммита, и предписывает не из вежливости: пока pull
request не открыт, событие `pull_request` не наступает и проверки CI
на пуши в ветку не запускаются вовсе. Скилл имплементации это исполняет —
`gh pr create --draft` стоит в нём прямым текстом.

Снимать черновой статус после этого не велено нигде. Скилл ревью
(`supervisor/skills/review.md`) в шаге 8 зовёт `gh pr merge` на pull
request, который так и остался черновиком, а GitHub черновик вливать
отказывается:

```
GraphQL: Pull Request is still a draft (mergePullRequest)
```

Поймано 03.09.2026 на задаче 0130: вливание прошло только после отдельной
команды `gh pr ready 119`, набранной вручную помимо скилла.

Беда не в одном потерянном вызове. Сессия ревью к этому месту приходит
с вынесенным вердиктом: проверки зелёные, замечаний нет, конфликтов нет.
Отказ вливания она видит на ровном месте, объяснения ему в своём же скилле
не находит и по правилу шага 9 обязана записать исход `failed` — «вливание
не удалось по иной причине». Задача уходит в разбор при полностью готовой
и одобренной работе. Это худший вид потери: не сломанный код, а верный код,
не доехавший до `main`.

Вторая половина задачи — проверить, что `gh pr ready` вообще проходит
правила разрешений. Сегодня он прошёл, но прошёл **попутно**: его накрывает
широкое `gh pr:*`. Именно так и выглядит везение, которое однажды кончается:
достаточно кому-нибудь сузить правило до перечня подкоманд, и ревью встанет
на команде, которой в перечне не окажется, — молча, отказом, без человека
рядом.

## Что меняется

**`supervisor/skills/review.md`:**

- шаг 2 (проверка «не влито ли уже») начинает читать заодно `isDraft` —
  одним и тем же вызовом `gh pr view`, лишнего обращения к сети не
  добавляется;
- шаг 8 (вливание) получает первым подшагом снятие чернового статуса:
  `gh pr ready <pr>`, и только затем `gh pr merge`. Порядок именно такой
  и обоснован в `design.md`;
- в перечне «чего делать нельзя» появляется строка о том, что черновой
  статус снимают **только** решив вливать: pull request, уезжающий
  в доработку, остаётся черновиком.

**`CLAUDE.md`, правило 5** — одна фраза о том, что перед вливанием
с pull request снимают черновой статус. Правило 5 и есть то место, где
черновик заводится и где описано вливание; человек, вливающий изменение
руками, упирается в ту же стену, что и конвейер.

**`supervisor/config/transitions.test.mjs`** — сторож на то, что команды
ревью, ведущие к вливанию (`gh pr ready`, `gh pr merge`, `gh pr view`),
покрыты правилами разрешений в обеих оболочках и не перекрыты ни одним
запретом. Сторож нужен ровно затем, чтобы покрытие перестало быть
везением: сегодня оно держится на широком `gh pr:*`, а сузить это правило
стоит одной правки.

Сам файл `supervisor/config/stage-settings.json` **не меняется**: разбор
показал, что `Bash(gh pr:*)` и `PowerShell(gh pr:*)` уже покрывают
`gh pr ready`, а ни один запрет с ним не пересекается. Новых разрешений
задача не требует — требует сторожа на существующие.

## Non-goals

- **Открытие pull request сразу непроектным (не черновиком) не
  рассматривается.** Черновик — не помеха, а способ получить проверки
  на каждый атомарный коммит (правило 5). Лечим последний шаг, а не отменяем
  первый.
- **Скилл имплементации не переписывается.** `gh pr create --draft`
  остаётся как есть.
- **Правила разрешений не расширяются и не сужаются.** Ни одной строки
  в `stage-settings.json`: покрытие есть, недостаёт только сторожа.
  В частности, широкое `gh pr:*` **не** дробится на перечень подкоманд —
  это была бы отдельная работа с отдельным разбором, а сегодняшняя польза
  от неё нулевая.
- **Расхождение шага 8 с самим собой не чинится.** В образце команды стоит
  `gh pr merge <pr> --rebase`, а в пояснении под ним сказано, что
  перевыкладка в репозитории запрещена и вливать надо коммитом слияния
  (`--merge`). Это отдельный дефект того же шага, замеченный по дороге;
  он уедет заявкой в отчёт, а не правкой здесь: смешав два исправления
  в одном изменении, мы лишим оба отдельной проверки.
- **Супервизор не учат вливать самостоятельно.** Вливает сессия ревью,
  и это осознанное устройство: код, вливающий pull request без прочтения
  дифа, снял бы последний предохранитель.
- **Задача 0132 (близнецы дельт в одной способности) здесь не решается.**

## Влияние на отзывчивость интерфейса и на сетевой трафик

**Влияния нет ни на то, ни на другое, и вывод не умозрительный.** Изменение
трогает три файла: правила этапа (`supervisor/skills/review.md`), памятку
проекта (`CLAUDE.md`) и сторожевой тест (`supervisor/config/transitions.test.mjs`).
Каталог `supervisor/` не входит ни в один пакет монорепозитория: он
не собирается вместе с клиентом и сервером, не импортируется из `apps/`
и `packages/` и в браузер не попадает ни байтом. `CLAUDE.md` — документ.
Кадр отрисовки, объём игровых сообщений и раскладка байтов протокола
не задеты; `PROTOCOL_VERSION` расти не должен.

Единственный прирост сетевого обмена — один вызов `gh pr ready` к GitHub
на каждое вливание, и то лишь когда pull request действительно черновик.
Вызов к чужому API, а не к игровому серверу; на игрока не влияет никак.

## Зависимости

Дельты пишутся на две способности, и обеих в `openspec/specs/` ещё нет —
их заводят незаархивированные изменения:

- `dev-pipeline-worker` заводит `agent-backlog-pipeline` (там же лежит
  требование «Ревью вливает pull request при трёх выполненных условиях»,
  рядом с которым встаёт наше);
- `dev-pipeline-supervisor` заводит `supervise-the-pipeline`.

Поэтому **это изменение архивируется ПОСЛЕ `agent-backlog-pipeline`
и ПОСЛЕ `supervise-the-pipeline`**. Заархивировав раньше, получим
требования, висящие без основы: `openspec validate` этого не ловит,
а падает архивация — через месяц и не у того, кто писал.
