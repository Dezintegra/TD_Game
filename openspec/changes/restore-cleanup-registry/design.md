## Context

Задача 0230 исправляет потерю записи при сохранённой регистрации дерева в Git. На базе 648754b `reconcile.mjs:118` отклоняет `cleanup` через `NEEDS_WORKTREE`, а строка 140 использует тот же перечень для `finish-claim`. В `transitions.mjs:215` уборки в перечне нет, что верно для создания дерева.

`repair.mjs` уже умеет восстанавливать запись с текущим этапом задачи и относительным путём через `worktreePathFor`. В `supervise.mjs:646–651` починки исполняются перед действиями, а `execute.mjs:1006` читает запись заново через IO. Поэтому достаточно разрешить существующую починку в нужном состоянии. При отсутствии записи `mayCleanup` выдаёт `skip`, после которого исполнитель может перейти к закрытию. При восстановленной записи работают проверки PR/собственных коммитов, а `swept.finished === false` уже удерживает задачу.

## Goals / Non-Goals

**Goals:** восстановление потерянной записи зарегистрированного дерева в `cleanup`; отсутствие повторного создания; сохранение принадлежности и предохранителей штатной уборки; регрессия на всей цепочке.

**Non-Goals:** перечислены в proposal. В частности, не меняем удаление незарегистрированных остатков каталогов, общее поведение `drop-entry`, `closed` и мерки безопасности уборки. Не вводим новый формат реестра или маршруты задачи.

## Decisions

### Отделить принятие существующего дерева от его создания

В `reconcile.mjs` для первой ветви использовать отдельно названный локальный предикат допустимости восстановления: текущее множество `NEEDS_WORKTREE` плюс `cleanup`. Для третьей ветви оставить `NEEDS_WORKTREE` без изменений. Существующие проверки строгой ветки, наличия задачи и чужого владельца выполняются до разрешения восстановления. Основное дерево по-прежнему исключает `parseWorktrees`.

Альтернатива «добавить cleanup в NEEDS_WORKTREE» отвергнута: следующий цикл создавал бы уже удалённое дерево через `finish-claim`, а прочие потребители перечня тоже изменили бы поведение. Отдельная копия всего перечня состояний отвергнута: она разойдётся с исходным. Предикат выводится из него и явно добавляет только случай существующего дерева.

### Восстановление не заменяет разрешение на удаление

Использовать `repairWorld` и существующий `register` без нового обработчика. Он записывает `stage: cleanup`, ветку, путь и служебные поля, не создаёт дерево и не меняет владельца. Поле `sessionTitle` остаётся метаданными; запуск сессии оно не означает.

`mayCleanup`, `cleanup` и `cleanupTask` сохраняют свои решения: PR проверяется даже при нуле собственных коммитов; без PR ноль разрешает уборку, положительное число или неизвестность запрещают её; недоступность PR даёт ожидание. Восстановленная запись должна читаться тем же IO до решения об уборке.

Альтернатива «чинить только skip внутри mayCleanup» отвергнута: у чистой функции нет инвентаризации Git, и она не может различить потерянную запись и отсутствие дерева. Прямое удаление из сверки отвергнуто, поскольку обходит проверку влитости и штатный переходник удаления.

### Проверить реальную цепочку на изменяемом состоянии

В `execute.test.mjs` использовать пустой изменяемый реестр: передать результат реального `reconcile` в реальный `repairWorld`, затем вызвать `execute` для `cleanup` с тем же IO. Подделывать только внешние эффекты, сохраняя действующие `mayCleanup` и `cleanup`. Проверить фактическое появление записи до удаления, её поля, обращения к PR/собственным коммитам, вызовы удаления и конечное состояние задачи.

Таблица проверок:

| Вход после потери записи | Наблюдаемый результат |
| --- | --- |
| Своя задача, PR влит | adopt, штатное удаление, closed; addWorktree не вызывался |
| Нет владельца | adopt без изменения owner |
| Дерева нет | нет adopt и finish-claim; addWorktree не вызывался |
| Чужой владелец | report-orphan, реестр пуст, починка ничего не удаляет |
| Основное/ручное дерево, нет задачи или статус closed | прежние исключения сохранены |
| PR открыт / unknown | остановка через существующий halt / ожидание, без удаления и closed |
| Без PR, ownCommits 0 / больше 0 / null | успешная уборка / остановка / остановка |
| Отказ удаления дерева | запись и cleanup сохраняются; повтор с успехом закрывает задачу |
| Отказ удаления локальной или удалённой ветки | finished false, запись сохраняется, closed не записывается |

Повтор после отказа дерева моделирует дерево, всё ещё зарегистрированное в Git: это граница данной задачи. Отдельные регрессии удаления незарегистрированных каталогов уже принадлежат `finish-worktree-cleanup`. Проверки из `remove-worktree.test.mjs` сохраняются: путь только внутри штатного каталога, отсутствие перенаправления родителя и символической ссылки, подтверждение отсутствия регистрации перед рекурсивным удалением остатка. Новая логика не должна добавлять обходной вызов удаления.

Альтернатива с заранее заполненной записью отвергнута: такие тесты уже есть и не ловят исходную ошибку. Запуск настоящего супервизора и удаление рабочих деревьев в проверке не нужны; IO позволяет проверить эффекты без доски и чужих ресурсов.

### Спецификация устойчивости и архитектурные границы

ADDED-требование относится к существующей `pipeline-supervision-resilience`. Общие требования реестра в открытом `agent-backlog-pipeline` не переписываются, поскольку в основной спецификации `dev-pipeline-orchestrator` их ещё нет. Порядок архивации и пересечения описаны в proposal.

Игровые пакеты не затрагиваются. Рассинхрон, реконнект, `PROTOCOL_VERSION` и эталоны детерминизма не меняются. Новых обращений к `Math.random`, `Date.now` и дробного состояния мира не появляется; запреты ядра сохраняются. Арена и замеры кадров не нужны.

## Risks / Trade-offs

- Поддельный IO со статической `registryEntry` скроет эффект восстановления → чтение и запись используют одну Map, а тест проверяет пустое начальное состояние и появление записи.
- Слишком широкое разрешение присвоит чужую работу → отрицательные сценарии фиксируют owner, строгую ветку, основное дерево, отсутствие задачи и closed.
- Восстановление пути по `worktreePathFor` и безопасное удаление уже заданы текущим IO → не расширять допустимые пути и не менять переходник удаления в этом PR.
- Общее удаление записи без Git-дерева и восстановление произвольных повреждений реестра остаются за границами этого исправления; оно гарантирует названный сценарий потери записи зарегистрированного дерева.

## Migration Plan

После вливания супервизор получает новый код штатным обновлением. Следующая сверка восстановит подходящие потерянные записи без ручной миграции; уже восстановленные записи повторно не создаются. Откат коммита возвращает прежнюю допустимость восстановления, формат записей остаётся совместимым. Реальные деревья в ходе реализации вручную не убираются.
