# Задачи

Изменение не заводит кода: правится текст одного скилла. Поэтому шагов
два, и первый же из них — цельный коммит, после которого открывается
черновой pull request.

**Блоки опознаются содержимым команд, а не номерами строк.** Номера ниже
даны подсказкой и сняты с базы этой ветки (коммит `8d2e5f8`). В `origin/main`
они уже другие: вставки задачи 0171 сдвинули два из трёх ограждений
с 178 и 195 на 203 и 244. Шаг, писанный по номерам, на свежем дереве
попал бы в чужой текст.

## 1. Разметить командные блоки скилла проработки как `powershell`

- [ ] В `supervisor/skills/design.md` дописать `powershell` к трём
      открывающим ограждениям, опознав их по содержимому блока:
  - блок с `openspec new change <имя> --description …` (в базе ветки
    строка 88);
  - блок с `openspec validate …` и `openspec status --change <имя>`
    (в базе ветки строка 178; в `origin/main` — 203, и тело там уже
    другое: `openspec validate <имя> --strict`);
  - блок с `git add -- …`, `git commit -m … -m …` и `git push -u origin
    HEAD` (в базе ветки строка 195, в `origin/main` — 244).
- [ ] Закрывающие ограждения не трогать: языка у них не бывает.
- [ ] Тела всех трёх блоков оставить **дословно прежними**. Это проверено
      при проработке по всем трём формам, которые сторожит
      `one-shell-for-stages`: голого `@{` нет, строки с обратной косой
      на конце нет, приставки `ИМЯ=значение` нет. Переписывание тел здесь
      было бы правкой не по задаче и вошло бы в спор с pull request 126.
- [ ] Отступ ограждений сохранить как есть: три пробела у блока в пункте
      6 и четыре у блоков в пунктах 11 и 12. Блоки лежат внутри пунктов
      перечня, и сдвиг к началу строки вынес бы их из пункта.
- [ ] **По условию.** Если в дереве найдётся блок с телом
      `✗ [ERROR] file: Change must have at least one delta. No deltas
      found.` — в `supervisor/skills/design.md`, в `supervisor/skills/audit.md`
      или в обоих, — разметить его `text`. В базе этой ветки таких блоков
      нет вовсе, и тогда пункт исполняется вхолостую; они появляются, лишь
      если дерево заведено от `main` свежее коммита `eeb6c68`. Разметка
      именно `text`, а не `powershell`: в блоке лежит вывод программы,
      а не команда, и сторож единственной оболочки, проверяющий тела
      командных блоков, споткнулся бы о строку, начинающуюся с `✗`.
- [ ] Никаких других файлов в этом коммите. В частности, разметку `bash`
      в `audit.md`, `implement.md`, `review.md`, `benchmark.md`
      и `revise.md` не трогать: её переводит pull request 126, и вторая
      рука по тем же строкам даёт конфликт.
- [ ] Открыть черновой pull request сразу после этого коммита: до его
      появления пуши в ветку не запускают проверок CI вовсе.

**Проверка.** Разобрать ограждения `supervisor/skills/design.md` попарно —
первое открывает блок, следующее закрывает — и убедиться, что **безъязыких
открывающих ограждений не осталось ни одного**. Проверка сформулирована
так нарочно: она верна и на базе ветки, и на свежем дереве, тогда как
счёт ограждений от базы зависит.

Счёт для базы ветки, если проверять поиском по выражению `^\s*```\s*$`:
до правки находится **семь** ограждений (88, 90, 178, 181, 195, 199, 354),
после правки — **четыре** (90, 181, 199, 354), и все четыре закрывающие.
Четвёртое, 354, закрывает блок-образец отчёта, открытый разметкой
` ```json ` на строке 341: считать его недоделкой не надо.

Дополнительно: `npx prettier --check supervisor/skills/design.md` —
каталог `supervisor/` из проверки формата не исключён, а `pnpm format:check`
стоит в CI первым.

## 2. Дождаться зелёного CI на pull request

- [ ] `gh pr checks <номер> --watch` — дождаться, пока проверки добегут.
      Задача не сделана, пока GitHub не сказал «зелено».
- [ ] Красный прогон — прочитать `gh run view --job <id> --log-failed`,
      починить отдельным атомарным коммитом, отправить, дождаться снова.
- [ ] Если GitHub сообщит о **конфликте с `main`** по `design.md`,
      разрешать его этап не вправе: `git merge` не покрыт ни одним
      правилом разрешений. Назвать конфликт в отчёте и оставить задачу
      ревью. Порядок разрешения назван в `design.md` изменения: обе правки
      берутся разом — тело команды из `main`, разметка `powershell` наша.
- [ ] Черновой статус **не снимать**: его снимает ревью первым подшагом
      вливания.

**Проверка:** все задачи проверок на pull request зелёные.
