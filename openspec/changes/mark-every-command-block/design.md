# Проектное решение

## Правка ложится своей веткой, а не в pull request 126

Задача советует внести правку тем же pull request 126, пока он открыт.
Так не делается, и вот почему.

Pull request 126 ведёт ветка `worktree-0156-svesti-komandy-etapov-k-odnoy-obolochke-`,
и задача 0156 стоит в состоянии `pr` — то есть её вот-вот возьмёт ревью
и, возможно, вольёт. Сессия-исполнитель в чужую ветку не коммитит:
конвейер отдал ей одно дерево и одну ветку, а правка чужой ветки посреди
её ревью означает, что проверенное и влитое разойдутся.

Проверено, что своя ветка обойдётся без конфликта. Pull request 126
трогает `design.md` единственным местом — вставляет раздел «Оболочка
команд» после строки 52 и ни одного из трёх ограждений (88, 178, 195)
не касается. Наша правка меняет ровно эти три строки. Куски расходятся
на три десятка строк, и слияние сойдётся само.

**Отвергнутый вариант — дождаться вливания 126 и лечь поверх.** Ждать
пришлось бы неопределённо долго, а дерево уже заведено от `origin/main`
и обновлять базу этап не вправе: `git merge origin/main` не покрыт
ни одним правилом разрешений (задача 0172). То есть ожидание не приблизило
бы правку к свежей базе, а лишь отсрочило её.

## Сторож заводится отдельным файлом

Дыра, сквозь которую недосмотр прошёл, лежит в `shell.test.mjs`
из pull request 126. Разбор ограждений там общий, а вот суд — нет:

```
bashMarkedBlocks  →  оставляет блоки, чей lang входит в BASH_LANGS
bashBodyForms     →  смотрит тела блоков, чей lang входит в COMMAND_LANGS
```

Безъязыкий блок даёт `lang === ''`, и в оба перечня не входит. Значит
он проходит обе проверки молча — ни разметка не покрашена, ни тело
не осмотрено.

Правильное лечение — дописать третью проверку в тот же файл. Так
и не делается, но по причине временной, а не по существу:
`supervisor/config/shell.test.mjs` в нашей базе (`origin/main`, коммит
`8d2e5f8`) **не существует**. Он приезжает вливанием pull request 126.
Шаг `tasks.md`, правящий несуществующий файл, имплементация исполнить
не сможет, а завести его заново значит гарантировать конфликт на всю
длину файла.

Поэтому сторож — отдельный файл `supervisor/config/skill-blocks.test.mjs`.
Ровно тем же доводом pull request 126 объясняет, почему `shell.test.mjs`
заведён отдельно, а не дописан в `transitions.test.mjs`: тот переписывался
изменением `hold-uncovered-stages`, и общий файл дал бы конфликт
при вливании.

Цена решения названа честно: разбор ограждений окажется в двух файлах.
Сводить их сейчас нечем — обе ветки ещё не в `main`. Заявка на сведение
подана отчётом этапа, чтобы долг не растворился.

**Отвергнутый вариант — не заводить сторожа вовсе, обойтись разовой
правкой и ручной сверкой остальных скиллов.** Ручная сверка отвечает
на вопрос «как сегодня», а завтра в скилл допишут блок без разметки,
и никто этого не заметит: сторож единственной оболочки, как показано
выше, безъязыкий блок пропускает. Разовая правка вылечила бы случай,
оставив причину.

## Что именно проверяет сторож

Правило простое и в одну строку: **у скилла этапа нет ни одного блока
кода без разметки**.

Отличать командный блок от некомандного правило не пытается, и это
осознанно. У безъязыкого блока нет языка — значит нет и признака,
по которому его можно было бы отнести к командным. Всякая попытка угадать
по телу («похоже на `git`») даёт сторожа, спорящего с человеком о том,
команда перед ним или нет.

Отсюда и охват: `json` проходит, `powershell` проходит, `bash` проходит
(о нём судит сторож единственной оболочки), пустое ограждение — нет.

Разбор ограждений повторяет разбор из `shell.test.mjs` в двух местах,
и оба важны:

- **ограждения считаются попарно** — первое открывает, следующее
  закрывает. Иначе закрывающее ограждение, у которого языка не бывает
  никогда, покрасит каждый скилл разом;
- **отступ у ограждения свой** — блоки скиллов лежат внутри пунктов
  перечня и с начала строки не начинаются. Привязка к началу строки
  не нашла бы ни одного блока, и сторож зеленел бы всегда.

Скиллы берутся по перечню `NEEDS_SESSION` из `supervisor/config/transitions.mjs`,
а не подбором файлов из каталога: перечень — это объявленный состав
этапов с сессией, и скилл, выпавший из него, сторожу и не подсуден.
Сегодня перечень и каталог совпадают: десять этапов, десять файлов.

К сторожу заводится **проба на порчу** — наведённый безъязыкий блок
обязан красить его, и это проверяется набором, а не руками. Сторож,
не краснеющий на сломанном скилле, — украшение. Обратная проба тоже
обязательна: блок `json` сторожа не тревожит.

## Тела трёх блоков остаются прежними

Смены разметки обычно мало: тело, написанное по-башевски, PowerShell
либо не разберёт, либо поймёт иначе, и провал выйдет молчаливым — ошибкой
разбора вместо кода 127. Здесь этого нет, и проверено это по всем трём
формам, которые сторожит pull request 126:

| Форма                              | Есть ли в трёх блоках `design.md` |
| ---------------------------------- | --------------------------------- |
| голый `@{`                         | нет                               |
| строка с обратной косой на конце   | нет                               |
| приставка `ИМЯ=значение`           | нет                               |

Все три команды — `openspec new change …`, `openspec validate …`
со `openspec status …`, `git add -- …` с `git commit -m … -m …`
и `git push -u origin HEAD` — PowerShell разбирает как есть. Значит после
вливания обеих веток `shell.test.mjs` останется зелёным и на `design.md`.

## Чего это решение не задевает

- **Рассинхрон и переподключение** — не задевает: правка целиком лежит
  в тексте скиллов и в наборе тестов конвейера, а не в матче.
- **Эталоны детерминизма** — не задевает: `packages/sim` не тронут
  ни одной строкой, правила игры не меняются.
- **`PROTOCOL_VERSION`** — не задевает: раскладка байтов протокола
  не меняется.
- **Запреты ядра** (`Math.random`, `Date.now`, числа с плавающей точкой
  в состоянии мира) — к решению неприменимы: новый код это тест
  на Vitest в `supervisor/`, он читает файлы и не входит в состояние мира
  вовсе.
