# Разметка есть у каждого командного блока скилла проработки

## Зачем

Скилл проработки `supervisor/skills/design.md` показывает сессии три
командных блока — `openspec new change`, `openspec validate` со
`openspec status` и `git add`/`git commit`/`git push`, — и ни один из них
не несёт разметки языка вовсе.

Изменение `one-shell-for-stages` (задача 0156, pull request 126) заводит
в этот же файл раздел «Оболочка команд» со словами: «Разметка `powershell`
у командных блоков стоит не для красоты: она — единственное, по чему
ты выбираешь оболочку». Сами блоки при этом остаются безъязыкими. Выходит
скилл, который велит выбирать оболочку по разметке и сам её не даёт,
а сессия выбирает буквально: 03.09.2026 имплементация задачи 0149 взяла
по разметке Git Bash и получила код 127 на `pnpm install`
и `cannot spawn sh` на `git push`. Оба провала пришли молча, обычным
ненулевым кодом, и стоили этапу следа.

Молчаливым остаётся и сам недосмотр. Сторож `supervisor/config/shell.test.mjs`
из того же pull request 126 считает виновными блоки, чья разметка входит
в `BASH_LANGS`, а тела проверяет лишь у блоков из `COMMAND_LANGS`. Блок
без разметки не попадает ни в один из двух перечней: он проходит обе
проверки, ничего о себе не сообщив. Поэтому сценарий «Сегодняшние скиллы
проходят» на ветке pull request 126 зелёный, хотя утверждение «все
командные блоки размечены `powershell`» для `design.md` неверно.

## Сверка десяти скиллов

Сверка снята по `origin/main` (коммит `eeb6c68`) 03.09.2026 попарным
разбором ограждений: первое открывает блок, следующее закрывает.
Безъязыкие **открывающие** ограждения есть ровно в двух скиллах:

| Скилл       | Строка | Что в блоке                              | Командный |
| ----------- | ------ | ---------------------------------------- | --------- |
| `design.md` | 88     | `openspec new change`                    | да        |
| `design.md` | 203    | `openspec validate` и `openspec status`  | да        |
| `design.md` | 218    | вывод валидатора `✗ [ERROR] file: …`     | **нет**   |
| `design.md` | 244    | `git add`, `git commit`, `git push`      | да        |
| `audit.md`  | 97     | вывод валидатора `✗ [ERROR] file: …`     | **нет**   |

Остальные восемь скиллов чисты: `deploy.md` показывает команды
как `powershell`, `benchmark.md`, `implement.md`, `review.md` и `revise.md` —
как `bash` (их переводит pull request 126), `triage.md`, `interpret.md`
и `postmortem.md` содержат только образцы отчётов разметкой `json`.

Два блока с выводом валидатора — не команды, а образцы того, что печатает
программа. Они приехали в `main` вместе с задачей 0171
(`admit-changes-without-deltas`, коммиты `ea51669`…`eeb6c68`), и постановка
этой задачи их не касается: она говорит о **командных** блоках.

## Что меняется

Три командных блока `supervisor/skills/design.md` получают разметку
`powershell`. Тела блоков остаются прежними: ни голого `@{`, ни строки
с обратной косой на конце, ни приставки `ИМЯ=значение` в них нет, — то есть
все три команды разбираются PowerShell как есть.

Больше не меняется ничего. В частности, **сторож на безъязыкий блок здесь
не заводится**: причина разобрана в `design.md` и коротко — в не-целях.
Заявка на него подана отчётом этапа.

## Non-goals

- **Не заводим сторожа на безъязыкий блок в этой ветке.** Он был бы
  заведомо красным на собственном pull request и неисправимо: два блока
  с выводом валидатора (`design.md` 218 и `audit.md` 97) пришли в `main`
  с задачей 0171 уже после того, как ветка ответвилась, в базе ветки их
  нет, а обновить базу этап не вправе. Разбор — в `design.md`, раздел
  «Почему сторож не заводится здесь». Сторож нужен и заводится отдельной
  задачей от свежей базы; заявка в отчёте.

- **Не правим сам pull request 126.** Он ведётся другой веткой и стоит
  в состоянии `pr`, то есть может вливаться прямо сейчас; чужую ветку
  сессия-исполнитель не трогает.

- **Не переводим на `powershell` командные блоки остальных скиллов.**
  Разметка `bash` в `audit.md`, `implement.md`, `review.md`,
  `benchmark.md` и `revise.md` — предмет pull request 126, и трогать её
  второй веткой значит гарантировать конфликт по каждой строке.

- **Не размечаем два блока с выводом валидатора**, если их не окажется
  в дереве. Они не командные, постановка задачи их не требует, а в базе
  ветки их нет вовсе. Шаг `tasks.md` размечает их `text` по условию —
  на случай, если имплементация получит дерево от свежего `main`.

- **Не трогаем `supervisor/README.md` и общие памятки проекта.**
  Их читает человек, оболочку он выбирает сам, и примеры разметкой `bash`
  там законны.

## Влияние на отзывчивость интерфейса и на сетевой трафик

Влияния нет ни на то, ни на другое. Изменение целиком лежит в тексте
одного скилла конвейера. Ни один файл `apps/client`, `apps/server`,
`packages/sim`, `packages/protocol` не затронут: в игру не уезжает
ни строки, отрисовка и сетевой обмен остаются прежними побайтно. Кода
изменение не заводит вовсе.

## Почему дельты нет

Правка приводит единичный текст в согласие с тем, что уже решено:
три ограждения получают разметку, которой требует уже написанное правило.
Ни одного нового правила она не вводит. Проверка по признаку из скилла
проработки — «после правки ни одно требование в `openspec/specs/`
и ни одна открытая дельта не читаются иначе, чем до неё» — идёт
по каждому требованию, которого правка касается:

- **`openspec/specs/` не касается вовсе.** Способности `dev-pipeline-worker`
  там нет: сверено по `origin/main`, в каталоге тридцать пять способностей,
  и все они об игре. Требования о конвейере живут пока только в открытых
  дельтах. Трогать в основе нечего.

- **«Скилл этапа называет оболочку своих команд»** (открытая дельта
  `one-shell-for-stages`) — читается ровно так же. Требование велит
  командным блокам скиллов нести разметку `powershell`; наша правка
  не меняет ни его буквы, ни охвата, а лишь приводит `design.md`
  в состояние, которого оно требует. Было требование нарушено — стало
  соблюдено; сам текст требования неподвижен.

- **«Проработка ведётся через OpenSpec»** и прочие требования о работе
  проработки (открытые дельты `agent-backlog-pipeline`,
  `admit-changes-without-deltas`) — не читаются иначе. Они говорят,
  что сессия делает, а не какой разметкой это набрано в скилле.

- **Требований о наличии разметки не существует ни одного** — ни в основе,
  ни в открытых дельтах. Завести такое требование здесь означало бы
  пообещать проекту проверку, которой в этой ветке не будет: сторож,
  как сказано выше, заводится отдельной задачей. Требование без сторожа
  уехало бы в `openspec/specs/` навсегда и осталось бы там ненаблюдаемым.

## Порядок архивации

Изменение бездельтовое, поэтому архивируется ключом `--skip-specs`
и ничьей очереди не занимает: ложиться поверх отсутствующей основы ему
нечем.

Зависимости от `one-shell-for-stages` нет. Правка полезна и до его
вливания — сессия выбирает оболочку по разметке в любом случае, —
и после: его требование застаёт `design.md` уже приведённым в порядок.
