# Команда, выписанная в `tasks.md`, пишется формой, которую этап сможет исполнить

## Зачем

Шаг 2 файла `openspec/changes/point-the-form-note-at-a-live-rule/tasks.md`
(строка 24) предписывает:

> `git fetch origin`, затем `git merge origin/main` в своей ветке.

Первая команда покрыта правилом, вторая — нет. Правила разрешений
сверяются с **приставкой** команды, а на `git` в
`supervisor/config/stage-settings.json` стоят в `allow` тринадцать правил
для PowerShell: `git -C:*`, `git --no-pager:*`, `git status:*`,
`git log:*`, `git diff:*`, `git add:*`, `git commit:*`, `git push:*`,
`git fetch:*`, `git rev-list:*`, `git rev-parse:*`, `git worktree:*`,
`git branch:*`. В Bash их четырнадцать — те же тринадцать и вдобавок
`git switch:*` (строка 63 файла); этапы работают в PowerShell, поэтому
счёт для них тринадцать. Правила `git merge:*` среди них нет ни в одной
оболочке, ни в `allow`, ни в `deny`.

При этом форма с `-C` покрыта: `git -C <дерево> merge origin/main`
попадает под `git -C:*` — приставка совпадает, а запреты закрывают
из формы с `-C` только `push --force`, `reset --hard` и `stash`. Это же
установила закрытая заметка 0180: команда не непокрыта вообще, непокрыта
её **голая** форма.

Чем это плохо. Отказ проверки разрешений в автономной сессии не ждёт
человека, а возвращается сессии ответом на вызов. Дальше исходов два,
и оба плохи: сессия либо исполняет шаг по-своему — голым `git pull`,
склейкой с `cd`, ещё одной непокрытой формой, — либо считает базу
подтянутой и идёт дальше. Проверка самого шага
(`git rev-list --count HEAD..origin/main` отвечает `0`) второй исход
поймала бы, но лишь если сессия её прогонит, а покрытой замены слиянию
в тексте шага нет: назвать её сессии неоткуда. Это ровно тот вид беды,
который правилами не ловится и в отчёте выглядит успехом.

Причина не в невнимательности написавшей сессии. Скиллы этапов держат
форму с `-C` **везде** — сорок с лишним команд в `audit.md`, `deploy.md`,
`implement.md`, `review.md`, `revise.md`, включая дословное
`git -C <дерево> merge origin/main` в шаге выкладки. А `supervisor/skills/design.md`,
которым пишется `tasks.md`, о форме не говорит ни слова: он объясняет,
почему нельзя склеивать `cd` с командой, и на этом останавливается.
Сессия проработки пишет команду так, как её пишут в памятках проекта, —
голой, — и передаёт её этапу, которому голая форма недоступна.

Сегодня не горит: шаг остался неотмеченным, а изменение
`point-the-form-note-at-a-live-rule` уже дошло до выкладки. Горит завтра:
текст остаётся образцом для следующих проработок, а повтор стоит
сожжённого этапа.

## Что меняется

**`supervisor/skills/design.md`, шаг 10 (`tasks.md`)** получает пункт
о форме команд. Смысл пункта:

- команда, выписанная в `tasks.md`, пишется той же формой, что и команды
  скиллов, — `git -C <дерево> …`;
- причина названа двумя половинами, потому что каждая по отдельности
  оставляет лазейку: заходить в каталог отдельным звеном цепочки этапу
  запрещено (об этом скилл уже говорит), а голая приставка покрыта
  не у всякой подкоманды — `git merge` не покрыт ни одним правилом,
  тогда как `git -C:*` покрывает любую подкоманду разом;
- назван источник правды — `supervisor/config/stage-settings.json`:
  перечень покрытых команд живёт там, а не в памяти пишущей сессии.

**`supervisor/config/transitions.test.mjs`** получает сторожа: в тексте
скилла проработки стоят обе подстроки нового пункта — форма
`git -C <дерево>` и оговорка «Перечень покрытого живёт», ведущая
к источнику правды. Обе взяты из самого пункта и сегодня в файле
не встречаются ни разу, поэтому каждая половина сторожа краснеет, пока
пункт не написан; полный путь `supervisor/config/stage-settings.json`
для сверки не годится — он уже стоит в скилле по другому поводу
(`design.md`, Решение 6). Правило, живущее одной фразой в длинном файле,
вычищается при первой же переписке — как уже вычищались формула следа
и запрет многострочного коммита, ради которых сторожа в этом файле
и стоят.

Оба файла конвейера прямо сейчас правят живые деревья соседних задач:
`supervisor/skills/design.md` — задачи 0175 (pull request 132) и 0173,
`supervisor/config/transitions.test.mjs` — задача 0173. Места их правок
и наших сведены в `design.md`, Решение 8; там же сказано, куда именно
ложатся наши вставки, чтобы разойтись с чужими.

**`openspec/changes/point-the-form-note-at-a-live-rule/tasks.md`, шаг 2**
приводится к той же форме: `git -C <дерево> fetch origin`,
`git -C <дерево> merge origin/main`, а проверка шага —
`git -C <дерево> rev-list --count HEAD..origin/main`. Проверка правится
не потому, что голый `git rev-list` не пройдёт (он покрыт), а потому что
шаг с двумя разными формами внутри читается как «форма не важна» —
то есть остаётся тем самым образцом, ради которого задача и заведена.

## Non-goals

- **Правило `git merge:*` не заводится** ни в `allow`, ни в `deny`.
  Об этом отдельная задача 0172, и решать её здесь значило бы вести два
  изменения об одном. К тому же покрытая форма уже существует, а лишнее
  правило её не отменит: склеивать `cd` с командой этапу всё равно
  нельзя, значит ходить через `-C` он обязан независимо от списка.
- **Скиллы прочих этапов не переписываются.** Форму с `-C` они держат;
  проверено поиском по всем десяти файлам `supervisor/skills/`.
- **`git mv plugins/pipeline supervisor`** в `portable-supervisor/tasks.md`
  (строка 7) не правится, хотя голый `git mv` тоже не покрыт: шаг отмечен
  `[x]`, изменение закрыто целиком, исполнять его больше некому. Живым
  нарушением считается неотмеченный шаг открытого изменения — таких ровно
  одно, и оно названо выше.
- **Архивные изменения не правятся вовсе** (`openspec/changes/archive/`).
  Там `git checkout` и `git rebase` встречаются трижды, но это запись
  сделанного, а не указание к исполнению.
- **Сторож, читающий `tasks.md` всех открытых изменений, не заводится.**
  Обоснование — в `design.md`, Решение 4.
- **Задача 0181 здесь не решается.** Ложное основание «`git merge`
  не покрыт ни одним правилом» в изменении `mark-every-command-block`
  живёт в другой ветке (pull request 132), и править его отсюда значило
  бы устроить два изменения об одном тексте.
- **Ни один этап не начинает проверять `tasks.md` на покрытость перед
  работой.** Проверка перед стартом — это `hold-uncovered-stages`, она
  про объявленные командой этапа списки, а не про прозу списка задач.

## Влияние на отзывчивость интерфейса и на сетевой трафик

**Влияния нет ни на то, ни на другое, и вывод не умозрительный.**
Изменение трогает правила этапа (`supervisor/skills/design.md`),
сторожевой тест (`supervisor/config/transitions.test.mjs`) и текст
списка задач чужого изменения OpenSpec. Каталог `supervisor/` не входит
ни в один пакет монорепозитория: он не собирается вместе с клиентом
и сервером, не импортируется из `apps/` и `packages/` и в браузер
не попадает ни байтом. Каталог `openspec/` — документы.

Кадр отрисовки, объём игровых сообщений и раскладка байтов протокола
не задеты, `PROTOCOL_VERSION` расти не должен. Сетевого обмена изменение
не добавляет: и скилл, и список задач читаются с диска.

## Зависимости

Дельта пишется на способность `dev-pipeline-worker`, и её
в `openspec/specs/` ещё нет — способность заводит незаархивированное
изменение `agent-backlog-pipeline`. Поэтому **это изменение архивируется
ПОСЛЕ `agent-backlog-pipeline`**. Заархивировав раньше, получим
требование, висящее без основы: `openspec validate` этого не ловит,
а падает архивация — через месяц и не у того, кто писал.

Соседей по способности двое, и с обоими наше требование уживается,
не переписывая их: `agent-backlog-pipeline` со своим «Проработка ведётся
через OpenSpec» говорит, какие артефакты создать, а не как писать в них
команды; `admit-changes-without-deltas` — о случае, когда дельты нет
вовсе. Пересечения по тексту требований нет, сводить при архивации
нечего.
