# Задачи

Каждый шаг — отдельный коммит, проверяемый сам по себе. Изменение
не заводит ни строки кода приложения: правятся два файла конвейера
и один текст OpenSpec, поэтому ни сборки, ни матчевых тестов, ни замеров
здесь нет, а проверки везде узкие и идут по своим файлам.

**Команды даны формой, покрытой правилами разрешений** — `git -C <дерево> …`,
где `<дерево>` — путь из поля `worktree` назначения. Это ровно то правило,
которое изменение и вводит; список задач, написанный иначе, опровергал бы
сам себя.

## 1. Открыть черновой pull request на артефактах проработки

- [ ] Артефакты проработки (`proposal.md`, `design.md`, `tasks.md`,
      `specs/dev-pipeline-worker/spec.md`) уже лежат в ветке отдельным
      коммитом — отправить ветку, если она ещё не отправлена
      (`git -C <дерево> push -u origin HEAD`), и открыть черновой pull
      request в `main`:
      `gh pr create --draft --base main --title "<заголовок>" --body-file <файл>`.
- [ ] Тело pull request писать файлом: `--body` длинной прозой
      отказывается ещё до `gh`.

**Проверка:** `gh pr view <номер> --json number,state,isDraft` отвечает
`OPEN` и `true`; `gh pr checks <номер>` показывает запущенные проверки.
Шаг стоит первым не из вежливости: до появления pull request пуши
в ветку не запускают CI вовсе, и каждый следующий коммит остался бы
непроверенным.

## 2. Сказать в скилле проработки о форме команд и поставить сторожа

Правило и его сторож едут **одним коммитом**. Порознь они не проверяемы:
сторож без правила красен, правило без сторожа переживёт первую же
переписку файла.

- [ ] В `supervisor/skills/design.md`, шаг 10 (`tasks.md`), добавить пункт
      о форме команд. Текст выписан в `design.md`, Решение 5 («Целевой
      текст пункта целиком»), — брать его дословно: сторож сверяет
      подстроки.
- [ ] В `supervisor/config/transitions.test.mjs`, в `describe('этапы
и скиллы')`, добавить проверку из `design.md`, Решение 6 («Целевой текст
      проверки»). Помощник `skillText` в файле уже есть — заводить заново
      не надо.
- [ ] Больше в этих двух файлах не менять **ничего**: ни соседних пунктов
      шага 10, ни раздела запретов, ни прочих сторожей.
- [ ] Править инструментом редактирования файла. `Set-Content`, `Out-File`
      и перенаправление `>` не применять: Windows PowerShell 5.1 читает
      UTF-8 как ANSI и превращает кириллицу в мохибейк.

**Проверка**, вся по своим двум файлам:

- `npx vitest run --root supervisor config/transitions.test.mjs` — зелёный,
  и новая проверка в перечне прогнанных. Ключ `--root supervisor`
  обязателен: без него тесты конвейера не находятся вовсе, и прогон
  зеленеет, ничего не прогнав. Нет `node_modules` в дереве — сначала
  `pnpm install --frozen-lockfile`;
- сторож обязан **падать** без правки скилла. Убедиться дёшево и без
  правки истории: временно убрать из скилла подстроку `git -C <дерево>`,
  прогнать тот же тест, увидеть красноту с текстом `design.md: git -C
<дерево>`, вернуть подстроку. Сторож, зеленеющий на чём угодно, — не
  сторож;
- `npx prettier --check supervisor/skills/design.md supervisor/config/transitions.test.mjs`
  — зелёный;
- `npx eslint supervisor/config/transitions.test.mjs` — зелёный;
- `git -C <дерево> diff --stat` показывает ровно два изменённых файла.

## 3. Привести шаг 2 изменения `point-the-form-note-at-a-live-rule` к покрытой форме

- [ ] В `openspec/changes/point-the-form-note-at-a-live-rule/tasks.md`
      переписать команды **шага 2 и только его**: `git fetch origin` →
      `git -C <дерево> fetch origin`, `git merge origin/main` →
      `git -C <дерево> merge origin/main` (строка 24), а в проверке шага
      (строка 33) `git rev-list --count HEAD..origin/main` →
      `git -C <дерево> rev-list --count HEAD..origin/main`. Почему правится
      и проверка, хотя она покрыта, — `design.md`, Решение 7.
- [ ] Отметок `[x]` и `[ ]` не переставлять, шаги 1, 3 и 4 не трогать,
      прочих изменений не открывать вовсе.
- [ ] **Конфликт при слиянии в этом файле — повод остановиться и назвать
      его в отчёте**, а не разрешать по своему представлению о чужом
      тексте: значит файл тронул кто-то третий (дерево задачи 0165 живо,
      см. `design.md`, Решение 8).

**Проверка:**

- `openspec validate point-the-form-note-at-a-live-rule --strict` —
  зелёный: правка прозы разметку списка задач не ломает. Валидатор
  зовётся по имени изменения, `openspec` — по имени средства, без `npx`;
- поиском по файлу: `git merge origin/main` без приставки `git -C`
  не встречается ни разу;
- `git -C <дерево> diff --stat` показывает ровно один изменённый файл;
- prettier по этому файлу не гоняется: каталог `openspec/` исключён
  из проверки формата (`.prettierignore`), и `--write` на списках задач
  не сходится.

## 4. Дождаться зелёного CI

- [ ] `gh pr checks <номер> --watch`. Красное чинить, коммитить отдельно
      и ждать снова: задача не сделана, пока GitHub не сказал «зелено».
- [ ] Локально ничего сверх шагов 2 и 3 не прогонять: полный набор
      проверок живёт в CI (правило 6 `CLAUDE.md`), а из дополнительного
      дерева его не запускают.

**Проверка:** все задачи pull request зелёные. Черновой статус
на этом шаге **не снимать** — его снимает ревью первым подшагом вливания.

## Чего в списке нет

- **Прогона арены не заказывается.** Правила игры, цены, доход, сила
  юнита и темп не задеты ни одной строкой: правятся правила этапа
  конвейера, его сторожевой тест и текст списка задач OpenSpec — всё
  вне пакетов монорепозитория.
- **Замеров кадров и стоимости тика нет** по той же причине: отрисовка
  и шаг мира не тронуты.
- **Правки правил разрешений нет.** `git merge:*` не заводится —
  `design.md`, Решение 3; об этом отдельная задача 0172.
- **Сторожа над списками задач чужих изменений нет** — `design.md`,
  Решение 4.
- **Архивации изменения нет.** Она переписывает `openspec/specs/`,
  её очередь задана зависимостями дельт, и решение принимает человек.
  Здесь важно одно: изменение архивируется **после**
  `agent-backlog-pipeline`, которое заводит способность
  `dev-pipeline-worker` (см. «Зависимости» предложения).
