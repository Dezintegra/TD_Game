## Context

База обновлена fast-forward с `a821fad` до `9878558`. `dependencies.mjs` проверяет только `closed`; `backlog-trello.mjs:520` возвращает для архивных карточек только идентификаторы, теряя `links.pr`. В `scan.mjs:390–398` общий `held` уже применяется до `engaged`, выдачи продолжений, лимитов и `runWaiting`. Эти места расширяются, а не заменяются вторым планировщиком.

Владелец подтвердил использование влитого `card-dependencies` и доработку только недостающего соответствия результату. Требуется машинная проверка конкретного PR. «Закрыто» и «влито» различаются: снятый предмет тоже может закончиться закрытием, а `deploy` после вливания ещё не `closed`.

## Goals / Non-Goals

**Goals:** явно назвать ожидаемый PR для выбранной зависимости, проверить его вливание без сессии и сохранить гарантии удержания основы для всех типов и этапов.

**Non-Goals:** перечислены в proposal; особенно не вводятся новые исходы, автоматическое заполнение карточек, произвольные условия или ранний допуск по одному лишь вливанию.

## Decisions

### 1. Дополнение к списку зависимостей

`dependsOn` остаётся массивом строк. Новое поле:

```json
{
  "dependsOn": ["0002-base"],
  "dependencyResults": [{ "taskId": "0002-base", "kind": "merged-pr", "pr": 168 }]
}
```

Это пример формы, не правка реальной доски. Результат уточняет ребро графа: один объект на taskId, taskId обязательно уже в dependsOn, PR — положительное целое, неизвестные ключи и виды недопустимы. Для разных предшественников допустим один общий PR, если именно он стоит в их links.pr (например, общая ремонтная доставка).

Действующая `supervisor/config/task-schema.json` проверяет структуру. Существующая `dependencyFormatProblem` проверяет весь контракт dependencyResults самостоятельно: структуру, допустимые ключи и вид, положительный целый PR, уникальность по taskId и принадлежность dependsOn. Она не читает `manage/schema.json`, поэтому удаление файлового режима не снимает ни одной проверки. Она же вызывается до допуска из requests, чтобы негодная заявка получила диагностический отказ и не создала ослабленную карточку. В пути чтения Trello негодные dependencyResults сохраняются как есть до общего удержания сканера, как сейчас dependsOn; новая ошибка не должна превращать обычное ожидание результата в карантин. Негодные по прочим полям карточки по-прежнему проходят штатный карантин. Пока файловый режим существует, его `manage/schema.json` также получает поле как временную совместимость; срок её удаления определён в Migration Plan.

`card.mjs` и `requests.mjs` явно переносят поле при всех циклах чтения/записи. Отсутствие поля и пустой массив равнозначны, но при round trip отсутствие не материализуется без необходимости. Старые карточки не мигрируются. `links.related` остаётся справкой.

Альтернатива — заменить строки dependsOn объектами: ломает уже влитый контракт, обход графа и старых читателей. Автоматически требовать PR у всех feature тоже нельзя: закрытие без PR бывает законным. Явный номер нужен, чтобы закрытие карточки с другим влитым артефактом не было ложным успехом.

### 2. Доказательство в снимке, без сети внутри scan

Добавить общий модуль `supervisor/lib/dependency-evidence.mjs` с внедряемым исполнителем команд. Его вызывают обе точки входа `bin/supervise.mjs` и `bin/cycle.mjs` при сборке state, до scan; тесты используют подставные ответы без сети. Существующий `io.readPr`, используемый уборкой, не менять: его упрощённый результат `state` недостаточен и имеет других потребителей.

Для каждого валидного объявления у задачи в new или NEEDS_SESSION, без живого процесса/ожидающего отчёта, сначала разрешить предшественника в единственную годную карточку текущего снимка. Только при closed и совпадающем links.pr читать PR. Собрать множество уникальных номеров: максимум один запрос на номер за цикл. Все вызовы исполняются в корне репозитория конвейера штатным runner, с конечным тайм-аутом 10 секунд на чтение. GitHub CLI получает аргументы массивом: `pr`, `view`, номер, `--json`, `number,state,mergedAt,baseRefName`. Номер в ответе должен совпасть; репозиторий определяется тем же корнем Git, не cwd дерева зависимой задачи. Невозможность определить репозиторий означает unknown.

Результат state, например `dependencyEvidence`, содержит подтверждения и причины unknown, привязанные к PR и ожидаемой главной ветке; модуль возвращает его без записи на доску. Успех: MERGED, корректная непустая дата mergedAt, совпадающая config.mainBranch. OPEN, CLOSED, null, неожиданные значения, тайм-аут, ошибка команды или JSON возвращают неподтверждённый результат. Исключение не прерывает сборку остальных доказательств. Сканер не выводит успех из одного булева флага без соответствия номеру и ветке.

Кэш существует только внутри одного снимка. Перезапуск и следующий оборот перечитывают доказательства; смена ожидания не наследует старый успех. Не нужна отдельная запись «влито» на карточке, которую можно потерять или оставить после смены links.pr. Постоянный кэш и новый poll-external action отвергнуты: это ещё один жизненный цикл состояния ради небольшой проверки. Необходимый служебный трафик ограничивается проверяемыми номерами; игровой трафик не затрагивается.

### 3. Архив и неоднозначность

Добавить к адаптеру доски метод получения записей архивных предусловий со status, links.pr и признаком валидности; прежний closedDependencyIds оставить для совместимости обычных зависимостей. Для усиленных условий одних ID недостаточно. Сопоставление учитывать по всем активным и архивным записям, включая известные негодные ID: негодный дубликат не должен исчезнуть при фильтрации и оставить ложную уникальность. Дубликаты, отсутствующая карточка, непарсящийся архив и незакрытая колонка удерживают задачу.

Архивные карточки уже входят в snapshot.cards, дополнительных запросов Trello не нужно. Архивирование Trello `card.closed` не равно состоянию задачи `status: closed`. Только до удаления файлового режима его закрытые записи берутся из tasks; отсутствие архивного адаптера означает отсутствие дополнительных доказательств, а не успех. Это временный путь совместимости, удаляемый вместе с файловым адаптером; постоянное разрешение предшественников работает по активным и архивным карточкам Trello и не зависит от файлов задач.

### 4. Использовать существующее удержание

Расширить pendingDependencies входами результата и архивных сведений, сохранив старые вызовы с пустыми входами по умолчанию. Для обычных ребёр действует прежняя проверка; для уточнённых — closed И ожидаемый PR в links.pr И подтверждённое вливание. Ошибки деклараций проверяются прежде результата. Самоссылки и циклы не получают обхода через GitHub.

Вернуть причины в существующий held: этим одним решением исключаются start-stage, continue-stage, fail-stage по попыткам, decompose-again по бюджету, engaged, exclusive и участие в deploy batch. Статус, returnTo и счётчики не меняются, отдельного состояния ожидания нет. Диагностика включает taskId предшественника, ожидаемый PR и причину (не закрыт, не тот PR, не влит, другая база, нет доказательства). Следующий свежий снимок с выполненными условиями возвращает штатное планирование.

Существующие исключения для running и hasReport сохраняются: живой процесс занимает реальное место и заканчивает работу, уже полученный отчёт переносится. Хвосты, очистка завершённых задач, ответы владельца и опрос внешних прогонов не превращаются в зависимые сессии. Сервисные действия могут идти; следующий запуск проверяется на новом снимке.

## Risks / Trade-offs

- Недоступный GitHub задержит зависимые задачи → ограниченный тайм-аут, явная причина, повтор на следующем снимке; без глобальной паузы, сессий и списания попыток.
- PR влит, но карточка ещё deploy → ожидание до closed осознанно сохраняет контракт основы. Выкладка и закрытие предшественника продолжают работать самостоятельно.
- Ожидаемый PR заменили другим → удержание сохраняется до явной правки dependencyResults и links.pr уполномоченным писателем доски. Автоматически подменять результат нельзя.
- Новое поле прочитает старая версия супервизора → сначала доставить поддержку на все работающие станции, только затем задавать поле. При откате сначала остановить выдачу сессий и снять/перенести усиленные условия по решению владельца; молчаливый откат на старого читателя небезопасен.
- Снимок устаревает между чтением и запуском → гарантия относится к одному снимку, как у существующего dependsOn; изменения увидит следующий оборот. Живую работу не отменяем.

## Migration Plan

Реализовать чтение и удержание атомарно, затем подключить общий сбор доказательств к обеим точкам входа. До этого новые условия безопасно остаются неподтверждёнными. Доставить поддержку штатным PR и самообновлением конвейера. Реальные карточки на design/implement этой задачи не менять; применение метаданных остаётся у супервизора/владельца. Дельта архивируется поверх существующей card-dependencies без зависимости от открытых дельт.

Согласование с `backlog-in-trello`, разделом «Перенос существующих задач» и пунктом 9.1:

- Если наша реализация доставлена первой, до уборки расширяются обе схемы и сохраняется существующий файловый путь. Пункт 9.1 затем удаляет `manage/schema.json`, файловый адаптер и относящиеся только к ним тесты. `dependencies.mjs`, проверка заявок, round trip Trello и проверка результата остаются; тесты этих гарантий не должны импортировать файловую схему или адаптер.
- Если пункт 9.1 доставлен первым, шаг 1.1 реализуется только для `supervisor/config/task-schema.json` и Trello. Удалённые файлы и тесты не восстанавливаются. Отсутствие `manage/schema.json` является предусмотренной базой, а не препятствием реализации.
- В обоих порядках обязательная проверка проходит по прямому пути Trello → scan и requests → карточка без загрузки файловой схемы. Негодное dependencyResults удерживает запуск и отвергает заявку; годное сохраняется при записи. Так проверяется постоянная гарантия после уборки, а временные тесты схемы не становятся единственным её доказательством.

Удаление файлового режима остаётся работой `backlog-in-trello`, чужие артефакты здесь не правятся. Жёсткий порядок «ждать полного завершения backlog-in-trello» отвергнут: оба порядка сохраняют контракт, а ожидание всего переезда задержало бы независимую защиту запусков. Требование навсегда поддерживать две схемы отвергнуто как противоречащее согласованной уборке. Порядок архивации независим: наша дельта описывает поведение метаданных, не устройство временного хранилища.

## Проверки и архитектурные ограничения

Узкие Vitest-тесты supervisor: схемы и round trip; смешанные зависимости; матрица статусов PR; недоступность и неполный ответ; архивные и негодные дубликаты; отсутствие запросов без условий и дедупликация; new/run против готовой feature; implement при maxConcurrent=1; exclusive/deploy; пределы попыток; running и reports; смена ожидания и новый снимок. Сборку snapshot проверять с подставным runner в обеих точках входа, без запуска боевого супервизора и без доски.

Геймплей, рассинхрон и реконнект не меняются. packages/sim и протокол не затронуты: эталоны детерминизма, PROTOCOL_VERSION и арена не нужны. В ядро не добавляются Math.random, Date.now или дробные значения состояния мира. Проверка даты mergedAt относится только к служебному доказательству, не к игровому времени.
