## Goals / Non-Goals

Цель — однозначный путь от заказанного исправления открытой дельты до собственного PR задачи. Не-цели перечислены в proposal.md; особенно важно сохранить исходную карточку и её незавершённый план. Данные карточек, роутинг, приёмка следа и код супервизора не меняются.

## Decisions

### 1. Выбор режима до создания изменения

В design перед требованием завести изменение добавить именованный раздел «Адресная правка открытой дельты», сохранив существующую нумерацию шагов. Применимость определяется всей постановкой и журналом: известна конкретная открытая дельта, а результат исчерпывается её исправлением и необходимым согласованием текстов внутри того же каталога. Это не общее разрешение реализовать задачу в design. Обычная правка инструкции, даже без новых требований, остаётся обычным изменением по правилу 0171.

Для адресного режима явно оговорить общие шаги создания proposal/specs/design/tasks и запрет файлов вне каталога: новым комплектом они не выполняются, каталогом работы становится исходный `links.change`. Сохранить проверки, свой свежий коммит, отправку и завершение этапа. Связанные артефакты исправлять лишь когда иначе заказанный текст оставит противоречие; не заменять исходное предложение и не переписывать чужой план. Возврат и продолжение используют ту же цель. Отсутствие цели не даёт разрешения написать её заново: применяется имеющийся контракт вопроса или обязательной предпосылки, исход moot запрещён при уже заполненном change.

Альтернатива — отдельное бездельтовое изменение для каждого исправления — законна для других работ, но здесь оставляет два каталога и неоднозначный предмет аудита. Альтернатива — вторая дельта с тем же требованием — создаёт конкурирующую редакцию при архивации. Обе не выполняют постановку 0147.

### 2. Область работы передаётся существующим отчётом

Не добавлять машинное поле режима: постановка и журнал уже передаются следующим этапам. В summary явно написать «Адресная правка открытой дельты», в decisions перечислить имя, пути, заголовки, основание исправления, SHA собственного коммита, результаты validate/status и фразу об отсутствии оставшихся правок по карточке. `links.change` — адрес чтения, не передача владения исходным изменением. `links.pr` не копировать из исходной карточки.

Аудит сверяет отчёт с собственным просмотром diff и текстов. Для сравнения ветки применяется `git -C <дерево> diff origin/main...HEAD -- openspec/changes/<links.change>`, а названный коммит читается через `git -C <дерево> show <коммит>`. Все вызовы — отдельными командами в назначенном дереве. Слияние базы само по себе не считается заказанной правкой. Одного заявления проработки о готовности недостаточно.

Альтернатива — отдельный файл списка работ или новое поле схемы — избыточна: потребует миграции и второго источника области задачи. Наблюдаемое ограничение выбранного решения: смысл отчёта проверяет следующая сессия, код супервизора его не классифицирует.

### 3. Аудит ограничивает предмет, сохраняя проверки последствий

В audit согласовать описание входов, сверку заказа, чтение способностей, проверку Non-goals и tasks, а не только добавить оговорку в конце. Исходные артефакты читаются для понимания требований, но их полный набор целей и открытых пунктов не становится заказом узкой карточки. Проверяются изменённые требования, сохранённые сценарии, связанные артефакты и пересечения именно этой правки с соседями. Наличие другого предложения с тем же требованием нельзя автоматически оправдать узким предметом.

Validate по имени проверяет исходное изменение целиком: ошибки не скрываются. Status отражает исходный комплект, а не число оставшихся работ карточки. Исключение для отсутствия `specs/` не применяется к существующей дельте. Постороннюю ошибку, которую нельзя устранить в заказанном объёме, этап описывает по действующему контракту; молча расширять правку нельзя.

Альтернатива — отключить проверку исходного изменения — теряет ошибки разметки. Альтернатива — принимать или отклонять всё чужое предложение по узкой карточке — воспроизводит дефект.

### 4. Имплементация доставляет готовый diff

В implement уточнить выбор задач при чтении входов и перед циклом `tasks.md`, связав их с уже существующим абзацем о PR без коммита. В адресном режиме после подтверждения аудита нет пунктов правки по этой карточке: исполнение чужих чекбоксов пропускается, выполняются применимые подготовка, проверка отправленной ветки и открытие собственного чернового PR по процедуре implement. Старые чекбоксы исходного изменения не закрываются и новые фиктивные не добавляются. PR описывает исправление из карточки, а не реализацию всего исходного проекта.

После отчёта implement супервизор продолжает обычный маршрут через проверки и ревью. Ранее известный PR сам по себе не новый след; текущая мерка приёмки сохраняется без новых исключений. Повторные этапы действуют по своим текущим контрактам, а не создают второй PR ради следа. Архивация исходного изменения в эту работу не входит.

Альтернатива — design → pr или audit → cleanup — обходит существующие обязанности доставки и контроля. Поэтому «шагов правки нет» не означает «этап implement не нужен».

### 5. Общие нормы не должны противоречить исключению

В открытом `agent-backlog-pipeline/specs/dev-pipeline-worker/spec.md` согласовать только требования «Проработка ведётся через OpenSpec», «Аудит проверяет предложение на пересечения» и «Имплементация ведётся атомарными коммитами с ранним pull request»: ограничить общие формулировки обычным случаем и сослаться на требование «Адресная правка открытой дельты проходит этапы в границах своей карточки». Все существующие сценарии сохранить, при необходимости уточнив условие обычного случая.

В `admit-changes-without-deltas/specs/dev-pipeline-worker/spec.md` так же ограничить требование «Изменение, не меняющее ни одного требования, ведётся без дельты» и сценарий о правке текста: адресный режим существующей дельты отличается от создания бездельтового изменения. Требование о проверке формы и вся диагностика 0251 остаются нетронутыми. Подробности исключения не размножать по этим файлам.

Если к реализации норма уже перенесена в `openspec/specs/dev-pipeline-worker/spec.md`, исправить её живое место с сохранением незатронутых сценариев, архивные снимки не трогать. Этот перенос предусмотрен только для реализации 0147; он не расширяет будущее разрешение design править основные спецификации. Дельта 0147 — ADDED, потому что основы пока нет; она не подменяет MODIFIED несуществующего требования.

## Verification matrix

Проверки инструкций — содержательный проход по примерам, без запуска боевого конвейера или изменения реальных карточек. При реализации записать для каждой строки результат и конкретные разделы трёх инструкций в собственный verification.md.

| Случай | Ожидаемый результат |
| --- | --- |
| Переименовать величину в открытой дельте, остальные сценарии не затронуты | Design правит один исходник в своём дереве, сообщает цель и коммит, не создаёт изменение |
| Там же есть десять чужих открытых задач и широкие Non-goals | Аудит сверяет узкий diff и последствия; implement не исполняет чужие задачи, открывает собственный PR |
| Исправление противоречит сохранённому сценарию или соседней дельте | Адресное замечание аудита, а не автоматическое принятие |
| CLI отвергает существующую дельту | Ошибка не маскируется исключением для отсутствующих specs |
| Возврат design после замечания | Та же цель из links.change; новый комплект не создаётся |
| Цель архивирована, отсутствует или неоднозначна | Нет записи в архив/основу и выбора цели наугад; отчёт по текущему контракту |
| Исправить пример в инструкции вне каталога изменения, требований не меняет | Обычное бездельтовое изменение с обоснованием, не адресное исключение |
| Нужно изменить код вместе с дельтой | Обычная проработка и реализация после аудита |
| Вся правка сделана design, PR ещё нет | Implement впервые открывает черновой PR без фиктивного коммита; обычная мерка следа соблюдена |
| В журнале уже есть PR и нет нового коммита implement | Ранее известный PR не объявляется новым следом; приёмка не ослабляется |

Узкая проверка существующих сторожей инструкций — `npx vitest run --root supervisor config/transitions.test.mjs`. Она проверяет сохранение действующих запретов и диагностики; новые тесты, зеркалящие текст абзацев, не нужны. Матрица выше проверяет связность нового пути, которой поиск отдельной фразы не доказывает.

## Risks / Trade-offs

- Совпадение файлов с PR 132 и 141 → освежать базу перед реализацией, сохранять нумерацию и действующие сторожи, не включать чужие правки. При реальном конфликте следовать implement, не сливать чужую ветку вслепую.
- Общая дельта меняется двумя карточками → собственные ветки и PR сохраняются, аудит сравнивает требования и diff; ссылка не разрешает перехват.
- Нормативное исключение и исходные общие формулировки могут разойтись → обе согласуются одним коммитом вместе с инструкциями.

## Migration Plan

Один согласованный коммит инструкций и адресных уточнений существующих норм. Схема и состояние не мигрируют. При откате возвращается весь коммит целиком. Архивировать после двух изменений из proposal.md, вне этапов этой задачи.

Геймплей, рассинхрон, реконнект, эталоны sim и раскладка протокола не затрагиваются; рост `PROTOCOL_VERSION` не требуется. Запреты `Math.random`, `Date.now` и чисел с плавающей точкой в состоянии мира сохраняются: исполняемый код не меняется.
