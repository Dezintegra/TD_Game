## Context

Исследование design выполнено чтением после обновления main до `c3d7700`. В основном коде `codex-environment.mjs:35–65` формирует отдельные safe.directory root/cwd. `supervisor.mjs:450` передаёт это окружение запускаемой сессии, `run-stage.mjs:62` умеет передавать `command.env`. На текущем этапе эти настройки не менялись.

В дереве 0299 на закреплённом `07b7085ff932d4ccd4d17d7ec6567092bff03645` прочитаны:

- `supervisor/lib/project-skill-writes.mjs:64–104`: validateTree зовёт Git с окружением хозяина; проверяет реальную Git-идентичность, а не только .git pointer.
- `supervisor/lib/project-skill-write-probe.mjs`: consumerAssignment вызывается перед setup; фиксированный setup создаёт main/tree/foreign; runSession принимает command с возможным env через startStage.
- `supervisor/bin/check-project-skill-writes.mjs`: фиксированный CLI пишет evidence через wx, но делает это после опыта; повторять его поверх старого evidence нельзя.
- `openspec/changes/permit-assigned-project-skill-writes/validation.md`: ownership-отказ, ноль native-сессий, неизменность девяти файлов 0083; исходный опыт на `e02ba861b4732a758d0d4d2d59613bb2bdf456b8`.

Официальная [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox), прочитанная 09.09.2026, описывает elevated через отдельных пользователей с ограниченными правами. Это объясняет необходимость различать хозяина и sandbox-команды, но не доказывает работоспособность конкретного установленного CLI. Фактические версии и результаты должны попасть в новую приёмку.

## Goals / Non-Goals

Цель — поддерживаемый жизненный цикл хозяина: заранее подготовленное окружение, проверенная 0083, готовый фиксированный стенд и подключение прежнего опыта без наследования прав хозяина. Non-goals — в proposal. Ни sim, ни игровой протокол не меняются; реконнект, рассинхрон, golden-эталоны и PROTOCOL_VERSION неприменимы. Запреты Math.random/Date.now и floating-point состояния ядра сохраняются.

## Decisions

### 1. Хозяин является отдельным процессом оснастки

Добавить `supervisor/lib/windows-diagnostic-host.mjs` и вход `supervisor/bin/prepare-project-skill-host.mjs`. Хозяин — обычный процесс Node, запущенный штатным владельцем Windows-маршрута до исполняющей сессии. Это та же граница ответственности, на которой супервизор сегодня создаёт рабочие деревья и готовит окружение Codex. Он не является модельной сессией и не получает от неё команды на повышение прав.

Единственная исполняющая CLI-форма — `node supervisor/bin/prepare-project-skill-host.mjs --prepare`; без ключа только помощь, остальные доводы отвергаются. CLI выводит подготовительное свидетельство, но не выполняет полную приёмку и не запускает супервизор. Cwd должен быть корнем назначенной собственной копии с совпадающим home инструмента. Потребитель фиксирован константами taskId 0083/change guard-declared-purpose-updates и находится по Git-регистрации, а не по строке промпта. Ни имя учётной записи, ни env-флаг сами по себе не доказывают полномочия хозяина: критерием служат успешные операции в заранее предоставленном контексте.

В активной sandbox исполнителю запрещено запускать этот вход другим способом после отказа или менять свой профиль. Владельцу нужен новый заранее согласованный запуск из его штатного контекста, с уже установленной поддерживаемой Windows sandbox для будущего Codex. Вход не вызывает runas, UAC, icacls, takeown, sandbox setup с новыми правами или изменение Git config. Если даже владельцу Git отказывает, это не ветвь автоматического исправления: результат отрицательный, требуется внешняя подготовка по действующему routing contract.

Отвергнуты: добавление 0083 в окружение обычного исполнителя (расширяет исключение fix-codex-startup), `safe.directory=*`, глобальная настройка и git -c после отказа (маскируют границу), чтение .git вместо Git (не подтверждает идентичность), запуск полного опыта прямо из текущей sandbox (повторяет причину 0299).

### 2. Подготовка замкнута на фиксированную топологию

Хозяин выполняет только read-only Git-проверки 0083: absolute-git-dir, абсолютный common-dir, show-toplevel, symbolic-ref и worktree list. Доверенный основной root выводится из собственного Git-назначения. Проверять соответствие всех ответов и ordinary/reparse/realpath, включая цепочку .git; неоднозначность или ошибка запрещает setup. Команды запускаются execFile с массивом аргументов, тайм-аутом 10 секунд и windowsHide; Git вызывается с -C, без shell-цепочек.

До действий зарезервировать новое evidence через wx. Для 0302 имена фиксированы: `.matchlog/0302-project-skill-host-evidence.json` и `.matchlog/0302-project-skill-host/`. Это отдельные данные; `.matchlog/0299-skill-write-evidence.json` и `.matchlog/0299-skill-write-probe/` неприкосновенны. Резервирование должно оставлять явное incomplete при аварии. Повторный запуск не удаляет и не переиспользует занятое место.

Создать внутри собственного стенда main, linked tree с веткой worktree-0083-pravka-purpose-speki-ne-dostavlyaetsya-d, foreign/control.txt и существующие цели/контроли с теми же относительными путями и начальным маркером `0299:initial`, что в PR 232. Main/foreign лежат вне cwd проверяемого ребёнка. Fixture не добавляется в Git worktree list настоящего проекта: это отдельный локальный Git-корень. Конфигурация user.name/email тестового коммита задаётся только локальной безвредной операции, не затрагивая пользовательскую идентичность.

Подготовка включает создание файлов наблюдения с тем же контрактом хешей и negative r+, а также тестовых perf-файлов. Отдельный модуль `supervisor/lib/project-skill-host-fixture.mjs` предоставляет fixture и его повторную проверку. Это ограниченная фабрика инфраструктуры стенда, не второй классификатор приёмки. Подготовительный вызов проверяет возможность запуска закреплённого CLI через --version, не отправляет промпт и не расходует две сессии/один resume 0299. Подготовка ограничена десятью минутами целиком, включая дочерние процессы; после отказа новых действий нет, кроме безопасного сохранения результата и проверки сохранности.

### 3. Подключение PR 232 без обратной зависимости

В main ещё нет project-skill-writes/probe из 0299. Модуль хозяина не импортирует отсутствующие файлы статически и не включает их копии в поставку 0302. Он предоставляет библиотечный адаптер для уже существующих effects runProjectSkillWriteProbe:

- setup возвращает только ранее подготовленный и заново сверенный fixture; настоящий consumer проверяется прежним resolver хозяина перед ним;
- runSession получает готовую command существующего builder, сохраняет argv/cwd/stdin, но устанавливает новое command.env через codexChildEnvironment и codexGitEnvironment для fixture.root/fixture.cwd;
- runSession передаёт команду прежнему runProbeSession; native-events, классификатор, лимиты, killTree и остановка при неожиданной записи остаются у прежнего опыта;
- после каждой фазы и перед resume сверяются профиль, source/digest назначения и fixture; baseline/target отличаются только штатными grants.

Адаптер вызывается доверенным кодом оснастки в хозяине, не RPC от модели. CLI не принимает путь импортируемого JS, callback, произвольный home или команду. Сборка adapter + fixture проверяется интеграционным тестом с интерфейсом effects; дополнительно совместимость проверяется с закреплённым исходником PR 232 только в собственном проверочном каталоге, без правки дерева/ветки 0299. До исполнения кода открытого PR подтвердить точный SHA и отсутствие незаписанных изменений в используемом наборе модулей; не импортировать произвольную изменяемую соседнюю копию. Для воспроизводимости исходник извлекается из Git-коммита в собственный `.matchlog/0302-host-contract/`, с записанным SHA; native runSession в этой проверке подменяется.

После доставки 0302 повторный анализ 0299 согласует вход её сохранённого CLI с этим адаптером в PR 232 и выбирает новый путь evidence по уже известной попытке. Это остаётся продолжением приёмки 0299. Поставка 0302 включает готовое подключение на уровне effects и проверку совместимости; она не требует влитого PR 232 и не доставляет его непроверенные файловые grants в main. Перенос исходного standalone CLI на новый хозяин не объявляется состоявшимся до этого повторного анализа.

### 4. Права ребёнка строятся заново

Использовать существующие codexChildEnvironment/codexGitEnvironment для каждого нового запуска и resume. Не передавать process.env хозяина напрямую: удалить его GIT_CONFIG_* и trace-переменные штатным builder, доверять только тестовым root/tree. Не менять глобальные функции окружения ради диагностики. GH_TOKEN остаётся только в памяти, полный env и config не печатаются.

Production argv из PR 232 проверять по смыслу: approval never, extends :workspace, текущий Windows sandbox, точные Git/perf grants. Для target только archive и sync SKILL.md, baseline без них; исключений для всего .agents, .codex или foreign быть не должно. Фиксированные файлы наблюдения и существующие control-файлы сохраняют исходные хеши. CLI-version сама по себе не свидетельствует о применении этих прав.

### 5. Свидетельства и границы успеха

Сохранять версию схемы, started/elapsed, SHA оснастки, SHA PR-источника при проверке совместимости, разрешённые версии Node/Git/Codex, роль хозяина, точные root/cwd, фазу/код ошибки, результаты Git-проверок, hashes до/после. Ошибку `detected dubious ownership` классифицировать отдельным ownership-кодом, без SID/owner-name и полной строки stderr. Отказ политики и сбой запуска sandbox — отдельные категории; неизвестное остаётся unknown.

hostReady=true требует Git-идентичности и созданного/проверенного fixture. cliStart=true требует отдельного успешного запуска CLI. permissionAcceptance остаётся not-run; sessions пуст. Только исходный классификатор 0299 после всех контролей может подтвердить приёмку. Прежнее evidence с unknown не исправляется задним числом.

Опись потребителя ровно соответствует прежней: четыре корневых артефакта изменения, все specs и четыре .matchlog/0083-* из validation.md. Снимать исходные и итоговые хеши и сравнивать состав; отсутствие файла — ошибка. Не копировать и не исполнять черновики. Записать также хеш прежнего evidence 0299 до/после, если он доступен; отсутствие доступа явно обозначить и не объявлять сохранность доказанной.

## Risks / Trade-offs

- Новый вход нельзя доказать тестами с mock → нужна отдельная настоящая подготовка Windows до исполняющей сессии. На design она не выполнялась.
- Нельзя самому установить новую оснастку в работающий home или перезапустить владельца → введение в действие делает штатный владелец между запусками. Отсутствие такой подготовки блокирует живую проверку, не оправдывает обход.
- Снимок PR 232 изменится → сохранить прежний SHA, повторный анализ сверяет новое содержимое; несовпадение не принимается молча.
- Две фабрики fixture разойдутся → контрактный тест сравнивает topology, содержимое, hashes и effects с PR 232; классификатор не копируется. После подключения 0299 использует подготовленный fixture.
- Политика Windows может не разрешить точные grants → задача 0299 остаётся непрошедшей приёмку; hostReady не означает её успех.
- Совместное использование данных несколькими запусками → exclusive create и привязка к cwd/SHA; никаких автоматических повторов поверх свидетельств.

## Migration Plan

1. Реализовать самостоятельную оснастку 0302, узкие тесты и проверку совместимости с сохранённым PR 232. Открыть собственный draft PR после первого коммита реализации.
2. После отправки пункта 2.1 первая сессия фиксирует полный SHA оснастки, хеши её модулей/конфигурации и номер собственного draft PR в `validation.md`. Источник внешнего запуска — этот отправленный коммит ветки `worktree-0302-podgotovit-razreshennyy-windows-marshrut`, а не будущий merge в main. При отсутствии свидетельства сессия завершает implement исходом `blocked`; супервизор сохраняет ветку, PR и отметки 1.1/2.1, оставляя 3.1 открытым. Конкретный контракт передачи приведён ниже. Это штатное ожидание внешнего результата, а не новый исход этапа и не фоновое ожидание в живой сессии.
   Штатный владелец диагностического запуска на NB3391 выполняет подготовку после завершения этой сессии и до назначения новой. Он использует сохранённое дерево 0302 с отправленным SHA и соответствующим home оснастки, не устанавливает её в работающий home супервизора и не перезапускает супервизор. Сам владелец в своём уже разрешённом PowerShell-контексте с cwd дерева 0302 вызывает `node supervisor/bin/prepare-project-skill-host.mjs --prepare`. Проверка чистоты исходников, SHA и отсутствия активного исполнителя предшествует вызову. Это внешняя операция владельца; модельная сессия не запускает её, не делегирует её дочерней модели и не получает новых полномочий. Настоящий prepare должен подтвердить Git-идентичность 0083, fixed fixture и CLI-start.
   Свидетельство остаётся в сохранённом дереве 0302 по `.matchlog/0302-project-skill-host-evidence.json`; владелец передаёт абсолютный путь, SHA-256 файла, SHA оснастки, время завершения и очищенный результат в журнал внешней предпосылки через штатный канал владельца. Никакие секреты или сырые потоки туда не попадают. Исполнитель доску не правит. Супервизор получает подтверждённый результат предпосылки, затем проводит новый анализ 0302 и назначает новую сессию для 3.1 с этой ссылкой в журнале. Новая сессия читает evidence, сверяет хеш, ревизию, конфигурацию и время до её старта; она не повторяет prepare и не принимает один комментарий без доступного файла за доказательство. Только плановые коммиты после SHA оснастки не инвалидируют evidence при совпадении хешей всех исполняемых модулей и конфигурации. Несовпадение или недоступность сохраняют блокировку. Без живого свидетельства 0302 не объявляется подтверждённой предпосылкой.
3. После доставки и подтверждения результата супервизор использует уже существующую dependsOn 0299 → 0302 и проводит новый анализ 0299 с сохранением PR 232, change, старых evidence и расхода. Не создавать заявку-дубликат, не менять доску или dependency из исполнителя. Не считать 0083 разблокированной до завершения самой 0299.
4. Откат — прекращение новых запусков через новый host entry. Уже созданные свидетельства сохраняются; профиль активных сессий, пользовательские настройки и данные 0083 не меняются. Уборка только хозяином по точной принадлежности и разрешённому пути, без обхода отказов.

### Контракт внешней предпосылки после отправки оснастки

В отчёте первой implement-сессии использовать `routingVersion: 1`, `categories: ["infrastructure"]`, `outcome: "blocked"`, сохранённые links.change и собственный links.pr. В `blockers` указать `requestKey: "windows-host-evidence"`, reason: «Оснастка отправлена, но настоящая подготовка хозяином между сессиями ещё не подтверждена», result: «Доступное свидетельство штатного владельца NB3391 для отправленного SHA: hostReady=true, cliStart=true, permissionAcceptance=not-run, sessions=[], неизменные опись/хеши 0083 и прежнее evidence 0299». SHA и адреса подставляются фактические из 2.1.

Соответствующая заявка `requests` имеет key `windows-host-evidence`, type `feature`, categories `["infrastructure"]`, area `pipeline`, title «Выполнить внешнюю подготовку Windows-хозяина по отправленной оснастке 0302». Description содержит полный SHA, ветку, собственный draft PR, точное сохранённое дерево и home, команду владельца и способ передачи evidence из шага 2. Результат заявки — внешнее свидетельство, не новый код или отдельная реализация маршрута. Она не зависит от completed/merged 0302 либо PR 232: необходимый исходник уже отправлен. Перед заявкой сверить назначение и журнал; существующую карточку этой подготовки использовать по taskId, не создавать повторно. `dependencyResult: merged-pr` не указывать: нужен наблюдаемый результат, а не вливание.

Внешнюю операцию исполняет именно штатный владелец Windows-процесса. Автоматическое создание карточки само её не выполняет: пока владелец не передал проверяемый результат, 0302 остаётся blocked, новые проверяющие сессии по возрасту не запускаются. Исполнитель этой предпосылки также не вправе добывать хозяина сменой пользователя, обходить отказ или считать её завершённой по наличию кода. Повторный анализ 0302 после результата сверяет evidence и сохраняет существующий change/PR; полная приёмка 0299 остаётся за её следующим анализом после доставки 0302.

Отвергнуты: ожидание вливания самой 0302 перед prepare (цикл, поскольку 3.1 обязателен до завершения), зависимость от вливания PR 232 (обратная зависимость), `done` с открытым 3.1 и автоматический запуск хозяина из первой сессии. Передача конкретного отправленного SHA позволяет внешней подготовке завершиться независимо от обеих поставок.

## Open Questions

Продуктового выбора нет. Технически не подтверждены реальная подготовка Windows и поддержка файловых grants текущим CLI. Первая проверяется между первой и новой исполняющей сессией 0302 по контракту выше; вторая остаётся приёмкой 0299. Наличие заранее выполненной подготовки не требуется для реализации 1.1/2.1: она использует подменённые эффекты. Для 3.1 требуется результат внешней предпосылки; mock и запуск из текущей sandbox его не заменяют.
