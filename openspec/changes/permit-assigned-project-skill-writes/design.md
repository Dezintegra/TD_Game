## Context

На design 09.09.2026 выполнены fetch и merge origin/main: `Already up to date`, база `7a12154`. `provider.mjs:37–88` формирует `td-pipeline`, наследующий `:workspace`, с отдельными записями Git/perf. `codexStageCommand` не передаёт сведения о назначенных скиллах. `supervisor.mjs:365–401` уже передаёт assignment с task, поэтому расширять карточку и routing schema не требуется. В установленном CLI прочитана версия `codex-cli 0.146.0`; команда предупредила `Could not find home directory`, но завершилась с кодом 0. Это не доказательство готовности sandbox.

Постановка фиксирует EPERM и отказ apply_patch в 0083. В её дереве прочитан tasks.md: одним коммитом должны обновляться archive и sync Codex-скиллы вместе с механизмом и Claude-маршрутами. Найдены все четыре `.matchlog/0083-*`; содержимое не исполнялось и не менялось. На design попыток записи защищённых файлов нет.

Официальная [документация Permissions](https://learn.chatgpt.com/docs/permissions), прочитанная 09.09.2026, описывает наследование защит `:workspace`, более специфичные файловые правила и отказ runtime от неисполнимых политик. Именованный профиль нельзя смешивать со старыми sandbox-настройками. [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox) описывает elevated как предпочтительный вариант. Эти сведения обосновывают выбранный механизм, но не доказывают, что точное исключение для SKILL.md сработает в установленной версии и профиле. Это отдельный критерий живой приёмки.

## Goals / Non-Goals

Цель: штатный запуск implement/revise с заранее назначенными двумя файлами, сохранённой защитой остальных скиллов и чужих деревьев, воспроизводимым доказательством. Non-goals перечислены в proposal. Геймплей не затрагивается: реконнект, рассинхрон, golden-эталоны, PROTOCOL_VERSION и ограничения Math.random/Date.now/целочисленного состояния sim остаются вне изменения.

## Decisions

### 1. Источник назначения вне изменяемого плана

Добавить `supervisor/config/project-skill-writes.json`: version=1, entries с taskId, change, stages и files. Первоначально ровно одна запись: taskId `0083-pravka-purpose-speki-ne-dostavlyaetsya-d`, change `guard-declared-purpose-updates`, stages implement/revise; files:

- `.agents/skills/openspec-archive-change/SKILL.md`;
- `.agents/skills/openspec-sync-specs/SKILL.md`.

Читатель `supervisor/lib/project-skill-writes.mjs` получает перечень из каталога запущенного инструмента `home`, как правила этапа. Не искать fallback в cwd. Производственный запуск не принимает разрешения из промпта, tasks.md, отчёта или произвольного assignment.files. Изменение перечня доставляется обычным проверенным PR. Саморедактирование копии в рабочем дереве не меняет уже запущенный инструмент или текущие права.

Проверять совпадение taskId и assignment.task.id, links.change и stages. Неизвестная задача получает пустое расширение; для совпавшей записи повреждённая схема, отсутствующая task/change или несоответствие change дают явную ошибку до запуска. Design/audit и остальные этапы не получают исключений, даже если карточка совпала. Пустой перечень сохраняет прежний профиль. Перечень перечитывается при каждом запуске/продолжении из доверенного home; его digest отражается в диагностике. Resume не наследует разрешение только из старого sessionId.

### 2. Точные файлы и проверка принадлежности

Удостоверить связанное дерево, его ветку `worktree-<taskId>`, соответствие cwd назначению и gitdir внутри общей .git. Корень main не подходит. Использовать реальные пути и сравнение по компонентам, с Windows-регистром, а не строковый startsWith. Файл должен существовать, быть обычным файлом под `.agents/skills/<имя>/SKILL.md`; абсолютные пути, `..`, `.`, glob, ADS, device/UNC-формы в относительном перечне и произвольные имена отвергаются. Запретить reparse points/symlink/junction в цепочке от дерева до файла и многоссылочные файлы; при невозможности проверить тип отказать. Это ограниченный маршрут правки существующих скиллов, не создание новых каталогов.

Передать проверенный абсолютный перечень в `codexExecutionArgs` отдельным параметром с пустым умолчанием, сохранив существующих вызывающих readiness/perf. На Windows добавить только точные записи `filesystem.<absolute-file>="write"` к нынешнему профилю; не расширять родителя `.agents`/skills, не добавлять новые workspace roots. Сохранить `approval_policy="never"`, `extends=":workspace"`, configured Windows sandbox и нынешние Git/perf исключения. Неназначенные обычные файлы внутри рабочего дерева сохраняют прежнюю writable-политику; отрицательный контроль неназначенных путей относится к защищённым скиллам/конфигурации и внешним деревьям, а не обещает read-only для всего репозитория.

На POSIX прежний маршрут не меняется; непустое защищённое назначение явно сообщает, что этот Windows-механизм на платформе не подтверждён, вместо молчаливого обещания записи. Ошибка CLI/managed policy не вызывает fallback на legacy, unelevated, другого исполнителя или полные права. Если runtime не поддерживает точные файлы, сохранить отказ и остановиться; расширение до каталога не допустимая техническая поправка.

### 3. Регрессия проверяет границы и сквозную передачу

Тестировать resolver отдельно и через `stageCommand → codexStageCommand → codexExecutionArgs`. Проверки: обе цели, пустой список, другая карточка/change/stage, main и чужая ветка, path traversal, похожий префикс дерева, регистр/разделители Windows, ссылки и повтор записи, malformed manifest. Убедиться в отсутствии абсолютных write-grants на корень/родителей и неназначенный скилл, в сохранности Git/perf, approval и режима. Отдельно новый запуск и resume; удаление передачи списка в одном звене обязано ломать тест. Ни заглушка записи, ни корректный argv не считаются живым положительным контролем.

### 4. Ограниченная приёмка в Windows

Добавить явную диагностическую команду `node supervisor/bin/check-project-skill-writes.mjs --run`; без `--run` только описание. Она не запускает супервизор и не трогает доску/его lock. Общий модуль опыта использует тот же resolver и builder запуска, выбранную Windows sandbox и CLI. Встроенные фиксированные fixtures живут строго в собственном `.matchlog/0299-skill-write-probe/` текущего дерева; внутри создаются изолированный Git-корень и назначенное связанное дерево, плюс соседний имитатор чужого дерева. Настоящее дерево 0083 только читается для описи и хешей исходных артефактов/четырёх черновиков, никогда не является целью опыта.

Процесс проверяемого Codex получает cwd только внутреннего назначенного дерева. Тестовые корень и сосед лежат вне этого cwd, но внутри собственного стенда хозяина: отрицательная запись при дефекте безопасна для настоящих деревьев. Не добавлять внешний cwd или весь стенд к writable roots проверяемой сессии. Копии двух скиллов имеют настоящие относительные пути и обычное содержимое, известные хеши; третий неназначенный SKILL.md и `.codex`-контроль тоже существуют. Подготовка стенда делает их доступными хозяину опыта, но не меняет ACL системно и не назначает sandbox-пользователю ручных исключений.

Опыт ограничен одной baseline и одной целевой сессией, каждая до пяти минут, и одним resume целевой сессии до пяти минут. Отдельная подготовка sandbox, если нужна, до десяти минут; тайм-аут не обнуляется продолжением карточки. В baseline точное назначение выключено: фиксированная запись canary в archive-скилл должна отказать. Целевой запуск отличается только штатным назначением двух файлов: native apply_patch записывает известный маркер в оба, native shell читает результат. Resume повторно получает актуальные права и меняет маркер в одном файле. Это заранее объявленная сравнительная диагностика нового профиля, не повтор отказанного действия другой оболочкой в той же сессии.

Отрицательные контроли целевой сессии отдельно пытаются изменить существующий третий скилл, защищённый `.codex`-файл и файл в соседнем тестовом дереве; использовать фиксированные маркеры, которые не исполняются. Для проверки обеих границ инструментов применить native apply_patch и один штатный shell-вызов фиксированного probe-скрипта, который пробует открыть контрольные файлы на запись без изменения байтов. Не принимать простое отсутствие diff за отказ: нужны связанные события политики либо отказ ОС на существующем доступном для чтения файле, плюс независимая проверка неизменности хешей. Любой успешный отрицательный контроль, отсутствие инструмента, неполные события или неподтверждённая подготовка делают результат неуспешным. Сразу остановить оставшиеся записи при неожиданном разрешении; стенд оставить для чтения, не снимать защиты ради уборки.

Сборщик ограничивает список действий, путь, время и число сессий; не позволяет передать произвольный root, target, команду, provider или профиль через CLI. Версия/режим/разрешения и SHA кода, идентификаторы сессий и tool events, исходные/итоговые хеши, stdout/stderr только относящихся к опыту операций, коды возврата и фактическая длительность попадают в очищенный `validation.md`. Ни секреты, env, личные настройки, полные потоки, ни содержимое черновиков туда не копируются. Отдельные сведения помечаются unknown, а не додумываются. Положительный и отрицательный результаты обязательны вместе.

Право запустить такой стенд не даёт текущему исполнителю права менять собственный активный профиль. Команда допускается только в среде, заранее разрешающей этот ограниченный диагностический запуск. Если внешняя sandbox или проверка команды откажет, нельзя запускать её через child_process/другой инструмент/вне sandbox: сохранить точный отказ и воспользоваться действующим routing contract. Не объявлять устранение причины без живой приёмки. Для Claude-этапа точная команда добавляется в stage-settings и проверяется тестом покрытия; это допуск диагностической команды, не доказательство прав Codex.

### 5. Сохранение и продолжение 0083

Перед и после опыта снять только чтением хеши `.openspec.yaml`, proposal/design/tasks и всех specs существующего изменения 0083 и файлов `0083-partial-docs.patch`, `0083-openspec-purpose.mjs`, `0083-openspec-archive.mjs`, `0083-edit-docs.mjs`. Сравнить опись и хеши; отсутствие файла нельзя принять за пустой файл. Изначальные локальные изменения остаются нетронутыми, их наличие не мешает проверке сохранности.

После приёмки и вливания 0299 штатно обновить используемую копию инструмента супервизора; не перезапускать работающий супервизор из дочернего этапа. Следующий назначенный implement 0083 должен получить перечень из обновлённого home, прежние дерево/ветку/change и сохранённые черновики. Простого merge main внутри 0083 недостаточно, если исполняемый provider остался старым. Документировать эту проверку версии инструмента и digest назначения. Возвращение карточки выполняет супервизор по своему контракту, не исполнитель 0299. Не объявлять выполненным пункт 1.1 исходной задачи: после разрешения записи она самостоятельно реализует оба маршрута и проверяет их своим планом.

## Risks / Trade-offs

- Точные права могут не поддерживаться установленным runtime → живая приёмка обязательна; отказ не лечится широким grant.
- Разрешённый файл является инструкцией → только заранее поставленный точный перечень и только implement/revise; никакого чтения grant из текста задачи.
- Живой стенд отличается абсолютным путём от 0083 → одинаковые resolver, относительные цели, linked-worktree topology и профиль обязательны; отдельно проверяется фактическое назначение 0083 без записи в её дерево.
- Удаление стенда упирается в защиту `.agents` → не обходить отказ, не включать остаток в коммит; оставить точный путь и причину для штатной уборки хозяином среды.
- Изменение home во время запуска → фиксировать digest прочитанного назначения для этого запуска, не переоценивать права посреди сессии.

## Migration Plan

Поставка через PR 0299, затем обновлённый инструмент и штатное продолжение 0083. Отдельной миграции карточек и архивации 0083 нет. Откат коммита прав/перечня прекращает новые выдачи прав; уже запущенные сессии не перенастраиваются автоматически, их завершение контролирует владелец запуска.

## Open Questions

Продуктовых вопросов нет. Неизвестен фактический результат точного grant в Windows 0.146.0: его устанавливает ограниченный опыт implement, не это предложение. На design причина не объявляется устранённой.
