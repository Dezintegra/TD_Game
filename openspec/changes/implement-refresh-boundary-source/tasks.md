## 7. Общая проверка каждого атомарного коммита

Каждый checkbox — один самостоятельно собираемый/проверяемый коммит с немедленным push. Допустимы только рабочие правки перечисленных файлов и соответствующая отметка в `openspec/changes/implement-refresh-boundary-source/tasks.md`; формулировка «тот же patch/source-manifest/coverage» означает ровно три пути из 3.1, не каталог целиком. Путь нового дополнительного файла сначала явно назвать в плане, не расширять scope молча.

Перед каждым commit выполнить отдельными вызовами `git -C . diff --check`, `git -C . diff --cached --name-only`, `git -C . diff --cached`; добавлять свои файлы через `git -C . add -- <точные пути>`. В индексе и созданном коммите не должно быть source/build/cache/binary/temporary artifacts из `.matchlog/0372-refresh/` или чужих правок. После commit проверить `git -C . show --stat --oneline HEAD` и `git -C . show --format=fuller HEAD`, затем немедленно `git -C . push -u origin HEAD`. Проверяется содержание diff, а не одно число файлов. Markdown OpenSpec не требует prettier; для новых mjs применить узкий eslint/prettier только по своим точным путям.

Режим check driver обязан собирать затронутые targets и запускать существующие на данном шаге `refresh_boundary` tests из закреплённого рецепта; фильтр group выбирает конкретные тесты с ненулевым счётом, не пропускает компиляцию. Метка partial допустима для промежуточного coverage, но не для готового пакета второго допуска. При превышении двух часов или технической невозможности сохранить уже проверенный результат и точный факт; не отмечать непроведённую сборку/контроль.

## 8. Граница полномочий после списка

Этот список исполняет первый допуск. После 6.1 исполнитель отправляет пакет и возвращает конкретный вопрос о втором допуске по design Decisions 6; все закрытые чекбоксы НЕ равны done всей 0372 или доказанному ремонту. Ожидания CI/ответа и действия хозяина не становятся checkbox. При фактической технической преграде указываются точные данные, доступный способ получения и ответственный; существующая обязательная внешняя предпосылка оформляется по контракту назначения, но обратное ребро 0372 → 0370 не создаётся.

После отдельного допуска план того же изменения дополняется разрешённой read-only приёмкой готовых первичных материалов или подтверждённой преграды. Обязательны absolute paths/hashes/UTC, mapping до read/Git outcomes, раздельные integrity/completeness/causalSufficiency и сохранность пакета до проверенной передачи. Активация и живой запуск идут только через владельца collector 0370, без нового launcher. На текущем design исполняются только создание/валидация/отправка артефактов, ни один пункт реализации не отмечается.
