## ADDED Requirements

### Requirement: Бэклог хранится файлом на задачу

Бэклог SHALL храниться в каталоге `backlog/tasks/` — по одному файлу
`<id>.json` на задачу. Единого файла со списком всех задач быть MUST NOT.

Схема задачи SHALL лежать рядом в `backlog/schema.json` в формате JSON Schema
и SHALL быть указана в каждой задаче полем `$schema`, чтобы редактор
подсказывал состав полей, а проверка схемы работала без внешнего каталога.

Идентификатор задачи SHALL быть устойчивым: он назначается при заведении,
не переиспользуется после закрытия и служит именем ветки, дерева и журнала.

#### Scenario: Две задачи заводятся на разных машинах одновременно

- **WHEN** две рабочие станции заводят по задаче и отправляют изменения
  в `main`
- **THEN** обе задачи попадают в бэклог без конфликта слияния, потому что
  каждая лежит в собственном файле

#### Scenario: Задача не проходит проверку схемы

- **WHEN** файл задачи не удовлетворяет `backlog/schema.json`
- **THEN** сканер конвейера отказывается брать задачу в работу и печатает
  причину с именем поля

### Requirement: Состав задачи

Задача SHALL содержать: идентификатор, тип, заголовок, описание, статус,
приоритет, отметку времени последней смены статуса, историю статусов,
владельца-машину и ссылки на порождённые артефакты — имя изменения OpenSpec,
номер pull request, номер прогона.

Тип задачи SHALL принимать одно из значений: `feature` — доработка,
`run` — прогон с замерами, `note` — замечание, вопрос или задумка владельца
продукта, требующие разбора.

Приоритет SHALL быть целым числом, где меньшее значение означает более
раннее взятие в работу; при равенстве приоритетов раньше берётся задача
с более ранней отметкой заведения.

Задача типа `run` SHALL дополнительно содержать вид прогона (`arena`,
`perf`, `bench-tick`), его параметры и то, ради какого вопроса он
заказывается: без ожидаемого результата прогон нечем истолковать.

#### Scenario: Прогон заведён без ожидаемого результата

- **WHEN** задача типа `run` не содержит формулировки ожидаемого результата
- **THEN** проверка схемы не проходит, и задача не берётся в работу

#### Scenario: Владелец продукта завёл задумку

- **WHEN** пользователь кладёт в бэклог запись типа `note` с вольным текстом
- **THEN** задача принимается со статусом «заведена» и разбирается конвейером
  без дополнительных полей

### Requirement: Автомат состояний

Задача SHALL находиться ровно в одном из состояний: `new` — заведена,
`triage` — разбор замечания, `design` — проработка, `audit` — аудит,
`implement` — имплементация,
`benchmark` — прогон, `pr` — pull request открыт и ожидает проверок,
`review` — ревью, `revise` — доработка по замечаниям, `deploy` — выкладка,
`cleanup` — чистка дерева и веток, `closed` — закрыта, `failed` — ошибка,
`awaiting-po` — ожидание ответа владельца продукта.

Переходы SHALL быть объявлены таблицей и проверяться программно. Переход,
не объявленный в таблице, выполнен быть MUST NOT.

Состояния `failed` и `awaiting-po` SHALL достигаться из любого рабочего
состояния. Возврат из них SHALL вести в то состояние, из которого задача
вышла, а состояние возврата SHALL храниться в задаче.

#### Scenario: Недопустимый переход отклоняется

- **WHEN** сессия пытается перевести задачу из `design` сразу в `pr`
- **THEN** переход отклоняется, задача остаётся в `design`, а попытка
  записывается в журнал

#### Scenario: Возврат из ожидания ответа

- **WHEN** владелец продукта отвечает на вопрос по задаче, ожидавшей ответа
  из состояния `design`
- **THEN** задача возвращается в `design`, а ответ доступен следующей сессии
  из журнала

### Requirement: Маршрут зависит от типа задачи

Задача типа `feature` SHALL проходить полный маршрут:
`new` → `design` → `audit` → `implement` → `benchmark` (если задача требует
прогона) → `pr` → `review` → `deploy` → `cleanup` → `closed`.
Аудит с замечаниями SHALL возвращать задачу в `design`, ревью с замечаниями —
в `revise`, а `revise` SHALL вести обратно в `review`.

Задача типа `run` SHALL проходить коротким маршрутом
`new` → `benchmark` → `closed`, без проработки, ветки и pull request.

Задача типа `note` SHALL проходить маршрут `new` → `triage` → `closed`, где
разбор порождает новые задачи в бэклоге и связывает их с исходной записью.

Мелкие правки в обход проработки допущены быть MUST NOT: любая доработка
кода SHALL иметь изменение OpenSpec.

#### Scenario: Прогон не заводит ветку

- **WHEN** конвейер берёт в работу задачу типа `run`
- **THEN** рабочее дерево и ветка не создаются, а задача сразу переходит
  в `benchmark`

#### Scenario: Разбор замечания порождает доработку

- **WHEN** сессия разбирает задачу типа `note`, содержащую пожелание изменить
  поведение игры
- **THEN** в бэклоге появляется задача типа `feature`, исходная запись
  переходит в `closed`, и обе ссылаются друг на друга

### Requirement: Журнал этапов

Каждая задача SHALL иметь журнал `backlog/journal/<id>.md`, который
дозаписывается при каждой смене статуса и никогда не переписывается целиком.

Запись журнала SHALL содержать дату и время смены статуса, прежнее и новое
состояние, что было сделано на этапе, принятые решения с обоснованием
и ссылки на созданные артефакты. При переходе в `failed` запись SHALL
содержать текст ошибки и то, на каком шаге она случилась.

Журнал SHALL быть исключён из проверки форматирования, потому что он
дозаписывается автоматически, а не редактируется человеком.

#### Scenario: Сессия завершила этап проработки

- **WHEN** сессия закончила проработку и перевела задачу в `audit`
- **THEN** в журнал дописывается запись с датой, парой состояний, именем
  созданного изменения OpenSpec и перечнем принятых решений

#### Scenario: Журнал не ломает проверку формата

- **WHEN** выполняется `pnpm format:check` после дозаписи журналов
- **THEN** проверка проходит, потому что каталог журналов исключён

### Requirement: Вопросы владельцу продукта

Сессия, упёршаяся в решение уровня продукта, SHALL перевести задачу
в `awaiting-po` и дописать вопрос в `backlog/questions.md`, а не выбирать
вариант самостоятельно.

Запись вопроса SHALL содержать идентификатор задачи, состояние, из которого
задача вышла, суть вопроса, перечень вариантов с последствиями каждого
и рекомендацию сессии. Вопрос без вариантов оставлен быть MUST NOT.

Ответ владельца продукта SHALL записываться в тот же файл под вопросом
и SHALL разбираться конвейером: ответ переносится в журнал задачи, задача
возвращается в прежнее состояние.

#### Scenario: Сессия не додумывает за владельца продукта

- **WHEN** при проработке выясняется, что требование допускает два
  несовместимых прочтения
- **THEN** задача переходит в `awaiting-po`, а в файл вопросов попадает
  запись с обоими прочтениями и рекомендацией

#### Scenario: Ответ возвращает задачу в работу

- **WHEN** владелец продукта дописал ответ под вопросом
- **THEN** на ближайшем цикле задача возвращается в состояние, из которого
  вышла, а ответ виден следующей сессии в журнале

### Requirement: Канбан-представление бэклога

Конвейер SHALL перегенерировать статичную HTML-доску по содержимому бэклога
при каждом изменении состава задач или их состояний и публиковать её
на постоянный адрес, не заводя новый адрес на каждую перегенерацию.

Доска SHALL показывать задачи колонками по состояниям, включая отдельную
колонку ожидания ответа владельца продукта, и для каждой задачи — тип,
приоритет, время в текущем состоянии и ссылки на изменение OpenSpec
и pull request.

Доска SHALL быть предназначена только для чтения: управление задачами
остаётся правкой файлов бэклога.

#### Scenario: Задача сменила состояние

- **WHEN** задача перешла из `implement` в `pr`
- **THEN** доска перегенерируется, задача показана в новой колонке,
  а адрес страницы не изменился

#### Scenario: Задача ждёт ответа дольше суток

- **WHEN** задача находится в `awaiting-po` более двадцати четырёх часов
- **THEN** доска выделяет её как требующую внимания владельца продукта
