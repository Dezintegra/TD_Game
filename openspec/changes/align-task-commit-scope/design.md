## Context

На базе `83f57f2` после `fetch origin` и `merge origin/main` дефект подтверждён: `supervisor/skills/design.md` в разделе составления задач не согласует состав коммита с отметкой выполнения, `supervisor/skills/implement.md:234–242` требует отметку перед явным добавлением путей. Исторический раздел 2 `probe-the-deltaless-archive/tasks.md` запрещает всё сверх одного рабочего файла.

## Goals / Non-Goals

Цель — сделать будущие ограничения и проверки выполнимыми при соблюдении обязанности отмечать пункты, не ослабляя границы коммита. Меняется один раздел инструкции проработки. Не-цели перечислены в proposal: историческая задача, реализация супервизора и правила имплементации не переписываются.

## Decisions

1. Добавить один пункт в существующий раздел «Напиши tasks.md», без изменения нумерации этапов. Именно там исполнитель принимает решение о будущей проверке. Правка только исторического примера не устраняет повторение дефекта; отмена отметки в implement ломает учёт выполненного.

2. Описать разрешённый состав как рабочие правки конкретного шага плюс его обязательная отметка в собственном `tasks.md`. Явное добавление обоих путей сохраняется. Проверка имён дополняется просмотром diff: иначе тот же разрешённый файл мог бы протащить постороннюю работу. Широкий допуск всего `openspec/changes/` отвергнут по той же причине.

3. Для запрета временных артефактов назвать их пути, отдельно исходную пустышку и архивированную копию. В примере использовать `probe-archive-sandbox` и фактическую дату архивирования. Проверять индекс до коммита и состав созданного коммита. Количество файлов не различает отметку и пустышку; замена «один» на «два» воспроизвела бы тот же дефект при следующем составе рабочих правок.

4. Проверку правила провести чтением инструкции по сценариям дельты, формат проверить штатной узкой командой. Нового теста, привязанного к словам инструкции, не добавлять: для этой небольшой правки проверяемое содержание и существующие проверки конвейера достаточны. Запуск пробы не нужен: поведение OpenSpec уже проверено исторической задачей, здесь проверяется состав плана.

5. Дельта ADDED в `dev-pipeline-worker` закрепляет новое общее правило; MODIFIED над отсутствующей основной спецификацией недопустим. Архивация после `agent-backlog-pipeline` сохраняет единую способность и её Purpose. Бездельтовый вариант отвергнут: исправляется не единичный пример, а норма составления будущих задач.

## Проверка по сценариям

При чтении новой инструкции проверить следующую таблицу; создавать файлы или настоящие ошибочные коммиты для неё не требуется.

| Предложенный состав | Результат, который требует инструкция |
| --- | --- |
| Рабочая правка и её отметка в собственном tasks.md | Допустить с явным добавлением путей |
| Рабочая правка с предписанием не отмечать пункт | Исправить план: отметка обязательна |
| Рабочая правка и отметка, плюс пустышка | Отклонить по конкретному пути пустышки |
| Рабочая правка и отметка, плюс архивированная копия | Отклонить по конкретному пути копии |
| Рабочая правка и отметка, плюс посторонний файл | Отклонить по разрешённому составу |
| Разрешённые имена, но несвязанные изменения внутри файла | Отклонить по содержанию diff |

## Risks / Trade-offs

- Общее разрешение на `tasks.md` можно прочесть слишком широко → прямо ограничить его отметкой соответствующего пункта и сохранить просмотр содержания.
- Несколько открытых задач трогают `design.md` → добавлять пункт без перенумерации, сверить свежую базу при реализации; не править соседние командные блоки и чужие артефакты.
- Проверка чтением не гарантирует поведение будущей сессии → аудит и ревью получают явные положительный и отрицательные сценарии вместо неявного ожидания.

## Migration Plan

Один атомарный коммит реализации с инструкцией и отметкой собственного пункта, затем немедленная отправка и черновой PR по правилам этапа. Новые планы используют правило после вливания. Обратная миграция исторических планов не требуется. Откат — обратная правка этого пункта инструкции отдельным коммитом.

Изменение не задевает геймплей, рассинхрон, реконнект, состояние мира или раскладку протокола. Эталоны детерминизма и `PROTOCOL_VERSION` не меняются; запреты `Math.random`, `Date.now` и плавающей точки в состоянии ядра соблюдаются отсутствием изменений игрового кода. Замеры кадров и арена не требуются.
