## Decisions

### 1. Отдельный режим существующей диагностики, без нового автомата восстановления

Добавить явный режим `refresh-investigation` к `diagnoseStageTools`, использующий `stageCommand`, `startStage`, provider configuration и hooks учёта 0244. Обычный режим controls сохраняет прежнюю классификацию и 120-секундный бюджет. Новый режим выбирается только конкретным диагностическим назначением; failed этап не включает его сам и не запускает бесконечный сбор.

Планируемые новые файлы: `supervisor/lib/refresh-evidence.mjs` (хранилище и проверка), `supervisor/lib/windows-refresh-observer.mjs` и `supervisor/bin/collect-refresh-evidence.mjs` (узкий host-only вход), `supervisor/refresh-diagnostics.md`. Тесты лежат рядом. Существующий `tool-diagnostics.mjs` остаётся владельцем запуска controls. Host-only CLI не принимает произвольную команду, скрипт, профиль или изменение ACL: только собственный контракт с путями и пределом наблюдения. Не добавлять широкого разрешения на `supervisor/bin/*`.

Отклонено: заменить обычные controls одной сессией глобально — это поменяет независимое подтверждение 0244 и приёмку unrelated stages. Отклонено: новый инцидентный реестр — existing pipeline-incidents/report-store/tool-hold уже владеют этим состоянием.

### 2. Предварительная запись и потоковое сохранение

В назначенном дереве резервируется уникальный `.matchlog/0370-refresh/<collectionId>/` без перезаписи. Сначала долговечно записываются manifest и план, затем разрешается diagnostic launch; ошибки записи предотвращают launch. Manifest включает schemaVersion, taskId 0370, consumerTaskId 0366, source incident reference если дан назначением, host identity, collectionId/launchId, UTC плюс монотонный порядок событий, root/home/cwd, worktree/branch/HEAD и состояние своих исходников.

Параметры берутся из уже разрешённого фактического invocation: executable с реальным путём/хешем/версией, очищенный argv по allowlist, выбранные permission/sandbox параметры, их источник и хеш, env/permissions fingerprints 0244. Полное окружение и сырые произвольные argv не сериализуются. Для загружаемых модулей фиксируются путь и байтовый SHA-256 до старта диагностического runner; повторная сверка обнаруживает изменение. HEAD сам по себе не доказывает версию уже работающего супервизора: его стартовая версия имеет отдельный статус known/unknown. При неизвестной версии старого процесса фиксируется этот пробел, новый runner не выдаётся за него.

После создания диагностического процесса хозяин записывает PID+creationTime+image и связь с parent; подтверждённый thread/sessionId приходит из события провайдера, не из сгенерированного UUID. Запуск должен удерживать первую tool-команду до фиксации доступной процессной идентичности: host observer предварительно вооружён, stdin/команды выдаются только после сохранения launch record. Helper может появиться лишь при refresh: наблюдатель уже работает и сохраняет его до завершения операции; он не выдумывается в prelaunch. В manifest это ожидаемое позднее наблюдение.

События startStage сохраняются по мере поступления: sequence, eventId, invocationId, command, requested/created/finished, timestamps, exitCode либо структурный pre-creation error, очищенный вывод. Записи append-only, с flush на границе наблюдения; в конце seal с хешами файлов. После обрыва читается максимальный корректный префикс, усечённая запись помечается; автоматического продолжения эксперимента нет. Повтор с тем же collectionId отвергается. Host supplement добавляется новым файлом, не исправляет старый manifest.

Первичные фрагменты растущего sandbox log копируются в неизменяемые очищенные файлы: исходный абсолютный путь, byte/line interval, UTC interval, время получения и SHA-256 копии. Хеш всего постоянно дописываемого лога не используется как вечная ссылка. Текст ошибки помогает человеку расследовать, но не становится структурным подтверждением outage.

### 3. Одна сессия и пригодный контроль

Базовый план ограничен двумя новыми диагностическими сессиями последовательно, максимум четырьмя отдельными вызовами в каждой, десятью минутами на весь сбор и двумя минутами на сессию. Предел включает подготовку и завершение записи; таймаут сохраняет partial и снимает только принадлежащее этому runner поддерево через existing killTree. Никакого resume или автоматического повтора сверх плана. Учёт диагностических launchId и usage остаётся через onStart/onResult 0244; host route перед запуском получает тот же бюджетный допуск. Отказ допуска сохраняет not-run, не обходит лимиты автономным CLI.

В каждой сессии: чтение закреплённого несекретного `CLAUDE.md`, `git -C <assigned-cwd> status -sb`, повтор того же чтения, повтор того же Git. Это четыре последовательных tool invocations, а не одна PowerShell-цепочка; content/hash файла сравнивается с исходным снимком. Предусмотреть фиксированный read control в `tool-controls.mjs` для этого режима. Git не делает fetch/merge/push и не меняет refs. Первый запуск даёт наблюдение initial/later refresh в одном процессе; второй — свежую сессию в том же назначенном каталоге при тех же CLI/profile/правах. Разница lifecycle задана заранее; cwd произвольным аргументом инструмента между командами не меняется.

Наблюдать реальные refresh begin/end и PID, а не объявлять каждый tool call refresh. Если CLI не даёт достаточной корреляции и хозяин её не установил, последовательность неполна. Если первый вызов отказал, оставшиеся разрешены только в пределах заранее заданных четырёх: не чинить среду между ними. Модельное сообщение о выполнении без событий не считается результатом.

Контроль второй сессии пригоден лишь при подтверждённых инвариантах: тот же realpath/объект каталога, descriptor до начала, helper image/version, режим и применённые permission inputs, идентичность relevant token либо явное наблюдаемое отличие. Изменение ACL самим штатным refresh сохраняется как наблюдение; это не разрешение скрипту менять ACL. Внешний конкурентный setup, неизвестный helper или дрейф descriptor исключают чистое сравнение lifecycle. Дополнительная сессия «для удачи» запрещена; новый эксперимент требует нового явного плана.

### 4. Read-only наблюдение Windows-хозяина

Хозяин запускает оснастку из отправленного SHA 0370 штатно, вне ограниченной сессии; исполнитель не вызывает runas, UAC, смену sandbox или пользователя. Сбор ориентирован на назначенный диагностический cwd, не на повтор audit 0011 и не на произвольные пути машины. Для каждого защищаемого target и его родителей нужны: lexical/real path, reparse information, file identity, owner, DACL с порядком ACE/наследованием, время до первого вызова и после каждого наблюдённого refresh.

Windows observer использует read-only системные запросы к выбранным процессам и security descriptor. Для refresh фиксируются PID/creationTime/image/hash/version, user/group/restricted-token и integrity/elevation сведения, существенные для проверки доступа; различаются process token и возможный effective thread token. Проверка прав — read-only вычисление effective access к конкретному descriptor для подтверждённого effective token, с методом и ограничениями (WRITE_DAC и относящиеся к наблюдаемой операции права). Нельзя проверять право пробной записью ACL или подставлять токен хозяина/дочернего PowerShell. Если token/query недоступен, сохраняется точный отказ, метод и время; полнота не объявляется.

Предварительный наблюдатель собирает только процессы/пути данной коллекции, не общесистемные секреты. Нативные read-only запросы допустимы внутри host collector; если фактический helper завершается раньше, чем его можно идентифицировать, результат incomplete и следующий различающий опыт должен заранее обеспечить наблюдение именно этой границы. Не обещать наличия API refresh или полей execution_error в установленной версии CLI: проверяется фактический поток. Недостаток структурного события не восполняется разбором фразы для автоматического outage verdict.

Отклонено: получить всё из команды внутри sandbox — до первой команды она не исполнится и покажет чужой токен. Отклонено: импортировать фиксированный fixture 0302 — он проверяет grants 0083, не refresh этой задачи. Общие фактически влитые функции идентификации процессов переиспользуются при совместимости; уникальный observer не управляет их жизненным циклом.

### 5. Две проверки: целостность/полнота и причинная достаточность

`refresh-evidence` возвращает независимые `integrity`, `completeness`, `causalSufficiency`, массив missing с путями полей и основаниями, и ссылки на исходные записи. Он проверяет хеши, границы путей, ordering prelaunch-before-first-command, происхождение identity/profile/helper/token/ACL и корреляцию вызовов одной сессии. Без indispensable поля completeness=false; explicit unknown честно описывает материал, но не засчитывает поле. Старые evidence 0244 остаются пригодными для availability, но без новой схемы не проходят причинную проверку.

Человек, ведущий реализацию, составляет причинную таблицу с первичными ссылками; машинная проверка требует полей и проверяет references, но не объявляет истинность свободного текста. Для приёмки нужен один из результатов:

1. `repair-supported`: доступный контроль и непосредственные наблюдения поддерживают конкретный механизм, по каждой конкурирующей гипотезе названо опровержение либо строгое ограничение вывода. Сам ремонт всё ещё выполняет 0366.
2. `experiment-supported`: современные наблюдения локализуют оставшуюся неоднозначность; задан конкретный опыт с переменной, инвариантами, предсказаниями минимум двух гипотез, измеримым различием, методом захвата, бюджетом, исполнителем и условиями неприменимости. Отсутствие неисправности в текущей пробе не доказывает устранение старой; опыт проверяет только явно сформулированную современную гипотезу.

Заранее заданная таблица для интерпретации:

| Гипотеза | Нужные наблюдения | Различающий признак / ограничение |
| --- | --- | --- |
| Права конкретного каталога | Descriptor/realpath до операции, effective token и требуемая access mask | Отказ доступа уже объясняется проверкой конкретного token+descriptor; один owner без access check недостаточен |
| Токен refresh | Effective token процесса/потока именно refresh, descriptor и helper неизменны | Разные effective rights при том же descriptor различают token от постоянной проблемы каталога; токен shell не годится |
| Helper/version | Реальный image/hash/version и операция при установленных правах | Корректный доступ при повторном отказе оставляет helper-кандидата; сравнение версий без равенства остальных условий ничего не доказывает; обновление/подмена helper здесь не выполняются |
| Жизненный цикл | Время/порядок setup и refresh, process identities, descriptor до/после, одновременные операции | Отказ только позднего refresh и успех свежего процесса при доказанных инвариантах поддерживают зависимость от lifecycle; дрейф token/ACL обязан оставаться альтернативой |

Например, при подтверждённых неизменных helper/token/descriptor и различии initial/later следующий допустимый опыт — две такие же ограниченные последовательности с заранее определённым порядком первого/повторного refresh, собирающие begin/end и состояния до/после. Предсказания: постоянный access-denied повторяется и на первом, lifecycle-гипотеза — только после первого успешного refresh. Если современный материал не установил инварианты, этот пример нельзя принять как готовый вывод; нужен иной конкретный план, выводимый из первичных записей, либо честное незавершение. Ни «команды работают», ни список неизвестных не удовлетворяет приёмке.

#### 6.1. Единственный владелец и подключение учёта

`collect-refresh-evidence.mjs --collect --plan <path>` становится узким одноразовым режимом владельца супервизора, а не независимым collector рядом с ним. CLI делегирует `supervisor/lib/refresh-diagnostic-runtime.mjs`. Модуль использует существующие `createOwnedSupervisor`, `claimSupervisorLock`, `releaseSupervisorLock` из `supervisor-startup.mjs`; долгий lock имеет тот же путь `<project-root>/.pipeline/supervisor.lock`, guard — существующий общий startup/recovery guard. Guard удерживается на время атомарного захвата; долгий lock — до завершения учёта. Не держать guard на всё десятиминутное окно. Живой/неизвестный владелец или занятый guard дают отказ без чтения stages/ledger/report-store и без spawn. Сторож обычного супервизора конкурирует за тот же lock; если он выиграл промежуток между остановкой и сбором, сбор отказывается, не снимает победителя.

После владения runtime читает актуальную конфигурацию обычного хозяина по явно закреплённому configPath и актуальное назначение из штатного read-only адаптера доски, проверяет taskId 0370, stage учёта, отсутствие чужого/живого назначения и совпадение переданных fingerprints. Недоступность или изменение этих данных отменяет запуск. SHA задаёт код оснастки, но не старую копию лимита из ветки. `root` — основной проект; `home` — supervisor отправленной оснастки; диагностический cwd — дерево 0370 из проверенного назначения. Совпадение provider/profile/permission inputs с планом проверяется явно; несовпадение не лечится сменой профиля.

Общие callbacks 0244 вынести без изменения политики в `supervisor/lib/diagnostic-accounting.mjs` и использовать как из `createSupervisor`, так и из diagnostic runtime. Они вызывают `tokenAdmission(task, stage, config, ledger)`, `beginTokenLaunch`, `readCodexAnswer` и `commitTokenLedger` с тем же `readTokenLedger`/`writeTokenLedger(root, config, ...)`. Runtime хранит один актуальный ledger; никаких пустых callbacks или отдельного файла расхода. Для каждой из двух сессий допуск проверяется заново перед spawn, begin сохраняется до spawn, result/usage — до следующей сессии. Расход относится к 0370 и фактическому диагностическому launchId, а не к audit 0011 или произвольно выбранной карточке. Несекретное назначение явно связывает внешний результат с 0370; чужой taskId не принимается как способ получить иной бюджет.

Одноразовый режим не запускает цикл доски, усыновление этапов, readiness model probe, самообновление, восстановление tool hold или incident settlement. Он не вызывает обычный `supervise.mjs` импортом с побочными эффектами. Существующие паузы не удаляет: разрешение диагностического наблюдения под сохранённой tool pause соответствует механизму 0244, но не разрешает обычные этапы или обход API/budget/storage отказа. `--verify` остаётся чистым чтением bundle, без захвата runtime и побочных запусков.

Ошибка записи begin предотвращает spawn. Ошибка записи result останавливает дальнейшие пробы, сохраняет raw result в evidence и в памяти единственного владельца и удерживает lock; повторяется только сохранение того же launchId. Успех повторной записи проверяется перечитыванием ledger под владением, повторного начисления нет. Пока расход не сохранён, нельзя штатно освобождать владение, запускать обычный супервизор или объявлять готовность. Лимит десять минут ограничивает сбор и штатное завершение проб, а не разрешает выбросить несохранённый расход: после него только состояние storage-blocked без модельных запусков. Если и evidence недоступен, результат остаётся в памяти; хозяину сообщается точный отказ и запрет принудительной остановки до сохранения.

При SIGINT/отмене закрыть ввод новых проб, снять только своё поддерево штатным killTree, дождаться завершения потоков, сохранить partial и usage, seal и только затем освободить свой lock. При crash/отключении питания нельзя обещать сохранение ещё не наблюдённых токенов: долговечный begin остаётся незавершённым; доступные raw/session evidence принимает существующее восстановление учёта, под теми же замками, без повторного spawn. Неизвестное не записывается нулём. Не вводить новый реестр восстановления. Возврат к обычному режиму не меняет действующую политику неполного учёта, но требует устранить ошибку сохранения наблюдённого расхода.

#### 6.2. Точные команды и порядок Windows-хозяина

Команды выполняются только хозяином в PowerShell с рабочим каталогом `C:/src/dezintegra/TD_Game`, отдельными вызовами. Они не являются командами сессии implement. План находится в `.matchlog/0370-refresh/host-plan.json` назначенного дерева; включает полный отправленный SHA, хеши модулей, абсолютные root/home/cwd/configPath, fingerprints, назначение, collectionId, разрешение владельца, параметры двух сессий/восьми вызовов и ограничения времени. Прежде чем останавливать процесс, хозяин проверяет отправленный SHA и чистоту исходников оснастки командами `git -C <дерево-0370> rev-parse HEAD`, `git -C <дерево-0370> status --porcelain`, `git -C <дерево-0370> rev-list --left-right --count @{upstream}...HEAD` (последний аргумент в PowerShell заключается в одинарные кавычки). Требуется 0/0, точное совпадение SHA плана и хешей. До конца окна дерево не обновляют. Основное дерево не переключают на ветку 0370.

1. Сохранить несекретную идентичность текущего владельца (PID, creationTime, image, root, home и config) и исходное состояние pause. Если `.pipeline/pause` отсутствует, хозяин создаёт её командой ниже; существующую не перезаписывает. Дождаться завершения текущего цикла и всех этапов, включая исполнителя 0370. Подтвердить по журналу владельца, дескрипторам процессов и сохранённым stages/pending-reports/ledger, что работа завершена и результаты сохранены. Сохранённые неприменённые отчёты допустимы; несохранённый результат, pending accounting, ошибка хранилища, живая сессия или неизвестное состояние запрещают остановку. Одно отсутствие PID в stages или строка «пауза» этого не доказывает. Если подтверждения не получить, сообщить конкретный недостающий факт в карточку через штатный отчёт, не снимать процесс вслепую.

В настоящем foreground допустим Ctrl+C самому владельцу и ожидание его выхода; Ctrl+C в watch владельца не останавливает. Отдельного `supervisor/bin/stop.mjs` нет.

Повторно проверить, что сторож не поднял нового владельца. CLI сбора также проверяет эти условия и атомарно получает существующие замки: чтение runtime до этого запрещено. Не называть передачу владения восстановлением исходного инцидента: новый процесс меняет lifecycle, это явное условие опыта.

Отклонено: `--stop` при живых этапах, удаление занятого lock, изменение лимитов/ACL/профиля — не относится к разрешённой передаче. Окно уже разрешено, повторного вопроса владельцу не требуется; конкретная техническая невозможность фиксируется с причиной.

#### 6.3. Проверка производственной композиции

`refresh-diagnostics-contract.test.mjs` вызывает тот же экспортированный entry/runtime, который вызывает CLI, с реальными `claimSupervisorLock/createOwnedSupervisor`, бюджетными функциями 0244 и сериализацией общего ledger. Подменяются только границы ОС, spawn, часов и чтения доски; успешные callbacks вместо реального учёта недопустимы. Файловый стенд использует отдельный корень внутри назначенного дерева, не `.pipeline` основного проекта. Проверки: занятый/неизвестный владелец и guard дают ноль runtime reads/writes/spawn; исчерпанный бюджет даёт ноль spawn; сохранённый begin предшествует spawn; результат первой сессии меняет допуск второй; ошибка begin/result write удерживает запуск/освобождение; повтор сохранения не удваивает расход; cancellation ждёт выхода проб и flush перед release; crash оставляет pending launch без replay; поздний release не снимает чужой lock; обычный runtime после передачи читает новый расход и сохраняет чужие задачи/отчёты. Отдельно проверить дрейф SHA/config/task, гонку со сторожем и чистый `--verify`. Отрицательный контроль обязан обнаружить обход gate или ранний release в производственной композиции. Это проверки оснастки, не живые регрессии ремонта 0366.

Host-only запуск не становится чекбоксом «исполнитель запускает хозяина». Исполнитель формирует контракт по отправленному SHA и возвращает blocked с адресной предпосылкой внешнего read-only сбора, если пригодных материалов ещё нет. Сначала сверить актуальную доску: существующую работу с тем же современным контрактом использовать, не создавать дубль; закрытая историческая 0369 и стендовая 0307 этим контрактом не являются. Новая обязательная заявка, если понадобится, имеет area pipeline, categories infrastructure, workKind service и конкретный result: immutable bundle с современной последовательностью, контролем, identity/profile/helper/token/target evidence и путями/хешами/временем. Она зависит от наличия отправленной оснастки, не от завершения 0370; обратного ребра на 0370 не добавлять.

После результата новый анализ 0370 принимает/отвергает bundle и продолжает существующие артефакты. Последний пункт tasks — проверка и интерпретация готового сбора, не чужое действие. В итоговой `validation.md` сохраняются manifest SHA-256, абсолютные пути, UTC, полный перечень primary references, результаты checker, ограничения и причинная таблица. Через отчёт это передаётся 0366. Текущий design ничего не пишет в чужие change/карточки и не объявляет её разблокированной.

## Risks / Trade-offs

- Наблюдение helper/token может быть запрещено даже хозяину → сохранить точный отказ, не расширять права; неполный bundle не принять. Продуктового выбора для подготовки оснастки не требуется.
- Предварительные hashes могут ошибочно выдаваться за загруженный старый код → отдельно именовать runner snapshot и доказанную стартовую версию supervisor; неизвестное не заменять HEAD.
- Наблюдатель влияет на timing → ограничить сбор, записывать interval/overhead; контроль обязан использовать тот же наблюдатель. Timing сам по себе не доказывает гонку.
- Логи содержат лишние данные → allowlist serialization до записи, bounded очищенные extracts; тест с секретом-канарейкой. Не читать полное окружение/secret stores для наполнения новых полей.
- Сбор зависнет либо оборвётся → конечные лимиты, incremental flush, recovery без повторного запуска; не затрагивать чужие процессы.

## Migration Plan

Аддитивная versioned evidence schema; существующие records, budgets, отчёты и incident state не мигрируются и не переинтерпретируются. Новая интеграция записывает manifest до launch и ссылки в имеющийся diagnostic result. Legacy records дают explicit incomplete для нового checker, но сохраняют прежний availability verdict. Откат кода прекращает новый сбор и оставляет первичные файлы; автоматического удаления нет. Служебный PR не требует выкладки игры.

## Validation

На implement: `pnpm install --frozen-lockfile --prefer-offline`, затем `pnpm test:pipeline` с нужными файлами. Fixtures проверяют отказ до первой команды и поздний отказ как свойства сохранения данных, а не как доказательство ремонта Windows (обе живые регрессии ремонта остаются 0366). Обязательны контроли отсутствующего поля, порчи хеша, чужой сессии, reuse PID, missing refresh, ложного сообщения модели, прерывания и storage failure. Полный verify, матчевые тесты, сборка игры, арена и замеры не нужны.
