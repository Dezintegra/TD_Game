## ADDED Requirements

### Requirement: Имплементация различает подготовку по плану и слияние соседней ветки

Правила `implement` SHALL предписывать выбирать способ подготовки по согласованным `design.md` и `tasks.md`. Порядок вливания PR сам по себе требовать включения соседней ветки в дерево или превращаться в обязательное предусловие запуска MUST NOT. Подготовка по отправленной версии открытого PR SHALL быть допустима, если она предусмотрена планом; исполнитель SHALL соблюдать указанные планом источник, состав собственной правки и последующую проверку после интеграции. Явное предусловие запуска этим разрешением обходить MUST NOT.

Обязательное обновление главной до первой правки задачи и установки зависимостей SHALL сохраняться. При конфликте `origin/main` исполнитель SHALL выяснить причины обеих сторон, разрешить конфликт с сохранением поведения main и требований задачи, затем проверить результат. В споре main SHALL служить основой для адаптации кода задачи. Сам конфликт причиной `failed` быть MUST NOT; доказательная остановка определяется требованием merge-conflict-resolution.

При конфликте дополнительного слияния соседней ветки исполнитель SHALL отменить это слияние командой `git -C <дерево> merge --abort`, проверить успешность отмены и состояние своего дерева, затем проверить доступность предусмотренного планом способа подготовки. При доступном способе он SHALL продолжить по плану; конфликт дополнительного слияния сам по себе основанием `failed` быть MUST NOT. Если отмена не удалась либо подтверждена техническая невозможность выполнить предусмотренный способ (ошибка доступа к существующей ревизии, ошибка инструмента, конфликт обязательного по плану слияния без альтернативы), исполнитель SHALL завершиться с `failed`, назвав конкретную причину, конфликтующие файлы и результат проверки способа (либо почему до неё нельзя безопасно дойти). Техническую ошибку доказательством отсутствия предмета считать MUST NOT. Неизвестные конфликты вслепую разрешать, затирать собственные или чужие правки и самостоятельно заменять согласованный план он MUST NOT.

При совместном чтении с требованием «Исполнитель сохраняет ожидание предмета через blocked» изменения `return-premature-tasks-to-the-queue` правила SHALL применять следующий приоритет: явное предусловие запуска сохраняется; при безопасном состоянии дерева доступная подготовка, прямо предусмотренная согласованным планом, исключает вывод об отсутствии предмета только по отсутствию файла в main; лишь затем проверяется случай отсутствующего предмета. Это уточнение SHALL ограничивать определение отсутствующего предмета и сценарий «Имплементации нечего править» соседнего требования: наличие файла только в открытом PR само по себе недостаточно, если план разрешает и позволяет подготовить собственную правку по его отправленной версии. Наличие либо отсутствие собственного PR этот разрешённый способ менять MUST NOT.

Если на свежей базе делом подтверждено ожидание результата другой задачи, а доступной подготовки по плану нет, исполнитель SHALL использовать действующий blocked с reason/result и проверяемой ссылкой при любом состоянии собственного PR. Начатая работа и артефакты SHALL сохраняться. Отдельный premature, его счётчик и второй граф ожидания вводиться MUST NOT. Непроверенное подозрение или ошибка доступа доказательством отсутствия предмета быть MUST NOT.

Различение SHALL быть явно изложено в `supervisor/skills/implement.md` и защищено проверкой конвейера, которая при потере обязательного условия называет этот файл. Проверка SHALL различать область правила обновления главной и дополнительную подготовку, а не удовлетворяться словами о конфликте в любой части документа.

#### Scenario: Подготовка задачи 0169 доступна после конфликта соседнего слияния

- **WHEN** `origin/main` успешно обновлена, PR 126 открыт, план задачи 0169 предусматривает получение конкретного файла из отправленной версии PR и собственную правку, чтение файла доступно, а дополнительное слияние всей ветки конфликтует
- **THEN** исполнитель отменяет дополнительное слияние, проверяет восстановление дерева и доступность предусмотренного получения файла, продолжает подготовку по плану и сохраняет порядок последующей интеграции PR; открытый PR и конфликт не становятся новым предусловием запуска или самостоятельной причиной `failed`

#### Scenario: Подготовка сразу идёт предусмотренным способом

- **WHEN** план разрешает подготовить файл по отправленной версии открытого PR и не требует слияния его ветки
- **THEN** исполнитель использует этот способ без обязательной попытки слить соседнюю ветку

#### Scenario: Конфликт обязательного обновления главной

- **WHEN** слияние `origin/main` в дерево имплементации конфликтует
- **THEN** исполнитель выясняет причины обеих сторон и разрешает конфликт, используя main как основу в споре и адаптируя код задачи; проверяет результат, включая связанные автоматически объединённые участки

#### Scenario: После отмены дополнительного слияния способ недоступен

- **WHEN** дополнительное слияние отменено, конкретная отправленная версия файла существует, но получить её невозможно из-за проверенной ошибки доступа или инструмента, независимо от наличия собственного PR
- **THEN** исполнитель возвращает `failed` с причиной недоступности и результатом проверки, не ограничивая объяснение конфликтом соседнего слияния и не выбирая сам иной план

#### Scenario: План действительно требует слияния ветки

- **WHEN** согласованный план требует именно слияния соседней ветки, оно конфликтует и альтернативного способа план не предусматривает
- **THEN** исполнитель отменяет слияние, проверяет план и возвращает `failed`, называя неисполненное условие и файлы, без разрешения неизвестных конфликтов вслепую

#### Scenario: Не удалось отменить дополнительное слияние

- **WHEN** команда отмены дополнительного слияния завершилась ошибкой либо проверка обнаружила незавершённое слияние
- **THEN** исполнитель не приступает к подготовке файла, возвращает `failed` с фактической ошибкой и не сбрасывает дерево ради продолжения

#### Scenario: Явно требуется дождаться вливания перед запуском

- **WHEN** задача имеет явное предусловие запуска с подтверждённым вливанием соседнего PR
- **THEN** разрешение подготовки по открытому PR не отменяет это предусловие и не разрешает исполнителю менять его

#### Scenario: Из инструкции исчезло различение

- **WHEN** из блока подготовки удалено требование разрешения конфликта обновления `origin/main`, выбор способа по плану, отмена дополнительного слияния, проверка доступности способа, разграничение отсутствия предмета и технической ошибки, правило blocked с сохранением собственного PR или запрет неизвестных конфликтов
- **THEN** проверка инструкции падает с указанием `supervisor/skills/implement.md` и потерянного условия

#### Scenario: Файл только в открытом PR и собственного PR ещё нет

- **WHEN** main обновлена, собственного PR нет, нужный файл есть только в отправленной версии открытого соседнего PR, подготовка по этой версии явно разрешена планом и доступна, явного запрета запуска нет
- **THEN** исполнитель продолжает предусмотренную подготовку; сценарий «Имплементации нечего править» не применяется, потому что отсутствие файла в main не исключило согласованную работу

#### Scenario: Разрешённая подготовка при уже открытом собственном PR

- **WHEN** при тех же условиях доступной подготовки собственный PR уже открыт
- **THEN** исполнитель продолжает по плану; наличие собственного PR не превращает доступную работу в ошибку

#### Scenario: Предмет ещё не появился и подготовки нет

- **WHEN** main обновлена, нужный предмет должна принести другая задача, доступной подготовки нет и это подтверждено
- **THEN** исполнитель возвращает blocked с reason/result и ссылкой; сохраняет уже открытый PR, а если собственного PR нет — не открывает его ради ожидания

#### Scenario: Неподдерживаемый исход из прежнего плана

- **WHEN** старый план предлагает premature, а действующий обработчик предоставляет blocked
- **THEN** используется действующий blocked при доказанном ожидании; новый исход и повторные круги не вводятся
