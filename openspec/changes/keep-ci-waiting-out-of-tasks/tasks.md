# Задачи

Каждый шаг — отдельный коммит, проверяемый сам по себе. Изменение не заводит
ни строки кода приложения: правятся два текста правил конвейера и один его
сторожевой тест, поэтому ни сборки, ни матчевых тестов, ни замеров здесь нет,
а проверки везде узкие и идут по своим файлам.

**Команды даны формой, покрытой правилами разрешений** — `git -C <дерево> …`,
где `<дерево>` — путь из поля `worktree` назначения. Покрытие сверено
с `supervisor/config/stage-settings.json`: правило `PowerShell(git -C:*)`
стоит строкой 65, `PowerShell(pnpm test:pipeline:*)` — строкой 120,
`PowerShell(npx prettier:*)` — строкой 102.

**Шага «дождаться зелёного CI» в этом списке нет намеренно** — см. раздел
«Чего в списке нет». Список задач, поставивший такой шаг, опровергал бы
правило, которое сам же вводит.

## 1. Открыть черновой pull request на артефактах проработки

- [ ] Артефакты проработки (`proposal.md`, `design.md`, `tasks.md`,
      `specs/dev-pipeline-worker/spec.md`) уже лежат в ветке отдельным
      коммитом — отправить ветку, если она ещё не отправлена
      (`git -C <дерево> push -u origin HEAD`), и открыть черновой pull
      request в `main`:
      `gh pr create --draft --base main --title "<заголовок>" --body-file <файл>`.
- [ ] Тело pull request писать файлом: `--body` длинной прозой отказывается
      ещё до вызова `gh`.

**Проверка:** `gh pr view <номер> --json number,state,isDraft` отвечает
`OPEN` и `true`; `gh pr checks <номер>` показывает запущенные проверки —
взглядом, один раз, не карауля. Шаг стоит первым не из вежливости: до
появления pull request пуши в ветку не запускают CI вовсе, и каждый
следующий коммит остался бы непроверенным.

## 2. Запретить в скилле проработки шаг ожидания зелёного CI

- [ ] В `supervisor/skills/design.md`, шаг 10 («Напиши `tasks.md`»), добавить
      пункт-запрет **последним в перечне шага 10**: сразу после пункта
      о форме команд, кончающегося словами `git merge origin/main`
      (строка 212 в `main`), и **выше** пустой строки перед заголовком
      `11. **Проверь форму.**`. Ниже не спускаться ни строкой.
- [ ] Пункт обязан содержать две подстроки целиком, каждую **на одной
      строке**, без переноса: `шага ожидания зелёного CI` (предмет запрета)
      и `опрашивает проверки сам` (его причина). Сторож шага 3 сверяет
      именно их, а перевод строки внутри фразы он видит обычным знаком
      и подстроку не найдёт.
- [ ] В пункте назвать механизм поимённо, файлами без номеров строк:
      проверки опрашивает супервизор (`supervisor/lib/io.mjs`, функция
      `summariseChecks` и вызов `gh pr view --json statusCheckRollup`),
      задачу из состояния `pr` двигает он же
      (`supervisor/lib/apply-report.mjs`, `applyExternal`: зелёные — в
      `review`, красные — в `revise`), а исполняющей сессии ждать запрещено
      (`implement.md`, шаг 8). Номера строк не писать: они разъезжаются
      при первой правке соседнего кода, а разъехавшейся ссылке читатель
      верит.
- [ ] Назвать и то, что смысл не теряется: «задача не сделана, пока GitHub
      не сказал зелено» стоит в правиле 6 `CLAUDE.md`, черновой статус
      снимает ревью первым подшагом вливания.

**Проверка:**

- поиском по `supervisor/skills/design.md`: обе подстроки встречаются
  ровно по одному разу и каждая целиком лежит на одной строке;
- `npx prettier --check supervisor/skills/design.md` — зелёный. Каталог
  `supervisor/` из проверки формата не исключён (`.prettierignore` называет
  только `openspec/`, `manage/` и рабочие деревья), а вставка кода,
  перешедшая на другую строку, теряет отступ — беда задачи 0184;
- `pnpm test:pipeline` — зелёный. Сторожа на новый пункт ещё нет, и падать
  тут нечему: проверка эта ловит поломку соседних сторожей, чей текст
  правка задевать не должна;
- `git -C <дерево> diff --stat` показывает ровно один изменённый файл.

## 4. Оговорить в скилле ревью открытый пункт ожидания проверок

Оговорка и её сторож едут **одним коммитом**: сторож без оговорки красен,
а шаг обязан проверяться сам по себе, без следующего, который всё починит.

- [ ] В `supervisor/skills/review.md`, шаг 6, в мерке «По спецификации
      изменения» — сразу после фразы про галочку у задачи-замера — добавить
      оговорку с подстрокой `недоделкой не считается`, целиком на одной
      строке. Оговорка узкая: она об одном лишь неотмеченном пункте
      ожидания зелёного CI, всякий иной открытый пункт остаётся замечанием.
- [ ] В оговорке сказать, откуда ревью берёт зелень (её проверяет
      супервизор, ревью смотрит итог один раз в шаге 3) и чем измеряется
      срок самой оговорки: она нужна для десяти уже написанных списков
      задач и снимается, когда последний из них уедет в архив. Числа
      заархивированных не писать вовсе: на 04.09.2026 не заархивирован
      ни один из десяти, а счёт этот меняется каждой архивацией и в файле
      правил устареет молча. Мерка срока — сам архив, а не цифра.
- [ ] В `supervisor/config/transitions.test.mjs`, тем же коммитом, добавить
      вторую проверку — `skillText('review')` содержит подстроку
      `недоделкой не считается`. Отдельной от проверки шага 3, чтобы
      по красному прогону было видно, чьё именно правило вычистили.

**Проверка:**

- `pnpm test:pipeline` — зелёный, обе новые проверки в выводе;
- **порчей:** убрать оговорку из `supervisor/skills/review.md`, прогнать
  `pnpm test:pipeline`, убедиться, что падает именно вторая новая проверка
  и называет `review.md`; вернуть оговорку и прогнать снова;
- `npx prettier --check supervisor/skills/review.md supervisor/config/transitions.test.mjs`
  — зелёный;
- `npx eslint supervisor/config/transitions.test.mjs` — зелёный;
- `git -C <дерево> diff --stat` показывает ровно два изменённых файла.

## Чего в списке нет

- **Шага «дождаться зелёного CI».** Его и запрещает это изменение: зелень
  опрашивает супервизор (`supervisor/lib/io.mjs`) и сам двигает задачу
  из состояния `pr` (`supervisor/lib/apply-report.mjs`), а исполняющей
  сессии караулить проверки запрещено. Взглянуть на итог один раз после
  первой отправки полезно, и это уже записано в шаге 1 как часть проверки,
  а не отдельным шагом.
- **Правки `tasks.md` чужих изменений.** Пункт стоит в десяти открытых
  изменениях, и трогать их отсюда нельзя: сторонняя правка даёт конфликт
  при слиянии (`design.md` изменения `write-covered-commands-in-tasks`,
  Решение 4). До того как их поправит собственная работа этих веток, их
  прикрывает оговорка шага 4.
- **Правки `implement.md`.** Его шаг 8 и шаг 5.3 верны и остаются дословно:
  беда не в том, что исполнитель не ждёт, а в том, что пункт заводят.
- **Правки определения исхода `done`.** Общая формула беды — предмет
  задачи 0087, и она не поехала; подменять ею наш узкий случай нельзя.
- **Прогона арены.** Правила игры, цены, доход, сила юнита и темп не задеты
  ни строкой: правятся два текста правил конвейера и его сторожевой тест.
- **Замера кадров и стоимости тика.** Ни `packages/`, ни `apps/` не задеты,
  отрисовка и игровой цикл остаются теми же.
- **`pnpm verify`, `pnpm test` и `pnpm test:match`.** Из дополнительного
  дерева их не запускают — это делает CI (правило 6 `CLAUDE.md`).
  `pnpm test:pipeline` не в счёт: правку в `supervisor/` проверяют именно
  им, узким прогоном по своему файлу тут не обойтись, потому что сторожа
  конвейера лежат в чужих файлах.
