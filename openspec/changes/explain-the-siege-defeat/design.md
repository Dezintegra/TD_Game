# Как это устроено

## Главное решение: измерить, а не починить

Механизмов, каждый из которых объясняет провал целиком, названо четыре
(см. `proposal.md`). Выбрать один по рассуждению нельзя: они не исключают
друг друга и все опираются на верные числа. Поэтому изменение не правит
осадный профиль вовсе, а даёт два прибора — разбор трат по профилям
и семью однопольных пробников, — после которых причина называется
цифрой, а не догадкой.

**Отвергнуто: починить сразу.** Соблазн понятен — поздняя фаза
начинается на трёхсотой секунде, медиана матча 417 секунд, сдвинуть
границу выглядит очевидным. Но ровно так же очевидно выглядела и правка
«дешёвое разбирает казну», её сделали, и перекос её пережил. Вторая
догадка подряд, попавшая в код без замера, стоила бы третьей.

## Разбор трат по профилям

### Откуда берётся имя профиля

Имя стороны лежит только в таблице `match` — двумя столбцами,
`profile_0` и `profile_1`. Таблицы `decision`, `attempt` и `command`
знают лишь номер стороны. Поэтому в основании раздела лежит
разворачивающее выражение: обе стороны каждого матча превращаются
в строки `(match_id, player, profile)` объединением, и всё остальное
соединяется с ним.

```sql
with side as (
  select match_id, 0 as player, profile_0 as profile from match
  union all
  select match_id, 1 as player, profile_1 as profile from match
)
```

Это то же построение, каким уже считаются доли побед по профилям
в `reportBatch`, и взято оно оттуда намеренно: два способа отвечать
на вопрос «чей это профиль» однажды разошлись бы.

**Отвергнуто: группировать по `profile_0`.** В зеркальном прогоне
`profile_0` и `profile_1` совпадают, и такая группировка потеряла бы
половину решений, не сказав об этом. Проверок с зеркальными прогонами
в очереди баланса больше, чем с разными профилями.

### Как считается каждая величина

| величина | как | почему так |
| --- | --- | --- |
| заказано юнитов, построек, прокачки | `command` где `accepted = 1`, соединённая с `decision` по `tick - 1` | решение записывается до шага мира, команда — после; смещение уже используется в `reportMatch` |
| заявленная доля | из самого профиля через `profileByName` | единственный источник истины о намерении — сам профиль |
| доля решений по фазам | `decision.phase_index`, доли от числа решений стороны | фаза уже записана в каждом решении; второй раз считать её по тику значило бы завести вторую истину о границах фаз |
| самая поздняя фаза | `max(phase_index)` по стороне, усреднённое по сторонам | «дожил ли профиль до своей манеры» — вопрос про сторону, а не про пачку |
| помехи покупке | `attempt.note`, доли | таблица заведена ровно под вопрос «чего не произошло» |
| длина накопления и упор в предел | `decision.wait_streak` и `impatient` | тот же расчёт, что в `reportMatch`, сложенный по пачке |
| медиана казны | `sample.energy`, запросом с `order by … limit 1 offset` | выгружать сотни тысяч снимков в память ради одного числа незачем |

**Отвергнуто: считать медиану в TypeScript.** Шестьдесят матчей по
двенадцать минут дают около полутора миллионов снимков; сводка,
поднимающая их в память, перестала бы работать ровно на тех пачках,
ради которых заведена.

### Что печатается и в каком порядке

Профили печатаются по имени, по возрастанию. Порядок устойчив нарочно:
сводки двух прогонов сличают глазами и `diff`, а порядок «по числу
побед» перетасовывал бы разделы от прогона к прогону.

Нулевые строки не печатаются, кроме одной — «объявлено профилем,
но не куплено ни разу». Это единственный случай, когда ноль и есть
ответ, и `reportMatch` уже поступает так же.

Объём: два профиля в пачке дают два раздела примерно по двадцать строк.
Требование «сводка читается целиком» этим не нарушается.

### Никаких новых сведений в момент матча

Раздел целиком производен от уже собираемых таблиц. Это осознанное
ограничение: всякий новый факт в логе обесценивает уже сыгранные матчи
(их пришлось бы переигрывать, чтобы сравнивать), а схема базы,
наоборот, пересобирается из старых логов без единого матча.

**Отвергнуто: записывать, кто кого убил.** Это ответило бы на вопрос,
гибнут ли осадные машины о башни или о толпу, и заметки
`fortify-approaches` прямо его просят. Но в `packages/sim` нет канала
событий вовсе: `step` — чистая функция, возвращающая состояние.
Завести канал значит тронуть ядро и обновить эталоны детерминизма тем же
коммитом — работа отдельного изменения с отдельным разбором цены.
Вопрос **этого** изменения — что осадный профиль купил и что ему
помешало — отвечается таблицами, которые уже есть.

## Семья пробных профилей

### Собираются раскрытием, а не переписыванием

```ts
export const SIEGE_PROBE_PATIENCE_PROFILE: AiProfile = deepFreeze({
  ...SIEGE_PROFILE,
  id: 'siege-probe-patience-2026-08',
  spending: {
    ...SIEGE_PROFILE.spending,
    savingHorizonSeconds: BASELINE_PROFILE.spending.savingHorizonSeconds,
  },
});
```

Два свойства этой записи существенны, и оба стоят того, чтобы их назвать.

Первое: возвращаемое значение берётся **из базового профиля**, а не
пишется числом `45`. Правка базового горизонта доедет до прибора сама;
списанное число молча разошлось бы с оригиналом.

Второе: раскрывается `SIEGE_PROFILE`, а не `BASELINE_PROFILE`. Прибор
изучает осадный профиль, значит совпадать он обязан с ним.

Поля фаз подменяются так же, но на два уровня глубже: раскрывается
список фаз, в нём — одна фаза по индексу, а в ней — одно поле. Фаза
целиком не подменяется никогда, и почему — сказано ниже.

```ts
/** Фаза базового профиля по номеру. Отсутствие фазы — ошибка сборки. */
const baselinePhase = (index: number): PhaseProfile => {
  const phase = BASELINE_PROFILE.phases[index];
  if (phase === undefined) throw new Error(`в базовом профиле нет фазы ${index}`);
  return phase;
};

/** Пробник, подменяющий одно поле одной фазы. */
const siegeProbe = (id: string, index: number, field: Partial<PhaseProfile>): AiProfile =>
  deepFreeze({
    ...SIEGE_PROFILE,
    id,
    phases: SIEGE_PROFILE.phases.map((phase, at) => (at === index ? { ...phase, ...field } : phase)),
  });

export const SIEGE_PROBE_LATE_MIX_PROFILE = siegeProbe('siege-probe-late-mix-2026-08', 2, {
  mix: baselinePhase(2).mix,
});
```

Проводник `baselinePhase` заведён не для красоты: в проекте включено
`noUncheckedIndexedAccess`, и обращение по индексу даёт тип «фаза или
`undefined`». Тот же приём уже применён в `profile.match.test.ts`.

Фазы берутся **по индексу, а не поиском по содержимому**: средняя фаза
у обоих профилей вторая, поздняя — третья, и совпадение это структурное,
а не случайное. Поиск «фазы, у которой `untilSecond` равен трёмстам»
сломался бы от первой же правки границ, причём молча — найдя не ту фазу
или не найдя никакой.

### Состав семьи задан правилом и проверяется тестом

Семья содержит пробник **на каждое поле, которым осадный профиль
отличается от базового**, кроме поимённо названного мёртвого. Отличий
восемь, мёртвое одно (`push.waveSize`: `baseShare` равен единице,
рывок закрыт, размер волны не читает никто), пробников семь.

Правило это не пожелание к аккуратности, а единственное, что делает
ответ прибора истолковываемым. Семья, покрывающая часть отличий,
при нулевом сдвиге у всех своих пробников говорит не «причина
не в профиле», а «причина в чём-то из неизмеренного» — то есть не говорит
ничего, зато после целого прогона арены.

Полнота закрепляется тестом в том же `packages/ai/src/probe.test.ts`:
перечень полей, подменяемых семьёй, сравнивается с перечнем расхождений
`SIEGE_PROFILE` и `BASELINE_PROFILE`. Расхождение, не закрытое ни одним
пробником и не занесённое в список мёртвых, роняет проверку и называет
поле. Значит, правка осадного профиля через полгода не сможет молча
оставить семью неполной — а именно так неполнота и появляется.

Список мёртвых полей живёт в коде рядом с семьёй, а не в этом документе:
довод «поле не читается» проверяем только по коду, и лежать он обязан
там, где его увидит правящий.

### До какой глубины считается расхождение

Сравнение идёт вглубь по вложенным объектам настроек (`spending`,
`push`, `building`, `escort`, `movement`, `posture`, `nuke`) и по фазам
списка `phases` — по индексу. Но останавливается оно на **словарях весов
и списках**: `upgrades`, `mix`, `towerMix`, `spend`, `frontierFractions`
считаются одной величиной каждый.

Граница выбрана по тому, как поле подменяется. Пробник возвращает
к базовому словарь весов целиком — потому что вес в словаре осмыслен
только рядом с прочими весами: «прокачка Теслы, вес 1» значит совсем
разное при `Base 4` и при `Base 40`. Считать такой словарь несколькими
полями значило бы требовать пробников на величины, которых по одной
не существует.

**Отвергнуто: один пробник на всю позднюю фазу.** Он напрашивается —
одна подмена вместо четырёх, и семья вышла бы из четырёх профилей вместо
семи. Но поздняя фаза отличается четырьмя полями сразу, и такой пробник
померил бы их сумму — ровно тот порок, ради избавления от которого семья
и заведена. Разница не умозрительная: `mix` («только Тесла») и `spend`
(«производство первым») тянут в разные стороны, и сложенные в одно число
они друг друга гасят.

**Отвергнуто: не заводить пробников на позднюю фазу вовсе.** Довод был
такой: медиана матча 417 секунд при границе фазы в 300, три четверти
матча проходят в средней фазе, значит поздняя ни при чём. Довод неверен
в основании — «фаза почти не наступает» это догадка, и она первая
из четырёх названных, — а прибора, который бы её проверил, при таком
решении не остаётся ни одного. Хуже того, без поздних пробников
неизмеренной остаётся именно та часть профиля, которая и делает его
осадным.

**Отвергнуто: один «правильно собранный» осадный профиль.** Собрать
профиль, играющий осадную манеру как надо (волна, прикрытие, дальность
Теслы — всё то, что умеет `swarm-siege-2026-08`), и сравнить с нынешним
было бы быстрее. Но такое сравнение меряет сумму отличий, а сумму
на слагаемые разложить нечем — и ответом на «почему проигрывает» стало бы
«потому что он не тот профиль».

**Отвергнуто: ключ командной строки, подменяющий поле.** Соблазнительно
не заводить профилей вовсе, а дать арене ключ вида
`--override spending.savingHorizonSeconds=45`. Против этого два довода.
Профиль неизменяем по требованию спецификации — подмена снаружи ломала бы
это свойство в самом чувствительном месте. И в запись матча попадает имя
профиля: матч, сыгранный подменённым `siege-2026-08`, был бы в базе
неотличим от матча, сыгранного настоящим, а значит несравним ни с чем.

### Приборы остаются в реестре

Разобравшись, пробники не удаляются — как не удалены
`swarm-patient-2026-08`, `wall-light-2026-08` и `long-range-2026-08`.
Прибор с записанным вопросом стоит дороже места в реестре: следующий,
кто усомнится в том же, получит готовый ответ, а не повод переставить
опыт заново.

### Проверка «отличается ровно одним полем»

Тест сравнивает пробник с `SIEGE_PROFILE` поле за полем и требует ровно
одного расхождения — названного. Живёт он в **быстром** наборе, отдельным
файлом `packages/ai/src/probe.test.ts`, а не в `profile.match.test.ts`.
Причина прямая: это сравнение двух замороженных объектов, матч ему
не нужен, а всё, что попадает в матчевый набор, откладывает ответ
на четверть часа.

Сравнение идёт вглубь: `push` и `spending` — вложенные объекты, и
поверхностное сравнение объявило бы расхождением любую перезаписанную
ветку целиком, не сказав, какое поле внутри неё изменилось. Тот же обход
служит и проверке полноты семьи, и написан он поэтому один раз.

Отдельная тонкость про раннюю фазу: у осадного профиля она — объект
`EARLY_ECONOMY`, у базового — первый элемент `BASELINE_PHASES`. Это
разные объекты с одинаковым содержимым, и сравнение обязано быть
по значению, а не по ссылке. Сравнение по ссылке объявило бы раннюю фазу
восьмым расхождением, и проверка полноты потребовала бы пробника
на отличие, которого нет.

## Что обязано остаться зелёным без правки

- **`determinism.golden.match.test.ts`.** `packages/sim` не трогается
  ни строкой: правила игры те же.
- **`profile.golden.match.test.ts`.** Базовый профиль не меняется
  ни числом; новые записи в реестре его не касаются.
- **`profile.match.test.ts`, «ядерные ветки покупает только стратег»**
  — проверка перебирает весь реестр. Пробники раскрывают
  `SIEGE_PROFILE`, у которого `nuke.invest` не выставлен, поэтому
  утверждение остаётся верным. Это надо помнить: пробник, собранный
  раскрытием `STRATEGIST_PROFILE`, уронил бы её.

  Отдельно про `siege-probe-late-reserve-2026-08`: он объявляет в поздней
  фазе запас `'nuke'`, и это выглядит нарушением того же правила, но им
  не является. Проверка смотрит на `nuke.invest` — право покупать ядерные
  ветки прокачки, — а не на запас; сам базовый профиль объявляет тот же
  запас, не будучи стратегом (`BASELINE_PHASES`, третья фаза).
  Держать заряд без права качать ветки — законное сочетание, и пробник
  меряет ровно его.
- **`siege.match.test.ts`.** Осадный профиль и окно проверки не трогаются.

## Известная цена

Правка в `packages/ai` попадает в список путей, по которым прогонщик
баланса решает, менялись ли правила игры (`BALANCE_PATHS`
в `scripts/balance-run.mjs`). Значит, ближайшей ночью очередь прогонится
целиком, хотя поведение существующих профилей не изменилось ни на тик.
Это плата за грубость признака, а не поломка: признак смотрит на пути,
а не на смысл правки, и делать его умнее ценой пропущенного сдвига
не стоит.

## Поведение при рассинхроне и переподключении

Изменение задевает геймплей единственным способом — в реестре профилей
становится больше записей. Отсюда три ответа.

**Рассинхрона новых случаев не появляется.** Имя профиля уже входит
в согласование сетевого матча наравне с seed мира и seed противника
(требование «Профиль участвует в согласовании сетевого матча»);
расхождение имён у сторон уже считается нарушением того же рода, что
расхождение раскладки байтов. Новые имена ведут себя как все прочие.

**Переподключение ничего нового не хранит.** Противник по сети
не передаётся: каждая сторона считает его сама из seed и имени профиля.
Обе величины переживают переподключение сегодня; пробники не добавляют
к ним ничего.

**В живой матч пробники не попадают.** Их выбирает только арена ключом
`--profiles` и стенд в тестах. Лобби и подбор соперника списка профилей
не расширяют — это не задето ни одной задачей изменения.

## Как это живёт с запретами ядра

Ни `Math.random`, ни `Date.now`, ни `performance.now` не появляются.
Профиль — замороженные данные, читаемые дважды в секунду; числа в нём
человеческие (секунды, клетки, доли) и переводятся во внутренние
существующими функциями `profile.ts`. В состояние мира из профиля
не попадает ничего, поэтому вопрос о числах с плавающей точкой в мире
здесь не возникает вовсе.

Сводка арены живёт в `apps/arena` — приложении, а не библиотеке,
и границы пакетов не задевает: она уже импортирует `@td/ai` и `@td/shared`.
