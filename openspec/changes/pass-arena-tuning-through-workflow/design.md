## Context

На освежённой базе `.github/workflows/arena.yml` собирает выбранную ревизию и вызывает `node apps/arena/dist/main.js` с массивом Bash-аргументов. Значения текущих полей поступают через `env`. CLI в `apps/arena/src/main.ts` содержит `TUNING_FLAGS`, `tuningOf` и `tuningArgs`: множители уже применяются до создания миров и передаются дочерним процессам. `packages/shared/src/rules.ts` отвергает неположительные и неконечные числа. Однако общий `flagsOf` молча игнорирует неизвестные ключи, а повторения заменяет последним значением; напрямую отдавать ему произвольную строку означало бы скрывать ошибки эксперимента.

## Goals / Non-Goals

Цель — получить разные настройки арены на одном коде через ручной workflow, сохранив существующие входы. Границы: шесть уже реализованных множителей, безопасный разбор, проверки доставки аргументов и краткая инструкция. Не меняются CLI, баланс, `RuleTuning`, поведение симуляции и ночные прогоны. Полный перечень исключений — в proposal.

## Decisions

### 1. Одно строковое поле с ограниченной грамматикой

Имя `tuning_args`, тип string, required false, default пустая строка. Описание поля содержит пример `--base-hp 0.8` и поясняет, что это множитель. Разделение по пробельным символам после удаления пробелов по краям: пробелы, табуляция и переводы строк равнозначны. Пустой результат даёт пустой массив.

Читаем ровно пары «разрешённый ключ — число», без кавычек, экранирования, формы с `=` или позиционных доводов. Десятичная запись допускает знак, дробную часть (в том числе `.8`) и экспоненту; после проверки записи преобразование в Number обязано дать конечное значение больше нуля. Шестнадцатеричная запись не поддерживается. Повтор ключа — ошибка, порядок разных ключей сохраняется, сами токены передаются без потерь. Экстремальное значение, при котором число переполнилось или округлилось в ноль, отвергается. Ограничения производных игровых величин остаются ответственностью существующей арены: универсальной гарантии играбельности любого положительного множителя здесь нет.

Альтернативы: отдельное поле для каждого множителя раздувает форму и требует отдельной проводки каждого поля; JSON-массив заставляет владельца писать служебную разметку; полноценный shell-парсер приносит кавычки и экранирование для значений, которым они не нужны. Выбран узкий текстовый формат, совпадающий с обычными примерами CLI.

### 2. Небольшой Node-адаптер на границе workflow

`scripts/arena-workflow.mjs` экспортирует чистый разбор множителей и построение полного argv из окружения, а прямой запуск вызывает собранную арену. Импорт модуля не запускает процессы. Workflow сохраняет существующие env-поля и добавляет `TUNING_ARGS` через выражение Actions в `env`; шаг «Прогнать матчи» вызывает адаптер постоянной командой. Адаптер строит тот же набор `run`, `--matches`, `--seed`, необязательных `--profiles` и `--seconds`, затем дописывает проверенные пары. Только новое поле получает новый строгий контракт; значения существующих полей по-прежнему передаются одним доводом каждое.

Запуск — текущим Node через `process.execPath`, с путём `apps/arena/dist/main.js` и отдельным массивом argv, shell выключен, stdio унаследован. Рабочий каталог — корень checkout. Ненулевой код дочернего процесса сохраняется; ошибка создания процесса или завершение сигналом дают ненулевой исход адаптера. Вся проверка множителей заканчивается до spawn. Для тестов управление процессом имеет точку подмены, не доступную через пользовательский вход.

Альтернативы: `eval` или подстановка поля прямо в `run` превращают данные в код; некавыченное расширение Bash добавляет globbing; просто разбить строку и отдать её CLI безопасно от выполнения, но опасно молчаливым игнорированием опечаток. Отдельный адаптер позволяет проверить контракт быстро, без Bash и без матчей, на Windows и в CI. Новые зависимости не нужны.

### 3. Повторное использование существующей арены

Whitelist содержит только шесть ключей, уже существующих в `TUNING_FLAGS` свежей базы. Перенос этого реестра, рефакторинг `main.ts` и сторож всех полей `RuleTuning` не требуются — это область задачи 0100. Тесты адаптера проверяют каждый обещанный ключ на явных ожидаемых argv. Доставка множителей от родителя арены дочерним процессам остаётся существующим `tuningArgs`.

Workflow по-прежнему делает ingest, report и загрузку артефактов обычными шагами. Каждое сравнение — отдельный workflow run, поэтому логи одинаковых seed не перезаписываются между настройками. Инструкция рекомендует один неизменный тег и одинаковые прочие параметры; одна ветка, передвинувшаяся между запусками, не доказывает одинаковую ревизию. `--base-hp 0.8` — 80 процентов базового здоровья выбранного кода, а не 0.8 HP и не фиксированные 400 HP. Новые метрики и формат базы не вводятся.

### 4. Проверять границу запуска без расчёта матчей

Быстрый Vitest-тест в `scripts/arena-workflow.test.mjs` проверяет точный argv для пустого ввода, каждого из шести ключей и нескольких ключей вместе с текущими полями; отдельные случаи покрывают whitespace, дроби и экспоненты, дубли, неизвестные и служебные ключи, отсутствующие значения, лишние токены и попытки shell-вставок. Через подмену spawn проверяются отсутствие вызова при ошибке, аргументы реального адаптера, выключенная оболочка и распространение ошибок процесса. Контроль удаления добавления tuning-пар обязан уронить положительный тест: одно лишь отсутствие ошибок не считается доставкой настроек.

Тест читает workflow и проверяет проводку `inputs.tuning_args` в `TUNING_ARGS`, пустое умолчание и постоянную команду вызова адаптера без прямой подстановки нового входа в исполняемый текст. Это дополняет поведенческий тест адаптера, а не заменяет его. Файл попадает в существующий набор `pnpm test:scripts`; новый сценарий package.json и настройка CI не нужны.

## Risks / Trade-offs

- Список ключей на входной границе может устареть при расширении CLI → ограничиваем обещание шестью текущими ключами и явно описываем список; задача 0100 не становится скрытой предпосылкой.
- Один запуск на движущейся ветке не равен другому → документируем неизменную ревизию и одинаковые параметры эксперимента.
- Модульные проверки не подтверждают доступность формы в GitHub → проверка проводки в workflow защищает объявление поля и вызов; фактические балансные измерения остаются отдельными задачами и не заявляются сделанными.
- В старой ревизии workflow нового входа нет → использовать ревизию, содержащую эту правку. Обратная доставка адаптера в исторические коммиты не входит в задачу.

## Архитектурные ограничения

Игровые пакеты, сетевой протокол, реконнект и обработка рассинхрона не меняются. Адаптер исполняется вне ядра; ни `Math.random`, ни `Date.now`, ни дробные значения в состоянии мира не добавляются. Правила `packages/sim` не меняются, поэтому обновление эталонов детерминизма и `PROTOCOL_VERSION` не требуется. Прогон баланса не заказывается: доставка уже существующих настроек не меняет нейтральные игровые правила, цены или ИИ.

## Migration Plan

Поставка — обычный PR с workflow, адаптером, тестом и документацией. Данные и сохранения не мигрируют. Пустой вход сохраняет прежний вызов. Откат атомарного коммита реализации возвращает прежний шаг запуска и убирает поле вместе с адаптером, не затрагивая результаты состоявшихся прогонов. Боевому серверу эти файлы не нужны.
