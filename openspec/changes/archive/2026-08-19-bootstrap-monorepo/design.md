## Context

Репозиторий пуст. Мы закладываем каркас под браузерный Tower Defense с PvP в реальном времени, где главное нефункциональное требование — отзывчивость: действие игрока должно давать визуальный отклик в том же кадре, то есть быстрее 16 мс, а сетевая задержка не должна проявляться как ожидание.

Из этого требования вытекает архитектурное следствие, которое надо зафиксировать до первой строчки геймплея. Отзывчивость в сетевой игре достигается не быстрым сервером, а тем, что клиент **не ждёт сервера**: он немедленно применяет действие игрока у себя и позже сверяется с авторитетным результатом. Это работает только если и клиент, и сервер исполняют **одну и ту же детерминированную симуляцию** из одного и того же кода. Поэтому симуляция обязана быть отдельным изоморфным пакетом без единой платформенной зависимости, и это ограничение надо защитить инструментами, а не договорённостью.

Второе следствие: игровое поле нельзя рендерить через React. React перерисовывает по изменению состояния, а нам нужен стабильный цикл на 60 кадров в секунду с сотнями движущихся объектов. Поэтому граница «React рисует HUD, PixiJS рисует поле» тоже закладывается в каркас.

## Goals / Non-Goals

**Goals:**

- Зафиксировать шесть пакетов с односторонним графом зависимостей и защитить границы линтом, а не ревью.
- Гарантировать изоморфность и детерминированность `packages/sim` на уровне инструментов.
- Дать разработчику одну команду `pnpm dev`, поднимающую всю среду с горячей перезагрузкой.
- Сделать проверки (типы, линт, формат, тесты) быстрыми за счёт кеширования, чтобы их реально запускали.
- Собрать тонкую сквозную вертикаль client → WebSocket → server, доказывающую, что каркас живой.

**Non-Goals:**

- Любая игровая механика: башни, волны, экономика, баланс.
- Реализация prediction и rollback — здесь только создаются условия для них.
- Аккаунты, матчмейкинг, база данных, деплой, докеризация.
- Оптимизация под мобильные устройства и арт-пайплайн.

## Decisions

### Решение 1: pnpm workspaces + Turborepo вместо Nx или npm workspaces

pnpm ставит зависимости через жёсткие ссылки на общий store, поэтому установка в монорепозитории с шестью пакетами занимает секунды, а не минуты. Его строгий `node_modules` — не плоский, в отличие от npm — даёт побочный, но ценный эффект: пакет физически не может импортировать зависимость, которую не объявил. Это ровно та защита границ, которая нам нужна для `sim`.

Turborepo отвечает за порядок и кеш задач. Он читает граф зависимостей workspace и сам решает, что можно выполнить параллельно, а что нельзя, плюс кеширует результат по хешу входов.

Альтернативы: Nx мощнее, но приносит генераторы, плагины и собственную ментальную модель — избыточно для шести пакетов. Голые npm workspaces не дают ни кеша, ни строгой изоляции.

### Решение 2: PixiJS v8 для игрового поля, React 19 только для HUD

Здесь два независимых рендерера с чёткой границей: PixiJS владеет `canvas` и игровым циклом, React владеет HTML-оверлеем поверх него. Они общаются через внешний store, а не через props.

PixiJS v8 использует WebGL2 с автоматическим переключением на WebGPU, батчит спрайты и держит тысячи объектов на стабильных 60 кадрах. Ключевое: игровой цикл крутится в `requestAnimationFrame` **вне** React, поэтому ни один рендер React не может уронить частоту кадров поля.

Альтернативы: рисовать всё в React с DOM или SVG — гарантированно не выдержит сотни движущихся врагов. Three.js избыточен для 2D. Phaser — полноценный движок со своим жизненным циклом, он будет конфликтовать с нашей собственной детерминированной симуляцией, а нам нужен только рендерер.

### Решение 3: симуляция — отдельный пакет с целочисленной математикой

`packages/sim` — чистая функция вида `(состояние, входы) → новое состояние` с фиксированным тиком. Три ограничения делают её пригодной для сетевой игры:

Во-первых, **никаких чисел с плавающей точкой в состоянии**. `0.1 + 0.2` может дать чуть разный результат на разных движках и платформах, и на длинной дистанции клиент с сервером разъедутся. Используем целые числа с фиксированной точкой: координаты хранятся в тысячных долях клетки, то есть `1500` означает полторы клетки.

Во-вторых, **никакого `Math.random`**. Случайность даёт seeded PRNG, чьё состояние — часть состояния мира, поэтому одинаковый seed плюс одинаковые входы всегда дают одинаковый результат.

В-третьих, **никакого `Date.now` и `performance.now`**. Время внутри симуляции измеряется номером тика, а не настенными часами.

Эти три правила проверяются ESLint-правилом `no-restricted-globals`, то есть нарушение видно сразу при написании кода, а не через месяц при разборе рассинхрона.

### Решение 4: бинарный протокол вместо JSON

`packages/protocol` кодирует сообщения в `ArrayBuffer` через `DataView`. Причина в том, что в lockstep-модели пакеты уходят каждый тик, то есть десятки раз в секунду на каждого игрока. JSON здесь дорог дважды: он раздувает объём (`{"type":"place_tower","x":12,"y":7}` — около 40 байт против 5 в бинарном виде) и требует парсинга строки на горячем пути, что порождает мусор для сборщика и микрофризы.

Кодек пишем руками, а не берём Protobuf или FlatBuffers: у нас меньше десятка типов сообщений, а ручной `DataView` не тянет за собой кодогенерацию в сборку и даёт полный контроль над раскладкой байтов.

### Решение 5: синхронизация входов, а не состояния мира

Сервер авторитетен, но рассылает не состояние мира, а подтверждённые команды игроков с номером тика, на котором их надо применить. Клиент применяет своё действие немедленно и продолжает симулировать; когда приходит подтверждение, он сверяет контрольную сумму и при расхождении откатывается к последнему совпавшему тику и переигрывает.

Такая модель даёт нулевую задержку отклика на собственные действия при трафике в единицы байт на тик. Плата — жёсткое требование детерминизма, ради которого и введены ограничения из решения 3.

### Решение 6: Fastify плюс `ws` на сервере

Fastify обслуживает REST — health-чек, позже матчмейкинг и профили. Реалтайм идёт отдельным WebSocket-слоем на библиотеке `ws`. Разделение осознанное: у HTTP и у игрового соединения разные требования к задержке, и смешивать их в одном обработчике не стоит.

`ws` выбран вместо `uWebSockets.js`, который быстрее, но распространяется как нативный модуль и усложняет установку на Windows — а разработка ведётся именно на Windows. Замена изолирована за интерфейсом транспорта, поэтому переход на `uWebSockets.js` под нагрузкой останется дешёвым.

### Решение 7: поведение при рассинхроне и реконнекте

Правило проекта требует описывать это для геймплейных изменений. Здесь геймплея ещё нет, но контракт фиксируется сразу, чтобы следующие изменения его реализовывали.

При **рассинхроне** — контрольная сумма клиента не совпала с серверной — клиент запрашивает полный снимок состояния, применяет его и продолжает с этого тика. Игрок видит короткий скачок картинки, но матч не прерывается. Факт рассинхрона логируется с номером тика и обеими суммами.

При **реконнекте** клиент восстанавливает соединение с экспоненциальной задержкой, получает снимок и журнал входов с момента обрыва и догоняет симуляцию ускоренным прогоном. Сервер держит слот игрока 30 секунд; после этого матч засчитывается техническим поражением.

## Risks / Trade-offs

- **Детерминизм легко сломать незаметно** → защита в три слоя: ESLint-правило на запрещённые глобальные объекты, целочисленное состояние, golden-тест с контрольной суммой в CI. Каждый слой ловит то, что пропустил предыдущий.
- **Целочисленная математика неудобна в написании** → все преобразования между клетками и внутренними единицами прячутся в хелперы `packages/sim`, наружу торчат только именованные функции, а не голые магические множители.
- **Два рендерера в одном приложении усложняют код** → граница проводится один раз и жёстко: React никогда не трогает `canvas`, PixiJS никогда не трогает DOM вне своего элемента. Обмен только через store.
- **Ручной бинарный кодек — источник тонких багов** → каждое сообщение покрывается round-trip-тестом «закодировали и раскодировали, получили исходное», а версия протокола передаётся в заголовке, чтобы несовместимые клиенты отсекались явно.
- **Turborepo-кеш может отдать устаревший результат** при неверно описанных входах задачи → в конфигурации задач явно перечисляются входные и выходные пути; при подозрении на устаревший кеш есть команда с `--force`.
- **`ws` медленнее нативных реализаций** → приемлемо на этапе разработки; транспорт спрятан за интерфейсом, замена не затронет игровой код.

## Migration Plan

Миграции нет: репозиторий пуст, изменение создаёт структуру с нуля. Откат — удаление созданных файлов, никакие данные не затрагиваются.

Порядок развёртывания каркаса: сначала корневая конфигурация и `@td/shared`, затем библиотеки `sim`, `protocol`, `ui`, затем приложения, и в конце CI-контур. Такой порядок позволяет проверять сборку после каждого шага, а не только в самом конце.

## Open Questions

- Какой формат хранения балансных конфигов выбрать — TypeScript-модули с типизацией или JSON со схемой валидации? Решение можно отложить до первого изменения с реальной механикой.
- Нужен ли отдельный Web Worker для симуляции на клиенте, чтобы гарантированно развязать её с рендером? Ответ зависит от замеров, которые появятся только с реальной нагрузкой.
- Частота тика симуляции: 20, 30 или 60 в секунду. Влияет и на трафик, и на плавность; определяется при реализации нетcode.
