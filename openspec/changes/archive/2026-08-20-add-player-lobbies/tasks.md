# Задачи

## 1. Профиль игрока в куки

- [x] 1.1 Чистые функции профиля в `apps/client/src/session/profile.ts`:
      разбор строки куки, сборка строки, проверка имени. Работают
      со строками, а не с `document`, — чтобы покрывались тестами
      без DOM.
      *Проверка:* `profile.test.ts` — 13 случаев: испорченный JSON,
      запись без имени, запись без идентификатора, имя из пробелов,
      точка с запятой внутри имени, знаки равенства в значении куки.
      Проверка самого имени по ходу дела переехала в `@td/shared`
      (см. 2.1) и покрыта там же семью случаями, включая обе границы
      длины: то же правило применяет сервер, и двум копиям расходиться
      нельзя.
- [x] 1.2 Обёртки над `document.cookie`: чтение, запись со сроком
      в год и `SameSite=Lax`, удаление. Генерация идентификатора через
      `crypto.randomUUID` с запасным путём на `Math.random` — с
      комментарием, почему запасной путь нужен (незащищённый контекст
      при открытии по локальному IP).
      *Проверка:* сквозной тест «профиль переживает перезагрузку
      и удаляется по требованию» — перезагрузка сохраняет имя, удаление
      возвращает к форме с пустым полем, новое имя работает.

## 2. Комнаты на сервере: логика отдельно от транспорта

- [x] 2.1 Модуль `apps/server/src/lobbies.ts`: хранилище комнат в памяти
      с внедрённой функцией времени. Операции: создать, войти, выйти,
      переключить готовность, отметить отключение, вернуть подключение,
      чистка просроченных. Каждая операция возвращает исход, включая
      отказ с причиной.
      *Проверка:* `lobbies.test.ts`, 28 случаев. Типы состояния и коды
      отказов вынесены в `@td/protocol`, чтобы клиент и сервер
      сверялись с одним объявлением, а расхождение падало на проверке
      типов, а не в браузере.
- [x] 2.2 Сброс готовности при любой смене состава: вход, выход,
      отключение. В комментарии — зачем (иначе следующий вошедший
      запустит матч чужим согласием).
      *Проверка:* тест «новый вошедший не застаёт чужой готовности»
      воспроизводит ровно этот случай; сквозной тест проверяет то же
      на двух браузерах.
- [x] 2.3 Старт матча по обоюдной готовности: выдача идентификатора,
      seed и сторон, перевод комнаты в состояние «играет» и исчезновение
      её из списка открытых.
      *Проверка:* тесты — общий seed и общий идентификатор, стороны 0
      и 1, комната пропала из списка, повторное нажатие отклонено
      с причиной `already-started`.
      Стороны при старте **замораживаются**, а не вычисляются из позиции
      в списке слотов: иначе уход соперника пересадил бы оставшегося
      со второй стороны на нулевую посреди партии. На это есть
      отдельный тест.
- [x] 2.4 Отсрочка при потере связи: слот помечается отключённым,
      возврат с тем же идентификатором занимает его обратно, просрочка
      удаляет. Матч не начинается, пока кто-то отключён.
      *Проверка:* тесты с подставными часами — возврат за миллисекунду
      до истечения сохраняет слот, истечение освобождает. Ожидания
      в реальном времени в тестах нет. Отдельно проверено, что закрытие
      одной из двух вкладок не считается уходом.

## 3. Комнаты по сети: HTTP и SSE

- [x] 3.4 Подключить маршруты в `main.ts` рядом с `/health`, не трогая

      которое её подтверждает, — иначе чужое действие, доехавшее
      в промежутке, вернуло бы кнопку назад и она мигнула бы

- [x] 6.1 Провести сторону и seed параметрами в `startGame`, заменив

## Что всплыло по ходу и стоит запомнить

Три ошибки, каждая тихая, — их стоит записать, потому что все три
проявлялись не там, где были сделаны.

**Проверочный запрос уходит не по тому адресу.** Шаблон
`OPTIONS /api/lobbies/*` ловит `/api/lobbies/ready`, но не сам
`/api/lobbies`, на который браузер шлёт проверку перед созданием
комнаты. Поток состояния при этом работал — `EventSource` шлёт простой
GET и проверкой не предваряется, — поэтому меню выглядело исправным,
а кнопка «Создать» молчала. Первый тест на OPTIONS ошибку пропустил,
потому что брал адрес с продолжением; теперь он перебирает все три.

**Селектор, возвращающий новый объект.** `useSessionStore(activeMatchOf)`
собирал новый объект на каждый вызов, и для zustand это означало
«состояние изменилось» — компонент перерисовывался бесконечно, пока
React не снял всё дерево. Наружу это вышло как «поле рисуется, а HUD
исчез». В компонентах выбираются существующие ссылки по отдельности;
у функции теперь стоит предупреждение.

**Панель, вытолкнувшая соседей за экран.** Разметка не ломается
и ошибок не выдаёт — содержимое просто уезжает за нижний край.
Поймано измерением `getBoundingClientRect().bottom` против высоты окна;
проверять новые панели HUD стоит именно так, а не на глаз.
