# Задачи

Порядок выбран так, чтобы каждый шаг проверялся сам по себе, а сеть
подключалась последней: библиотека ведения матча проверяется без
сокетов, кодек — без сервера, сервер — без браузера.

## 1. Общие величины

- [x] 1.1 Константы сетевого матча в `packages/shared/src/constants.ts`:
      границы задержки ввода (`INPUT_DELAY_MIN_TICKS`,
      `INPUT_DELAY_MAX_TICKS`), период контрольной суммы, предел
      переигрывания при пересборке предсказания, срок ожидания
      подключения к матчу. Каждой — комментарий «почему столько»,
      а не только «сколько».
      *Проверка:* типы собираются, значения читаются из одного места
      и клиентом, и сервером; ни одной новой константы баланса
      не добавлено.
- [x] 1.2 Тип «команда без стороны» в `packages/shared/src/commands.ts` —
      то, что участник отправляет по сети. Сторону проставляет сервер,
      поэтому поля `player` в сетевой команде быть не должно.
      *Проверка:* проверка типов ловит попытку отправить команду
      с проставленной стороной; существующий `Command` не изменился.

## 2. Ведение матча: `packages/netplay`

- [x] 2.1 Завести пакет `@td/netplay` (package.json, tsconfig, место
      в `vitest.workspace.ts`, правила границ в `eslint.config.js`).
      Зависимости — только `@td/shared`, `@td/sim`, `@td/protocol`.
      *Проверка:* `pnpm -r build` собирает пакет; линт падает
      на подсунутом импорте `ws` и на импорте из `apps/*`.
- [x] 2.2 Ведущая сторона: приём команды, назначение ей тика исполнения
      (`текущий + задержка`, опоздавшей — ближайший несыгранный),
      сборка кадра тика, продвижение мира вызовом `step`.
      Время — внедрённая функция, а не `Date.now()` внутри: иначе
      тесты потребуют реальных секунд ожидания.
      *Проверка:* тесты с подставными часами — команда на будущий тик
      исполняется на нём же; команда на сыгранный тик уезжает вперёд,
      а не пропадает; сыгранный кадр повторно не отправляется.
- [x] 2.3 Ведущая сторона: назначение задержки ввода по худшему каналу,
      её односторонний рост, объявление с тиком вступления в силу.
      *Проверка:* тесты — при разных RTT обоим назначена одна величина;
      ухудшение канала поднимает её, улучшение не опускает; граничные
      значения не выходят за `INPUT_DELAY_MIN_TICKS`
      и `INPUT_DELAY_MAX_TICKS`.
- [x] 2.4 Ведущая сторона: история команд матча и выдача её с заданного
      тика; контрольная сумма раз в период; объявление исхода
      с причиной (разрушена база или техническое поражение).
      *Проверка:* тесты — история, воспроизведённая с нуля, даёт то же
      состояние и ту же контрольную сумму, что у ведущего; исход
      объявляется один раз и не переигрывается.
- [x] 2.5 Сторона участника: подтверждённая копия мира, продвигаемая
      кадрами, и очередь своих неподтверждённых команд.
      *Проверка:* тесты — кадры, поданные не по порядку или повторно,
      не сбивают подтверждённую копию; пропуск кадра обнаруживается,
      а не проглатывается.
- [x] 2.6 Сторона участника: предсказанная копия — подтверждённая плюс
      свои неподтверждённые команды, пересобираемая на каждый кадр.
      Предохранитель на глубину переигрывания.
      *Проверка:* тест «предсказание точно» — участник, чьи команды
      доехали вовремя, получает предсказанное состояние, побитово
      равное будущему подтверждённому. Тест на упор в предохранитель
      сообщает о просадке, а не тихо теряет тики.
- [x] 2.7 Сторона участника: сверка контрольных сумм, одна пересборка
      из истории при расхождении, остановка матча при повторном.
      *Проверка:* тесты с подставленным расхождением — первая
      пересборка чинит, вторая останавливает матч с номером тика.
- [x] 2.8 Сквозной тест библиотеки без сокетов: ведущий и два участника
      связаны напрямую вызовами функций, матч прогоняется целиком.
      *Проверка:* оба участника и ведущий приходят к одной контрольной
      сумме на каждом периоде; при искусственной задержке доставки
      команд одному из участников результат не меняется.

## 3. Протокол версии два

- [x] 3.1 Сообщения в `packages/protocol/src/messages.ts`: `Join`,
      `Command`, `HistoryFrom`, `Welcome`, `TickFrame`, `Checksum`,
      `InputDelay`, `History`, `MatchOver` рядом с существующими
      `Ping`/`Pong`. `PROTOCOL_VERSION = 2`.
      *Проверка:* типы собираются; направление каждого сообщения
      обозначено в объявлении, а не в комментарии на память.
- [x] 3.2 Кодек переменной длины в `codec.ts`: кадр как раньше начинается
      с версии и типа, дальше поля по типу. Команда — вид и аргументы
      в трёх байтах, без стороны.
      *Проверка:* `codec.test.ts` — круговое кодирование каждого типа,
      включая кадр с максимальным числом команд; ни один тип
      не проходит мимо теста.
- [x] 3.3 Разбор недоверенных данных: новые причины отказа (длина
      не сходится с числом записей, вид команды вне диапазона),
      результат-объединение вместо исключения.
      *Проверка:* тесты на обрезанный кадр, лишние байты в хвосте, вид
      команды 255, число команд больше поместившегося. Ни один случай
      не бросает исключение.

## 4. Сервер ведёт матчи

- [x] 4.1 Реестр матчей в `apps/server/src`: создание матча в состоянии
      ожидания при старте из комнаты, выдача билетов, сопоставление
      соединения со стороной по билету.
      *Проверка:* тесты — билет действует один раз, чужой и пустой
      отклоняются, матч не начинает тикать до подключения обоих,
      неподключившийся получает техническое поражение по истечении
      срока.
- [x] 4.2 Цикл тиков сервера поверх `@td/netplay`: накопитель времени,
      досчёт при отставании, рассылка кадров всем участникам матча.
      *Проверка:* тест — за отмеренную секунду просчитано
      `TICKS_PER_SECOND` тиков ±1; искусственная задержка в обработчике
      не приводит к накоплению долга без предела.
- [x] 4.3 Игровой сокет обслуживает матчи: `game-server.ts` вместо
      «`Pong` на `Ping`» разбирает `Join`, `Command`, `HistoryFrom`
      и адресует их нужному матчу; сервер сам шлёт `Ping` для замера
      канала.
      *Проверка:* тесты на подставном транспорте — команда от участника
      доезжает в мир его стороной; команда до `Join` игнорируется;
      битый кадр закрывает одно соединение и не трогает матч соперника.
- [x] 4.4 Разрыв и возврат: удержание места на `RECONNECT_GRACE_SECONDS`,
      продолжение мира без отключившегося, техническое поражение
      невернувшемуся, выдача истории вернувшемуся.
      *Проверка:* тесты с подставными часами — мир продолжает считаться
      при отключении; возврат за миллисекунду до истечения продолжает
      матч; истечение завершает его с технической причиной.
- [x] 4.5 Билет и параметры матча в `MatchView` по SSE.
      *Проверка:* `lobby-routes.test.ts` — билеты у сторон разные, seed
      и стороны прежние, форма сообщения не сломала существующие тесты.

## 5. Клиент как участник

- [x] 5.1 Сетевой слой матча в `apps/client/src/game/net.ts`: подключение
      с билетом, приём кадров, отправка команд, переподключение поверх
      существующей экспоненциальной задержки.
      *Проверка:* матч между двумя вкладками идёт по общему миру;
      выключенный сервер даёт честное сообщение, а не молчание.
- [x] 5.2 Игровой цикл становится ведомым: `loop.ts` больше не владеет
      миром единолично, а продвигает подтверждённую копию кадрами
      и рисует предсказанную. Источник команд противника
      (`options.commands`) из цикла убирается.
      *Проверка:* существующие тесты цикла переписаны на новую роль;
      частота кадров при 30 тиках в секунду не изменилась.
- [x] 5.3 Ввод игрока отправляет команды и одновременно кладёт их
      в предсказание.
      *Проверка:* наблюдаемо — генерал трогается в том же кадре, что
      нажатие; замер `performance.now()` между событием клавиатуры
      и первым сдвигом на экране укладывается в кадр.
- [x] 5.4 Отклик на дискретные действия, которые мир увидит через
      задержку: подсветка клетки при заказе постройки, отметка о заказе
      юнита, о покупке улучшения.
      *Проверка:* наблюдаемо — нажатие даёт отклик немедленно, объект
      появляется в мире через задержку ввода, и промежуточное состояние
      не выглядит зависанием.
- [x] 5.5 Догон матча по истории с показом хода восстановления.
      *Проверка:* перезагрузка страницы посреди матча возвращает игрока
      в тот же матч на текущем тике; на экране виден ход
      восстановления; замер времени догона занесён в design как факт.
- [x] 5.6 Расхождение и исход в интерфейсе: сообщение о расхождении,
      исход матча от сервера с причиной, предупреждение при выходе
      из идущего матча.
      *Проверка:* тесты интерфейса — при пришедшем исходе показан
      победитель и причина; выход из идущего матча спрашивает
      подтверждение и засчитывает поражение.

## 6. Компьютер как участник

- [x] 6.1 Завести пакет `@td/bot` (package.json, tsconfig, место
      в `vitest.workspace.ts`, правило границ: импорт `apps/server`
      запрещён).
      *Проверка:* линт падает на подсунутом импорте из `apps/server`;

- [x] 6.2 Клиент комнат для компьютера: профиль, создание комнаты,

      *Проверка:* тесты на подставном HTTP — комната создаётся,
      готовность подтверждается при появлении соперника, после сброса
      подтверждается снова.
- [x] 6.3 Участник-компьютер: сторона участника из `@td/netplay`,
      решения из `@td/ai` по подтверждённому состоянию, отправка команд

      *Проверка:* тест — команды компьютера не исполняются раньше

- [x] 6.5 Запуск службы вместе с сервером — отдельным модулем, через
      публичные HTTP и WebSocket, без единого импорта внутренностей.
      *Проверка:* `pnpm dev` поднимает сервер, и дежурная комната
      появляется в списке сама; отключение службы делает игру
      с компьютером недоступной с внятной причиной, а не молчаливой

## 8. Проверка целиком

- [x] 8.1 Замер под нагрузкой: матч с числом юнитов, близким к потолку
      в 200 на игрока. Стоимость шага, стоимость пересборки предсказания,
      время догона матча из истории.
      *Проверка:* цифры занесены в design рядом с уже имеющимися; если
      догон превысил пять секунд, открыт вопрос о серверных снимках,
      как и было условлено.
- [x] 8.2 Матч двух участников: сверка контрольных сумм по ходу партии,
      поведение при обрыве и возврате, поведение при выходе.
      *Проверка:* сквозной тест на двух браузерных контекстах — у обоих
      совпадают тик и контрольная сумма подтверждённого мира, действие
      одного меняет мир другого, выход спрашивает подтверждение
      и присуждает победу сопернику с технической причиной. Обрыв
      и возврат покрыты в `@td/netplay` подставными часами: мир идёт
      без отключившегося, вернувшийся догоняет по истории и сходится
      с соперником по сумме.
      **Остаётся человеку:** прогон на двух настоящих машинах через
      сеть. Локальный канал не воспроизводит ни джиттер, ни потери,
      а именно они двигают задержку ввода, и подобранный запас
      на дрожание (см. Open Questions в дизайне) без такого прогона
      остаётся предположением.
- [x] 8.3 `pnpm verify` и `pnpm e2e` целиком, эталон детерминизма
      без правки числа.
      *Проверка:* `pnpm verify` зелёный — 622 юнит-теста в 48 файлах,
      линт и сборка без замечаний; `pnpm e2e` зелёный — 17 сценариев,
      включая матч двух браузеров и матч с компьютером.
      `determinism.golden.test.ts` не изменён, `packages/sim` в диффе
      отсутствует целиком.
- [x] 8.4 Обновить `README.md`: раздел о сетевой модели перестаёт
      описывать замысел как действительность, а раздел «что пока
      не работает» лишается пункта про несетевого соперника.
      *Проверка:* прочитать README глазами и сверить каждое
      утверждение о сети с кодом.
