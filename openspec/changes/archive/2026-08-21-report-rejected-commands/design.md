# Технические решения

## Где живёт отказ

Рассмотрены три места. Выбрано третье.

### Вариант А: `step` возвращает пару

```ts
step(world, commands) => { world: WorldState; rejected: readonly Rejection[] }
```

Честно и очевидно, но ломает каждое место вызова: цикл в клиенте, сервер,
все тесты, эталон детерминизма. Главное — ломает форму, на которую
опирается предсказание с откатом: сейчас «состояние тика» это ровно один
объект, который можно сохранить и к которому можно вернуться. Пара
превращает его в два объекта, из которых откатывать надо только один.

### Вариант Б: колбэк-приёмник

```ts
step(world, commands, onReject?)
```

Не ломает вызовы, но делает шаг наблюдаемо небезразличным к внешнему
миру. Это плохо не абстрактно: клиент пересчитывает одни и те же тики
повторно после отката, и колбэк выстрелит на каждом пересчёте. Отказы
задвоятся, а отличить «отказали дважды» от «отказали один раз, но тик
пересчитали» будет нечем.

### Вариант В (выбран): поле в состоянии мира

```ts
WorldState {
  ...
  shots:      readonly ShotState[]
  rejections: readonly Rejection[]   // ← новое
}
```

Прецедент прямой и уже документирован. `ShotState` живёт в состоянии
мира, нужен исключительно рендеру и намеренно исключён из контрольной
суммы (`checksum.ts:108-118`). Комментарий в `world.ts:99-102` этот
приём даже называет образцом для подражания.

Что это даёт:

- сигнатура `step` не меняется, места вызова не трогаются;
- шаг остаётся чистым: вход не мутируется, выход зависит только от входа;
- откат работает сам собой — отказы часть состояния, к которому
  откатываются, и при пересчёте тика они пересчитываются вместе с ним;
- контрольная сумма не меняется, эталон детерминизма остаётся зелёным.

## Срок жизни: ровно один тик

`shots` живут `SHOT_LIFETIME_TICKS`, потому что выстрел надо успеть
нарисовать, а рендер идёт с частотой монитора и может не совпасть с тиком.
Отказу этого не нужно: его потребитель не рендер, а обработчик `onTick`,
который вызывается на каждом тике без пропусков (`loop.ts:93`).

Отсюда важное следствие для интерфейса: **отказы читаются в `onTick`,
а не в снимке HUD.** Снимок снимается раз в шесть тиков
(`HUD_EVERY_TICKS`), и пять отказов из шести в него не попали бы. Это
ровно тот сорт ошибки, который потом ловится месяцами как «иногда
не показывает».

## Причина отказа — закрытое перечисление в `@td/shared`

Не строка. Строку нельзя перевести, по ней нельзя сгруппировать
в аналитике и её легко разойтись с кодом. Перечисление живёт рядом
с `CommandKind`, потому что производит его ядро, а читают и ядро,
и клиент.

```
RejectReason
  NotEnoughEnergy       не хватает энергии
  CellBlocked           клетка занята рельефом или постройкой
  CellOccupiedByLiving  в клетке живой юнит или генерал
  OutsideBuildRadius    вне радиуса строительства генерала
  QueueFull             очередь производства заполнена
  GeneralDead           генерал мёртв
  NukeNearBase          цель удара в запретной зоне у базы
  InvalidCell           клетки с таким номером не существует
  InvalidTarget         цель своя либо это не постройка
  InvalidArgument       направление, тип юнита или ветка вне диапазона
  MatchOver             матч окончен
```

Одна проверка — одна причина. Там, где сегодня один `return` закрывает
два случая (например, «клетка непроходима» и «в клетке кто-то стоит»),
проверки разводятся: слитая причина бесполезна и игроку, и аналитике.

## Что попадает в запись отказа

```ts
interface Rejection {
  readonly player: PlayerId;
  readonly kind: CommandKind;
  readonly reason: RejectReason;
}
```

Номер тика не хранится: запись живёт внутри состояния конкретного тика,
и тик известен из него самого. Подробностей вроде «не хватило столько-то»
тоже нет — их можно вывести из состояния, а раздувать запись, живущую
один тик, незачем.

## Поведение при рассинхроне и реконнекте

Правило `openspec/config.yaml` требует это описать явно.

Отказы **производны от входов**: они выводятся из состояния мира
и списка команд, а оба на клиенте и на сервере одинаковы. Поэтому:

- **рассинхрон**: расхождение по отказам невозможно без расхождения
  по состоянию, а его ловит контрольная сумма. Отдельной сверки
  отказов не нужно;
- **снимок состояния при рассинхроне**: поле `rejections` в снимке
  приходит пустым или игнорируется — отказы прошлых тиков смысла
  не имеют;
- **реконнект**: пропущенные за время обрыва отказы не восстанавливаются
  и показаны не будут. Это правильно: сообщение «вам не хватило энергии»
  через восемь секунд после нажатия дезориентирует сильнее, чем молчание;
- **откат предсказания**: отказ пересчитывается вместе с тиком, потому
  что лежит в состоянии этого тика. Задвоения не возникает.

## Показ отказа игроку

Показываются только отказы **своих** команд: чужие игрока не касаются
и выдали бы ему сведения о действиях соперника, которых он видеть
не должен (сам факт неудачной попытки соперника — не то же самое, что
отсутствие тумана войны).

Форма показа — короткая строка в HUD, гаснущая за пару секунд, плюс
вздрагивание соответствующего элемента панели там, где он есть
(шкала энергии при `NotEnoughEnergy`, панель очереди при `QueueFull`).
Все цвета и длительности берутся из `packages/ui/src/tokens.css`,
литералов в компонентах быть не должно.

Повторы гасятся: отказ с той же парой «команда, причина», уже
показанный в пределах секунды, не порождает второго сообщения. Иначе
зажатая клавиша строительства даст тридцать сообщений в секунду.
