## ADDED Requirements

### Requirement: Конфликт PR обнаруживается при ожидании CI

При каждом штатном опросе задачи в состоянии `pr` оркестратор SHALL получать
возможность слияния PR вместе с результатами CI. Подтверждённый GitHub конфликт
SHALL переводить задачу в `revise` независимо от состояния проверок.
Журнал карточки SHALL называть PR, конфликт с главной веткой и необходимость
обновить ветку и устранить конфликты перед повторным CI.

#### Scenario: Конфликт не дал запустить проверки

- **WHEN** GitHub сообщает `CONFLICTING`, а список проверок пуст
- **THEN** ближайший успешный опрос переводит задачу из `pr` в `revise`
  и записывает причину возврата в журнал карточки

#### Scenario: Проверки не отменяют конфликт

- **WHEN** GitHub сообщает `CONFLICTING`, а проверки ещё идут или уже зелёные
- **THEN** задача возвращается в `revise` и не допускается к ревью

#### Scenario: Повтор после состоявшегося возврата

- **WHEN** устаревшее поручение опроса выполняется после перехода в `revise`
- **THEN** новый переход и дублирующая запись журнала не создаются

### Requirement: Неопределённость не считается конфликтом

Оркестратор SHALL сохранять задачу в `pr`, если возможность слияния ещё
не определена либо данные GitHub не удалось прочитать. При `MERGEABLE`
результаты CI SHALL обрабатываться прежним маршрутом: успешные проверки
открывают ревью, неуспешные отправляют в доработку, отсутствующие и идущие
сохраняют ожидание.

#### Scenario: GitHub ещё вычисляет слияние

- **WHEN** GitHub сообщает `UNKNOWN`, в том числе при зелёных проверках
- **THEN** задача остаётся в `pr` до следующего опроса без ложного возврата

#### Scenario: Ответ недоступен или повреждён

- **WHEN** запрос GitHub завершился ошибкой либо данные не разобрались
- **THEN** состояние карточки не меняется, причина ожидания указывает проблему чтения

#### Scenario: Конфликта нет и CI завершён

- **WHEN** GitHub сообщает `MERGEABLE` и завершённые проверки
- **THEN** успешный CI переводит задачу в `review`, неуспешный — в `revise`

### Requirement: Причина ожидания сохраняется в диагностике

Оркестратор SHALL передавать причину ожидания из опроса в журнал цикла.
Отсутствие проверок, незавершённые проверки и недоступность данных SHALL
объясняться собственными причинами. Неизменное ожидание SHALL NOT создавать
новый комментарий на карточке каждый цикл.

#### Scenario: Проверок пока нет

- **WHEN** слияние возможно, но GitHub вернул пустой список проверок
- **THEN** журнал цикла сообщает отсутствие проверок, а не их выполнение

#### Scenario: Известны незавершённые проверки

- **WHEN** слияние возможно и часть проверок ещё выполняется
- **THEN** журнал цикла сохраняет названия этих проверок без записи нового комментария
