## Context

В состоянии `pr` сканер каждый цикл выдаёт `poll-external`. Переходник читает
только `statusCheckRollup`: пустой набор становится `pending`, а `applyExternal`
теряет пояснение и всегда пишет «проверки идут». На PR 126, 132, 141 и 177
GitHub вернул пустые проверки и `mergeable: CONFLICTING`.

## Goals / Non-Goals

**Goals:** автоматически вернуть конфликтующий PR в доработку, сохранить
причину ожидания при неполных данных, оставить действующий маршрут и частоту опроса.

**Non-Goals:** перечислены в proposal.md; таймеры, автоматическое разрешение
конфликтов и изменение маршрута закрытых PR сюда не входят.

## Decisions

1. В тот же `gh pr view` добавить `mergeable`. `mergeStateStatus` не подходит:
   у наблюдавшихся черновиков он был `UNKNOWN`, хотя `mergeable` явно сообщал
   `CONFLICTING`. Отдельный REST-запрос удвоил бы число обращений без пользы.
2. Отдельное чистое сведение PR сначала проверяет возможность слияния.
   `CONFLICTING` даёт исход `conflict` независимо от отсутствующих, идущих
   или зелёных проверок. `UNKNOWN` и непрочитанные данные сохраняют ожидание;
   `MERGEABLE` передаёт проверки существующему сведению CI.
3. `applyExternal` переводит `conflict` в `revise`, называя PR и необходимое
   исправление. Существующий исполнитель сохраняет переход и журнал карточки.
   Отдельная задача на конфликт не нужна: доработка уже владеет нужной веткой.
   Инструкция доработки принимает такую причину без требования отсутствующего
   лога красного CI или ревью; конкретные файлы определяются при слиянии базы.
4. Для `pending` сохранять `external.why`. При неизменном статусе причина
   видна в журнале цикла; комментарий на карточке каждый цикл не создаётся.

## Risks / Trade-offs

- GitHub вычисляет возможность слияния асинхронно → `UNKNOWN` не разрешает
  ревью и не считается конфликтом; следующий цикл повторяет опрос.
- Незавершённый запрос или некорректный JSON → ожидание с точной причиной,
  без ложного возврата в доработку.
- После перехода карточка уже не находится в `pr` → обычный сканер перестаёт
  опрашивать её CI; повторный устаревший опрос не пишет второй переход.
- Пустые проверки при `MERGEABLE` всё ещё требуют ожидания: причина отсутствия
  запуска не доказывается его возрастом, потому таймер не подменяет диагноз.

## Migration Plan

Четыре наблюдавшиеся карточки возвращены в доработку по явному запросу
пользователя. Для новых случаев достаточно обычного обновления супервизора
после зелёного CI и вливания PR. Поля карточек и реестров не мигрируют.
Откат кода возвращает прежнее поведение опроса без отката уже сделанных переходов.
