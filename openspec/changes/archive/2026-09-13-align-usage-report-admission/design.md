## Context

tokenAdmission уже допускает неполный учёт; readCodexAnswer и finish всё ещё переводят done в failed при usageError. Инцидент 0242 подтверждает, что отказ распространяется на разбор того же отказа. Основные спецификации отстают от выполненной, ещё не архивированной unblock-the-stalled-board.

## Goals / Non-Goals

Согласовать допуск результата с действующим правилом запуска, сохранив весь учёт и штатную доставку. Не повышать лимиты, не переписывать историю и не восстанавливать карточки вручную в рамках этой правки.

## Decisions

1. Удалить бюджетную проверку usageError из адаптера. После проверки процесса result и done означают завершённый протокол, а пригодность отчёта решает finish.
2. В finish оставить usageError диагностикой. Только ошибка сохранения ledger или оставшаяся ошибка его записи блокирует приёмку; эта причина действует и без лимита. Проверять устойчивое множество writeErrors после попытки сохранения, чтобы не принять результат поверх неудачной записи.
3. Не добавлять второй классификатор причин неизвестности. Разделение historical/current не требуется: действующее правило уже допускает любую неполноту при разрешённом известном бюджете. Частичное исключение для legacy-unknown оставило бы тот же тупик для missing-baseline и ambiguous-durable-turns.
4. Использовать прежние parseReport, проверку stage, reportStore и transfer-report. Сохранение логов не становится механизмом повторной доставки отвергнутых результатов.
5. Обновить матрицу существующих тестов; добавить связанный сценарий unknown → штатный done → очередь → restart → transfer-report → идемпотентный повтор. Отдельно проверить postmortem, неверный JSON, чужой этап, обрыв и ошибку записи с обоими режимами лимита.
6. Синхронизировать основные требования трёх перечисленных capabilities и актуальные неархивированные дельты, которые иначе вернут прежний отказ. Исторические архивы и завершённые чек-листы не переписывать.

## Risks / Trade-offs

- Неизвестный хвост может скрывать перерасход → сохранять причины и нижнюю границу, не менять лимиты и блокировку по известному исчерпанию. Этот выбор уже закреплён правилом запуска владельца.
- Ошибка диска отличается от неизвестной истории → отдельный отказ по записи сохраняет прежнюю границу долговечности.
- Положительный исход процесса не доказывает готовность изменения → проверки отчёта, следа, CI и review остаются обязательными.

## Migration Plan

Форматы состояния не меняются. Правка поступает через отдельный PR с узкими локальными проверками и зелёным CI. Новые завершения следуют единому правилу после штатного обновления супервизора. Сохранённые старые отказы сами не переигрываются. Откат кода возвращает прежний отказ; журнал учёта остаётся совместимым.
