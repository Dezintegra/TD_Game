## Context

На свежей origin/main `provider.mjs:104` разбирает agent_message, а затем смешивает ошибку протокола и уменьшение usage в одной переменной error. Ранний возврат сохраняет result=null. Отсутствие обязательного usage также возвращает null. `supervisor.mjs` в finish разбирает result один раз до записи лога, но tokenBudget судит о полноте по наличию answer.usage; при уменьшении там остаются числа после Math.max. reportOutcome не учитывает failed при разобранном JSON, а reportedDone выбирает спокойную метку по stage/outcome JSON. reports.push уже защищён answer.outcome !== done.

## Goals / Non-Goals

Цель — доступный итоговый текст, честная диагностика расхода и неприменения при прежнем отказе в применении. Границы задач 0236 и 0233 перечислены в proposal. В этой работе нет исправления арифметики или нового механизма паузы, автоматического повторного применения и изменения квот.

## Decisions

### Независимый признак ошибки учёта

Добавить к ответу адаптера `usageError: string | null` (либо использовать эквивалентный структурный результат 0236, если он уже влит). Уменьшение по действующей проверке и отсутствие/негодность обязательного usage заполняют его. Ошибки протокола остаются отдельно; при совпадении причин первичный outcome определяется прежними проверками процесса, а ошибка учёта не теряется. Строка why для одиночной ошибки учёта сохраняет существующее объяснение.

Не менять значения usage, usageTotals, вычитание baseline, recordTokenUsage или сохранение реестра: это предмет 0236. Для вывода tokenBudget проверять usageError и пригодность usage последнего хода, а не truthiness объекта с числами. Существующее «учтено N / лимит» остаётся известной суммой реестра и сопровождается «расход текущего запуска неизвестен» и причиной; оно не называется полным расходом. При выключенном лимите отсутствие usage остаётся допустимым, но расход всё равно показывается неизвестным. Не определять ошибку по поиску слов в why: такой контракт ломается от редакторской правки сообщения.

### Сохранение текста после проверки завершения

Присваивать result последнему agent_message текущего хода после проверки успешного turn.completed, нулевого кода и отсутствия снятия/ошибки запуска/ошибки протокола, но до отказа по usageError. Это расширяет контракт только для ошибки учёта: result есть, outcome остаётся failed. При turn.started сбросить кандидат текста как сейчас: сообщение прошлого хода не выдаётся за ответ нового. Пустой ответ остаётся пустым, отсутствующий — null.

Альтернатива «вернуть done, раз JSON есть» отвергнута: она пропускает бюджетный барьер. Альтернатива отдельного rawResult не нужна: result уже читает parseReport, а за применение отвечает outcome. Альтернатива искать текст в сыром stdout в журналировщике дублирует разбор протокола и рискует взять промежуточное сообщение.

### Единое представление неприменения

Сохранить единственный parseReport(answer.result) в finish до записи лога и всех ранних возвратов. reportOutcome для сохранённого корректного JSON при failed печатает объявленный исход и «не применён» с причиной; для чужого этапа дополнительно сохраняет оба имени этапов. При некорректном JSON печатает причину parseReport, а ошибка учёта остаётся отдельной диагностикой в той же шапке/строке. Фраза «сессия ответа не оставила» допустима только при result=null, а не при ошибке учёта с доступным текстом.

Строка консоли использует TAG.warn при answer.outcome !== done независимо от JSON done. В обычном случае сохраняется прежняя метка по исходу отчёта и совпадению этапа. Завершение процесса не объявляется подтверждением принятия этапа: собственно проверка следа и перенос остаются далее в конвейере.

В renderLog добавить читаемый раздел итогового текста для доступного result, сохранив исходные stdout/stderr и отказы целиком. Это даёт доступ к JSON без ручного раскодирования строк JSONL, но не создаёт файл очереди для восстановления. В cycle.log и консоли назвать ошибку учёта и неприменение; тело отчёта хранить в существующем журнале этапа. Даже некорректный JSON сохраняется без изменений. Запись происходит до раннего возврата failed. reports.push остаётся недостижимым при usageError; продолжения, сроки, API-ошибки и существующие ограничения бюджета не меняются.

### Согласование открытых требований

При реализации в `supervise-the-pipeline/specs/dev-pipeline-supervisor/spec.md`, требовании «Ответ сессии берётся из кода возврата и вывода», уточнить: исход отчёта двигает задачу только после допуска ответа к применению; при ошибке учёта текст сохранён, но не применяется. В `name-both-outcomes-in-the-log/specs/dev-pipeline-supervisor/spec.md`, требовании «Шапка лога этапа различает ответ сессии и исход отчёта», уточнить условие спокойной метки и обязательность пометки неприменения при ошибке учёта. Сохранить все прежние сценарии. Сейчас эти файлы не меняются: этап design пишет только своё изменение. Наша ADDED-дельта задаёт узкие новые сценарии и не копирует отсутствующую основу через MODIFIED.

## Risks / Trade-offs

- Расширенный result может повлиять на другие потребители → просмотреть все вызовы readCodexAnswer и не подменять outcome наличием result; адаптер и finish менять одним атомарным шагом с тестами.
- Общие участки с 0236 → обновить базу и использовать её диагностику, если появилась, не создавать второй reducer. Ошибка определяется действующей арифметикой, её смысл здесь не переопределяется.
- Журнал будет длиннее на итоговый текст → дублируется только финальный ответ, не поток событий; это оправдано читаемостью разбора.
- Журнал не обеспечивает повторное применение после перезапуска и может подчиняться существующей политике перезаписи → гарантия этой задачи ограничена текущим finish; долговременная доставка остаётся 0233.

## Migration Plan

Миграции формата состояния нет. Первый коммит реализации включает адаптер, безопасное потребление result, журналирование, согласование требований и минимальные тесты. После его отправки открывается черновой PR. Следующий коммит расширяет регрессионную матрицу. Откат кода возвращает прежнее журналирование без миграции реестра.

Игровой код не меняется: рассинхрон и реконнект, golden-эталоны, PROTOCOL_VERSION не затронуты. Math.random, Date.now и дробное состояние мира в sim не вводятся.
