## Context

На свежей origin/main `provider.mjs:104` разбирает agent_message, а затем смешивает ошибку протокола и уменьшение usage в одной переменной error. Ранний возврат сохраняет result=null. Отсутствие обязательного usage также возвращает null. `supervisor.mjs` в finish разбирает result один раз до записи лога, но tokenBudget судит о полноте по наличию answer.usage; при уменьшении там остаются числа после Math.max. reportOutcome не учитывает failed при разобранном JSON, а reportedDone выбирает спокойную метку по stage/outcome JSON. reports.push уже защищён answer.outcome !== done.

## Goals / Non-Goals

Цель — доступный итоговый текст, честная диагностика расхода и неприменения при прежнем отказе в применении. Границы задач 0236 и 0233 перечислены в proposal. В этой работе нет исправления арифметики или нового механизма паузы, автоматического повторного применения и изменения квот.

## Decisions

### Независимый признак ошибки учёта

0236 вливается первой; реализация 0235 начинается только после её появления в origin/main. Источник истины — общий reducer `token-budget.mjs` и долговечный status задачи с completeness и причинами, введённые 0236. Адаптер получает результат обработки всех наблюдений запуска с долговечной базой, finish использует status после идемпотентного учёта тех же наблюдений. `usageError: string | null` — только представление причин unknown этого результата, а не ещё одна проверка снимков. Если 0236 уже предоставляет поле причин, передавать его напрямую с форматированием для журнала. Наличие числового answer.usage или валидного последнего completed не заменяет status задачи. Ошибки протокола остаются отдельно; при совпадении причин первичный outcome определяется прежними проверками процесса, а ошибка учёта не теряется.

Не менять арифметику и запись реестра 0236, не возвращать `known[stage].usage`, stage usageBaseline, покомпонентный Math.max или вычитание cached как критерий ошибки. При включённом бюджете unknown запуска или долговечная неполнота задачи не допускают отчёт к применению: result сохраняется, а ответ остаётся failed. Если неполнота выявлена только при долговечной записи в finish, finish присоединяет её причины и устанавливает failed до журналирования и очереди применения. Это потребление результата учёта, не повторный расчёт. Неудача сохранения бюджета также не даёт пройти допуск; её причина сохраняется отдельно от текста. При выключенном лимите неизвестность сама по себе не блокирует ответ по токеновому правилу, но остаётся в диагностике; проверки процесса действуют всегда.

Существующее «учтено N / лимит» остаётся известной нижней границей задачи. Полнота задачи и известность расхода запуска показываются раздельно: исторический unknown не маскируется известной дельтой текущего запуска. Причины берутся из status, не из поиска слов в why. Миграция v2, launchId, watch/finish и resume-учёт полностью принадлежат 0236.

Совместный контракт после объединения:

| Наблюдение при успешном ходе и коде 0 | Учёт 0236 | Сохранение и допуск 0235 при включённом бюджете |
| --- | --- | --- |
| Новое уменьшение input либо output | unknown с причиной; известная нижняя граница сохранена | исходный result, failed, неприменение и предупреждение, очередь пуста |
| Уменьшился только cached, input/output прежние и история полна | известный input+output, диагностическое замечание без unknown | result сохранён, обычный допуск отчёта; замечание не превращается в usageError |
| Ранее возник unknown, затем пришёл валидный больший снимок | нижняя граница может вырасти, долговечная неполнота остаётся | result сохранён, failed, названа историческая причина; done не попадает в очередь |
| Нет обязательного usage либо оно непригодно | unknown с причиной | корректный и некорректный JSON сохраняются, failed; для некорректного дополнительно причина разбора |

Альтернатива поддержать оба порядка вливания отвергнута: временный старый классификатор ошибки расходится с cached и долговечной неполнотой. Последовательное вливание позволяет проверить единый контракт, не реализуя арифметику в 0235.

### Сохранение текста после проверки завершения

Присваивать result последнему agent_message текущего хода после проверки успешного turn.completed, нулевого кода и отсутствия снятия/ошибки запуска/ошибки протокола, но до бюджетного отказа по status. При включённом бюджете result есть, outcome остаётся failed. При turn.started сбросить кандидат текста как сейчас: сообщение прошлого хода не выдаётся за ответ нового. Пустой ответ остаётся пустым, отсутствующий — null.

Альтернатива «вернуть done, раз JSON есть» отвергнута: она пропускает бюджетный барьер. Альтернатива отдельного rawResult не нужна: result уже читает parseReport, а за применение отвечает outcome. Альтернатива искать текст в сыром stdout в журналировщике дублирует разбор протокола и рискует взять промежуточное сообщение.

### Единое представление неприменения

Сохранить единственный parseReport(answer.result) в finish до записи лога и всех ранних возвратов. reportOutcome для сохранённого корректного JSON при failed печатает объявленный исход и «не применён» с причиной; для чужого этапа дополнительно сохраняет оба имени этапов. При некорректном JSON печатает причину parseReport, а ошибка учёта остаётся отдельной диагностикой в той же шапке/строке. Фраза «сессия ответа не оставила» допустима только при result=null, а не при ошибке учёта с доступным текстом.

Строка консоли использует TAG.warn при answer.outcome !== done независимо от JSON done. В обычном случае сохраняется прежняя метка по исходу отчёта и совпадению этапа. Завершение процесса не объявляется подтверждением принятия этапа: собственно проверка следа и перенос остаются далее в конвейере.

В renderLog добавить читаемый раздел итогового текста для доступного result, сохранив исходные stdout/stderr и отказы целиком. Это даёт доступ к JSON без ручного раскодирования строк JSONL, но не создаёт файл очереди для восстановления. В cycle.log и консоли назвать ошибку учёта и неприменение; тело отчёта хранить в существующем журнале этапа. Даже некорректный JSON сохраняется без изменений. Запись происходит до раннего возврата failed. reports.push остаётся недостижимым при непроверенном обязательном бюджете; продолжения, сроки, API-ошибки и существующие ограничения бюджета не меняются. При отключённом лимите unknown показывается без ложной пометки неприменения, если остальные проверки допускают отчёт.

### Согласование открытых требований

При реализации в `supervise-the-pipeline/specs/dev-pipeline-supervisor/spec.md`, требовании «Ответ сессии берётся из кода возврата и вывода», уточнить: исход отчёта двигает задачу только после допуска ответа к применению; при ошибке учёта текст сохранён, но не применяется. В `name-both-outcomes-in-the-log/specs/dev-pipeline-supervisor/spec.md`, требовании «Шапка лога этапа различает ответ сессии и исход отчёта», уточнить условие спокойной метки и обязательность пометки неприменения при ошибке учёта. Сохранить все прежние сценарии. Сейчас эти файлы не меняются: этап design пишет только своё изменение. Наша ADDED-дельта задаёт узкие новые сценарии и не копирует отсутствующую основу через MODIFIED.

## Risks / Trade-offs

- Расширенный result может повлиять на другие потребители → просмотреть все вызовы readCodexAnswer и не подменять outcome наличием result; адаптер и finish менять одним атомарным шагом с тестами.
- Общие участки с 0236 → обязательное вливание 0236 первой и обновление базы перед реализацией 0235. При отсутствии влитой зависимости реализацию не начинать; сообщить о невыполненном предусловии по правилам этапа, не собирать временный старый путь и не ждать в сессии.
- Журнал будет длиннее на итоговый текст → дублируется только финальный ответ, не поток событий; это оправдано читаемостью разбора.
- Журнал не обеспечивает повторное применение после перезапуска и может подчиняться существующей политике перезаписи → гарантия этой задачи ограничена текущим finish; долговременная доставка остаётся 0233.

## Migration Plan

Собственной миграции формата состояния нет: используется уже влитый v2 из 0236. Первый коммит реализации включает адаптер, безопасное потребление result, журналирование, согласование требований и минимальные совместные тесты. После его отправки открывается черновой PR. Следующий коммит расширяет регрессионную матрицу. Откат только 0235 возвращает прежнее журналирование поверх 0236, сохраняя reducer и v2; откат к baseline этапа не допускается.

Игровой код не меняется: рассинхрон и реконнект, golden-эталоны, PROTOCOL_VERSION не затронуты. Math.random, Date.now и дробное состояние мира в sim не вводятся.
