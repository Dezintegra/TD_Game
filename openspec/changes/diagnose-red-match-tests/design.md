## Context

Задача 0106 меняет только инструкции автономных исполнителей. В свежей базе `revise.md` разбирает CI в шаге 7, а `implement.md` разрешает однократное чтение CI в шаге 9 и заказывает обычные балансные прогоны в шаге 8. Общий routing-контракт уже допускает blocked на обоих этапах; `blockers.mjs` проверяет reason/result, ссылки и циклы и после результата возвращает задачу на анализ.

## Goals / Non-Goals

Цель — остановить повторную подгонку матчевой проверки и дать исполнителю завершимую передачу диагностики. Границы — два файла инструкций и согласование их собственных описаний отчётов. Non-goals перечислены в proposal; код маршрутизации, правила игры, канарейка и параметры конкретного будущего матча не меняются.

## Decisions

### Локальные пункты в обеих инструкциях

В revise добавить именованный подпункт внутри разбора CI, перед циклом правок. В implement разместить аналогичный протокол рядом с однократным чтением CI и отсылку из заказа обычного прогона. Сохранить номера существующих шагов: это не ломает соседние ссылки. Обновить вводные описания переходов и перечни исходов: revise → pr и implement → pr описывают успешное завершение, а ожидание диагностики уходит в blocked.

Отдельный общий файл отвергнут: добавил бы третий обязательный источник чтения при коротком протоколе, который нужен в обеих точках. Смысл и пример отчёта должны совпадать при допустимой разнице stage. Не добавлять новые действия в routing-contract: он уже приложен к назначению.

### Причина падения важнее суффикса

Сначала прочитать лог текущего задания и соответствующий assertion на его ревизии. Записать источник падения и связь с изменёнными правилами. Суффикс охватывает также golden и сетевые тесты: без этого различения запрет подгонки отменил бы законное обновление эталонов. Неизвестную причину нельзя объявить балансной по одному имени файла; сначала использовать имеющиеся логи и код. Ошибки другого класса идут по действующим правилам, без расширения области карточки.

### Единственная коррекция не является способом закрыть красноту

Окно можно изменить один раз при объяснимой связи со временем события и комментарием в тесте у значения. Проверить историю файла и журнал, записать старое/новое значение и источник основания также в decisions. Считается вся текущая диагностика этого окна, а не один запуск исполнителя. Повторная коррекция требует нового замера именно исходной пары на релевантной ревизии и нового обоснования. Порог ради зелёного результата не ослабляется ни в первой, ни в следующей попытке.

Абсолютный запрет всех изменений окна отвергнут: постановка допускает обоснованную коррекцию. Безусловная «одна бесплатная попытка» тоже отвергнута: воспроизводит прежнюю догадку. Комментарий со ссылкой только на зелёный CI или зеркальный прогон другой пары не является обоснованием.

### Диагностика отправленной ветки без цикла зависимостей

Заявка содержит `type: run`, уникальный key, категории, `run.kind: arena`, profiles в исходном порядке, matches, seed, change и явную ветку в params; в description фиксируются SHA упавшей проверки и SHA отправленного кода, окно, сценарий, настройки и доступные величины. `benchmark.md` уже использует ветку через `--ref`, поле params свободное. Для arena не подменять выбор ветки локальным perf/bench-tick source.

Если ветка с момента падения изменена, назвать различия и требуемую контрольную ревизию. Замер на чужом SHA нельзя выдавать за воспроизведение старого падения. Ожидание описывает, какое событие или измерение отличит неверное окно от регрессии, а не просто «должно стать зелёным». Если стандартная арена не воспроизводит существенное условие теста, это явно указать в заказе и требуемом результате; не заменять его ближайшим доступным профилем и не принимать несопоставимые числа за ответ.

Диагностика использует уже опубликованный код. В заявке не ставить dependsOn на родительскую задачу и не требовать её вливания. Обычный замер после появления изменения остаётся отдельным случаем: для него нельзя создавать обратную зависимость. Если подходящий диагностический run уже есть в описи, сослаться на него вместо нового; если результат уже получен, проверить пригодность и использовать при анализе, а не блокироваться на выполненном.

### Завершение через действующий blocked

В обоих файлах дать синтаксически корректный пример полного JSON-отчёта: routingVersion, taskId, stage, outcome blocked, categories, summary с названием заказа, decisions, links, requests и blockers. У blocker ровно одна ссылка requestKey на key заявки; reason объясняет невозможность продолжить исправление без измерения, result называет требуемый содержательный ответ. Рядом объяснить замену на taskId существующего заказа без повторного requests. Пример не должен выглядеть как уже исполненный прогон: links.run остаётся null до фактического номера.

Собственные незавершённые правки сохраняются и отправляются перед отчётом. Не нужен фиктивный коммит, если при диагностике ничего не менялось: требование свежего коммита для done не превращает blocked в обязанность менять тест. Принятый заказ не означает закрытый assertion или выполненный пункт реализации. Получение результата возвращает задачу на новый анализ, сохраняя ветку, change и PR; переписка состояния доски остаётся работой супервизора.

Новый исход waiting отвергнут, потому что дублировал бы blocked. failed и question отвергнуты для ожидания уже обязательного результата: первый отправляет к человеку технически исправный маршрут, второй просит заново принять уже заданное решение.

## Risks / Trade-offs

- Две копии протокола могут разойтись → в одном атомарном шаге согласовать оба текста и проверить каждый сценарий дельты для обоих этапов.
- Новая сессия может обнулить счёт коррекций → явно требовать чтения истории теста и журнала; автоматический счётчик вне области.
- Кандидат 0317 описывает ту же диагностическую пару → зафиксировать покрытие в отчёте; не создавать ещё одну дельту или заявку. Владение карточкой 0317 не присваивать.
- Другие открытые изменения правят те же файлы → сохранить их независимые разделы при освежении; порядок архивации новой ADDED-нормы quality-gates от них не зависит.
- Инструкции не обеспечивают механического запрета произвольной правки тестов → приёмка остаётся содержательной, по комментарию, истории и результатам. Автоматический контроль кода потребовал бы другой постановки.

## Verification

Проверить оба текста по девяти сценариям дельты и сопоставить пример blocked с `blockerReportProblem`, `planBlockers` и `taskFromRequest` по коду: обязательные поля, совпадение key, отсутствие обратного ребра. Проверить точечно Prettier для двух файлов и diff на отсутствие посторонних изменений. Новые исполняемые тесты для этой обратимой правки Markdown не нужны; общие проверки инструкций остаются в CI.

## Migration Plan

Один атомарный коммит инструкций после аудита и черновой PR. Новые сессии получают обновлённый текст после обычной доставки изменения; миграция карточек не нужна. При откате возвращаются две инструкции, состояние уже созданных зависимостей не переписывается.

Геймплей, рассинхрон и реконнект не затронуты. `packages/sim` и бинарный протокол не меняются: обновление golden и PROTOCOL_VERSION для этой карточки не нужны. Запреты Math.random, Date.now и дробного состояния мира сохраняются без изменений. Отзывчивость и игровой трафик не затронуты.
