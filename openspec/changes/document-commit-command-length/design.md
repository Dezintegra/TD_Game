## Context

База освежена 09.09.2026: `git -C . fetch origin`, затем `git -C . merge origin/main` дали актуальный HEAD `734733f`. В design:407, implement:330 и revise:274 стоят образцы коммита; рядом нет ни 965, ни `Command too long for parsing`. В implement:215–223 уже есть файл тела PR и `--body-file`.

Постановка 0072 ссылается на `cycle.log:12165`, `:12740`, `:12741` задачи 0043. Это предоставленное историческое свидетельство; точная граница и версия разборщика в назначении отсутствуют, текущая сессия их не измеряла. Новая инструкция должна честно отделять это наблюдение от воспроизводимой гарантии.

## Goals / Non-Goals

Цель — дать исполнителю каждого коммитящего этапа применимый способ сократить команду, сохранив «почему». Область реализации — три Markdown-скилла; остальные не-цели перечислены в proposal. Нового кода и автоматического измерителя не требуется.

## Decisions

1. **Предупреждение в разделе коммита каждого скилла.** Единая ссылка в общей памятке не подходит: этап получает свой текст. Добавить согласованный абзац о приблизительном наблюдении около 965 байт, полном составе строки и отказе до Git. Не увеличивать allow: это не исправляет описанный разбор.

2. **Короткая причина вместо большого числа абзацев.** Рекомендуемый образец для implement/revise:

   ```powershell
   git -C <дерево> commit -m "docs: shorten commit examples" -m "Long commands fail before Git. Keep details in the PR."
   ```

   Для design заголовок — `docs(openspec): <имя>`, тело — короткое объяснение, например `Keep the rationale reviewable before implementation.` Все примеры однострочные. Повторные `-m` остаются допустимыми, но каждый абзац расходует тот же общий объём. Мерка две-три короткие фразы — редакционная подсказка; длина пути и кодирование не позволяют вывести гарантию из числа фраз. Не вводим новый обязательный точный порог или алгоритм подсчёта байтов.

3. **Подробности передаются через файл PR.** Использовать существующий механизм implement с собственным файлом в `.matchlog/`, правилами сохранения при ошибке и уборки после успеха. В revise обновлять тело существующего PR через файл, сохраняя относящийся к нему контекст; не создавать второй PR. В design подробности уже принадлежат `design.md`; отправленный артефакт переживает завершение сессии, implement переносит нужное в PR. Отвергнуты длинный `--body` (снова длинная команда) и `git commit -F` (отдельная карточка 0199).

4. **Документальное требование — отдельное ADDED в dev-pipeline-worker.** В основе такой способности ещё нет; имя переиспользует открытое изменение `agent-backlog-pipeline`, после которого выполняется архивация. Новая норма не меняет требования приёмки отчёта, покрытия команд и однострочных вставок. Порядок вливания короткого предупреждения не зависит от архивации основы.

## Verification

Реализация проверяется чтением всех трёх разделов по сценариям дельты, узким Prettier по трём файлам и просмотром diff. Новый тест, проверяющий только заданные слова, не доказывает прохождение внешнего парсера и для этой правки не нужен.

Критерий журнала проверяется после вливания на новых запусках, действительно получивших обновлённые скиллы: зафиксировать SHA влитой правки, начало наблюдения, по одному завершённому коммитящему заходу design/implement/revise и диапазоны соответствующих записей `cycle.log`. Ожидание — ни одного отказа `Command too long for parsing` на их командах коммита; учитывать диагностические записи отказов, а не цитаты этой строки в промптах. Если подходящего этапа ещё не было, результат по нему «не наблюдался», а не успех. Старые записи не удаляются. Это последующая эксплуатационная проверка, не пункт ожидания внутри implement и не утверждение о всех будущих командах. На проработке и при сдаче документальной реализации этот результат ещё не заявляется.

## Risks / Trade-offs

- Приблизительное число могут принять за спецификацию инструмента → явно назвать источник, непроверенную точную границу и отсутствие универсальной гарантии.
- Короткий коммит может потерять причину → образец содержит причину, подробности сохраняются в артефакте или PR.
- Другие открытые изменения правят те же скиллы → сверять свежий контекст, сохранять чужие разделы, ограничить правку образцами и пояснениями коммита. Не исправлять попутно старую разметку остальных блоков.
- Инструкция не обеспечивает нулевую частоту ошибок сама по себе → отдельно фиксировать наблюдение реальных запусков; не вводить бессрочное ожидание в tasks.

## Migration Plan

Один атомарный коммит с тремя скиллами и отметкой tasks; после отправки implement открывает черновой PR. После вливания новые сессии получают текст из основного дерева; уже запущенные сессии не считаются проверкой новой инструкции. Откат возвращает только эту правку текста. Игровая выкладка, миграция данных и арена не нужны.

## Architecture

Геймплей, рассинхрон и реконнект не меняются. `packages/sim` и состояние мира не затронуты: эталоны детерминизма не обновляются, `Math.random`, `Date.now` и дробные числа в состояние не вводятся. Раскладка байтов протокола прежняя, роста `PROTOCOL_VERSION` нет.

## Open Questions

Продуктовых вопросов нет. Точное значение границы и версия исторического разборщика неизвестны; устанавливать их вне области карточки, а приблизительное предупреждение с оговоркой выполнимо сейчас.
