## Context

Постановка 0096 уже определяет продуктовый выбор: сравнивать величины на общих доживших мирах и показывать размер пересечения. Данные имеются в `apps/arena/src/schema.ts`: таблицы match и sample. Текущий `scripts/analysis/mirror-timeouts.mjs` читает одну базу, проверяет её паспорт и сравнивает группы по end_reason. `apps/arena/src/report.ts` также описывает один источник. Ни один не выполняет нужное соединение двух прогонов.

Исторические числа 49/57 и 5/14 взяты из постановки, а не пересняты этим этапом. Для приёмки штатного алгоритма нужны небольшие контролируемые базы, не доступность старых артефактов GitHub.

## Goals / Non-Goals

Цель — повторяемый расчёт A, B, B−A на одной выборке каждой метрики и отсечки с прозрачным знаменателем. Границы — в proposal. В частности, не переносим сюда интервальную диагностику mirror-timeouts и не изменяем трактовку живых башен: поле towers может включать недострой, это должно быть подписано.

## Decisions

### Отдельная команда и один паспорт

Добавить `scripts/analysis/paired-cutoffs.mjs` с экспортируемыми функциями чтения/расчёта, форматирования и runCli, защищённым входом CLI. Node SQLite загружается существующим способом через createRequire, совместимым с Vitest проекта. Модуль не импортирует приложения или sim и не запускает симуляцию. Новый файл сохраняет контракт и код mirror-timeouts целиком; импортировать оттуда весь анализатор ради пары функций не нужно: его проверка требует не относящиеся к задаче таблицы decision/attempt/command.

CLI: `node scripts/analysis/paired-cutoffs.mjs --config .matchlog/paired-cutoffs.json`. Необязательный `--out .matchlog/paired-cutoffs-result.json` пишет JSON; без него Markdown идёт в stdout. Паспорт JSON содержит `before` и `after`, каждое с `db`, `run`, `sha`, `profiles` (массив ровно двух непустых идентификаторов), `seedStart`, `matches`, `ticksPerSecond`, `capSeconds`; общий `cutoffsSeconds` — необязательный массив положительных целых, по умолчанию [300, 600]. Пути db разрешаются относительно каталога паспорта. Повторённые/неизвестные аргументы и поля отвергаются; cutoffs сортируются и не допускают повторений. Целые параметры проверяются на безопасный диапазон, положительность и безопасное умножение секунд на частоту тиков; seedStart допускает ноль.

Один паспорт вместо двух десятков ключей сохраняет короткий воспроизводимый вызов. README даст полный пример JSON и команды. Сам паспорт пользователя не коммитится. Выход MUST NOT перезаписывать паспорт или любую базу, включая совпадение через realpath и hardlink; сравнение источника с самим собой допустимо как нулевой контроль. SQLite открывается readOnly, дескрипторы закрываются и при ошибке. Ошибка ввода даёт stderr и код 1 без успешного отчёта; корректный пустой результат даёт код 0 и явное «нет данных».

### Проверка источников и ключ пары

Для каждого источника проверяется точный диапазон seedStart..seedStart+matches−1, по одному матчу на мир, SHA и git_dirty=0, профили в указанном порядке, целые непустые зерна ИИ и корректный footer. Timeout требует ticks=capSeconds×ticksPerSecond и winner=null; base-destroyed требует winner 0/1 и 0<ticks<=cap. Неизвестная причина или отсутствующий footer — ошибка входа. Обязательные столбцы match соответствуют перечисленным полям; в sample обязательны match_id, tick, player. Отсутствие столбца отдельной метрики означает недоступность именно этой метрики, а не непригодность всей базы.

Паспорта обоих источников должны иметь одинаковые ordered profiles и ticksPerSecond. SHA, предел и диапазоны миров могут различаться и остаются видны. Run, частота и cap — внешние сведения, база их не доказывает. Само имя профиля не доказывает неизменность его реализации или генератора мира между SHA: отчёт не называет эксперимент причинным и явно оставляет эту проверку автору интерпретации.

После проверки уникальности строятся индексы по world_seed. Отсутствующий с одной стороны мир обозначается before-only/after-only; разные ai_seed_0/1 — ai-seed-mismatch. Эти записи не становятся парами. match_id сохраняется только как адрес исходной строки. Подбор ближайшего зерна, zip строк по порядку и автоматический обмен сторон отвергнуты: они создают ложные пары.

### Дожитие, снимки и метрики

На каждой отсечке t независимо считаются survivorBefore/After по footer каждого валидного источника, затем commonSurvivors среди сопоставленных миров, где ticksA>=t и ticksB>=t. В диагностиках по каждому миру сохраняются обе причины недожития, если их две. В JSON различаются непарность, недожитие и отсутствие наблюдения. Даже cutoff за пределом обоих прогонов допустим: он даёт пустое пересечение с названными пределами.

Для стороны берётся sample с максимальным tick<=t, не позже footer, при 0<=t−tick<=ticksPerSecond. Это та же давность, что объявлена существующим mirror-timeouts. Если на выбранном тике несколько строк — сторона недоступна, даже если строки одинаковы: произвольный LIMIT 1 скрыл бы повреждение. Если выбранный sample содержит null/неконечное/нечисловое значение метрики, назад к более удобному снимку не отступаем. Строки после footer не используются. Не надо требовать полную секундную сетку: измеряем точку, а не долю времени в интервале.

Список метрик фиксирован: energy, income_per_tick, units_alive, structures, towers, walls, base_hp, general_hp, general_alive, queue_len, upgrade_total_level, path_to_enemy. Идентификаторы клеток и цели general_cell/target_structure усреднять бессмысленно, они не включаются. Численности показываются в объектах, HP/энергия в единицах исторической базы, доход за тик, уровни в уровнях; средние general_alive/path_to_enemy — доли 0/1 на отсечке, не доли времени. Современные балансные константы для конвертации не импортируются.

Для метрики m и стороны p множество V состоит из commonSurvivors с годными mA,p и mB,p. Итог: n=|V|, meanA=sum(A)/n, meanB=sum(B)/n, meanDelta=sum(B−A)/n. В JSON остаются строки пары с world_seed, match_id A/B, выбранными ticks A/B, значениями и delta. Отдельная строка both использует только миры с четырьмя годными значениями: внутри каждого источника берётся среднее сторон, затем равновесное среднее миров. Колонки n относятся к мирам, никогда к двум сторонам сразу. Отдельные n сторон могут различаться — это подписано; both не усредняет уже готовые средние сторон с разными составами.

Числа в JSON не округляются для расчёта; Markdown округляет только отображение. При n=0 все три средних null. commonSurvivors остаётся общим числом доживших, а n каждой метрики может быть меньше: путать эти знаменатели нельзя. Независимые средние по всем выжившим в сравнительные колонки не добавляются — их легко прочитать как эффект изменения.

### Вывод и воспроизводимость

Markdown содержит паспорт A/B, SHA256 файлов, направление B−A, единицы, предупреждение об обусловленности совместным дожитием и таблицу: отсечка, метрика, сторона, survivorBefore, survivorAfter, commonSurvivors, n, A, B, B−A, причины пропусков. n располагается рядом с тремя средними в той же строке. Строки с n=0 сохраняются. JSON содержит те же итоги и полную опись принятых/исключённых миров и снимков, чтобы восстановить расчёт без скрытого отбора. Порядок фиксирован по отсечке, списку метрик, стороне и зерну; часы и случайность в результат не добавляются.

Приёмка строится на синтетических SQLite из match/sample без симуляции. Главный контроль намеренно меняет состав выживших: A: мир 1=10, мир 2=0; B: мир 1=11, мир 3=0. Для более сильного контроля противоположного знака B-only мир получает 0, а A-only мир 100: независимое среднее падает 55→5.5, парное растёт 10→11. Проверяется и значение, и состав n=1, и печать; простого сравнения двух вызовов одного алгоритма недостаточно.

## Risks / Trade-offs

- Совместное дожитие всё ещё отбирает подмножество → отчёт не переносит результат на всю пачку и не утверждает причину сдвига.
- Seed не гарантирует ту же карту между версиями генерации → сохраняются SHA, параметры и явное ограничение интерпретации; автоматическая проверка diff исторических ревизий вне задачи.
- Старый столбец отсутствует → метрика недоступна с n=0, остальные сохраняются; ноль не служит заглушкой.
- Чтение подробных decision увеличило бы время и память → запрашиваются только match и необходимые sample в окнах отсечек, используются существующие индексы.
- Разрастание одного коммита → расчёт с тестами поставляется первым, CLI/README с интеграционными тестами вторым; каждый шаг работоспособен самостоятельно.

## Migration Plan

Миграция данных не нужна. Доставка — новые аналитические файлы и раздел README через один PR. Откат удаляет новую команду и её документацию; старый анализатор продолжает работать. Изменение не затрагивает sim, golden-эталоны, протокол и PROTOCOL_VERSION. Рассинхрон и реконнект сохраняют прежнее поведение: инструмент вообще не подключается к матчу. Math.random, Date.now и дробные числа в состоянии мира не добавляются; дробное усреднение выполняется исключительно офлайн. Прогон арены и perf не нужны: правила и отрисовка не меняются.

## Open Questions

Продуктовых вопросов нет. Исторические прогоны не являются обязательными тестовыми входами: исправление доказывается контролируемыми данными с известным составом пересечения.
