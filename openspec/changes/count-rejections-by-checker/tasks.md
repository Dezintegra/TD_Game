# Шаги реализации

Каждый шаг — отдельный коммит, отправляемый сразу. Каждый собирается
и проверяется сам по себе: следующего шага, который «всё починит», нет.

Команды даны покрытой формой: `git` — только с ключом `-C <дерево>`,
`pnpm` и `npx` — по имени. Тесты супервизора обычным `vitest` не видны:
у них свой корень, и зовутся они `pnpm test:pipeline`.

- [ ] 1. **Предикат проверяющего этапа.** В `supervisor/lib/apply-report.mjs`
      завести и экспортировать `isChecking(stage)` — истина тогда и только
      тогда, когда `afterRejected({ status: stage })` даёт цель. Отдельного
      перечня этапов не заводить: он разошёлся бы с таблицей возвратов.
      В `supervisor/lib/apply-report.test.mjs` — тест перебором всех состояний
      автомата из `supervisor/config/transitions.mjs`: предикат обязан совпасть
      с таблицей на каждом, а не на двух выбранных.

      _Проверка:_ `npx vitest run --root supervisor supervisor/lib/apply-report.test.mjs`
      зелёный. Ничьё поведение шаг не меняет — предикат пока никто не зовёт.

      _После этого коммита открыть черновой pull request:_ до его появления
      проверки CI на пуши в ветку не запускаются вовсе.

- [ ] 2. **Ключ у `resetAttempts`.** В `supervisor/lib/task-file.mjs` дать
      `resetAttempts(task, { keepRejections = false } = {})`: при `false` —
      прежнее поведение слово в слово, при `true` — обнуляется всё, кроме
      `attempts.rejections`. Умолчание менять нельзя: функцию зовут ещё
      и подъём задачи из ошибки (`returnTask` в `supervisor/lib/execute.mjs`),
      которому нужен полный сброс. Тесты — в `supervisor/lib/task-file.test.mjs`:
      без ключа счёт возвратов гаснет, с ключом переживает, прочие счётчики
      обнуляются в обоих случаях.

      _Проверка:_ `npx vitest run --root supervisor supervisor/lib/task-file.test.mjs`
      зелёный; прежние тесты этого файла не правлены.

- [ ] 3. **Выбор формы гашения при переносе отчёта.** В `supervisor/lib/execute.mjs`
      (ветвь на строках 131-135) при исходе `done` звать
      `resetAttempts(moved.task, { keepRejections: !isChecking(task.status) })`.
      Ветвь `rejected` и ветвь остановки не трогать. Комментарий над ветвью
      переписать: гасит счёт возвратов проверяющий этап, а не любой удавшийся.
      Тесты — в `supervisor/lib/execute.test.mjs`: `done` проработки счёт
      сохраняет, `done` аудита гасит, `done` доработки сохраняет, `done` ревью
      гасит.

      _Проверка:_ `npx vitest run --root supervisor supervisor/lib/execute.test.mjs`
      зелёный, в том числе прежние тесты про возврат и про предел.

- [ ] 4. **Сторож круга качелей.** В `supervisor/lib/execute.test.mjs` завести
      тест, проигрывающий через `execute` полный круг при `maxRejections: 3`:
      возврат аудита → `done` проработки → возврат аудита → `done` проработки →
      возврат аудита. Требовать `postmortem` на третьем возврате и причину
      в журнале, называющую число возвратов подряд. Тест обязан быть красным
      на коде до шага 3 — это и есть доказательство почина, а не украшение.

      _Проверка:_ `npx vitest run --root supervisor supervisor/lib/execute.test.mjs`
      зелёный. Красноту «до» снять заранее, отложив шаг 3 в сторону
      `git -C <дерево> stash`, и вернуть его `git -C <дерево> stash pop`;
      число возвратов из красного прогона назвать в теле коммита.

- [ ] 5. **Обещание в схемах и комментариях.** Описание поля `rejections`
      в `supervisor/config/task-schema.json` и в `manage/schema.json` привести
      к делу: счёт гасит проверяющий этап, принявший работу, а не любой
      удавшийся. Тем же коммитом поправить обещание в комментарии
      `countRejection` (`supervisor/lib/task-file.mjs:174-178`) и в пояснении
      к `maxRejections` (`supervisor/config/defaults.mjs`, около строки 195),
      где сказано, что счёт возвраты «не считал вовсе». Состав полей обеих
      схем не менять — правится только текст описаний.

      _Проверка:_ `npx prettier --check supervisor/config/task-schema.json manage/schema.json`
      зелёный; `npx vitest run --root supervisor` зелёный целиком — схема
      читается тестами разбора задач, и поломанный JSON уронил бы их.

- [ ] 6. **Отметить сделанное.** Проставить отметки в этом файле и свести
      `design.md` с тем, что вышло, если по дороге решение отклонилось.

      _Проверка:_ `openspec validate count-rejections-by-checker --strict`
      зелёный; незакрытых пунктов в `tasks.md` не осталось.
