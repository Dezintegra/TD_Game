# Шаги реализации

Каждый шаг — отдельный коммит, отправляемый сразу. Каждый собирается
и проверяется сам по себе: «следующего шага, который всё починит», ни
у одного из них нет.

Проверки идут узкие и местные — по своим файлам, не полным набором
(правило 6 в `CLAUDE.md`):

```
npx vitest run --root supervisor lib/<файл>.test.mjs
npx eslint supervisor/lib/<файл>.mjs
npx prettier --check supervisor/lib/<файл>.mjs
```

Полный набор гоняет CI. Из дополнительного дерева `pnpm verify` не
запускается.

## 1. Дескриптор живого этапа ложится на диск и стирается

- [ ] В `supervisor/lib/supervisor.mjs` при удавшемся порождении писать
      в `known[at]` поле `live: { pid, machine, supervisorPid, startedAt, timeoutMs }`
      и звать `saveStages`. Писать **после** проверки `handle.pid`
      (`supervisor.mjs:189`): у процесса без номера дескриптора быть не должно.
- [ ] В `finish` стирать `live` и звать `saveStages` — при любом исходе,
      включая снятие по сроку и неразобравшийся отчёт.
- [ ] `remembered` (`supervisor.mjs:404`) научить переносить `live`,
      сохранив терпимость к записи-строке прежней раскладки.
- [ ] Имя станции и номер супервизора приходят доводами `machine`
      и `supervisorPid`, а не читаются из `node:os` внутри: счётная часть
      супервизора уже принимает так же и часы, и порождение.

**Проверка:** `npx vitest run --root supervisor lib/supervisor.test.mjs` —
новые тесты: после `spawnStage` сохранённый снимок несёт `live` с номером
процесса; после завершения процесса `live` в снимке нет; запись прежней
раскладки (голая строка) читается без `live` и без ошибки.

**После этого шага открыть черновой pull request** — до него проверки CI
на пуши в ветку не запускаются вовсе:

```
gh pr create --draft --base main --title "Идущий этап переживает смену супервизора" --body-file <файл>
```

## 2. Опознание процесса: спросить систему об имени образа

- [ ] В `supervisor/lib/run-stage.mjs` завести `createProbeProcess(run, platform)`
      по образцу `createKillTree` (`run-stage.mjs:309`): возвращает
      `(pid) => ({ known, alive, image })`.
- [ ] Windows: `tasklist /FI "PID eq <pid>" /NH /FO CSV`, имя образа —
      первое поле CSV. Ответ «нет такого процесса» приходит текстом,
      а не кодом возврата: строку, не начинающуюся с кавычки, читать
      как «процесса нет».
- [ ] Прочие системы: `ps -p <pid> -o comm=`, ненулевой код возврата —
      «процесса нет».
- [ ] Неудача самой команды (нет `tasklist`, вывод не разобрался) даёт
      `known: false` — «спросить не удалось», и это НЕ равно «процесса нет».

**Проверка:** `npx vitest run --root supervisor lib/run-stage.test.mjs` —
тесты на подставном `run`: живой процесс с именем образа; отсутствующий
процесс; неразобравшийся вывод даёт `known: false`. Живых процессов
тесты не поднимают.

## 3. Сироты при запуске попадают в перечень идущих

- [ ] `createSupervisor` принимает довод `probe` и при сборке разбирает
      прочитанные `stages`: каждая запись с `live` — сирота.
- [ ] Дескриптор с чужим `machine` не судится: стирается, причина уходит
      в `log`.
- [ ] Сирота считается живым при `probe(pid).alive && image === live.image`.
- [ ] `running()` отдаёт живых сирот наравне с собственными детьми;
      `busy()` считает их же.

**Проверка:** `npx vitest run --root supervisor lib/supervisor.test.mjs` —
супервизор, собранный поверх `stages` с `live` и подставным `probe`,
отдаёт этап в `running()`; при несовпадении имени образа — не отдаёт;
дескриптор чужой станции стёрт, причина в журнале.

## 4. Развод сирот по обороту: исчез, протух, пережил срок

- [ ] Завести `sweep()` — обход сирот, годный для вызова раз в оборот.
- [ ] Сирота мёртв либо протух (опознание не совпало) — убрать из перечня,
      стереть `live` **не сразу**, а поставить исход в очередь
      `orphanOutcomes` (см. шаг 5); стирание — по удавшейся записи.
- [ ] Сирота жив и опознан, но `nowMs() - live.startedAt >= live.timeoutMs` —
      снять `killTree(pid)` и поставить исход «снят по сроку».
- [ ] Сирота неопознан (`known: false`) — **не снимать никогда**, причина
      в журнал цикла.

**Проверка:** `npx vitest run --root supervisor lib/supervisor.test.mjs` —
четыре теста на подставных `probe`, `killTree` и часах: исчезнувший даёт
исход и уходит из `running()`; переживший срок снят, и `killTree` позван
с его номером; протухший даёт исход, а `killTree` НЕ позван; неопознанный
не снят и остаётся в перечне.

## 5. Исход сироты доезжает до журнала задачи

- [ ] Супервизор отдаёт наружу `orphanOutcomes` — очередь по образцу
      `reports` (`supervisor.mjs:44`), с методом «забыть исход».
- [ ] `scan.mjs`: новый вид действия `note-orphan` в `ACTIONS` — **перед**
      `continue-stage`; на каждый исход из нового довода состояния
      `orphans` назначается действие, если задача есть в бэклоге.
- [ ] `execute.mjs`: обработчик `note-orphan` пишет журнал через
      `io.amendTask(taskId, text, message, source)` и зовёт «забыть исход»
      только при удавшейся записи. Поля задачи не трогаются.
- [ ] Текст записи называет: этап осиротел при смене супервизора, номер
      прежнего процесса, отметку начала, чем кончился (исчез либо снят
      по сроку), что отчёт потерян и сделанное надо искать в ветке.

**Проверка:**
`npx vitest run --root supervisor lib/scan.test.mjs lib/execute.test.mjs` —
сканер при непустых `orphans` даёт `note-orphan` и ставит его раньше
`continue-stage`; исполнение зовёт `amendTask`, не зовёт `saveTask`,
и при неудачной записи исход из очереди не убирает.

## 6. Сшивание в супервизоре: опрос, обход, остановка

- [ ] `supervisor/bin/supervise.mjs`: собрать `probe` из `runCommand`
      и передать в `createSupervisor` вместе с `machine: hostname()`
      и `supervisorPid: process.pid`.
- [ ] Звать `supervisor.sweep()` в начале `turn()`, до чтения
      `supervisor.running()` в `state`.
- [ ] Положить `orphans: supervisor.orphanOutcomes` в `state` и метод
      «забыть исход» в `io`.
- [ ] Убедиться, что `stopAll()` сирот не трогает: снимает только
      собственных детей.

**Проверка:** `node --check supervisor/bin/supervise.mjs`;
`npx eslint supervisor/bin/supervise.mjs supervisor/lib/supervisor.mjs supervisor/lib/scan.mjs supervisor/lib/execute.mjs supervisor/lib/run-stage.mjs`;
`node supervisor/bin/cycle.mjs` — печатает решение и завершается, ничего
не делая: мира он не трогает и работы не порождает.

## 7. Описать дескриптор в документах

- [ ] `supervisor/README.md`, таблица файлов `.pipeline` (строка ~555):
      уточнить строку `stages.json` — идентификаторы сессий и дескрипторы
      идущих этапов.
- [ ] Там же, раздел «Прерванный этап возобновляется» (строка ~143):
      дописать про смену супервизора — чужой живой этап признаётся идущим,
      исход исчезнувшего попадает в журнал задачи, снятие требует опознания
      процесса.

**Проверка:** `npx prettier --check supervisor/README.md`; глазами —
таблица и раздел не противоречат поведению шагов 1–6.

## 8. Дождаться зелёного CI и снять черновик

- [ ] `gh pr checks <номер> --watch` — дождаться всех проверок.
- [ ] Красное — прочитать `gh run view --job <id> --log-failed`, починить
      отдельным атомарным коммитом, отправить, дождаться снова.
- [ ] Снять с pull request пометку черновика.

**Проверка:** все проверки CI зелёные. Задача не сделана, пока GitHub
не сказал «зелено».

## Прогон арены не требуется

Правил игры, цен, дохода, силы юнита и темпа изменение не задевает:
правок за пределами `supervisor/` и `supervisor/README.md` в нём нет ни
одной. Заявки на задачу-прогон в отчёте нет намеренно — заказывать нечего.
