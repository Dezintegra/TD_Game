# Проектное решение

## Устройство в двух словах

К записи `stages.json` добавляется поле `live` — дескриптор идущего
процесса. Супервизор, начинающий работу, читает эти дескрипторы и заводит
из них «сирот»: этапы, порождённые не им. Живой сирота попадает в ответ
`running()`, и вся счётная часть перестаёт видеть в задаче мёртвый этап.
Исчезнув, сирота встаёт в очередь исходов, а оттуда — записью в журнал
задачи.

```
supervisor.mjs                        scan.mjs            execute.mjs
  known[at].live ──┐
                   ├─► running() ────► isRunning ──► нет continue-stage
  orphans (Map) ───┘                                 нет push-tail
       │                                             место занято
       └─ sweep() ─► orphanOutcomes ─► note-orphan ─► io.amendTask
```

## Решение 1: дескриптор живёт в `stages.json`, а не в своём файле

**Выбрано:** расширить существующую запись до
`{ sessionId, startedAt, live: { pid, image, machine, supervisorPid, startedAt, timeoutMs } }`.

**Почему.** Два файла об одном и том же расходятся молча — это уже
проверено на проекте очередью баланса, которую пришлось выносить обратно
в бэклог. Здесь расхождение было бы особенно злым: «сессия помнится,
а живость нет» и есть ровно та беда, которую мы чиним.

Плюс к тому запись и стирание дескриптора происходят в тех же двух точках,
где уже пишется `known` (`supervisor.mjs:196-198` при рождении и `finish`
при завершении), и обе уже зовут `saveStages`. Новых мест записи не
появляется вовсе.

**Отвергнуто:** отдельный `.pipeline/running.json`. Дал бы независимую
запись при рождении процесса — то есть второе место, где можно забыть
стереть.

**Две отметки времени, и путать их нельзя.** `startedAt` верхнего уровня
отвечает на вопрос «когда на этот этап зашли ПЕРВЫЙ раз» и намеренно
не двигается продолжениями (`supervisor.mjs:66-75`): ею отличают свой
коммит от чужого. `live.startedAt` — начало конкретного процесса, и от неё
считается срок. Второй перезаписывает первую при каждом порождении, первая
переживает их все.

## Решение 2: опознание процесса записывается, а не выводится

Номера процессов переиспользуются системой. Довериться одному лишь
`process.kill(pid, 0)` значит согласиться на два исхода, и второй
недопустим:

- сирота «жив» вечно, потому что его номер занял посторонний процесс, —
  задача держит место, пока не истечёт срок;
- по истечении срока `taskkill /PID N /T /F` (`run-stage.mjs:313`) уносит
  **постороннее дерево процессов** на рабочей станции. Снятие поддерева —
  не мягкий сигнал: `/T /F` убивает браузер, редактор и всё, что этот
  посторонний процесс успел породить.

**Выбрано:** при рождении этапа спросить у системы имя образа процесса
и записать его в дескриптор. Проверка живости — конъюнкция: номер
существует И имя образа то же.

```js
// Windows: первое поле CSV — имя образа.
tasklist /FI "PID eq 29704" /NH /FO CSV   →   "claude.exe","29704",...
// Прочие системы:
ps -p 29704 -o comm=                      →   claude
```

**Почему записывать, а не выводить из настройки.** `config.claudeCommand`
равно `claude` (`defaults.mjs:36`), а на Windows это почти наверняка
обёртка `.cmd`, и живой образ окажется `node.exe` либо `cmd.exe`. Сверять
живой процесс с именем из настройки значило бы получать несовпадение
всегда — то есть тихо выключить всю проверку. Записанное при рождении
имя сверяется само с собой и от вида обёртки не зависит.

**Отвергнуто:** сверять время старта процесса вместо имени образа. Точнее,
но переносимого способа спросить его нет: в Node такого API не существует,
`wmic` объявлен устаревшим и с Windows 11 выпиливается, а `Get-Process`
тянет за собой PowerShell из процесса Node.

**Неопознанный сирота не снимается никогда.** Если спросить систему
не удалось — команды нет, вывод не разобрался, — дескриптор считается
протухшим, и этап обрабатывается как исчезнувший. Цена ошибки здесь
несимметрична: лишнее ожидание стоит одного оборота цикла, ошибочное
снятие — чужого дерева процессов.

## Решение 3: чужой живой процесс дожидаются, а не снимают

**Выбрано:** преемник признаёт живого сироту идущим этапом и ждёт его
конца, снимая только по истечении его же срока.

**Почему.** Отчёт сироты потерян в любом случае: он приходит стандартным
выводом, а тот был трубой в умерший процесс. Но отчёт — не вся работа
этапа. Этап коммитит и отправляет по ходу дела (правило 4 в `CLAUDE.md`),
и коммит в отправленной ветке переживает потерю отчёта: следующий заход
возобновляет ту же сессию и видит сделанное. Снять сироту посреди
`git push` значит потерять это гарантированно; дать ему доработать —
не потерять ничего сверх уже потерянного отчёта.

**Отвергнуто:** снимать сироту сразу при взятии замка. Проще в коде
и хуже по существу — превращает вероятную потерю в достоверную.

**Отвергнуто:** пытаться перечитать вывод чужого процесса. Перехватить
стандартный вывод живого чужого процесса нельзя ни на Windows, ни в POSIX
без отладчика. Сохранение отчёта на диске самим этапом — предмет задачи
0080 (`keep-the-report-on-disk`), и она о завершившемся этапе; здесь она
ничего бы не спасла, потому что писать было бы некому.

## Решение 4: правка сканера не нужна вовсе

`scan.mjs` получает живость единственным доводом `running` и трактует его
в четырёх местах: `isRunning` при негодной карточке (`:150`), при хвосте
ветки (`:188`), при выдаче сессии (`:322`) и подсчёт свободных мест
(`:371`). Все четыре трактовки для сироты верны дословно.

Поэтому весь фикс на стороне сканера — это включение сирот в ответ
`supervisor.running()`. Ни строки в `scan.mjs` не правится, и это
не экономия, а проверка замысла: если бы сирота требовал особого случая
в счётной части, значит он не то же самое, что идущий этап, — а он то же
самое.

Сканер остаётся чистым счётом: диск и система процессов остаются
в `supervisor.mjs`, где `spawn`, `killTree` и часы уже приходят доводами.
Опрос системы приходит туда же доводом `probe`, и тесты обходятся без
единого живого процесса — как и весь остальной супервизор.

## Решение 5: исход сироты пишется `amendTask`, а не `saveTask`

**Выбрано:** очередь исходов `orphanOutcomes` в супервизоре (полное
подобие очереди `reports`), действие сканера `note-orphan`, исполнение
через `io.amendTask(taskId, text, message, source)` —
дописать в журнал, не трогая карточки (`backlog-trello.mjs:231`).

**Почему не `saveTask`.** Задача 0070 описывает живой дефект: два действия
по одной задаче в один оборот делаются по одному и тому же снимку доски,
и второе затирает первое. А `note-orphan` и `continue-stage` попадают
в один оборот по построению — сирота исчез, значит этапу тут же нужна
сессия. `amendTask` полей задачи не трогает вовсе, и затирать ему нечего:
он добавляет комментарий и на этом всё.

**Почему через сканер и `execute`, а не прямо из супервизора.** Бэклог
правит только `execute` — это единственное, что удерживает доску от гонки
между машинами и от полузаписей. Дать супервизору второй путь к доске
значило бы завести исключение в правиле, на котором держится всё
остальное.

**Порядок действий важен.** В `ACTIONS` (`scan.mjs:25-37`) `note-orphan`
ставится **перед** `continue-stage`: сперва в журнал ложится причина,
почему прошлый заход ничего не дал, и только потом порождается новый.
Тогда запись успевает попасть в промпт продолжателя — журнал задачи едет
в назначение (`execute.mjs:452`). Оговорка: пока не починена задача 0074,
журнал в промпте режется с хвоста, и именно свежая запись может
не доехать; на устройство это не влияет — запись всё равно остаётся
на карточке и достаётся разбору.

**Дескриптор стирается после удавшейся записи, а не до неё.** Обрыв
оставляет дескриптор на диске, и следующий оборот пробует снова.
Повторная запись стоит одного лишнего комментария; потерянная —
необъяснимого провала в журнале.

## Решение 6: продолжение сироты считается как прежде

**Выбрано:** `attempts.continuations` наращивается обычным порядком,
когда после исчезновения сироты задаче выдаётся сессия.

**Почему.** Сессия действительно была: она стоила денег, работала минуты
и могла оставить коммит. Не считать её значило бы завести случай, в котором
крутящийся в падениях супервизор порождает сессии без предела. Правится
не счёт, а его молчаливость: до сих пор задача теряла продолжение
и не могла объяснить, на что, — теперь причина стоит в журнале.

**Отвергнуто:** отдельный счётчик `attempts.orphans` со своим пределом,
по образцу `attempts.spawnFailures` из `count-only-real-launches`. Отвергнут
не из лени: у `spawnFailures` есть основание, которого здесь нет, — там
сессии **не было вовсе**, и остановка с причиной «продолжения исчерпаны»
уводила разбор искать несуществующий лог. Здесь сессия была и лог у неё
есть. Третий счётчик добавил бы третий ответ на вопрос «какой предел
остановил задачу» ради случая, который случается при падении супервизора
и никогда — при исправной работе. Справедливость счётчиков вообще —
предмет задачи 0081, и решать её мимоходом здесь неверно.

## Решение 7: своя остановка сирот не трогает

Супервизор при остановке даёт своим детям доработать и снимает их
поддеревьями (`supervise.mjs:700-702`). Сирот он оставляет жить.

**Почему.** Своего ребёнка он снимает **и записывает** — `finish` получает
`killedBy: 'shutdown'`, и исход уезжает в журнал этапа. Чужого он снял бы,
не сумев записать: очередь исходов в этот момент уже некому исполнять,
доска закрывается вместе с оборотом. Получилась бы ровно та потеря,
из-за которой всё изменение и затеяно, только сделанная нашими руками.

Оставленный сирота ничего не теряет: дескриптор лежит на диске, и
следующий супервизор судит его тем же правилом. Плата названа честно —
рабочее дерево остаётся занятым до конца сироты, и уборка по нему в эти
минуты упадёт на «каталог занят».

## Поведение при рассинхроне и переподключении

Требование `openspec/config.yaml` относится к правкам геймплея. Изменение
геймплея не задевает: правок в `packages/sim`, `packages/protocol`,
`apps/client` и `apps/server` нет ни одной, `PROTOCOL_VERSION` не растёт,
эталоны детерминизма не пересматриваются. Ни `Math.random`, ни `Date.now`,
ни чисел с плавающей точкой в состоянии мира изменение не добавляет —
оно их и не касается, супервизор в сборку игры не входит.

Свой рассинхрон у изменения всё-таки есть, и он назван правилами выше:
расхождение диска и памяти. Разбирается оно так.

| Что разошлось                                | Как узнаётся            | Что делается                                  |
| -------------------------------------------- | ----------------------- | --------------------------------------------- |
| дескриптор есть, процесса нет                 | опрос системы           | исход в журнал, дескриптор стёрт               |
| дескриптор есть, номер занят посторонним      | несовпадение опознания  | то же, и **без снятия**                        |
| дескриптор есть, процесс жив                  | опознание совпало       | этап числится идущим, ждём                     |
| дескриптор чужой станции                      | несовпадение имени      | не судится, стирается, названо в журнале цикла |
| дескриптора нет, а этап шёл                   | —                       | прежнее поведение: продолжение обычным порядком |

Последняя строка — то, что происходит при первом запуске на новом коде
поверх старого `stages.json`. Раскладка читается терпимо (`remembered`
в `supervisor.mjs:404` уже делает это для прежнего вида записи), и
отсутствие `live` означает «этап не идёт» — честный ответ, а не поломка.

## Что и чем проверяется

Тесты идут туда же, где живут их предметы, и живых процессов не требуют:
`spawn`, `killTree`, часы и новый `probe` приходят доводами.

| Предмет                                    | Файл                    |
| ------------------------------------------ | ----------------------- |
| запись и стирание `live`, терпимость чтения | `supervisor.test.mjs`   |
| сирота при запуске попадает в `running()`   | `supervisor.test.mjs`   |
| разбор вывода `tasklist` и `ps`             | `run-stage.test.mjs`    |
| снятие по сроку и отказ снимать неопознанного | `supervisor.test.mjs` |
| действие `note-orphan` и его порядок         | `scan.test.mjs`         |
| запись в журнал через `amendTask`            | `execute.test.mjs`      |

Тесты супервизора просят свой корень: `pnpm test:pipeline` — это
`vitest run --root supervisor` (`package.json:19`). Обычный прогон их
не видит, и запуск отдельного файла тоже требует ключа:
`npx vitest run --root supervisor lib/supervisor.test.mjs`.
