## Goals / Non-Goals

Единый расчёт подтверждённых снимков, идемпотентность повторов, долговечный бюджет и явная неизвестность. Границы — в proposal. ## Decisions

### 1. Одна область накопления — thread; один порядок доставки — запуск

В `token-budget.mjs` выделить чистый reducer нормализованных наблюдений; `provider.mjs` использует его для расчёта ответа, `supervisor.mjs` — для долговечной записи. Наблюдение содержит taskId, sessionId, persisted launchId и порядковый номер completed в stdout. launchId назначается до spawn и сохраняется в записи реестра; при повторном чтении того же stdout сохраняются launchId и номера. Новый resume получает новый launchId при прежнем sessionId. Граница запуска не сбрасывает накопительную базу.

Для каждого launch сохранить обработанные наблюдения (номер и нормализованный снимок либо причину unknown), чтобы finish мог воспроизводить весь поток, не принимая старый снимок за новое уменьшение. Одинаковый ключ и payload — no-op; несовпадающий payload того же ключа — unknown, а не второе списание. Суммы значений или хэш текста не заменяют идентичность события: два разных completed могут иметь одинаковые числа.

### 2. Снимки и расход запуска различаются

Для валидной последовательности компонентов input/output текущий снимок заменяет предыдущий. Вклад сессии — максимальный подтверждённый `input_tokens + output_tokens`, сумма задачи — сумма вкладов разных сессий. Cached input уже входит в input; reasoning output не прибавляется повторно к output. Проверять safe integers >= 0, cached <= input и безопасную сумму. Дополнительные поля не обязательны для расчёта input+output.

`answer.usageTotals` явно означает последний валидный накопительный снимок thread; `answer.usage` — разность с долговечным снимком ДО запуска, только когда база и все наблюдения сопоставимы. Новый thread имеет базу ноль. Отсутствие baseline для ранее существовавшего thread означает неизвестный расход запуска. Baseline из `known[stage].usage` больше не используется как источник истины. Обработать все completed, не только последний; валидные снимки до ошибки процесса или невалидного отчёта учитываются.

Уменьшился любой компонент input/output в новом наблюдении — сохранить прежний известный вклад и поставить неполноту с причиной. Не складывать старое и новое значение: новый снимок может уже содержать часть старого расхода. Не применять покомпонентный max: он способен создать сумму, которой не было ни в одном снимке. Последующие большие снимки могут поднять известную нижнюю границу, но не снимают неполноту без доказательства непрерывности. Отдельное падение cached при неизменных input/output диагностируется, но не превращает известную сумму input+output в отрицательную дельту.

### 3. Полнота знания — часть долговечного бюджета

Реестр версии 2: `version`, `tasks`; у задачи sessions и launches. Session содержит knownTokens, последний сопоставимый снимок и причины неполноты. Launch содержит sessionId (временно null до thread.started), baseline, обработанные наблюдения и состояние завершения. Неполнота задачи выводится из записей, а не хранится сбрасываемым флагом в этапе. Идущий незавершённый запуск не выдаётся за окончательный нулевой расход.

Успешно родившийся процесс без usage, невалидное значение, неизвестный thread или уменьшение дают unknown; известные суммы сохраняются. Несостоявшийся spawn не создаёт выдуманный расход. Оборванный следующий ход после валидного completed оставляет известную часть и неизвестный хвост. Успешный ответ без usage при включённом бюджете по-прежнему не принимается; извлечение и доставка отчёта — отдельная работа 0235.

`taskTokens` сохраняет числовую нижнюю границу для совместимости; отдельный status сообщает completeness и причины. На границе `scan.mjs` сначала применять существующее превышение лимита к известной сумме (переход decompose с прежними исключениями), затем не разрешать обычный запуск при unknown и включённом лимите, возвращая диагностируемое решение без расходования попытки. Это следствие действующего запрета считать неизвестность нулём. При отключённом лимите неизвестность сохраняется и показывается, но не блокирует по токеновому правилу. Автоматически очищать unknown при смене этапа/провайдера/забывании session запрещено.

### 4. Долговечность и повтор finish

watch и finish вызывают одну операцию с теми же ключами наблюдений; finish не передаёт отдельный итог как ещё один расход. Запись суммы, идентификаторов и unknown атомарна через существующие temp+rename. Публиковать новое in-memory состояние только после успешной записи: иначе повтор после I/O ошибки ошибочно станет no-op. Неудачная запись не допускает следующий обычный запуск с устаревшим бюджетом. Отдельная переработка сохранения отчётов сюда не входит.

После рестарта загружать ledger вместе с launchId, не создавать новую идентичность для старого результата. Уже сохранённые события не списываются повторно. Если процесс продолжал работать без наблюдателя и stdout недоступен, сохранять unknown вместо выдуманного восстановления; это ограничение существующего `outlive-the-supervisor`. Удаление `known`/live не удаляет launches/sessions из ledger. Последующий новый процесс получает новый launchId.

### 5. Отвергнутые варианты

- Сумма всех turn.completed: учитывает накопленные токены многократно.
- Каждый resume — новый независимый счётчик: опровергается восстановлением token usage, даёт двойное списание истории.
- Максимум без полноты: устойчив к повтору, но маскирует уменьшение и неизвестный хвост.
- Разность с baseline этапа: baseline теряется при забывании и не решает двойную обработку.
- Считать любое уменьшение сбросом и добавить новый снимок: недостаточно данных, чтобы отличить сброс от частичного восстановления.
- Переход на app-server ради дополнительных usage-событий: отдельная замена транспорта, несоразмерная задаче.

## Migration Plan

Старый формат `{taskId: {sessionId: number}}` читать без потери каждого значения, переносить в knownTokens. Нельзя восстановить компоненты, обработанные запуски и полноту из числа: сохранять `legacy-unknown`, не объявлять старую запись точным расходом и не складывать с ней следующий накопительный снимок. Новое значение может только поднять известную границу соответствующей session. Пустой старый реестр становится пустым v2 без unknown. Повторное чтение/сохранение v2 ничего не начисляет. Проверять обе схемы, повреждённый JSON и неизвестную версию не заменять пустым реестром.

При выкладке переносить ledger вместе с супервизором. Legacy-unknown при включённом лимите требует явного разбора исторической полноты владельцем; автоматического обнуления или эвристического backfill нет. Откат старого кода поверх v2 несовместим: сохранить актуальный файл и восстановить совместимый снимок только с осознанием неполной истории; удаление ledger не является откатом. Реализация обязана сообщить эту миграционную особенность в PR.

## Risks / Trade-offs

При legacy-unknown часть действующих задач будет удержана до разбора истории; это цена отказа от ложной точности. Реестр grows по числу completed, а не по объёму stdout; полные выводы туда не кладутся. CLI может вернуть Usage::default при отсутствии уведомления: JSONL ноль неотличим от реального нуля, этот предел наблюдаемости фиксируется, не лечится гаданием. При обновлении версии CLI перепроверять producer total и replay; синтетические тесты не доказывают внешний контракт.
