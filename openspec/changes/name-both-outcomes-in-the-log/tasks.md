# Задачи

Каждый пункт — отдельный коммит, отправляемый сразу. Каждый собирается
и проверяется сам по себе: следующего шага, который что-нибудь починит,
нет ни у одного.

Правка целиком лежит в `supervisor/`, поэтому проверяется она
`pnpm test:pipeline` (`vitest run --root supervisor`), а не узким
`npx vitest run <файл>`: обычный прогон этих тестов не видит вовсе.

Прогон арены изменению не нужен: правил игры, цен, дохода, силы юнита
и темпа оно не задевает — правится запись журнала на рабочей станции.

## 1. Стенд начинает видеть записанный лог

**Сделано.**

`harness()` в `supervisor/lib/supervisor.test.mjs` не передаёт
`writeStageLog` вовсе, а умолчание в `createSupervisor` — пустая функция.
Содержимое лога сегодня не видно ни одной проверке.

Передать `writeStageLog: (taskId, stage, text) => wrote.push({ taskId,
stage, text })` тем же порядком, каким стенд уже собирает журнал
(`log: (line) => logged.push(line)`), вернуть `wrote` из `harness()`
и поставить сторожа на то, что от правки шапки не зависит:

- лог пишется на **каждый** кончившийся этап — и на отчитавшийся,
  и на не оставивший отчёта;
- в нём есть код возврата, перечень отказанных действий и `stdout`
  целиком.

Ставится первым, потому что ничего не меняет в поведении и должен
зеленеть на нынешнем коде сразу.

**Проверка:** `pnpm test:pipeline` зелёный. Проба на порчу: временно
заменить в `supervisor/lib/supervisor.mjs` вызов `writeStageLog(…)`
пустой строкой — новые сторожа обязаны покраснеть; вернуть, прогнать
снова.

**После этого коммита** — открыть черновой pull request (`gh pr create
--draft --base main`), иначе проверки CI на последующие пуши в ветку
не запустятся вовсе.

## 2. Разбор отчёта переезжает выше записи лога

**Сделано.**

В `finish` (`supervisor/lib/supervisor.mjs`) `parseReport(answer.result)`
встаёт сразу после `readAnswer(run)`, а на прежнем месте (ныне строка 689)
переиспользуется готовый результат. Второго вызова не заводить: два
источника истины об исходе расходятся молча.

Состав шапки в этом коммите **не меняется** — это перестановка, а не
правка вывода. Смысл отдельного шага в том, что здесь лежит весь риск
изменения: в `finish` три досрочных возврата, и запись лога обязана
остаться **раньше** каждого из них.

**Проверка:** `pnpm test:pipeline` зелёный — в разделах «этап кончился»,
«отказанные действия едут вместе с отчётом» и «этап не дошёл до отчёта»
уже стоят сторожа на то, что отчёт уезжает в очередь переноса, отчёт
о чужом этапе не принимается, а место освобождается при любом исходе.
Глазами: поиск по файлу даёт ровно одно вхождение `parseReport(`.

## 3. Шапка называет ответ сессии и исход отчёта разными словами

**Сделано.**

`renderLog` принимает разобранный отчёт и печатает вместо строки `исход:`
две:

```
ответ сессии:  done
исход отчёта:  failed
```

Строку `исход:` не оставлять ни в каком виде: знакомое слово остановит
читателя раньше, чем он дойдёт до нужного поля.

Заполнение второго поля, когда отчёта нет, — три различимых случая
(таблица в `design.md`, «Решение 3»):

- отчёт разобран — его исход;
- ответ есть, отчёта в нём нет — `отчёта нет — <причина разбора>`;
- ответа нет вовсе (`answer.result == null`: снятие по сроку, не
  состоявшийся запуск) — `отчёта нет — сессия ответа не оставила`.

Отчёт о чужом этапе получает приписку с обоими этапами и словами
«не применён».

Здесь же — перевыравнивание **всей** шапки: колонку значений задаёт самое
длинное имя поля, и новые имена длиннее нынешнего `стоимость:`. Править
по одной строке нельзя, сводка разъедется.

**Проверка:** `pnpm test:pipeline` зелёный, и в нём новые сторожа:
конверт с нулевым кодом и отчётом `failed` даёт в шапке `ответ сессии:
done` и `исход отчёта: failed`; ответ без отчёта даёт «отчёта нет»
с причиной; снятие по сроку даёт `timeout` и «сессия ответа не оставила».
Проба на порчу обязательна: вернуть в `renderLog` единственную строку
`исход: ${answer.outcome}` — сторожа обязаны покраснеть. Не покраснели —
они проверяют не то.

## 4. Строка итога на консоли называет оба значения

**Сделано.**

Строка `say.line` в `finish` (ныне 637–645) печатает и ответ сессии,
и исход отчёта, а метку выбирает по **исходу отчёта**: `TAG.stage`
причитается только отчитавшемуся `done`. Всё прочее — `TAG.warn`:
`failed`, `question`, `rejected`, отсутствие отчёта, снятие по сроку.

Отдельным коммитом от задачи 3 потому, что это другой читатель и другой
сценарий: тот смотрит лог после падения, этот — консоль по ходу работы.
Откат ровно этого коммита оставляет верную шапку.

**Тем же коммитом правится `supervisor/README.md`** — руководство самого
инструмента, где эта строка показана образцом. Два места:

- **строка 495** — образец вывода в разделе про консоль:
  `22:52:46 ЭТАП   0042 implement завершён: done, 4 мин 27 с, ходов 5,
стоимость $0.20, отказов 1`. Привести к тому, что программа печатает
  после этой задачи, — с обоими значениями и тем же порядком слов;
- **строка 72** — «исход берётся из кода возврата, а не угадывается
  по отметке последней активности». Назвать величину своим именем:
  из кода возврата берётся **ответ сессии**. Голое «исход» здесь значит
  ровно то, что изменение и объявляет двусмысленным.

Не сделать этого нельзя: образец не проверяется ничем и потому
не покраснеет, а руководство переносимого инструмента останется учить
формату, которого программа не печатает, — и учить именно словом
`завершён: done`, ради которого затеяно изменение. Правка едет тем же
коммитом, а не отдельным, потому что порознь они дают состояние,
в котором руководство разошлось с кодом; вместе — откат одного коммита
возвращает согласованную пару.

**Проверка:** `pnpm test:pipeline` зелёный, и в нём сторож на выбор метки:
этап с отчётом `failed` и нулевым кодом возврата даёт предупреждающую
метку, а не спокойную. Метка проверяется по своему значению из `TAG`,
а не по знакам в строке. По руководству —
`npx prettier --check supervisor/README.md` зелёный, и глазами: поиск
по `завершён:` во всём дереве даёт два попадания, код и образец, и они
говорят одно и то же (третье, `apps/server/src/matches.ts:185`, к делу
не относится — оно об исходе матча).

## 5. Правила разбора называют оба поля

**Сделано.**

В `supervisor/skills/postmortem.md` состав сводки (ныне строка 65: «код
возврата, снятие по сроку, исход, число ходов, стоимость, число отказанных
действий») называет **ответ сессии** и **исход отчёта** порознь, и одной
фразой объясняет разницу: ответ сессии говорит о процессе, исход отчёта —
об этапе; `ответ сессии: done` не значит, что этап удался.

Идёт последним: правила описывают уже сложившийся вид лога, а не
предвосхищают его. Разбор — единственный читатель этих логов, и скилл,
разошедшийся с делом, вводит в заблуждение вернее отсутствующего.

**Проверка:** `npx prettier --check supervisor/skills/postmortem.md`
зелёный; `pnpm test:pipeline` зелёный (в `transitions.test.mjs` есть
сторожа на содержимое скиллов). Глазами: перечень полей сводки совпадает
с тем, что печатает `renderLog` после задачи 3, поимённо и по порядку.
