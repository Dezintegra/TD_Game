## Context

Постановка 0049 и журнал анализа требуют профиль с единственным числовым отличием и последующий отдельный прогон. Проверено на `origin/main` (`c7076cd`, merge: Already up to date).

`BASELINE_PROFILE` глубоко заморожен; `DEFAULT_PROFILE_ID` указывает на него. `pushStance` в `opponent.ts:1010` сравнивает выбранную долю рубежа с `advanceFraction` строгим `>`, при отсутствии рубежа использует 0. То же сравнение в строке 424 определяет `escorting`, а строка 462 переключает порядок трат. `frontiersOf` в `posture.ts:833–837` возвращает доли из `profile.posture.frontierFractions`, у baseline это `[0, 0.15, 0.35, 0.55, 0.75, 0.95]` (`profile.ts:792`). Наблюдаемое продвижение 1,10 из постановки не следует путать с этим конечным набором долей выбранного рубежа.

Основные требования «Манера игры задаётся именованным профилем», «Профиль по умолчанию воспроизводит поведение до переезда» остаются в силе. Новое самостоятельное требование добавляется в `ai-opponent`. Игровой замысел сохраняет выбор между остановкой для боя и продвижением с огнём на ходу (`docs/game-design.md`, 5.3–5.4).

## Goals / Non-Goals

Цель: воспроизводимый именованный контроль общего порога наступления, доступный обеим сторонам арены, с точно одним числовым отличием от baseline.

Границы перечислены в proposal: алгоритмы, правила игры, лобби, действующие умолчания и исторические записи не меняются; прогон доставляется отдельной карточкой.

## Decisions

### Порог 2 и имя advance-control-2026-08

Добавить `ADVANCE_CONTROL_PROFILE: AiProfile` рядом с baseline: копирование baseline, собственный id и копирование `movement` с переопределением `advanceFraction: 2`, затем существующий `deepFreeze`. Число 2 конечно, больше 1,10 и всех текущих долей рубежа; не требует особых значений при записи и сравнении. Значение 1 отвергнуто из-за наблюдения в постановке; 1,10 не оставляет запаса; Infinity не нужен. Имя описывает изменяемый порог и не обещает изолировать режим атаки.

Остальные поля, включая все фазы, состав войска, `lookaheadCells`, охрану, ядерные настройки и рубежи, остаются равны baseline. Общие вложенные ссылки допустимы, поскольку они уже неизменяемы. Не копировать все числа вручную: это создаст независимую конфигурацию и риск незаметного второго отличия.

### Существующая регистрация

Добавить одну запись в `PROFILES`. Экспорт из `index.ts` уже идёт через `export *`, арена использует `profileByName` в `match.ts:230`. Не вводить новую ветку разрешения профиля, флаг CLI или изменение workflow. Имя доступно для каждой стороны, умолчание остаётся baseline.

### Проверять конфигурацию и настоящее решение ИИ

В новом быстром `advance-control.test.ts` проверить глубокое равенство после нормализации только id и `movement.advanceFraction`, отдельное значение 2, отличие от baseline, регистрацию и прежний default. Сравнивать объекты непосредственно, без JSON-сериализации, которая теряет Infinity в фазах. Проверить заморозку нового объекта и `movement`, попытку записи и сохранность baseline.

Проверить границу: все доли `frontierFractions` конечны и меньше 2; это связывает гарантию режима с реальным источником рубежей. Для поведения использовать короткие вызовы публичного `createOpponent().decide`, без полного матча. Через тестовый mock выбора вердикта дать реальные по форме рубежи из списка baseline и отдельно отсутствие вердикта; не подменять `pushStance` и не переписывать его формулу в тесте. Прогнать для обеих сторон с исходным `Breakthrough`: должен быть `SetStance(Engage)`. С исходным `Engage` повторной команды нет. На одном наступательном рубеже 0,75 и недостатке сопровождения сравнить с baseline: baseline из Engage отдаёт Breakthrough, контроль — нет; наблюдатель подтверждает у baseline `escorting: true`, у контроля `false`. Это положительный контроль, исключающий успех теста из-за невызванного выбора режима. Тестовые подмены сбрасываются между случаями.

Такая проверка имеет право изолировать вход выбора рубежа: предмет — действие существующего потребителя порога, не качество оценки позиции. Полный матч здесь отвергнут как дорогая и менее адресная проверка. Если конкретный тест потребует длительного проигрывания партии, он должен быть матчевым и исполняться только CI; вместо этого план использует отдельные решения.

### Границы толкования будущего прогона

Заявка: зеркало `advance-control-2026-08`, 60 матчей, seed 1, предел 36000 тиков = 1200 секунд при текущих 30 тиках/с. Запуск после вливания профиля, на текущей main с сохранением фактического SHA и параметров. Сопоставить медиану с 762 секундами и долю остановок по времени с 18,3 %, указав числитель/знаменатель, разницу секунд и процентных пунктов.

Это описательное сравнение с прогоном 33430184681 из задачи 0005. Профиль устраняет откат кода как часть самого прибора, но не отменяет уже произошедшие между историческим и будущим прогонами изменения правил. Ожидание из исходной задачи: прежние 762 секунды не больше медианы контроля и прежние 18,3 % не больше доли контроля. Невыполнение отмечается как неподтверждённое ожидание, а не как основание автоматически менять баланс. Даже выполнение не доказывает эффект одного режима: одновременно отключается приоритет сопровождения, а ревизии могут различаться. Отдельный факторный эксперимент со специальным переключателем потребовал бы другой постановки и не входит в эту карточку.

### Детерминизм, рассинхрон и реконнект

Новые решения используют прежние команды и seeded PRNG; `Math.random`, системное время и новые поля состояния мира не появляются. Число 2 живёт в настройке ИИ вне `packages/sim`, в состоянии мира остаётся целочисленная модель. Правила sim и baseline не меняются, поэтому эталоны детерминизма не обновляются; их регрессия означает дефект, а не разрешение переснять числа. Если при реализации выяснится необходимость менять sim, это выход за текущий план; изменение игровых правил потребует обновления эталонов тем же коммитом.

Арена безголовая, сетевой реконнект в ней отсутствует. В сетевом использовании уже существующее описание участника сохраняет id/seed; восстановление берёт тот же профиль, а рассинхрон обрабатывается прежним механизмом подтверждённых команд и восстановления мира. Подмены на baseline нет: неизвестный id по-прежнему ошибка. Бинарная раскладка не меняется, рост `PROTOCOL_VERSION` не требуется.

## Risks / Trade-offs

- Связь режима с сопровождением → явная оговорка у определения профиля и в заявке прогона, без утверждения о чистом эффекте «Прорыва».
- Будущий рост набора рубежей → быстрый тест границы делает потерю гарантии заметной.
- Изменение baseline другой задачей → профиль наследует текущую основу, а тест допускает только два пути различий; для воспроизведения нужны SHA, id и seed.
- Регистрация может расширить тесты, перебирающие весь `PROFILES` → при реализации проверить эти места; полный матчевый набор остаётся в CI, не менять чужие пороги ради добавления профиля.

## Migration Plan

Один атомарный коммит реализации с определением, регистрацией, проверками и отметкой tasks; после отправки открывается черновой PR. Миграции данных нет. Существующие профили и записи сохраняются. При отмене прибора новые прогоны его не выбирают; исторические результаты воспроизводятся на сохранённой ревизии.
