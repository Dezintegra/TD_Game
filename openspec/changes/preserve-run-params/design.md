## Context

На освежённой базе `b08fd3b648db710725e8751d8bdaf4f41fc0597f` путь состоит из `taskFromRequest` → `createTrelloBacklog` → `metaOf`/`joinDescription` → следующий `readBoard`/`parseCard` → `stage-prompt.mjs:taskForPrompt`. Первое звено сохраняет params, последние передают task.run целиком, а обе стороны card.mjs их теряют. Проверка только объекта сразу после create/save не ловит дефект: хранилище обновляет `byId` исходным task.

Исходный отчёт проверен чтением секции «итоговый текст» файла основного дерева `.pipeline/logs/0095-podobrat-paru-profiley-na-kotoroy-dolya--design-2026-09-09T05-04-38.763Z-3f106aea-07c1-4e67-a4f8-17c496a49bd7.log`, строки 19–82. Это отчёт design с outcome blocked, ключ заявки `screen-reference-pairs`. Параметры совпадают с постановкой 0310; `tuning_args` — пустая строка, не массив и не отсутствие. Снимок доски из назначения подтверждает прежний ID 0308 и зависимость 0095 от него. Живую доску этап design не читает и не меняет.

## Goals / Non-Goals

Цель — непрерывная сохранность JSON-заказа до benchmark и безопасное адресное исправление 0308. Ограничения и Non-goals заданы в proposal. Измерение не является тестом этой инфраструктурной правки; отдельная заявка run не нужна, существующая 0308 остаётся единственным заказом.

## Decisions

### Один источник каждого поля

В машинном блоке сохранять `run: { params: ... }` только при наличии params у run-задачи. При чтении добавлять params по наличию свойства, без `|| {}` и без приведения значений к строкам. Отсутствующее поле оставить отсутствующим, ошибочный тип сохранить для диагностики. Kind и expectation не сериализовать; при чтении игнорировать их возможные старые машинные копии. `joinDescription` уже экранирует конец HTML-комментария и подходит для вложенных строк.

Альтернатива — сохранять весь run и считать его единственным источником — отвергнута: она отменяет человеческое ожидание и метки. Белый список полей params тоже отвергнут: он снова потеряет новые параметры арены и source. Формат — JSON, произвольные JS-объекты с функциями, NaN и циклическими ссылками не являются допустимой заявкой; проверка на входе должна отвергать не сохраняемые без потерь значения, а не тихо исправлять их.

### Допуск проверяет структуру заказа до процесса

Добавить чистый `run-params.mjs` с проверкой сериализуемости объекта для входящих заявок и отдельной проверкой готовности к benchmark. В `requests.mjs` проверять перед созданием заданный params; не ломать прежний приём заявок arena без params, но на допуске такой заказ останавливается. В `createAssignmentPreparer` из `benchmark-source.mjs` выполнять проверку готовности для любого benchmark до подготовки источника, ACL и порождения процесса, в том числе при продолжении.

Готовность: params — объект; arena с отсутствующим, null, массивом или пустым объектом получает ошибку `run.params`. Присутствующее profilePairs проверяется как непустой массив двухэлементных строковых пар с указанием индекса при ошибке. Perf/bench-tick используют существующий `runSourceProblem`, его правила не копируются. Не объявлять ref, seconds или tuning_args обязательными для старых форм арены: действующий пример использует только matches/seed, а иной — profiles/matches/seed/change. Валидация не определяет, достаточны ли профили для обещанного вывода: это 0291.

Альтернатива — карантин всех старых карточек в checkCard — отвергнута: мешает штатному разбору и возврату failed-задачи. Ошибка предподготовки уже возвращается супервизором как неудача запуска без процесса; использовать этот путь с именем задачи и поля. Инструкцию benchmark дополнить коротким запретом самостоятельно достраивать потерянный params, не менять команды и не затрагивать сторож 0309.

### Регрессия проходит настоящую границу хранения

Тест создаёт заявку через taskFromRequest, записывает её через настоящее createTrelloBacklog с подменённым транспортом Trello, затем создаёт новый экземпляр хранилища только из сериализованных карточек. После служебного saveTask повторяет новое чтение и формирует настоящий промпт benchmark. Из JSON-раздела задачи в промпте извлекается run и сравнивается с исходными параметрами через глубокое равенство. Нельзя использовать исходный task или текущий byId как доказательство нового чтения.

Матрица: полный заказ 0308; perf и bench-tick, каждый с branch и worktree; вложенные JSON-значения, пустая строка и строка с концом HTML-комментария; смена kind и expectation с сохранением params. Источник локальных тестов подтверждается управляемой подменой дисковых операций существующего prepareBenchmarkSource; реальных замеров и чужих деревьев тест не требует.

Отрицательные контроли применяются в памяти к тому же тестовому пути: транспорт удаляет params из записанного машинного блока (прежний metaOf), отдельно результат чтения лишается params (прежний parseCard). Та же функция проверки заказа обязана обнаружить оба дефекта. Исправный путь обязан пройти; проверка, которая лишь ожидает undefined, не считается контролем сохранности.

### Восстановление выполняет штатный цикл, не сессия

У существующих requests/amendments нет команды адресного изменения params, а повтор исходного отчёта способен создать вторую 0308 или переиграть blocked 0095. Поэтому доставляется узкая декларативная запись `supervisor/config/run-param-recoveries.json` и модуль `supervisor/lib/run-param-recovery.mjs`, подключённый к владельцу цикла. Это часть данной реализации, не зависимость от 0242: та добавляет зависимости, а не исправляет заказ.

Запись содержит точные targetTaskId 0308, sourceTaskId 0095, sourceStage design, launchId, requestKey, params из следующего раздела и fixedByTaskId 0310. Свидетельство — проверенный выше отчёт; переносить весь stdout или секреты в репозиторий нельзя. Runtime не ищет похожие заявки по тексту и не зависит от наличия локального лога на другой машине: проверенная выдержка доставлена вместе с исправлением.

Перед обработкой нужны mayWrite, владение циклом, полный свежий снимок и отсутствие running/pending report для цели. Действовать до обычных решений этой цели; после записи исключать цель из остальных действий текущего снимка. Сверять единственность ID карточки, type run, kind arena, сохранённое ожидание, связь с 0095 и её dependsOn на ту же 0308. Снимать чужого владельца нельзя. Для первой записи допустим только stopped failed-заказ без params либо с пустым объектом. Частично непустой иной заказ не перетирать.

Запись через store.saveTask сохраняет остальные поля, статус failed и исходный returnTo. Квитанции существующего report-receipts используются с отдельным стабильным ключом восстановления и частями «params записаны» / «новое чтение подтверждено». Не использовать ключ исходного blocked-отчёта 0095. Если returnTo не benchmark или счёт автоматических возвратов исчерпан, сохранить диагностику и не обходить ограничение.

Следующий штатный readBoard даёт независимый снимок. Модуль сравнивает params с декларацией и формирует назначение через используемый supervisor путь сборки промпта без spawn; извлечённый run.params также должен совпасть. Только тогда он записывает подтверждение в журнал 0308: источник отчёта, точные params и результат обеих сверок. Квитанция подтверждения не заменяет повторное сравнение при фактическом допуске benchmark.

Для остановленной 0308 подтверждённый заказ позволяет заполнить recovery.causedBy=pipeline и добавить 0310 в recovery.fixedBy, сохраняя прежние необходимые fixedBy и returns. Существующий scan/returnTask дождётся завершения 0310 и прочих обязательных починок, применит правила возврата, забудет старую сессию и отправит 0308 на benchmark. Этот переход не объявляет зависимость 0095 выполненной. При фактической подготовке назначения повторно сравнить восстановленный заказ с декларацией и зафиксировать подтверждение; несовпадение блокирует процесс.

Повтор при равных params завершает только недоставленную часть. После подтверждения рецепт не переносит снова карточку, которая уже пошла дальше, и не сбрасывает счётчики. Конфликт, отсутствующая карточка, ошибка записи/чтения или связь с другой задачей оставляют диагностируемое ожидание без замера. Журнал и квитанции делают сбой между записью и комментарием повторяемым без дубликата.

Альтернативы: ручной PUT нарушает единственного писателя; общий replay отчёта трогает чужой переход; отдельный CLI-писатель создаёт конкуренцию с владельцем замка. Узкая восстановительная операция в обычном цикле сохраняет существующую модель владения.

### Архитектурные ограничения

Ни packages/sim, ни игровой протокол не меняются. Golden-эталоны, PROTOCOL_VERSION, рассинхрон и реконнект игры не затрагиваются. JSON здесь принадлежит служебной карточке и не попадает в состояние мира; запреты Math.random, Date.now и дробных чисел в ядре остаются в силе. Поведение при сетевом обрыве Trello описано повтором операции и новым снимком, не игровым rollback.

## Risks / Trade-offs

- Старые версии супервизора способны снова стереть params → включать восстановление после штатного подхвата исправленной версии владельцем цикла; не считать один push свидетельством обновления работающего процесса.
- Старые карточки без params не восстанавливаются автоматически по тексту → получают точную диагностику; адресный рецепт существует только для подтверждённой 0308.
- Params растут в описании Trello → сохранять JSON без усечения; ошибка API не считается успешной записью. Бинарный протокол игры здесь неприменим.
- Снимок после записи устарел → никаких дальнейших действий по цели до следующего readBoard. Это не требует изменения политики всех остальных карточек и не дублирует 0070.
- Часть параметров могла быть потеряна ещё до этого исправления → общая структурная проверка не восстанавливает неизвестные поля. Для 0308 полнота проверяется против всего исходного объекта.

## Migration Plan

Сначала доставляется исправление хранения и защита допуска. Затем — восстановительная операция и рецепт 0308 в том же PR. После вливания обычный владелец супервизора подхватывает новую версию; его цикл применяет рецепт, новым снимком подтверждает заказ и готовит штатный возврат после завершения 0310. Сессия implement не запускает второй супервизор, не ждёт CI и не пишет карточку; реализация автоматического действия проверяется интеграционным тестом до PR.

Живое подтверждение остаётся обязательным результатом самой восстановительной операции: комментарий 0308 с исходными params, фактом нового чтения и проверкой назначения. Тестовый результат нельзя назвать живым восстановлением. Если работающий владелец ещё не обновлён, это прямо указывается в отчёте реализации; замер остаётся остановленным до автоматической сверки. Ошибки операции видны в cycle.log и журнале цели, а не скрываются закрытием tasks.

Откат не удаляет сохранённые параметры и квитанции. При возврате старой сериализации новые служебные записи снова опасны; до исправленной версии автоматический повтор benchmark удерживается, а данные восстанавливаются из проверенного рецепта. Никакой откат не меняет 0095.dependsOn и не создаёт новый заказ.

## Open Questions

Продуктовых вопросов нет: точный заказ, источник и запрет повторных измерений в рамках 0310 даны постановкой. Фактическое состояние 0308 при применении является проверяемым предусловием операции, а не основанием выбрать другую карточку.
