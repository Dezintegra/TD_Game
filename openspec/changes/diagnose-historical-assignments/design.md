## Decisions

### 1. Хозяин runtime принимает запрос, исполнитель только получает свидетельства

Добавить `supervisor/bin/diagnose-assignment.mjs` как короткий клиент владельца и `supervisor/lib/addressed-tool-diagnostics.mjs` как обработчик в уже владеющем runtime. Клиент не создаёт supervisor, не берёт его замок и не пишет ledger/reports. Транспорт — локальный Windows named pipe, обслуживаемый владельцем существующего supervisor.lock; адрес и nonce поколения публикуются владельцем в его runtime-метаданных. Канал ограничивается текущим OS-пользователем, без сетевого listener и без изменения ACL рабочих деревьев. Проверка владельца использует существующие process-identity/lock проверки, не один PID или наличие файла. Несовпадение поколения, потеря владельца, удалённый клиент или недоступный канал дают структурированный отказ.

CLI предлагает `submit --request <json>` и `get --request-id <id>`. В запросе только schemaVersion, requestId, полный taskId, stage, sourceLaunchId (либо явный unknown) и profile. Произвольные command/argv/cwd/config/env и неизвестные поля отвергаются. Подтверждение полномочий — отдельное действие хозяина в его доверенной конфигурации запросов, а не boolean из JSON исполнителя. Разрешение связывается с requestId, fingerprint полного запроса, поколением runtime и текущей проверенной идентичностью назначения; одно разрешение не открывает чужие назначения.

Владелец подготавливает ограниченную авторизацию четырёх назначений и подтверждает координацию других станций: никакой конкурирующий хозяин не вправе запускать их во время диагностики. Проверяются свежие доступные данные владельцев/живых процессов и собственный scheduler. При невозможности доказать это — отказ, не захват чужой карточки. В рамках одного runtime запрос и выдача этапа сериализуются по назначению существующим владельцем; повторная проверка перед каждым spawn закрывает смену контекста во время ожидания. Диагностика не создаёт фиктивного живого этапа: учитываются реальные диагностические процессы и штатные ограничения ресурсов. Карточки, их владельцы и статусы не переписываются; scoped-авторизация хозяина не равна возврату карточки в работу.

Ручная пауза сохраняется. Только явно разрешённый хозяином диагностический запрос может быть обслужен во время неё; обычный scheduler остаётся на паузе. API/token/incident ограничения применяются в части допуска диагностического процесса; диагностический результат не расходует и не выдаёт пробу восстановления исходного этапа.

Альтернативы: самостоятельный host-процесс с записью ledger отвергнут из-за гонки с runtime; произвольная запись request-файлов в .pipeline из агента — из-за отсутствия полномочий; запуск исходного revise для получения envelope — из-за круговой зависимости от 0381. Локальный транспорт добавляет только доставку запроса, не автомат восстановления.

Подключение остаётся в существующей фабрике runtime после получения startup/supervisor locks: `supervise.mjs` открывает `openReportStore(local('pending-reports.json'))`, передаёт его в `createSupervisor`, а `createIo` получает `supervisor.reportStore`. Обработчик нового endpoint получает именно этот экземпляр; CLI и endpoint не открывают свой store. `supervisor.reports` остаётся массивом представлений для scheduler, не объектом очереди из плана 0080. Подробнее — решение 4.1.

### 2. Текущая идентичность проверяется независимо от исторической

Runtime сверяет сохранённое назначение/исторические логи, resource registry и фактический Git worktree: taskId, stage, абсолютный real cwd, branch, HEAD, source launch/session, provider/version, runtime SHA, происхождение настроек и окружения. Для 0074 оба сохранившихся audit указываются как исторические ссылки; неизвестные идентификаторы не выдумываются. Рабочее дерево не создаётся, ветка не переключается, main не сливается.

Хозяин подтверждает текущие environmentId/permissionsId штатным toolContext от реальной stageCommand. Перед вызовом diagnoseStageTools expectedContext сравнивается с заново вычисленным actual через sameToolContext. Обнаруженная смена ветки/real cwd отдельно запрещает запуск. Исторические fingerprints сохраняются отдельно с known/unknown; сегодняшние не подставляются вместо них. Read-only проверка Git из host может подтвердить принадлежность, но только выполнение контроля в назначенном provider/cwd подтверждает его командный путь.

Проверку соответствия нельзя заменить строками из карточки. Отсутствие части исторической хронологии не блокирует текущую диагностику, если текущая идентичность и полномочия доказаны; неизвестная принадлежность дерева блокирует.

### 3. Фиксированные профили поверх 0244

Расширить каталог toolControls именованными профилями исторического чтения и параметр diagnoseStageTools с безопасным умолчанием для существующего пути. Общий набор 0244 и его раннее прекращение остаются прежними. Исторический профиль содержит только требуемые чтения (каждое отдельным control с invocationId) и Git status; произвольного массива argv публичный вход не принимает.

| Профиль | Task/stage | Контроли в назначенном cwd |
| --- | --- | --- |
| historical-revise | 0156-svesti-komandy-etapov-k-odnoy-obolochke- / revise | Get-Content supervisor/skills/revise.md; Git status |
| historical-revise | 0208-zavesti-storozha-na-ssylki-po-nomeram-sh / revise | Get-Content supervisor/skills/revise.md; Git status |
| historical-revise-design | 0175-razmetit-komandnye-bloki-supervisor-skil / revise | Get-Content supervisor/skills/revise.md; Get-Content supervisor/skills/design.md; Git status |

Git-контроль: `git -C <проверенное-дерево> --no-optional-locks status --porcelain`. Он читает индекс без optional refresh write. Семиколоны таблицы — разделители описания, не исполняемая командная строка. Для исторического профиля попытаться выполнить каждый контроль в общем сроке TOOL_DIAGNOSTIC_TIMEOUT_MS = 120000; неисполненный по deadline/бюджету контроль обозначить not-run с причиной. При confirmed ранний выход обычного набора не должен молча скрыть заказанные чтения. Дополнительных GitHub/SSH/push контролей этому профилю не требуется.

Переиспользовать powerShellControl, controlFacts, normalizeControlFact/classifyToolControls, stageCommand, startStage и killTree. Диагностическая сессия всегда новая, не resume исторического этапа. SessionId записывается только при подтверждении создания; иначе null с причиной. Обёртки команд распознаются существующим точным механизмом; пробелы распознавания не чинить широким regex или разбором prose. Неизвестная форма остаётся inconclusive с первичной записью для 0381.

### 4. Durable request — не report envelope

Расширить существующий report-store отдельной коллекцией `diagnosticRequests` и отдельными методами; `entries()`/retainedReportView/обычная доставка видят только reports. Обратное чтение версии 2 даёт пустую коллекцию. Новая версия валидирует requestId и fingerprint, source identity, authorization reference, состояние доставки, список launch intents/results и ссылки на доказательства. Никаких фиктивных originalResult/reportId/charge или disposition retry-ready.

Внутренние состояния запроса: accepted, running, completed, refused, uncertain. Это запись жизненного цикла диагностического вызова; из неё нет перехода к исходному этапу. До spawn сохраняются request и launchId конкретного control. onStart/onResult и вычисление Claude cost выделяются из supervisor.mjs в общий адаптер 0244, используемый обоими входами. Фактический новый расход сохраняется в прежнем ledger по taskId/launchId, без изменения исторического расхода или attempts. Цена Codex не выдумывается из нулевого costUsd: сохраняются токены, единица учёта и состояние учтено/unknown; Claude — фактическая стоимость. Ошибка учёта явно удерживает завершение, raw result остаётся пригодным для сверки.

Перед onResult долговечно сохранить первичный run, затем провести идемпотентный учёт по launchId, затем сохранить итог и проверить чтением. И onStart не должен запускать процесс при провале persistence. После потери связи get возвращает сохранённые байты и их SHA-256; повтор submit с тем же fingerprint возвращает существующую запись, с другим — conflict. Unknown spawn после рестарта сверяется с процессом, логами и ledger по launchId; при недостатке данных uncertain и без автоматического повторного spawn. Новый запрос для той же незавершённой операции не обходит эту защиту.

Ошибка сохранения после завершения удерживает raw result в памяти/уже сохранённых первичных файлах, блокирует новый запуск затронутого запроса и использует существующий storage-blocked механизм. Повторять можно сохранение, не диагноз. После аварии без сохранившегося run результат честно uncertain, а не completed. Готовый результат возвращается только после подтверждения диска. Существующие envelope, plan/receipts/charge и их автомат неизменны.

### 4.1. Совместимость с открытым keep-the-report-on-disk (0080)

Проверены proposal/design/tasks и дельта 0080 из SHA `d24c7e8c48365db76e037a456229566e504d31a9`. Локальный `openspec list` её не показывает, поскольку план находится в отдельной отправленной ветке. Открытый план не считается кодом: на свежей базе `report-store.mjs` уже реализует версии 1/2, fsync/rename, accept/retain/update/acknowledge и verifySaved; `supervise.mjs:505,725,779–780` подключает store и массив views; `supervisor.mjs:133–187,345–359,1383` связывает hold, учёт, блокировку сохранения и приём результата. `report-delivery.mjs` сохраняет plan/progress и удаляет envelope после подтверждения всех эффектов. Это результат 0233/0244, который обе работы обязаны сохранять.

Сохраняемый контракт для расширения 0383:

- Один владелец и один экземпляр store на runtime. Каждая атомарная запись сохраняет обе коллекции: изменение reports не затирает diagnosticRequests, изменение диагностики не меняет envelopes. Для чтения старых версий 1 и 2 новая коллекция пуста; все существующие plan/progress/rejection/disposition/charge/retry и идентичности запусков сохраняются.
- `entries/get/accept/retain/update/reject/retry/archive/acknowledge` остаются API отчётов. Ключ отчёта — reportId с проверкой launch identity, а не только taskId/stage; новый заход не вытесняет старый. Диагностический requestId не подставляется в reportId. Delivery и retainedReportView не видят diagnosticRequests.
- Store восстанавливается после получения locks и до orphan recovery/scheduling. Обновление версии не обходит storage-blocked и проверку сохранности перед рестартом: verifySaved сверяет обе коллекции, но существующий count для отчётов не включает диагностические записи. Ошибка или неизвестная версия не превращается в пустую очередь. Ошибки диагностики подключаются к блокировке сохранения/рестарта явно, не фиктивным отчётом.
- Производственная связка `supervise → createSupervisor → createIo/toolHold` сохраняется. Общий адаптер учёта 2.2 обслуживает прежний hold и новый вход без изменения правил settlement/refund/retry. Endpoint 3.2 получает store из этой связки. Восстановление адресного запроса не вызывает report delivery либо tool settlement.

Оставшийся совместимый объём исходной 0080 определён по её пунктам, без утверждения, что они уже закрыты:

| Пункты 0080 | Совместимая работа на поставленной базе |

Повреждённый store сохраняется и блокирует запуск по действующему контракту, а не игнорируется. Различие отсутствующей и негодной карточки проверяется без потери отчёта; дальнейшая политика отставления требует отдельного обоснования внутри 0080. |

Противоречащие формулировки должны исправляться в исходных артефактах 0080 её исполнителем; оговорка 0383 не объявляет их снятыми и не разрешает реализовать старый план. Передаём карту и свидетельства через amendments без изменения состояния/захвата 0080. Это согласование технических границ, а не зависимость от всей 0080: действующий механизм уже поставлен. На реализации 0383 повторно сверяется актуальный diff соседа и сохраняемый контракт. При новом несовместимом изменении фиксируется конкретное расхождение, а не молча подключается вторая очередь.

Проверка пересечения — собственная интеграционная фикстура с ordinary envelope с частично подтверждённым plan, infrastructure-held envelope и addressed request в одном store. После записи каждой коллекции и пересоздания runtime все идентичности и содержимое сохранены; ordinary delivery завершает только недостающие эффекты, hold не получает settlement от get, get не создаёт spawn/charge. Acknowledge ordinary envelope не удаляет diagnostic request или hold. Проверка должна проходить через production-фабрику подключения; если для неё потребуется извлечение фабрики, оно остаётся в названных supervise.mjs/supervisor.mjs с сохранением порядка locks, без нового runtime-владельца.

Отвергнуты: ожидание завершения всей 0080 (нужная основа уже работает); реализация её report-queue параллельно (два источника истины теряют hold и запросы); перенос старой эвристики отставления (несовпадение этапа не доказывает полную доставку).

### 5. Поставка Windows-хозяину и адресная приёмка

Ни наличие CLI в ветке, ни новый allow не доказывают доступный маршрут. При реализации хозяин должен загрузить согласованный SHA входа в свой runtime штатным управлением, подтвердить его PID/поколение/SHA и полномочия, предоставить исполнителю читаемые результаты. Подготовка хозяина входит в эту работу и не требует завершения или merge 0381. Обычный исполнитель не останавливает супервизор, не меняет его main и не пишет .pipeline. Если хозяин недоступен, критерий остаётся открытым; фактическое препятствие оформляется по контракту этапа, не заменяется обещанием будущей проверки.

Проектируемая форма вызова **для хозяина**, из каталога поставленного supervisor (не утверждение о существующей сегодня команде):

```powershell
node supervisor/bin/diagnose-assignment.mjs submit --request <файл-запроса-хозяина.json>
node supervisor/bin/diagnose-assignment.mjs get --request-id <requestId>
```

Хозяин заполняет request-файлы отдельно для четырёх ID из таблицы, проверяет endpoint/авторизацию и запускает submit/get. Конкретные заполненные вызовы, абсолютный cwd клиента, SHA установленного кода и ответы попадают в acceptance.md. CLI для агента не объявляется разрешённым через существующие правила: это host operation. Агенту достаточно штатного чтения переданных файлов. Никакие тестовые фикстуры не обращаются к настоящему .pipeline или чужим деревьям.

Результат каждого request содержит: source identity и ссылки на историю (включая оба audit 0074), сведения о наличии конвертов, authorizer/runtime identity, current/historical context с unknown, проверенные cwd/branch/HEAD, UTC начала/конца, controls и факты, каждый diagnostic launchId/sessionId или причина отсутствия, usage receipt, verdict и отдельное состояние полноты результата. Владелец сохраняет доступные очищенные первичные события и их SHA-256. Секреты, полный env, credentials и содержимое пользовательских настроек в результат не включаются; пути закрытых первоисточников описываются без ложного обещания доступности.

Манифест с четырьмя ссылками на результаты и хешами передаётся 0381 в читаемом месте внутри проекта; путь и SHA-256 самого манифеста указываются в acceptance.md и итоговом отчёте реализации. При ограничениях публикации в Git идут очищенные материалы и хеши, оригиналы остаются у хозяина, доступность каждого источника помечается явно. Проверка get для каждого request после потери соединения/перезапуска клиента подтверждает те же launchId и отсутствие добавленного расхода. Подтверждённый helper refusal принимается как результат входа, но не как восстановление. Отсутствие маршрута или ответа одного адресата — незавершённая приёмка.

## Risks / Trade-offs

- Работающий runtime может быть старее ветки → фиксировать фактически загруженный SHA и участие хозяина; не выдавать тестовую копию за поставку.
- Межмашинное владение невозможно доказать одним локальным lock → обязательная scoped-авторизация хозяина и проверка отсутствия конкуренции; неизвестность даёт отказ, без изменения карточек.
- Windows pipe недоступен или подменён → проверить identity/nonce/OS caller; структурированный transport refusal, без альтернативного обхода sandbox.
- Запрос прерван между spawn и записью → долговечный launch intent, сверка и uncertain; приоритет отсутствия дубля над автоматическим повтором.
- Raw events не содержат нужного structured failure → inconclusive с первичными данными; не расширять вывод до причинного ремонта.

## Migration Plan

Сначала добавить профили и их совместимые тесты, затем хранилище и общий учёт, затем подключить защищённый host transport и производственный runtime, затем получить четыре адресных результата. Старые reports читаются без изменения семантики. Откат runtime не должен затирать новую коллекцию: неизвестная версия хранилища вызывает отказ запуска, требуется совместимая версия; автоматического downgrade/очистки нет. Диагностические результаты и их первичные файлы не удаляются обычной очисткой логов до передачи потребителю.

## Validation

Установка при реализации: `pnpm install --frozen-lockfile --prefer-offline`. Узкие проверки через `pnpm test:pipeline` с конкретными файлами в tasks.md. Проверять production wiring, реальные store round-trips и число spawn/учёт, а не одну строку промпта. Windows pipe проверять на собственном временном endpoint; fake provider только для регрессий, живые четыре ответа — отдельная обязательная приёмка. Ошибки persistence инъецировать только в фикстуры.

Геймплей не затрагивается: арена, sim golden, PROTOCOL_VERSION, рассинхрон и реконнект неприменимы. В ядре не появляются Math.random, Date.now или float. Полный verify и полный матчевый набор не планируются, ожидание CI выполняет супервизор.

## Open Questions

Продуктовых развилок нет. На design не проверялись фактическая готовность Windows-хозяина, сохранность каждого исторического источника и текущая работоспособность helper. Это предмет исполнимой адресной приёмки реализации, а не основания заявить их успешными сейчас.
