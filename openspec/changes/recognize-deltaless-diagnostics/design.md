База освежена `git -C . fetch origin` и `git -C . merge origin/main` (Already up to date). В `supervisor/skills/design.md` возле проверки формы стоит «Любая другая строка вывода», в audit.md — дословная короткая цитата. `supervisor/config/transitions.test.mjs` проверяет только наличие начала цитаты, поэтому противоречие проходит сторож. Основы `openspec/specs/dev-pipeline-worker/spec.md` пока нет; исходное требование и сценарий находятся в открытом `admit-changes-without-deltas`.

## Goals / Non-Goals

Цель — одинаковое решение design и audit при одинаковой диагностике и содержании изменения. Область и исключения перечислены в proposal.md. Автоматический анализ содержания предложения, новый парсер CLI и изменение переходов супервизора не требуются.

## Decisions

### 1. Считать ошибки, сравнивать начало сообщения

В обоих скиллах целиком заменить спорный абзац правила. После служебного оформления `✗ [ERROR] file:` диагностическое сообщение должно начинаться с `Change must have at least one delta. No deltas found.`. Во всём выводе должна быть ровно одна ошибка. Заголовок результата, продолжение `Ensure your change…`, `Tip: run…`, `Next steps` с рекомендациями сами по себе ошибками не являются. Дополнительная диагностика ошибки не исчезает из рассмотрения даже после заголовка `Next steps`; искать только первый ERROR недостаточно.

Дословное совпадение всей строки или всего вывода отвергнуто: оно воспроизводит дефект. Поиск произвольного вхождения слова delta либо нужной цитаты в подсказке отвергнут: он способен скрыть другую ошибку. Игнорирование всего после `Next steps` также отвергнуто: дополнительная ошибка там сохраняет силу.

### 2. Содержание — обязательный второй рубеж

Проверка вывода лишь разрешает рассмотреть исключение. Для его применения одновременно нужны отсутствие каталога `specs/` (даже пустой каталог нарушает условие), точный раздел `## Почему дельты нет` в proposal.md и содержательное подтверждение, что ни основа, ни открытые дельты не меняют прочтения после заявленных задач. Проработка обосновывает это, аудит независимо сверяет. Пустой раздел или голословная декларация не подходят. Остальные артефакты и вызов status остаются обязательными; красный код CLI не переписывается в ноль.

### 3. Согласовать исходную норму по её живому месту

В реализации после освежения базы найти требование «Проверка формы изменения зовётся по имени этого изменения» и сценарий «Валидатор назвал что-то ещё». Пока `admit-changes-without-deltas` открыт, исправить соответствующий абзац и два сценария в его `specs/dev-pipeline-worker/spec.md`: допустима штатная справка, недопустима другая либо дополнительная ошибка; положительный сценарий сохраняет все обязательные условия. Остальные сценарии и правила вызова по имени, `--strict`, status сохранить. Это явно заказанная правка исходной дельты, а не перехват её реализации.

Если исходник уже архивирован, согласовать живое требование в `openspec/specs/dev-pipeline-worker/spec.md`; архивный снимок не редактировать. Если при синхронизации требование переименовали или объединили, искать по содержанию нормы и править её живое место, сохраняя незатронутые сценарии. Наша ADDED-дельта имеет отдельное имя и уточняет распознавание; она не претендует на MODIFIED отсутствующей сегодня основы. При будущей архивации соблюдать порядок из proposal.md. Архивация не входит в реализацию этой задачи.

### 4. Проверить инструкции как инструкции

Расширить существующий сторож `transitions.test.mjs` для обоих скиллов: полное начало сообщения, единственность ошибки, три вида пояснений, три обязательных условия, запрет другой/дополнительной ошибки. Проверять фрагмент самого правила, а не случайное совпадение в примере; старую фразу о любой другой строке запретить в этом фрагменте. Контрольными мутациями текста каждого скилла показать, что удаление каждого условия или возврат старого запрета делает сторож красным.

Поведенческую матрицу ниже пройти отдельно по тексту каждого этапа и записать решения с основаниями в `verification.md` своего изменения. Не писать тестовый парсер, используемый только тестом: он проверял бы придуманную реализацию, тогда как исполняет правило сессия. Автоматический сторож защищает наличие и согласованность нормы; ручной разбор проверяет её смысл. Проверять содержательное обоснование регулярным выражением нельзя.

## Контрольный вывод и матрица приёмки

Вывод получен 07.09.2026 установленным OpenSpec 1.6.0 командой `openspec validate recognize-deltaless-diagnostics --strict` после создания proposal.md, до создания дельты. Код возврата 1. Это воспроизведение структуры, описанной владельцем в постановке; отдельной дословной стенограммы владельца в назначении нет. Текущий скелет не объявлялся законным бездельтовым изменением: для положительных случаев ниже задаются отдельные предусловия.

```text
Change 'recognize-deltaless-diagnostics' has issues
✗ [ERROR] file: Change must have at least one delta. No deltas found. Ensure your change has a specs/ directory with capability folders (e.g. specs/http-server/spec.md) containing .md files that use delta headers (## ADDED/MODIFIED/REMOVED/RENAMED Requirements) and that each requirement includes at least one "#### Scenario:" block. Tip: run "openspec change show <change-id> --json --deltas-only" to inspect parsed deltas.
Next steps:
  - Ensure change has deltas in specs/: use headers ## ADDED/MODIFIED/REMOVED/RENAMED Requirements
  - Each requirement MUST include at least one #### Scenario: block
  - Debug parsed deltas: openspec show recognize-deltaless-diagnostics --json --deltas-only
```

В строках таблицы по умолчанию каталога specs/ нет, раздел с точным заголовком присутствует, обоснование верно и проверено по задачам, основе и открытым дельтам. «Допустить» означает только применить исключение к ошибке формы, а не автоматически принять всю задачу.

| Случай | Ожидание design и audit |
| --- | --- |
| Полный вывод выше | Допустить исключение; подсказки не дополнительные ошибки |
| Только строка ERROR с полным началом сообщения без пояснений | Допустить исключение |
| Полный вывод плюс `✗ [ERROR] specs/example/spec.md: Requirement must have at least one scenario` | Не допустить; дополнительная ошибка |
| Та же дополнительная ошибка стоит после списка Next steps | Не допустить; просмотреть весь вывод |
| Единственная ошибка — `Delta parsing found no operations` | Не допустить; другая ошибка |
| Нужная цитата есть только в Tip, а единственная ошибка другая | Не допустить; сравнивается начало сообщения ошибки |
| Полный вывод, но каталог specs/ существует и пуст | Не допустить; обязательное условие отсутствует |
| Полный вывод, но в proposal.md нет нужного раздела | Не допустить |
| Полный вывод и заголовок есть, но обоснование пустое | Не допустить |
| Полный вывод и обоснование заявлено, но задача меняет требование | Не допустить; содержательная проверка опровергает обоснование |
| Полный вывод и обоснование ещё не проверено | Не допустить до содержательной проверки |

## Risks / Trade-offs

- Текстовый сторож не доказывает понимания инструкции сессией → матрица разбирается для обоих этапов отдельно, с указанием применённых условий.
- Новая версия CLI может поменять начало ошибки → разрешаем только названное начало; новые ошибки разбираются обычным порядком, версия контрольного вывода сохранена.
- Исходная дельта может переместиться → повторный поиск живой нормы после освежения базы, без записи в архивный снимок.

## Migration Plan

Один атомарный коммит реализации согласует оба скилла, живую исходную норму, сторож и результаты матрицы. После отправки открывается черновой PR; ожидание CI ведёт супервизор. Откат того же коммита возвращает предыдущие инструкции без миграции данных.

Игровой код не затрагивается: рассинхрон и реконнект не меняются; обновление эталонов sim и рост PROTOCOL_VERSION не нужны. Запреты Math.random, Date.now и чисел с плавающей точкой в состоянии мира сохраняются, новых зависимостей от ядра нет.
