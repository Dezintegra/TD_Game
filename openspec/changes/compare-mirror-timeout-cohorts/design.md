## Goals / Non-Goals

Цель — численно описать отличия двух групп, проверить совместность и временной порядок признаков предполагаемого истощения, отделить объяснимое от ненаблюдаемого. Non-goals перечислены в proposal: игровые правила, новый прогон и изменение телеметрии сюда не входят.

## Decisions

### 1. Изолированный модуль анализа сохранённой базы

`scripts/analysis/mirror-timeouts.mjs` использует только стандартные модули Node, включая `node:sqlite`. Экспортирует функцию анализа и форматирование Markdown/JSON; CLI запускается только при прямом вызове файла, импорт не запускает анализ или арену. Входная база открывается readOnly, запросы параметризованы. Для чтения не использовать openDatabase из ingest: сборка базы и анализ имеют разные права и задачи.

CLI получает `--db`, `--run`, `--sha`, `--profile`, `--seed-start`, `--matches`, `--ticks-per-second`, `--cap-seconds` и необязательный `--out` для JSON. По умолчанию печатает Markdown; при `--out` пишет только явно названный файл. Для 0050 параметры: run 33430184681, SHA выше, profile baseline-2026-08, seed-start 1, matches 60, ticks-per-second 30, cap-seconds 1200. Множители и предел подтверждаются логом workflow и описанием источника: в match нет полей tuning и tickCap, поэтому прибор не обещает проверить их по SQLite.

Вместо расширения reportBatch выбран отдельный прибор: обычная сводка должна оставаться короткой, расследование требует таблиц по всем матчам. Вместо разового SQL без проверок — небольшой тестируемый модуль, чтобы ошибки знаменателя и смешение выборок не повторялись. Новый универсальный статистический фреймворк не нужен.

### 2. Проверка источника до чисел

Проверить наличие таблиц/столбцов через schema introspection, наличие footer, допустимые значения исхода и ticks, согласованность winner с исходом, единственный чистый git_sha, обе стороны нужного профиля, по одному match_id на каждый ожидаемый world_seed. Сохранить ai_seed_0/1 в описи. Все матчи базы входят в опись, лишние записи делают проверку точного источника красной, а не исчезают из неё. Timeout обязан иметь ticks равный объявленному пределу; base-destroyed может закончиться на последнем тике предела. NULL end_reason не равно timeout.

Неполный источник/несовместимая обязательная схема — ненулевой выход с причинами. Отдельный пропуск наблюдений не выдумывается: уменьшает n соответствующего показателя и явно указывается. Нет одной из групп — пустая группа и невозможность сравнения, без нулевых средних или мнимого успеха гипотезы.

Для исходного прогона итог сверяется с независимым job log: 11/49 и перечисленные timeout seed. При расхождении сохранить диагностику и выяснить состав артефакта; не подгонять фильтры под 11.

### 3. Единицы и агрегирование

Единица сравнения — матч; стороны 0/1 видны отдельно. Сначала вычислить показатель для каждой стороны, затем среднее двух годных сторон внутри матча, затем равновесное среднее, медиану и Q1/Q3 по матчам. Для медианы и квартилей использовать один явно документированный метод: линейную интерполяцию по индексу `(n - 1) * p`. Если одной стороны нет, исключить матч из симметричной агрегации данного показателя и назвать это; доступная сторона остаётся в деталях.

Для долей хранить числитель и знаменатель стороны, а не только процент. Дополнительно можно вывести pooled fraction, но подписать её как долю снимков/решений, не средний матч. Различия групп описательные: seed групп не совпадают, парный причинный тест между timeout и base-destroyed невозможен. Интервальное сравнение парное только внутри одного матча на обоих концах окна.

Тики и энергия выводятся с единицами исходной базы. Игровое время переводится через явно переданные 30 тиков/с; текущие балансные константы не используются для нормирования исторической базы. Базовый ориентир HP — первый имеющийся снимок стороны с его тиком, не максимум и не прочность из нынешнего main: прокачка может менять максимум. Относительное изменение подписать «от первого наблюдения», не «доля полного здоровья». Рост HP не обрезать до нуля.

### 4. Общие отсечки и временные окна

Два представления обязательны: вся наблюдённая жизнь (для сопоставления с прежней сводкой, с предупреждением о разной длине) и отсечки 300, 600, 900, 1200 секунд. Состояние на отсечке берётся из последнего sample не позже неё и не старше одной секунды. Завершившийся до отсечки матч исключается даже при близком последнем sample. У каждой точки печатать завершившиеся раньше, отсутствующие данные, n оставшихся матчей.

Интервалы: от первого снимка до 300 секунд, затем 300–600, 600–900, 900–1200. Первый интервал показывает фактический старт наблюдения каждой стороны (допуск не позже первой секунды). Для изменения HP/численности требуются оба конца одного матча, для долей времени — полная секундная сетка в окне; пропуски/дубли/нерегулярность снимков делают долю недоступной, а не «меньшим временем смерти». Интервал включает sample с `a < tick <= b`, не дублируя границу. Решения выбираются по тому же диапазону, не размножаются соединением с attempt.

В окне вычислить net-изменение HP обеих баз и число соседних секундных переходов со снижением HP; последнее — наблюдаемое давление, не весь нанесённый урон. Для timeout показать последнее наблюдаемое снижение HP и длину хвоста без снижения для каждой базы. По двум сторонам вывести изменения войск, башен/стен, закупки и смерть генерала. Точная длительность будущей победы неизвестна; продолжение после 1200 секунд не моделируется.

### 5. Признаки и проверка объяснений

| Область | Величины и ограничения |
| --- | --- |
| Постройки | towers/walls/structures в начале, конце, пик; сокращение относительно пика. Недострой включён; истинное число уничтоженных объектов из этих полей не следует. |
| Войска и производство | units_alive, queue_len; принятые TrainUnit, распределение attempt для производства. Заказ не равен появившемуся юниту. |
| Экономика | energy, income_per_tick, upgrade_total_level; доли решений с bought/saving/impatient по фактическим значениям records/ingest. Суммы покупок не считать числом решений. |
| Генерал | доля sample с general_alive=0; его присутствие, HP и путь сопоставлять по времени с ослаблением войска и прекращением снижения HP базы. Это секундные наблюдения, не точное число смертей. |
| Сопровождение | дальнее решение: approach_shortest>0, general_from_home>=0, отношение >0.5; числитель nearby_units=0, знаменатель все такие решения. Дополнительно live_units>0 AND nearby_units=0 отличает отсутствие рядом от отсутствия войска вообще. |
| Доступ к базе | доля sample с path_to_enemy=0; это записанная доступность пути, не доказательство физической позиции всех юнитов. |

Все показатели считать независимо, затем соединять итоговые строки по match_id/player/window, чтобы многократные attempt/frontier не умножали sample. Успешные команды — только accepted=1. Для привязки команды к решению безголовой арены используется command.tick=decision.tick+1; для основной ведомости команд привязка не нужна.

Отчёт `docs/analysis/mirror-timeouts-33430184681.md` содержит паспорт источника и контрольную сумму скачанной SQLite, команду воспроизведения анализа, определения и покрытия, числовые таблицы групп, список всех 11 timeout с обеими сторонами и временными ориентирами. Для каждого timeout сопоставить: продолжающееся давление; недостаток войск/покупок; отсутствие генерала/сопровождения; потерю пути; двустороннее ослабление построек и армии. Фиксировать численное основание и контрпримеры, не вводить произвольный порог «истощён».

Завершённый контроль для подробного примера выбирать воспроизводимо: среди base-destroyed максимальная длительность, при равенстве минимальный seed. Для общей картины используются все 49, а не только подобранный пример. Проверить последовательность признаков на минутных подокнах нужного матча теми же функциями анализа; интервалы и основание выбора назвать в отчёте. Если временной ряд не устанавливает причину, закончить ранжированными гипотезами, ограничениями наблюдения и конкретным будущим экспериментом, а не выдуманным диагнозом. Реализовывать предложенное лечение в этой карточке нельзя.

### 6. Совместимость с ядром и сетью

Симуляция, ИИ, протокол и сбор логов не меняются; функции анализа не импортируются игровыми приложениями. Рассинхрон и реконнект ведут себя по действующим правилам, нового сетевого состояния нет. Анализ исторической базы вообще не требует replay; если отдельная будущая задача использует replay, действующий запрет продолжать при несовпадении контрольных сумм остаётся.

Golden-эталоны детерминизма не обновляются: правила packages/sim не затронуты. PROTOCOL_VERSION не увеличивается: раскладка байтов не меняется. Math.random/Date.now и плавающие числа в состоянии мира не вводятся; дробные статистические величины существуют только в офлайн-отчёте.

## Risks / Trade-offs

- Артефакт может истечь до implement → сначала скачать существующую базу; если она уже недоступна, вернуть обязательную предпосылку восстановления конкретного источника, не заменять его новым прогоном молча.
- Длинные матчи сами успевают потерять больше построек → общие временные окна и явные n; конечные средние не служат причинным доказательством.
- Выбор по будущему исходу и дожитие до отсечки создают смещение → назвать его, не обещать причинный эффект или статистическую независимость сторон.
- Секундные снимки не фиксируют все смерти, завершения строительства и урон → не называть net-изменения истинными потерями и не расширять сбор данных без отдельного заказа.
- 11 тайм-аутов могут иметь разные причины → индивидуальная таблица всех матчей обязательна.

## Migration Plan

Миграций базы и выкладки игры нет. Модуль, тесты, документация и исторический отчёт доставляются обычным PR. Откат удаляет только офлайн-инструмент и документацию; исходный артефакт не модифицируется.

Новый прогон баланса не требуется: игровые правила и профили не меняются, выполняется чтение старой SQLite. Любой предлагаемый по итогам эксперимент оформляется отдельной заявкой с ожидаемым результатом в отчёте implement, после получения фактов.

## Open Questions

Продуктового решения для построения сравнения не требуется. Остаётся эмпирический вопрос карточки — чем отличаются timeout; ответ даёт применение прибора к базе, а не этап design. Недоступное наблюдение должно остаться ограничением, а не поводом выбрать лечение за владельца.
