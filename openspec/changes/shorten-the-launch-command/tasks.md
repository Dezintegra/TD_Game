# Шаги реализации

Каждый шаг — отдельный коммит, собирающийся и проверяемый сам по себе.
Черновой pull request открывается сразу после шага 1: до его открытия
проверки CI на пуши в ветку не запускаются вовсе.

## 1. Короткие команды в корневом `package.json`

- [ ] Добавить в `scripts` корневого `package.json` четыре сценария:
      `supervisor`, `supervisor:shadow`, `supervisor:detached`,
      `supervisor:stop`. Каждый зовёт `node supervisor/bin/launch.mjs`
      с соответствующим ключом (первый — без ключей).
- [ ] Ключи брать те, что понимает пускатель: `--shadow`, `--detached`,
      `--stop`. Никаких доводов через `--` в сценарии не закладывать.
- [ ] Открыть черновой pull request сразу после этого коммита.

**Проверка.** `pnpm run` в корне репозитория перечисляет четыре новых
сценария. `pnpm supervisor:shadow` в корне поднимает супервизор в тени:
печатается стартовая сводка окружения и первый оборот цикла, мира при этом
никто не касается; остановить `Ctrl+C`. Если на машине уже работает боевой
супервизор, тот же вызов вместо запуска печатает «СУПЕРВИЗОР УЖЕ РАБОТАЕТ»
— это тоже годное доказательство того, что команда разрешилась в пускатель.

## 2. Померить, как короткая команда ведёт себя из вложенного каталога

- [ ] Набрать короткую команду тени из `packages/sim` и из `apps/client`.
- [ ] Записать в отчёт этапа и в руководство (шаг 5) ровно тот вид команды,
      который сработал: `pnpm supervisor` либо `pnpm -w supervisor`.
- [ ] Ничего не «чинить» под ожидаемый ответ: если pnpm к корню рабочего
      пространства не поднимается, годным считается вид с `-w`, а не
      попытка завести сценарий в каждом пакете.

**Проверка.** Оба вложенных каталога дают тот же результат, что и корень:
либо запуск в тени, либо сообщение о уже работающем супервизоре. Записанный
вид команды воспроизведён из третьего каталога — например, из `packages/ui`.

Коммитом этого шага может оказаться нечего править: если сработал
`pnpm supervisor`, замер живёт в отчёте этапа, а его результат уезжает
в руководство шагом 5. Пустой коммит не заводить.

## 3. Отказ пускателя запускаться в дополнительном рабочем дереве

- [ ] Завести в `supervisor/lib/` чистую функцию, которой на вход даётся
      содержимое файла `.git` (строка `gitdir: …`) и путь корня, а на выходе
      — путь основного рабочего дерева либо признак «это основное дерево».
      Внешних программ не звать, к диску внутри функции не обращаться.
- [ ] Позвать её из `bin/launch.mjs` после того, как корень найден, и до
      всего остального. Дополнительное дерево — печатать путь основного
      дерева и команду, которую надо набрать там, и завершаться с ненулевым
      кодом, ничего не запустив.
- [ ] Отказ не срабатывает, если корень назван явно: доводом `--root=`
      либо переменной `PIPELINE_ROOT`.

**Проверка.** Тест `*.test.mjs` рядом с функцией: разбирает строку `gitdir`
вида `<путь>/.git/worktrees/<имя>` и отдаёт `<путь>`; на каталоге `.git`
отдаёт признак основного дерева; на испорченном содержимом не бросает
исключение. Прогон — `pnpm test:pipeline`. Наблюдаемый результат: короткая
команда, набранная в любом каталоге `.claude/worktrees/*`, ничего
не запускает и называет путь основного дерева; она же с `--root=<основное
дерево>` запускается.

## 4. `bin` инструмента переводится на пускатель

- [ ] В `supervisor/package.json` заменить
      `"pipeline-supervisor": "bin/supervise.mjs"` на
      `"pipeline-supervisor": "bin/launch.mjs"`.
- [ ] Завести сторожа: тест читает `supervisor/package.json`, берёт
      объявленный путь и проверяет, что файл существует и это пускатель,
      а не решающая часть.

**Проверка.** `pnpm test:pipeline` зелёный, новый тест падает при откате
строки обратно на `bin/supervise.mjs`.

## 5. Раздел «Запуск» в руководстве инструмента

- [ ] Переписать раздел «Запуск» в `supervisor/README.md`: короткая команда
      первой, обёртки и полный путь рядом с ней, двойной щелчок там же.
      При каждом способе сказать, от чего он зависит: короткая команда — от
      корневого `package.json` проекта, обёртки — ни от чего, кроме Node.
- [ ] Записать вид команды, проверенный шагом 2.
- [ ] Назвать вслух, что короткая команда не работает в дополнительном
      рабочем дереве и почему, и как настоять доводом `--root=`.
- [ ] Назвать глобальную установку возможностью, а не порядком работы,
      и сказать, что она требует установки на каждой машине.
- [ ] Поправить перечень файлов в шапке руководства, если он перестал
      совпадать с действительностью.

**Проверка.** `npx prettier --check supervisor/README.md` зелёный (каталог
`openspec/` из проверки формата исключён, а `supervisor/` — нет). Человек,
читающий раздел впервые, находит команду запуска, не открывая других файлов.

## 6. Дождаться зелёного CI

- [ ] `gh pr checks <номер> --watch` до зелёного.
- [ ] Красное — прочитать лог, починить отдельным атомарным коммитом,
      отправить, дождаться снова.
- [ ] Снять с pull request черновой статус.

**Проверка.** Все задачи CI зелёные на последнем коммите ветки.
