# Шаги реализации

Каждый шаг — отдельный коммит, собирающийся и проверяемый сам по себе.
Черновой pull request открывается сразу после шага 1: до его открытия
проверки CI на пуши в ветку не запускаются вовсе.

## Чем здесь можно проверять, а чем нельзя

Правила разрешений конвейера (`supervisor/config/stage-settings.json`)
не пропускают ни `pnpm run`, ни `pnpm supervisor*`, ни `pnpm test:pipeline`,
ни `node supervisor/bin/launch.mjs`. В автономной сессии отказ не ждёт
человека — он тихо меняет результат этапа, и шаги отмечаются сделанными
без единой проверки. Поэтому проверки шагов ниже написаны только теми
командами, которые разрешены: `pnpm install`, `npx vitest`, `npx prettier`,
`npx eslint`, `git`, `gh pr`.

Наборы тестов зовутся напрямую, а не через сценарий проекта:

| вместо чего      | чем                              |
| ---------------- | -------------------------------- |
| `pnpm test:pipeline` | `npx vitest run --root supervisor` |
| `pnpm test:scripts`  | `npx vitest run --root scripts`    |

Это те же команды, что стоят за сценариями, — сверено с корневым
`package.json`. Перед первым прогоном нужен `pnpm install --frozen-lockfile`:
в новом рабочем дереве `node_modules` своих нет, а `vitest` берётся оттуда.

Живой запуск супервизора этапу недоступен вовсе. Всё, что требует
поднять пускатель, объявлено ниже **проверкой владельца продукта** —
и такие пункты не считаются следом этапа. Открыть их должна задача
`0130-razreshit-konveyeru-progon-scenariev-pak`; пока она не влита,
доказательством служат сторожа в наборах тестов.

## 1. Короткие команды в корневом `package.json` и сторож на них

- [ ] Добавить в `scripts` корневого `package.json` четыре сценария:
      `supervisor`, `supervisor:shadow`, `supervisor:detached`,
      `supervisor:stop`. Каждый зовёт `node supervisor/bin/launch.mjs`
      с соответствующим ключом (первый — без ключей).
- [ ] Ключи брать те, что понимает пускатель: `--shadow`, `--detached`,
      `--stop`. Никаких доводов через `--` в сценарии не закладывать.
- [ ] Завести сторожа `scripts/supervisor-scripts.test.mjs`. Он проверяет
      два утверждения, и оба — чтением вывода `pnpm run` **без имени
      сценария**: такой вызов только печатает список и не исполняет ничего.
  - в корне репозитория `pnpm run` перечисляет все четыре сценария,
    и каждый ведёт на `supervisor/bin/launch.mjs`;
  - из вложенного каталога пакета (`packages/sim`) те же четыре сценария
    видны по виду `pnpm -w run`, — то есть закреплён вид команды, которым
    короткая команда разрешается к корневому описанию пакета извне корня.
- [ ] **Супервизор в стороже не поднимать и не останавливать.** Ни
      `pnpm supervisor`, ни `pnpm supervisor:stop`: первый поднял бы боевой
      конвейер прямо из прогона тестов, второй снял бы работающий у того,
      кто гоняет тесты на своей машине. Проверяется разрешение имени,
      а не запуск.
- [ ] Если `pnpm` в среде не найден, тест обязан **падать** с внятным
      сообщением, а не зеленеть пропуском: проверка, тихо ничего
      не проверившая, хуже отсутствующей.
- [ ] Открыть черновой pull request сразу после этого коммита.

**Проверка (след этапа).** `pnpm install --frozen-lockfile`, затем
`npx vitest run --root scripts` — зелёный, и новый тест среди прогнанных.
`npx prettier --check package.json` зелёный. `npx eslint
scripts/supervisor-scripts.test.mjs` зелёный. Сторож падает, если убрать
любой из четырёх сценариев, — проверяется правкой в рабочем дереве
с откатом обратно, без коммита.

**Проверка владельца продукта.** `pnpm run` в корне перечисляет четыре
новых сценария; `pnpm supervisor:shadow` поднимает супервизор в тени,
мира никто не касается, остановка — `Ctrl+C`. Если на машине уже работает
боевой супервизор, тот же вызов печатает «СУПЕРВИЗОР УЖЕ РАБОТАЕТ» —
это годный ответ, он тоже доказывает, что команда разрешилась в пускатель.

## 2. Отказ пускателя запускаться в дополнительном рабочем дереве

- [ ] Завести в `supervisor/lib/` чистую функцию, которой на вход даётся
      содержимое файла `.git` (строка `gitdir: …`) и путь корня, а на выходе
      — путь основного рабочего дерева либо признак «это основное дерево».
      Внешних программ не звать, к диску внутри функции не обращаться.
- [ ] Позвать её из `bin/launch.mjs` после того, как корень найден, и до
      всего остального. Дополнительное дерево — печатать путь основного
      дерева и команду, которую надо набрать там, и завершаться с ненулевым
      кодом, ничего не запустив.
- [ ] Отказ не срабатывает, если корень назван явно: доводом `--root=`
      либо переменной `PIPELINE_ROOT`.
- [ ] Тест `*.test.mjs` рядом с функцией: разбирает строку `gitdir` вида
      `<путь>/.git/worktrees/<имя>` и отдаёт `<путь>`; на каталоге `.git`
      отдаёт признак основного дерева; на испорченном содержимом
      не бросает исключение.

**Проверка (след этапа).** `npx vitest run --root supervisor` зелёный,
новый тест среди прогнанных. `npx eslint supervisor/lib/<новый файл>.mjs
supervisor/bin/launch.mjs` зелёный. Тест падает, если из `launch.mjs`
убрать вызов функции, — сторож стоит на поведении, а не на её существовании.

**Проверка владельца продукта.** В любом каталоге `.claude/worktrees/*`
набрать `pnpm supervisor:shadow` — ничего не запускается, назван путь
основного дерева. Отговорка проверяется прямым вызовом пускателя, минуя
пакетный менеджер:

```
node supervisor/bin/launch.mjs --shadow --root=C:\src\dezintegra\TD_Game
```

Тень (`--shadow`) здесь обязательна: без неё из дополнительного дерева
поднялся бы **боевой** супервизор кодом этого дерева поверх хозяйства
основного — ровно та смесь, которую `design.md` объявляет недопустимой.
Годных ответов два: стартовая сводка тени либо «СУПЕРВИЗОР УЖЕ РАБОТАЕТ»
(последнее означает, что запуск дошёл до отсечения двойного запуска,
то есть отказ по дереву не сработал — чего мы и добиваемся доводом).

Довод через пакетный менеджер не пробрасывается — правила проброса
у менеджеров разнятся, и съеденный `--root=` дал бы запуск не от того
корня. Поэтому подмена доводу одна: переменная окружения `PIPELINE_ROOT`,
выставленная перед вызовом, либо прямой вызов пускателя, как выше.

## 3. `bin` и сценарии описания пакета инструмента ведут на пускатель

- [ ] В `supervisor/package.json` заменить
      `"pipeline-supervisor": "bin/supervise.mjs"` на
      `"pipeline-supervisor": "bin/launch.mjs"`.
- [ ] Там же перевести на пускатель сценарии запуска супервизора:
      `start` → `node bin/launch.mjs`, `shadow` → `node bin/launch.mjs
      --shadow`. Иначе правка `bin` обходится тремя строками ниже:
      у `pnpm start` из каталога инструмента не было бы ни остановки,
      ни фона, ни отсечения двойного запуска.
- [ ] Сценарии `cycle`, `board`, `board-setup` и `test` не трогать:
      они зовут другие программы инструмента, и пускатель к ним отношения
      не имеет.
- [ ] Завести сторожа: тест читает `supervisor/package.json`, проверяет,
      что объявленная программа указывает на существующий файл пускателя,
      и что ни один сценарий запуска супервизора не зовёт `bin/supervise.mjs`
      напрямую.

**Проверка (след этапа).** `npx vitest run --root supervisor` зелёный.
Сторож падает при откате любой из двух строк обратно на `bin/supervise.mjs`
— проверяется правкой в рабочем дереве с откатом обратно, без коммита.

## 4. Раздел «Запуск» в руководстве инструмента

- [ ] Переписать раздел «Запуск» в `supervisor/README.md`: короткая команда
      первой, обёртки и полный путь рядом с ней, двойной щелчок там же.
      При каждом способе сказать, от чего он зависит: короткая команда — от
      корневого `package.json` проекта, обёртки — ни от чего, кроме Node.
- [ ] Записать оба вида короткой команды — из корня и из вложенного
      каталога, — ровно те, что закреплены сторожем шага 1. Не «вероятно
      работает», а то, что проверяется прогоном тестов.
- [ ] Назвать вслух, что короткая команда не работает в дополнительном
      рабочем дереве и почему, и как настоять: `PIPELINE_ROOT` либо прямой
      вызов пускателя с `--root=`.
- [ ] Назвать глобальную установку возможностью, а не порядком работы,
      и сказать, что она требует установки на каждой машине.
- [ ] Поправить перечень файлов в шапке руководства, если он перестал
      совпадать с действительностью.

**Проверка (след этапа).** `npx prettier --check supervisor/README.md`
зелёный (каталог `openspec/` из проверки формата исключён, а `supervisor/`
— нет). Каждая команда, названная в разделе, дословно совпадает с тем,
что стоит в корневом `package.json` и в сторожах шагов 1 и 3.

## 5. Дождаться зелёного CI

- [ ] `gh pr checks <номер> --watch` до зелёного.
- [ ] Красное — прочитать лог, починить отдельным атомарным коммитом,
      отправить, дождаться снова.
- [ ] Снять с pull request черновой статус.

**Проверка.** Все задачи CI зелёные на последнем коммите ветки.
