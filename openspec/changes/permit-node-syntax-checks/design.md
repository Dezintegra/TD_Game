## Context

На базе этапа после fetch/merge остаётся конкретный пробел: в `stage-settings.json` нет `node --check`. Установка зависимостей и eslint/prettier/vitest уже покрыты и в Bash, и в PowerShell. Текущий `implement.md` предписывает установку в шаге 4, узкие проверки — внутри цикла реализации; исторические номера шагов из постановки не используются как адрес правки. `node --check` также выписан в задачах открытых `outlive-the-supervisor` и `pause-on-api-overload`.

`permissions.mjs` экспортирует `SHELLS`, `patternOf`, `coversCommand` и `uncoveredCommands`. Последний учитывает allow и deny для каждой оболочки, различает точную форму и приставку с границей слова. Отдельного `permissions.test.mjs` сейчас нет; сторожа разрешений находятся в `transitions.test.mjs` и `install-snapshot-permissions.test.mjs`.

## Goals / Non-Goals

Цель — разрешить указанную форму синтаксической проверки и обнаруживать потерю допуска регрессионным тестом. Границы работы приведены в proposal: изменения ограничены настройкой и одним тестовым файлом. Основная спецификация `build-tooling` уже описывает оснастку и окружение, поэтому сюда добавляется отдельное требование без создания способности, отсутствующей в основных спецификациях. Дельта нужна: это постоянное правило допуска команды, а не исправление единичного пояснения.

## Decisions

### Два правила с узкой приставкой

Добавить `Bash(node --check:*)` и `PowerShell(node --check:*)` рядом с разрешениями Node. Файл проверки меняется от задачи к задаче, поэтому точное правило для одного файла непригодно. Общий `node:*` отвергнут: он открывает обычный запуск сценариев. Короткий синоним `-c` не добавлять: постановка и планы используют `--check`. Переход на одну оболочку не смешивать с этой задачей: текущий `SHELLS` содержит обе.

Все существующие allow/deny и пояснения настройки сохранить. Допуск разрешает форму команды, но не меняет ограничения каталогов, составных команд и исполняемых строк среды. JSON этим способом не проверяется: его синтаксис проверяется чтением через JSON.parse в тесте.

### Тест без собственной копии механизма разрешений

Создать `supervisor/config/syntax-check-permissions.test.mjs`: прочесть соседний реальный `stage-settings.json`, импортировать `uncoveredCommands` и проверить сценарии дельты. Отдельный маленький файл предпочтительнее расширения большого `transitions.test.mjs`, где много чужих сторожей; новую копию сопоставителя, подобную install-snapshot-тесту, не заводить.

Положительная таблица содержит конкретные пути: `node --check supervisor/config/permissions.mjs`, `node --check "supervisor/config/path with spaces.mjs"`, обе формы установки из дельты, `npx eslint supervisor/config/syntax-check-permissions.test.mjs`, `npx prettier --check supervisor/config/stage-settings.json`, `npx vitest run --root supervisor config/syntax-check-permissions.test.mjs`. Путь с пробелом — строковый пример, создавать такой файл не надо.

Отрицательные пробы меняют глубокую копию настройки в памяти отдельно для каждой оболочки: удаляют новое правило, заменяют его на точное `node --check`, добавляют перекрывающий deny. Проверять точный список виновных оболочек/команд. Дополнительный контроль подменяет узкое правило общим `node:*` и доказывает, что проверка закрытых форм из дельты обнаруживает расширение. Боевой JSON ради контролей не портить, процессы этими строками не запускать. Это проверка конфигурации, а не проверка парсера JavaScript или стороннего исполнителя.

### Один коммит реализации

Настройка и её сторож меняются вместе: один без другого либо оставляет отказ, либо даёт красный тест. В тот же коммит входит отметка собственного tasks.md. После отправки можно сразу открыть черновой PR. Полный набор исполняет CI, локально — только названные узкие проверки. `STAGE_COMMANDS` не расширяется частичной выборкой implement: текущий контракт требует полного перечня, а его аудит выходит за эту задачу.

## Risks / Trade-offs

- Правила из ветки не применяются к уже запущенному этапу автоматически. Claude получает настройку из каталога инструмента через `--settings`; Codex имеет отдельный маршрут подготовки среды. Поэтому положительный тест JSON доказывает покрытие в проектной модели, но не успешность исторического запуска 0067 и не получение новой настройки текущей сессией. Не ослаблять среду ради прямой пробы и не делать живой допуск до вливания обязательным пунктом tasks.
- Общий файл может измениться соседней задачей. Освежить базу на implement, сохранить чужие правила и проверить содержимое diff; зависимости архивации не требуются.
- Совпадение allow не гарантирует прохождения независимых предохранителей среды. Новый допуск не заявляет обхода этих предохранителей. При фактическом отказе применить обычный контракт отчёта этапа с точной командой и причиной.

## Migration Plan

Миграций данных и новых зависимостей нет. Настройка поступит следующим сессиям штатным способом после вливания; текущий супервизор не перезапускать и вручную настройки среды не переписывать. Откат — возврат атомарного коммита с двумя правилами и тестом. Изменение остаётся служебным, маршрут после вливания выбирает супервизор по полному diff.

## Архитектурные ограничения

Код игры, sim, протокол и состояние мира не затрагиваются. Рассинхрон и реконнект работают по прежним правилам; обновление golden-эталонов и `PROTOCOL_VERSION` не нужны. Запреты `Math.random`, `Date.now` и плавающей точки в состоянии мира сохраняются без новых исключений. Арена и замер кадров не нужны.

## Open Questions

Продуктовых решений для этой правки нет. Фактический допуск конкретным исполнителем после получения настройки не выводится из теста модели и не объявляется проверенным этим этапом.
